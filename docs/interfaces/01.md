# O Problema de Depender de Classes Concretas: Acoplamento, Rigidez e Evolução em C#

## Objetivo do material

Neste material, você aprenderá por que depender diretamente de classes concretas pode tornar um sistema orientado a objetos mais rígido, mais difícil de testar e mais caro de modificar. O foco não é apresentar uma nova sintaxe, mas construir a necessidade de uma solução: em muitos casos, uma classe não deveria depender de uma implementação específica, e sim de um comportamento esperado.

Ao final, você deverá ser capaz de:

Reconhecer quando uma classe está fortemente dependente de outra classe concreta.

Explicar o que é acoplamento e por que ele afeta a manutenção do sistema.

Identificar sinais de rigidez em código orientado a objetos.

Diferenciar dependência de implementação e dependência de comportamento.

Entender por que contratos, como interfaces em C#, ajudam a reduzir dependências concretas.

Material elaborado a partir do conteúdo-base enviado sobre dependências concretas, acoplamento e rigidez em C#. 

---

## 1. Contextualização do problema

Em programação orientada a objetos, é comum criarmos classes que colaboram entre si. Uma classe pode finalizar um pedido, outra pode enviar uma notificação, outra pode processar um pagamento e outra pode gerar um relatório.

Essa colaboração é normal. O problema surge quando uma classe passa a depender diretamente de uma classe concreta específica, conhecendo detalhes demais sobre ela.

Considere um sistema simples de vendas. Quando um cliente realiza um pedido, o sistema precisa:

1. registrar que o pedido foi finalizado;
2. enviar uma mensagem de confirmação ao cliente.

Uma solução inicial poderia ser criar uma classe responsável por enviar e-mail e outra responsável por finalizar o pedido.

```csharp
public class EmailNotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"Enviando e-mail para {destinatario}: {mensagem}");
    }
}
```

A classe `EmailNotificador` representa uma implementação concreta. Ela sabe exatamente como enviar uma mensagem por e-mail, ainda que neste exemplo o envio esteja apenas simulado com `Console.WriteLine`.

Agora observe a classe de serviço responsável por finalizar pedidos:

```csharp
public class PedidoService
{
    private readonly EmailNotificador _emailNotificador;

    public PedidoService()
    {
        _emailNotificador = new EmailNotificador();
    }

    public void FinalizarPedido(string cliente, string email)
    {
        Console.WriteLine($"Pedido de {cliente} finalizado.");
        _emailNotificador.Enviar(email, "Pedido finalizado.");
    }
}
```

Esse código funciona. Ao chamar `FinalizarPedido`, o pedido é finalizado e uma mensagem é enviada por e-mail.

Mas funcionar não significa estar bem preparado para mudanças.

O problema não aparece enquanto o sistema é pequeno e possui apenas uma forma de notificação. O problema aparece quando o sistema precisa evoluir.

---

## 2. Onde está o problema no código?

O problema principal está no fato de `PedidoService` depender diretamente da classe concreta `EmailNotificador`.

Existem dois pontos importantes nesse código.

Primeiro, a declaração do campo:

```csharp
private readonly EmailNotificador _emailNotificador;
```

Essa linha diz que `PedidoService` só aceita trabalhar com `EmailNotificador`. O tipo do campo já prende a classe a uma implementação específica.

Segundo, a criação interna do objeto:

```csharp
_emailNotificador = new EmailNotificador();
```

Essa linha mostra que `PedidoService` cria sua própria dependência. Isso impede que outra implementação seja fornecida de fora. A classe não apenas usa um notificador; ela decide qual notificador será usado.

Na prática, `PedidoService` está dizendo:

“Para finalizar um pedido, eu preciso obrigatoriamente de um `EmailNotificador`.”

Essa frase revela o acoplamento. A classe que deveria cuidar da finalização do pedido agora também está presa ao mecanismo específico de notificação por e-mail.

---

## 3. O que é uma classe concreta?

Uma classe concreta é uma classe que possui implementação real e pode ser instanciada diretamente com `new`.

Exemplo:

```csharp
EmailNotificador notificador = new EmailNotificador();
```

Nesse caso, `EmailNotificador` é uma classe concreta porque ela define exatamente como o método `Enviar` funciona.

Classes concretas são necessárias. O problema não é existir uma classe concreta. O problema é quando uma classe principal fica diretamente dependente dela em locais onde o comportamento poderia variar.

Em outras palavras, o problema não é ter `EmailNotificador`. O problema é `PedidoService` estar presa a `EmailNotificador`.

---

## 4. O que acontece quando o sistema precisa mudar?

Imagine que a empresa começou enviando confirmações por e-mail. Depois de algum tempo, surgem novos requisitos:

O cliente quer receber confirmação por SMS.

O aplicativo precisa enviar notificação push.

A empresa quer registrar notificações em um log interno.

Durante testes, a equipe quer simular o envio sem mandar mensagens reais.

Futuramente, o sistema pode precisar enviar mensagens por WhatsApp ou por outro canal.

A primeira solução que muitos iniciantes imaginam é alterar `PedidoService` para tratar todos os tipos de notificação.

```csharp
public class PedidoService
{
    private readonly EmailNotificador _emailNotificador;
    private readonly SmsNotificador _smsNotificador;

    public PedidoService()
    {
        _emailNotificador = new EmailNotificador();
        _smsNotificador = new SmsNotificador();
    }

    public void FinalizarPedido(string cliente, string contato, string tipoNotificacao)
    {
        Console.WriteLine($"Pedido do cliente {cliente} finalizado.");

        if (tipoNotificacao == "email")
        {
            _emailNotificador.Enviar(contato, "Seu pedido foi finalizado.");
        }
        else if (tipoNotificacao == "sms")
        {
            _smsNotificador.EnviarSms(contato, "Seu pedido foi finalizado.");
        }
    }
}
```

Esse código parece resolver o problema no curto prazo, mas cria um problema maior.

Agora `PedidoService` conhece:

o `EmailNotificador`;

o `SmsNotificador`;

os métodos específicos de cada classe;

as regras para decidir qual notificador usar;

os textos que serão enviados;

a lógica de escolha baseada em `if` e `else`.

Com isso, a classe começa a saber demais.

---

## 5. A classe que sabe demais

Uma classe “sabe demais” quando acumula conhecimentos que não fazem parte da sua responsabilidade principal.

A responsabilidade principal de `PedidoService` deveria ser coordenar a finalização de um pedido. Isso pode envolver validar o pedido, alterar o status, registrar a data da finalização e acionar ações posteriores.

Mas, ao depender diretamente de notificadores concretos, `PedidoService` passa a acumular responsabilidades indevidas.

Ela passa a saber que existe envio por e-mail.

Ela passa a saber que existe envio por SMS.

Ela passa a conhecer os nomes das classes concretas.

Ela passa a conhecer nomes diferentes de métodos, como `Enviar` e `EnviarSms`.

Ela passa a decidir qual implementação usar.

Ela passa a precisar ser alterada sempre que surgir uma nova forma de notificação.

Esse acúmulo torna o código mais difícil de manter. Uma mudança pequena em uma parte do sistema pode obrigar alterações em uma classe que deveria estar protegida dessas decisões.

---

## 6. O conceito de acoplamento

Acoplamento é o grau de dependência entre partes de um sistema.

Quando uma classe depende muito dos detalhes de outra classe, dizemos que existe acoplamento forte.

Quando uma classe depende menos dos detalhes internos de outra e conhece apenas um comportamento esperado, dizemos que existe acoplamento fraco.

### Acoplamento forte

No acoplamento forte, uma classe conhece diretamente a implementação que usa.

Exemplo:

```csharp
private readonly EmailNotificador _emailNotificador;
```

Essa linha mostra que `PedidoService` depende especificamente de `EmailNotificador`.

O acoplamento forte causa alguns efeitos importantes:

Mudanças em `EmailNotificador` podem exigir mudanças em `PedidoService`.

Trocar e-mail por SMS exige alterar `PedidoService`.

Adicionar uma nova forma de notificação exige modificar a classe principal.

Testar `PedidoService` pode acabar acionando comportamentos reais ou difíceis de controlar.

A classe principal fica menos reutilizável.

### Acoplamento fraco

No acoplamento fraco, a classe principal não depende diretamente de uma implementação específica. Ela depende de um contrato de comportamento.

A ideia seria algo como:

```csharp
private readonly AlgumContratoDeNotificacao _notificador;
```

Esse exemplo ainda não apresenta a sintaxe real da interface, mas mostra a mudança de pensamento. A classe deixa de dizer “preciso de um `EmailNotificador`” e passa a dizer “preciso de algo que saiba notificar”.

No acoplamento fraco:

a classe principal não conhece detalhes de implementação;

novas variações podem ser adicionadas com menos impacto;

o código fica mais fácil de testar;

as responsabilidades ficam mais separadas;

a evolução do sistema se torna mais simples.

---

## 7. Rigidez: quando o código resiste à mudança

Rigidez é a dificuldade que um sistema apresenta quando precisa mudar.

Um código rígido é aquele em que uma alteração aparentemente simples exige muitas alterações em cadeia.

No exemplo do pedido, trocar a notificação por e-mail para SMS não deveria obrigar uma grande mudança em `PedidoService`. Afinal, a regra de finalizar pedido continua sendo a mesma. O que mudou foi apenas o mecanismo de envio da mensagem.

Quando uma classe depende de implementações concretas, ela tende a ficar rígida porque cada nova variação exige edição no código existente.

Considere a evolução:

Hoje, o sistema envia apenas e-mail.

Amanhã, precisa enviar SMS.

Depois, precisa enviar notificação no aplicativo.

Mais tarde, precisa registrar log interno.

Depois, precisa simular notificações nos testes.

Se cada nova opção exigir alteração em `PedidoService`, essa classe se tornará um ponto de manutenção constante. Quanto mais ela for alterada, maior o risco de introduzir erros em uma regra que já funcionava.

---

## 8. Responsabilidades legítimas e responsabilidades indevidas

Uma boa modelagem exige separar responsabilidades.

No caso de `PedidoService`, algumas responsabilidades fazem sentido:

validar se o pedido pode ser finalizado;

alterar o status do pedido;

registrar a data de finalização;

calcular valores finais, quando necessário;

coordenar ações após a finalização.

Essas responsabilidades pertencem ao processo de finalização do pedido.

Por outro lado, algumas responsabilidades não deveriam ficar dentro de `PedidoService`:

conhecer detalhes de envio de e-mail;

conhecer detalhes de envio de SMS;

decidir diretamente qual tecnologia de envio usar;

conhecer métodos específicos de cada notificador;

misturar regra de pedido com detalhes de comunicação.

Enviar uma mensagem ao cliente pode ser uma colaboração necessária, mas isso não significa que `PedidoService` deva conhecer todos os detalhes de cada tecnologia de envio.

A diferença é importante: colaborar com outra parte do sistema é aceitável; depender rigidamente dos detalhes dessa parte é problemático.

---

## 9. A pergunta certa de modelagem

A forma como você faz a pergunta muda a solução que você encontra.

Uma pergunta ruim seria:

“Qual classe concreta o `PedidoService` precisa usar?”

Essa pergunta leva diretamente a respostas como:

“Ele precisa usar `EmailNotificador`.”

“Ele precisa usar `SmsNotificador`.”

“Ele precisa conhecer todos os notificadores possíveis.”

Esse raciocínio aumenta o acoplamento.

Uma pergunta melhor seria:

“Qual comportamento o `PedidoService` precisa que alguém execute?”

Essa pergunta muda o foco. Agora a resposta não é mais uma classe específica. A resposta é um comportamento:

“O `PedidoService` precisa de algo capaz de enviar uma notificação.”

Essa mudança é essencial. O foco sai da implementação concreta e vai para o contrato de comportamento.

---

## 10. Dependendo de comportamento, não de implementação

Depender de comportamento significa que uma classe principal não precisa saber como uma tarefa será executada internamente. Ela precisa apenas confiar que alguém sabe executar aquela tarefa.

No exemplo do pedido, `PedidoService` não deveria se importar se a mensagem será enviada por e-mail, SMS, aplicativo, log interno ou simulação. Ele precisa apenas que exista algo capaz de enviar uma notificação.

A dependência concreta aparece assim:

```csharp
private readonly EmailNotificador _notificador;
```

Esse código prende a classe a uma implementação específica.

A ideia desejada seria depender de um contrato:

```csharp
private readonly INotificador _notificador;
```

Nesse caso, `INotificador` representaria um contrato de comportamento. O nome com `I` no início é uma convenção comum em C# para interfaces.

Uma interface define o que uma classe deve ser capaz de fazer, sem determinar como ela fará isso.

Exemplo conceitual:

```csharp
public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}
```

Esse contrato diz:

“Qualquer classe que for um `INotificador` precisa ter um método `Enviar` que recebe um destinatário e uma mensagem.”

Agora diferentes classes podem cumprir esse contrato:

```csharp
public class EmailNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"Enviando e-mail para {destinatario}: {mensagem}");
    }
}
```

```csharp
public class SmsNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"Enviando SMS para {destinatario}: {mensagem}");
    }
}
```

Observe que `PedidoService` não precisa mais conhecer `EmailNotificador` ou `SmsNotificador` diretamente. Ele pode depender de `INotificador`.

```csharp
public class PedidoService
{
    private readonly INotificador _notificador;

    public PedidoService(INotificador notificador)
    {
        _notificador = notificador;
    }

    public void FinalizarPedido(string cliente, string contato)
    {
        Console.WriteLine($"Pedido de {cliente} finalizado.");
        _notificador.Enviar(contato, "Pedido finalizado.");
    }
}
```

Esse código mostra uma melhoria importante: `PedidoService` depende de um comportamento, não de uma classe concreta.

A classe ainda envia uma notificação, mas não sabe qual tecnologia será usada. Isso permite trocar a implementação sem alterar a regra de finalização do pedido.

---

## 11. Exemplo comentado: substituindo a implementação

Agora imagine que o sistema precise usar e-mail em produção.

```csharp
INotificador notificador = new EmailNotificador();
PedidoService pedidoService = new PedidoService(notificador);

pedidoService.FinalizarPedido("Cliente Exemplo", "cliente@email.com");
```

Nesse caso, `PedidoService` recebe um `EmailNotificador`, mas seu código interno continua dependendo apenas de `INotificador`.

Se depois for necessário usar SMS, a troca acontece fora de `PedidoService`:

```csharp
INotificador notificador = new SmsNotificador();
PedidoService pedidoService = new PedidoService(notificador);

pedidoService.FinalizarPedido("Cliente Exemplo", "11999999999");
```

O comportamento de notificação muda, mas a classe `PedidoService` não precisa ser alterada.

Esse é o ponto central: a classe que finaliza pedidos não deve ser obrigada a mudar sempre que o mecanismo de notificação muda.

## 12. Exemplo em outro domínio: pagamento

O mesmo problema aparece em várias partes de um sistema.

Imagine uma classe `VendaService` que depende diretamente de pagamento por cartão de crédito.

```csharp
public class PagamentoCartaoCredito
{
    public void Processar(decimal valor)
    {
        Console.WriteLine($"Processando pagamento no cartão: R$ {valor}");
    }
}
```

Agora observe a classe de venda:

```csharp
public class VendaService
{
    private readonly PagamentoCartaoCredito _pagamento;

    public VendaService()
    {
        _pagamento = new PagamentoCartaoCredito();
    }

    public void RealizarVenda(decimal valor)
    {
        Console.WriteLine("Venda registrada.");
        _pagamento.Processar(valor);
    }
}
```

Enquanto o sistema aceitar apenas cartão de crédito, o código parece suficiente.

Mas e se a empresa quiser aceitar Pix, boleto ou cartão de débito?

Se `VendaService` depender diretamente de `PagamentoCartaoCredito`, cada novo meio de pagamento tende a exigir alteração na classe de venda.

A pergunta correta não é:

“Qual classe de pagamento a venda precisa usar?”

A pergunta correta é:

“Qual comportamento de pagamento a venda precisa acionar?”

A resposta é:

“A venda precisa de algo capaz de processar um pagamento.”

Esse comportamento poderia ser representado por um contrato:

```csharp
public interface IProcessadorPagamento
{
    void Processar(decimal valor);
}
```

Agora diferentes formas de pagamento podem implementar o mesmo contrato:

```csharp
public class PagamentoCartaoCredito : IProcessadorPagamento
{
    public void Processar(decimal valor)
    {
        Console.WriteLine($"Processando cartão de crédito: R$ {valor}");
    }
}
```

```csharp
public class PagamentoPix : IProcessadorPagamento
{
    public void Processar(decimal valor)
    {
        Console.WriteLine($"Processando Pix: R$ {valor}");
    }
}
```

E `VendaService` pode depender do contrato:

```csharp
public class VendaService
{
    private readonly IProcessadorPagamento _pagamento;

    public VendaService(IProcessadorPagamento pagamento)
    {
        _pagamento = pagamento;
    }

    public void RealizarVenda(decimal valor)
    {
        Console.WriteLine("Venda registrada.");
        _pagamento.Processar(valor);
    }
}
```

Agora `VendaService` não precisa conhecer todos os meios de pagamento. Ela apenas aciona o comportamento necessário.

## 13. Sinais de dependência concreta excessiva

Existem sinais que ajudam a identificar quando uma classe está dependendo demais de classes concretas.

### Uso de `new` internamente

Quando uma classe cria suas dependências com `new`, ela passa a controlar diretamente qual implementação será usada.

Exemplo:

```csharp
_emailNotificador = new EmailNotificador();
```

Isso importa porque dificulta a substituição da dependência. Para validar esse sinal, procure construtores ou métodos que instanciam diretamente classes auxiliares. Se a classe principal cria tudo sozinha, talvez esteja acoplada demais.

Se esse problema for ignorado, trocar a implementação exigirá editar a própria classe principal.

### Muitos `if/else` ou `switch` para escolher implementação

Quando uma classe possui várias condições para escolher qual classe usar, ela pode estar acumulando decisões que deveriam estar fora dela.

Exemplo:

```csharp
if (tipoNotificacao == "email")
{
    _emailNotificador.Enviar(contato, mensagem);
}
else if (tipoNotificacao == "sms")
{
    _smsNotificador.Enviar(contato, mensagem);
}
```

Isso importa porque cada nova opção aumenta a quantidade de condicionais. Para validar, procure blocos condicionais que escolhem tecnologias, formatos, tipos de envio ou formas de processamento.

Se esse problema crescer, a classe ficará cada vez maior e mais difícil de testar.

### Alteração frequente da mesma classe

Se toda nova variação de comportamento exige alterar a mesma classe, ela provavelmente está concentrando responsabilidades demais.

Isso importa porque aumenta o risco de quebrar funcionalidades antigas. Para validar, observe o histórico de mudanças: a mesma classe é alterada sempre que surge uma nova forma de envio, pagamento, relatório ou processamento?

Se faltar separação, a classe vira um ponto de manutenção constante.

### Conhecimento excessivo sobre classes auxiliares

Uma classe principal não deveria conhecer muitos detalhes internos de suas colaboradoras.

Sinais comuns incluem:

nomes específicos de classes;

nomes diferentes de métodos;

parâmetros específicos de cada tecnologia;

regras internas de cada implementação.

Isso importa porque a classe principal fica presa ao formato das classes auxiliares. Para validar, pergunte: “Esta classe precisa mesmo saber esse detalhe?”

Se a resposta for não, há indício de acoplamento forte.

### Dificuldade para testar

Quando uma classe depende diretamente de envio de e-mail, acesso a banco, API externa ou leitura de arquivo, o teste pode se tornar difícil.

Isso importa porque testes devem conseguir validar a regra principal sem depender de efeitos externos reais.

Para validar, tente responder: “Consigo testar `PedidoService` sem enviar e-mail de verdade?” Se a resposta for não, o acoplamento está atrapalhando os testes.

### Responsabilidades misturadas

Uma classe com responsabilidades misturadas combina regra de negócio com detalhes técnicos.

Exemplo: uma classe de pedido que também sabe detalhes de e-mail, SMS e log.

Isso importa porque mudanças técnicas passam a afetar regras de negócio. Para validar, descreva a responsabilidade da classe em uma frase. Se a frase precisar de muitos “e também”, há sinal de excesso.

## 14. Aplicação prática resolvida: relatórios em diferentes formatos

### Cenário

Um sistema precisa emitir relatórios. Inicialmente, o relatório será gerado em PDF. Para isso, foi criada a classe `RelatorioPdf`.

```csharp
public class RelatorioPdf
{
    public void Gerar(string conteudo)
    {
        Console.WriteLine($"Gerando relatório em PDF: {conteudo}");
    }
}
```

A classe de serviço usa diretamente essa implementação:

```csharp
public class RelatorioService
{
    private readonly RelatorioPdf _relatorioPdf;

    public RelatorioService()
    {
        _relatorioPdf = new RelatorioPdf();
    }

    public void EmitirRelatorio(string conteudo)
    {
        Console.WriteLine("Preparando relatório.");
        _relatorioPdf.Gerar(conteudo);
    }
}
```

### Objetivo

Identificar o acoplamento concreto e propor uma forma mais flexível de modelar o comportamento necessário.

### Análise do problema

A classe que depende de uma classe concreta é `RelatorioService`.

O campo abaixo mostra a dependência direta:

```csharp
private readonly RelatorioPdf _relatorioPdf;
```

O construtor reforça o problema:

```csharp
_relatorioPdf = new RelatorioPdf();
```

Isso significa que `RelatorioService` está presa ao formato PDF.

Se amanhã o sistema precisar gerar relatório em Excel, HTML ou CSV, a classe `RelatorioService` provavelmente precisará ser alterada.

### Pergunta correta

A pergunta errada seria:

“Qual classe concreta o `RelatorioService` precisa usar?”

A pergunta correta é:

“Qual comportamento o `RelatorioService` precisa?”

A resposta é:

“O `RelatorioService` precisa de algo capaz de gerar um relatório a partir de um conteúdo.”

O formato não deveria ser responsabilidade direta de `RelatorioService`.

### Solução com contrato de comportamento

Podemos criar um contrato chamado `IGeradorRelatorio`.

```csharp
public interface IGeradorRelatorio
{
    void Gerar(string conteudo);
}
```

Agora a implementação em PDF cumpre esse contrato:

```csharp
public class RelatorioPdf : IGeradorRelatorio
{
    public void Gerar(string conteudo)
    {
        Console.WriteLine($"Gerando relatório em PDF: {conteudo}");
    }
}
```

Também poderíamos ter uma implementação em HTML:

```csharp
public class RelatorioHtml : IGeradorRelatorio
{
    public void Gerar(string conteudo)
    {
        Console.WriteLine($"Gerando relatório em HTML: {conteudo}");
    }
}
```

Agora `RelatorioService` depende do contrato:

```csharp
public class RelatorioService
{
    private readonly IGeradorRelatorio _geradorRelatorio;

    public RelatorioService(IGeradorRelatorio geradorRelatorio)
    {
        _geradorRelatorio = geradorRelatorio;
    }

    public void EmitirRelatorio(string conteudo)
    {
        Console.WriteLine("Preparando relatório.");
        _geradorRelatorio.Gerar(conteudo);
    }
}
```

### Comentário da solução

A classe `RelatorioService` continua coordenando a emissão do relatório. Porém, ela não decide mais se o relatório será PDF, HTML, Excel ou CSV.

Essa decisão fica fora dela.

Isso reduz o acoplamento porque `RelatorioService` conhece apenas o comportamento `Gerar`, definido por `IGeradorRelatorio`.

### Resultado esperado

Usando PDF:

```csharp
IGeradorRelatorio gerador = new RelatorioPdf();
RelatorioService service = new RelatorioService(gerador);

service.EmitirRelatorio("Relatório de vendas do mês.");
```

Saída esperada:

```text
Preparando relatório.
Gerando relatório em PDF: Relatório de vendas do mês.
```

Usando HTML:

```csharp
IGeradorRelatorio gerador = new RelatorioHtml();
RelatorioService service = new RelatorioService(gerador);

service.EmitirRelatorio("Relatório de vendas do mês.");
```

Saída esperada:

```text
Preparando relatório.
Gerando relatório em HTML: Relatório de vendas do mês.
```

Observe que `RelatorioService` não mudou. Apenas a implementação fornecida mudou.

### Como validar

A validação principal é observar se novas formas de relatório podem ser adicionadas sem alterar `RelatorioService`.

Para validar, crie uma nova classe, por exemplo `RelatorioCsv`, implementando `IGeradorRelatorio`. Depois, injete essa nova classe em `RelatorioService`.

Se funcionar sem mudar o código de `RelatorioService`, o acoplamento foi reduzido.

### Possíveis erros

Um erro comum é criar a interface, mas continuar instanciando a classe concreta dentro do serviço.

Exemplo problemático:

```csharp
public class RelatorioService
{
    private readonly IGeradorRelatorio _geradorRelatorio;

    public RelatorioService()
    {
        _geradorRelatorio = new RelatorioPdf();
    }
}
```

Apesar de o campo usar a interface, o serviço ainda escolhe a implementação concreta internamente. Isso reduz pouco o acoplamento, porque `RelatorioService` continua presa ao PDF.

Outro erro comum é criar métodos diferentes para cada implementação:

```csharp
GerarPdf();
GerarHtml();
GerarCsv();
```

Se cada classe tiver um método diferente, o contrato comum perde força. O ideal é que o serviço consiga acionar um comportamento padronizado, como `Gerar`.

## 15. Erros comuns e dúvidas frequentes

### “Se o código funciona, por que mudar?”

Porque o problema não é apenas o funcionamento atual. O problema é a capacidade de evolução.

Um código pode funcionar hoje e ainda assim estar mal preparado para mudanças futuras. Quando uma classe depende diretamente de implementações concretas, qualquer nova variação pode exigir alteração em código já existente.

### “Toda dependência concreta é errada?”

Não. Classes concretas são necessárias. Em algum lugar do sistema, objetos concretos precisam ser criados.

O problema ocorre quando uma classe que deveria representar uma regra principal fica presa a detalhes que variam, como forma de envio, meio de pagamento, formato de relatório ou tecnologia externa.

### “Sempre devo criar interface?”

Não. Criar interface sem necessidade também pode aumentar a complexidade.

Interfaces fazem mais sentido quando existe ou pode existir variação de comportamento, quando a substituição facilita testes ou quando a classe principal não deveria conhecer detalhes de implementação.

Se existe apenas uma classe simples, sem previsão realista de variação, uma interface pode ser desnecessária naquele momento.

### “Usar interface resolve tudo?”

Não. Interface é uma ferramenta, não uma solução automática.

O projeto também precisa manter responsabilidades bem separadas, nomes claros e contratos coerentes. Uma interface mal definida pode apenas esconder um problema de modelagem.

### “Qual é a diferença entre depender de uma classe e depender de um comportamento?”

Depender de uma classe significa que o código está preso a uma implementação específica.

Depender de um comportamento significa que o código exige apenas que alguém cumpra uma ação esperada.

No exemplo do pedido, depender de `EmailNotificador` é depender de uma classe. Depender de `INotificador` é depender de um comportamento: enviar uma notificação.

## 16. Checklist explicado de revisão

### Verifique se a classe principal cria dependências com `new`

O que verificar: procure dentro da classe principal por instâncias como `new EmailNotificador()`, `new PagamentoCartaoCredito()` ou `new RelatorioPdf()`.

Por que importa: quando a própria classe cria a dependência, ela escolhe a implementação e fica presa a ela.

Como validar: tente trocar a implementação sem editar a classe principal. Se não for possível, há acoplamento concreto.

O que acontece se faltar: a classe ficará rígida e exigirá alteração sempre que uma nova implementação surgir.

### Verifique se a classe depende de um comportamento ou de uma implementação

O que verificar: observe os tipos dos campos e parâmetros. Se aparecem classes específicas, como `EmailNotificador`, pode haver dependência concreta. Se aparece um contrato, como `INotificador`, a classe tende a depender de comportamento.

Por que importa: depender de comportamento permite substituir implementações com menor impacto.

Como validar: crie uma segunda implementação do mesmo comportamento e veja se a classe principal continua funcionando sem mudanças internas.

O que acontece se faltar: cada nova variação exigirá alteração direta na classe principal.

### Verifique se há muitos `if/else` ou `switch` escolhendo classes

O que verificar: procure condicionais que decidem qual tecnologia, formato ou implementação usar.

Por que importa: essas estruturas costumam crescer sempre que surge uma nova opção.

Como validar: imagine adicionar uma nova forma de notificação. Se for necessário adicionar mais um `else if` na classe principal, há sinal de acoplamento e responsabilidade misturada.

O que acontece se faltar: a classe se tornará extensa, difícil de testar e mais propensa a erros.

### Verifique se a classe sabe detalhes demais sobre outras classes

O que verificar: veja se a classe principal conhece nomes específicos de métodos, parâmetros próprios de uma tecnologia ou regras internas de outra classe.

Por que importa: quanto mais detalhes uma classe conhece sobre outra, maior a dependência entre elas.

Como validar: pergunte se a classe realmente precisa saber aquele detalhe para cumprir sua responsabilidade principal.

O que acontece se faltar: mudanças em classes auxiliares podem causar alterações em cadeia.

### Verifique se a classe é fácil de testar isoladamente

O que verificar: avalie se é possível testar a regra principal sem enviar e-mail real, sem acessar serviço externo, sem gerar arquivo real ou sem depender de infraestrutura.

Por que importa: classes fortemente acopladas costumam ser difíceis de testar porque executam efeitos colaterais difíceis de controlar.

Como validar: substitua a dependência real por uma implementação simulada. Se a classe aceitar essa substituição facilmente, o acoplamento está menor.

O que acontece se faltar: os testes ficam lentos, frágeis ou dependentes de recursos externos.

### Verifique se cada classe possui uma responsabilidade clara

O que verificar: tente resumir a responsabilidade da classe em uma frase simples.

Por que importa: quando uma classe mistura regra principal com detalhes técnicos, ela se torna mais difícil de manter.

Como validar: se a descrição da classe precisa incluir muitas tarefas diferentes, como “finaliza pedido, decide canal de envio, monta mensagem e conhece SMS”, há mistura de responsabilidades.

O que acontece se faltar: mudanças em uma área do sistema passam a afetar áreas que deveriam estar separadas.

## 17. Síntese final

Depender diretamente de classes concretas pode tornar um sistema mais acoplado, rígido e difícil de evoluir.

No exemplo de pedidos, `PedidoService` não deveria depender obrigatoriamente de `EmailNotificador`. A responsabilidade principal de `PedidoService` é finalizar pedidos, não conhecer todos os mecanismos de notificação.

A mudança de pensamento mais importante é sair de:

“Preciso usar esta classe específica.”

E passar para:

“Preciso de algo que cumpra este comportamento.”

Esse raciocínio aparece em vários domínios:

uma venda precisa de algo capaz de processar pagamento;

um pedido precisa de algo capaz de notificar o cliente;

um serviço de relatório precisa de algo capaz de gerar relatório;

uma regra principal precisa colaborar com outras partes sem conhecer detalhes desnecessários.

Em C#, o recurso usado para representar contratos de comportamento é a interface. A interface permite definir o que uma classe deve fazer, sem prender o código à forma específica como isso será feito.

---

## Conclusão

O problema das dependências concretas não está no uso de classes concretas em si, mas no excesso de dependência direta entre classes que deveriam variar de forma independente.

Quando uma classe principal conhece implementações específicas demais, ela fica rígida. Cada nova necessidade exige alteração no mesmo ponto, os testes ficam mais difíceis e as responsabilidades se misturam.

Um projeto mais flexível busca depender de comportamentos esperados. Isso permite que diferentes implementações sejam usadas sem alterar a regra principal.

A classe que finaliza um pedido não precisa conhecer todos os mecanismos de notificação. A classe que realiza uma venda não precisa conhecer todos os meios de pagamento. A classe que emite um relatório não precisa conhecer todos os formatos possíveis.

Em muitos casos, essas classes precisam apenas de algo que cumpra um contrato claro de comportamento.
