# Diferença entre Classe Abstrata e Interface em C#

Material elaborado a partir do conteúdo-base enviado sobre classe abstrata e interface em C#, com foco em modelagem orientada a objetos, escolha correta de abstrações e uso consciente desses recursos. 

## Objetivo do material

Neste material, você aprenderá a diferenciar **classe abstrata** e **interface** em C#, entendendo quando cada recurso faz sentido em uma modelagem orientada a objetos.

O objetivo não é decorar uma regra única, como “use interface sempre” ou “use classe abstrata quando tiver código repetido”. A ideia é aprender a analisar o domínio do problema e escolher a estrutura que melhor representa a realidade do sistema.

Ao final, você deverá ser capaz de:

1. explicar a finalidade de uma classe abstrata;
2. explicar a finalidade de uma interface;
3. diferenciar relação de herança de relação de contrato;
4. reconhecer quando uma abstração melhora o projeto;
5. evitar interfaces e classes abstratas criadas sem necessidade;
6. combinar classe abstrata e interface quando isso fizer sentido.

---

## 1. O problema da escolha entre classe abstrata e interface

Em C#, tanto uma classe abstrata quanto uma interface podem obrigar classes concretas a implementar determinados métodos.

Observe os dois exemplos:

```csharp
public abstract class FormaPagamento
{
    public abstract void Pagar(decimal valor);
}
```

```csharp
public interface IFormaPagamento
{
    void Pagar(decimal valor);
}
```

À primeira vista, os dois códigos parecem resolver o mesmo problema: ambos exigem que uma classe implemente o método `Pagar`.

No entanto, a decisão correta não deve ser tomada apenas pela sintaxe. A pergunta mais importante não é:

> “Qual dos dois compila?”

A pergunta correta é:

> “O que estou tentando representar no domínio do problema?”

Em orientação a objetos, modelar bem significa escolher estruturas que representem corretamente conceitos, comportamentos e relações do sistema.

Uma escolha inadequada pode gerar problemas como:

* excesso de arquivos sem função real;
* código mais difícil de entender;
* heranças artificiais;
* interfaces que apenas repetem classes;
* acoplamento desnecessário;
* dificuldade para evoluir o sistema.

A boa modelagem usa abstrações quando elas tornam o domínio mais claro, mais flexível ou mais reutilizável.

## 2. Classe abstrata: base conceitual comum

Uma **classe abstrata** deve ser usada quando existe uma ideia geral que representa uma família de objetos.

Ela serve como uma base para classes mais específicas. Essa base pode conter:

* propriedades comuns;
* atributos compartilhados;
* construtores;
* validações;
* métodos já implementados;
* métodos abstratos que as subclasses precisam implementar.

Uma classe abstrata não representa apenas um contrato. Ela representa uma **base conceitual**.

### Exemplo: funcionário

```csharp
public abstract class Funcionario
{
    public string Nome { get; private set; }
    public string Matricula { get; private set; }

    protected Funcionario(string nome, string matricula)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("O nome é obrigatório.");

        if (string.IsNullOrWhiteSpace(matricula))
            throw new ArgumentException("A matrícula é obrigatória.");

        Nome = nome;
        Matricula = matricula;
    }

    public abstract decimal CalcularSalario();
}
```

Nesse exemplo, `Funcionario` é uma classe abstrata porque representa uma ideia geral. Existem vários tipos de funcionário, como professor, coordenador e técnico administrativo.

A classe abstrata concentra dados e regras comuns:

* todo funcionário tem nome;
* todo funcionário tem matrícula;
* nome e matrícula precisam ser validados;
* todo funcionário deve ter uma forma de calcular salário.

A classe abstrata não sabe exatamente como calcular o salário de cada tipo de funcionário. Por isso, o método `CalcularSalario` é abstrato.

### Classe derivada: professor

```csharp
public class Professor : Funcionario
{
    private readonly decimal _valorHora;
    private readonly int _horasTrabalhadas;

    public Professor(
        string nome,
        string matricula,
        decimal valorHora,
        int horasTrabalhadas
    ) : base(nome, matricula)
    {
        if (valorHora <= 0)
            throw new ArgumentException("O valor da hora deve ser maior que zero.");

        if (horasTrabalhadas < 0)
            throw new ArgumentException("As horas trabalhadas não podem ser negativas.");

        _valorHora = valorHora;
        _horasTrabalhadas = horasTrabalhadas;
    }

    public override decimal CalcularSalario()
    {
        return _valorHora * _horasTrabalhadas;
    }
}
```

A relação aqui faz sentido porque:

> Professor é um funcionário.

A classe `Professor` herda de `Funcionario` porque pertence à mesma família conceitual. Ela reaproveita o estado comum (`Nome` e `Matricula`) e implementa sua própria regra de salário.

## 3. Interface: contrato de comportamento

Uma **interface** deve ser usada quando queremos representar um comportamento que uma classe promete oferecer.

Ela não precisa indicar que as classes pertencem à mesma família. O foco da interface é a capacidade.

Uma interface responde à pergunta:

> “O que este objeto é capaz de fazer?”

### Exemplo: notificável

```csharp
public interface INotificavel
{
    void EnviarNotificacao(string mensagem);
}
```

A interface `INotificavel` não representa uma entidade do domínio. Ela representa uma capacidade: algo que pode receber ou enviar notificação.

Classes completamente diferentes podem implementar essa interface.

```csharp
public class Aluno : INotificavel
{
    public string Nome { get; private set; }

    public Aluno(string nome)
    {
        Nome = nome;
    }

    public void EnviarNotificacao(string mensagem)
    {
        Console.WriteLine($"Notificação para o aluno {Nome}: {mensagem}");
    }
}
```

```csharp
public class Professor : INotificavel
{
    public string Nome { get; private set; }

    public Professor(string nome)
    {
        Nome = nome;
    }

    public void EnviarNotificacao(string mensagem)
    {
        Console.WriteLine($"Notificação para o professor {Nome}: {mensagem}");
    }
}
```

Aluno e professor podem ser notificados, mas a interface não está dizendo que ambos pertencem à mesma família de herança. Ela apenas diz que ambos cumprem o contrato de enviar notificação.

A interface é útil porque permite tratar objetos diferentes por uma capacidade comum.

## 4. Diferença principal: “é um” versus “é capaz de”

Uma forma simples e didática de diferenciar classe abstrata e interface é observar o tipo de relação que está sendo modelada.

### Classe abstrata representa “é um”

Use classe abstrata quando a relação for de identidade ou pertencimento a uma família conceitual.

Exemplos:

* `Professor` é um `Funcionario`;
* `ProdutoFisico` é um `Produto`;
* `ContaCorrente` é uma `ContaBancaria`;
* `HistoricoEscolar` é um `DocumentoAcademico`.

Nesse caso, a classe abstrata representa um conceito geral, e as classes derivadas representam especializações desse conceito.

### Interface representa “é capaz de”

Use interface quando a relação for de capacidade ou comportamento.

Exemplos:

* `HistoricoEscolar` é capaz de exportar;
* `RelatorioFinanceiro` é capaz de exportar;
* `Aluno` é capaz de receber notificação;
* `Usuario` é capaz de autenticar;
* `Pedido` é capaz de calcular desconto.

Nesse caso, as classes não precisam pertencer à mesma família. Elas apenas compartilham um comportamento esperado.

### Exemplo com interface de exportação

```csharp
public interface IExportavel
{
    void Exportar();
}
```

```csharp
public class HistoricoEscolar : IExportavel
{
    public void Exportar()
    {
        Console.WriteLine("Exportando histórico escolar.");
    }
}
```

```csharp
public class RelatorioFinanceiro : IExportavel
{
    public void Exportar()
    {
        Console.WriteLine("Exportando relatório financeiro.");
    }
}
```

`HistoricoEscolar` e `RelatorioFinanceiro` podem ser muito diferentes entre si. Um pertence ao contexto acadêmico; o outro, ao contexto financeiro. Mesmo assim, ambos podem cumprir o contrato `IExportavel`.

A interface permite que o sistema trabalhe com qualquer objeto exportável, sem depender da classe concreta.

## 5. Classe abstrata pode ter estado comum

Uma das principais vantagens da classe abstrata é a possibilidade de armazenar estado comum.

Estado significa dados mantidos por um objeto, como propriedades, atributos e valores internos.

### Exemplo: produto

```csharp
public abstract class Produto
{
    public string Nome { get; private set; }
    public decimal Preco { get; private set; }

    protected Produto(string nome, decimal preco)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("Nome obrigatório.");

        if (preco <= 0)
            throw new ArgumentException("Preço inválido.");

        Nome = nome;
        Preco = preco;
    }

    public abstract decimal CalcularValorFinal();
}
```

A classe `Produto` possui estado comum:

* `Nome`;
* `Preco`.

Também possui uma regra comum de construção:

* o nome não pode ser vazio;
* o preço precisa ser maior que zero.

Essas regras são aplicadas a todos os produtos derivados.

### Produto físico

```csharp
public class ProdutoFisico : Produto
{
    private readonly decimal _frete;

    public ProdutoFisico(string nome, decimal preco, decimal frete)
        : base(nome, preco)
    {
        if (frete < 0)
            throw new ArgumentException("O frete não pode ser negativo.");

        _frete = frete;
    }

    public override decimal CalcularValorFinal()
    {
        return Preco + _frete;
    }
}
```

### Produto digital

```csharp
public class ProdutoDigital : Produto
{
    public ProdutoDigital(string nome, decimal preco)
        : base(nome, preco)
    {
    }

    public override decimal CalcularValorFinal()
    {
        return Preco;
    }
}
```

A classe abstrata é adequada porque existe uma família conceitual real: produtos. Além disso, há estado e regras comuns que podem ser reaproveitados.

## 6. Interface não deve substituir entidade com estado

Uma interface pode declarar propriedades, mas isso não significa que ela deva ser usada para representar uma entidade com estado.

Veja um exemplo pouco útil:

```csharp
public interface IProduto
{
    string Nome { get; }
    decimal Preco { get; }
}
```

Essa interface apenas repete propriedades que provavelmente pertencem a uma classe `Produto`.

Se existe uma entidade com dados, validações e comportamento comum, uma classe abstrata ou uma classe concreta pode ser mais adequada.

O problema não é a sintaxe. O problema é criar uma interface sem necessidade real.

Uma interface mais significativa seria:

```csharp
public interface IDescontavel
{
    decimal CalcularDesconto();
}
```

Nesse caso, a interface representa uma capacidade: calcular desconto.

Diferentes classes podem ser descontáveis sem pertencer à mesma hierarquia:

```csharp
public class ProdutoPromocional : IDescontavel
{
    public decimal Preco { get; private set; }

    public ProdutoPromocional(decimal preco)
    {
        Preco = preco;
    }

    public decimal CalcularDesconto()
    {
        return Preco * 0.10m;
    }
}
```

```csharp
public class Cupom : IDescontavel
{
    public decimal Valor { get; private set; }

    public Cupom(decimal valor)
    {
        Valor = valor;
    }

    public decimal CalcularDesconto()
    {
        return Valor;
    }
}
```

`ProdutoPromocional` e `Cupom` são conceitos diferentes, mas ambos são capazes de calcular desconto.

## 7. Classe abstrata pode ter comportamento pronto

Uma classe abstrata pode conter métodos concretos, ou seja, métodos já implementados. Esses métodos podem ser reutilizados pelas classes derivadas.

### Exemplo: conta bancária

```csharp
public abstract class ContaBancaria
{
    public string Numero { get; private set; }
    public decimal Saldo { get; private set; }

    protected ContaBancaria(string numero)
    {
        if (string.IsNullOrWhiteSpace(numero))
            throw new ArgumentException("Número da conta obrigatório.");

        Numero = numero;
        Saldo = 0;
    }

    public void Depositar(decimal valor)
    {
        if (valor <= 0)
            throw new ArgumentException("O valor do depósito deve ser maior que zero.");

        Saldo += valor;
    }

    public abstract void Sacar(decimal valor);
}
```

Nesse exemplo, `Depositar` é um método concreto. Todas as contas bancárias depositam dinheiro da mesma forma.

Já `Sacar` é abstrato, porque cada tipo de conta pode ter regras diferentes de saque.

```csharp
public class ContaCorrente : ContaBancaria
{
    public ContaCorrente(string numero) : base(numero)
    {
    }

    public override void Sacar(decimal valor)
    {
        Console.WriteLine($"Saque em conta corrente: R$ {valor:F2}");
    }
}
```

Esse é um bom caso para classe abstrata porque existem:

* estado comum: número e saldo;
* comportamento comum: depósito;
* comportamento variável: saque;
* relação “é um”: conta corrente é uma conta bancária.

## 8. Interface prioriza o contrato

Uma interface prioriza a existência de um comportamento, não a forma como esse comportamento será implementado.

### Exemplo: processador de pagamento

```csharp
public interface IProcessadorDePagamento
{
    void Processar(decimal valor);
}
```

Agora diferentes classes podem implementar esse contrato.

```csharp
public class ProcessadorPix : IProcessadorDePagamento
{
    public void Processar(decimal valor)
    {
        Console.WriteLine($"Processando via Pix: R$ {valor:F2}");
    }
}
```

```csharp
public class ProcessadorCartaoCredito : IProcessadorDePagamento
{
    public void Processar(decimal valor)
    {
        Console.WriteLine($"Processando via cartão: R$ {valor:F2}");
    }
}
```

```csharp
public class ProcessadorBoleto : IProcessadorDePagamento
{
    public void Processar(decimal valor)
    {
        Console.WriteLine($"Gerando boleto: R$ {valor:F2}");
    }
}
```

A vantagem da interface é permitir que o sistema dependa do contrato, e não da implementação concreta.

Por exemplo:

```csharp
public class ServicoPagamento
{
    private readonly IProcessadorDePagamento _processador;

    public ServicoPagamento(IProcessadorDePagamento processador)
    {
        _processador = processador;
    }

    public void FinalizarPagamento(decimal valor)
    {
        _processador.Processar(valor);
    }
}
```

A classe `ServicoPagamento` não precisa saber se o pagamento será feito por Pix, cartão ou boleto. Ela só precisa saber que existe um processador capaz de processar o pagamento.

Isso facilita substituição de implementações e reduz dependência direta de classes concretas.

## 9. Uma classe pode implementar várias interfaces

Em C#, uma classe pode herdar diretamente de apenas uma classe base. Isso significa que uma classe não pode ter duas superclasses diretas.

Por outro lado, uma classe pode implementar várias interfaces.

### Exemplo com herança única

```csharp
public abstract class Pessoa
{
    public string Nome { get; private set; }

    protected Pessoa(string nome)
    {
        Nome = nome;
    }
}
```

Uma classe `Aluno` pode herdar de `Pessoa`:

```csharp
public class Aluno : Pessoa
{
    public Aluno(string nome) : base(nome)
    {
    }
}
```

Mas `Aluno` não pode herdar diretamente de duas classes base ao mesmo tempo.

### Exemplo com múltiplas interfaces

```csharp
public interface IAutenticavel
{
    bool Autenticar(string senha);
}
```

```csharp
public interface INotificavel
{
    void EnviarNotificacao(string mensagem);
}
```

```csharp
public class Aluno : Pessoa, IAutenticavel, INotificavel
{
    private readonly string _senha;

    public Aluno(string nome, string senha) : base(nome)
    {
        _senha = senha;
    }

    public bool Autenticar(string senha)
    {
        return _senha == senha;
    }

    public void EnviarNotificacao(string mensagem)
    {
        Console.WriteLine($"Notificação para {Nome}: {mensagem}");
    }
}
```

Nesse exemplo, `Aluno`:

* é uma `Pessoa`;
* é capaz de autenticar;
* é capaz de receber notificação.

A classe abstrata representa a base conceitual. As interfaces representam capacidades adicionais.

## 10. Usando classe abstrata e interface juntas

Classe abstrata e interface não são recursos concorrentes. Em muitos casos, elas podem ser usadas juntas.

### Exemplo: usuário notificável

```csharp
public abstract class Usuario
{
    public string Nome { get; private set; }
    public string Email { get; private set; }

    protected Usuario(string nome, string email)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("Nome obrigatório.");

        if (string.IsNullOrWhiteSpace(email))
            throw new ArgumentException("E-mail obrigatório.");

        Nome = nome;
        Email = email;
    }

    public abstract string ObterPerfil();
}
```

```csharp
public interface INotificavel
{
    void EnviarNotificacao(string mensagem);
}
```

```csharp
public class Aluno : Usuario, INotificavel
{
    public Aluno(string nome, string email) : base(nome, email)
    {
    }

    public override string ObterPerfil()
    {
        return "Aluno";
    }

    public void EnviarNotificacao(string mensagem)
    {
        Console.WriteLine($"Enviando notificação para o aluno {Nome}: {mensagem}");
    }
}
```

Nesse caso:

* `Usuario` representa uma base conceitual comum;
* `INotificavel` representa uma capacidade;
* `Aluno` é um usuário e é capaz de receber notificação.

Essa combinação é útil quando parte da modelagem envolve identidade e outra parte envolve comportamento.

## 11. Exemplos comentados de escolha

### Exemplo 1: material didático

Uma instituição possui apostilas, videoaulas e livros digitais. Todos possuem título, autor e uma forma de exibir resumo. Cada tipo calcula o tempo de estudo de maneira diferente.

Nesse caso, uma classe abstrata pode ser adequada.

```csharp
public abstract class MaterialDidatico
{
    public string Titulo { get; private set; }
    public string Autor { get; private set; }

    protected MaterialDidatico(string titulo, string autor)
    {
        if (string.IsNullOrWhiteSpace(titulo))
            throw new ArgumentException("Título obrigatório.");

        if (string.IsNullOrWhiteSpace(autor))
            throw new ArgumentException("Autor obrigatório.");

        Titulo = titulo;
        Autor = autor;
    }

    public void ExibirResumo()
    {
        Console.WriteLine($"{Titulo} - Autor: {Autor}");
    }

    public abstract int CalcularTempoDeEstudo();
}
```

A classe abstrata faz sentido porque:

* existe uma família conceitual: materiais didáticos;
* há estado comum: título e autor;
* há comportamento comum: exibir resumo;
* há comportamento variável: calcular tempo de estudo.

### Exemplo 2: avaliável

Um sistema possui prova, projeto, seminário, participação em aula e desafio prático. Esses elementos têm estruturas diferentes, mas todos podem calcular uma nota final.

Nesse caso, uma interface pode ser adequada.

```csharp
public interface IAvaliavel
{
    decimal CalcularNotaFinal();
}
```

O foco está no comportamento: calcular nota final.

As classes não precisam pertencer à mesma família de herança. Elas apenas precisam cumprir o mesmo contrato.

```csharp
public class Prova : IAvaliavel
{
    public decimal Nota { get; private set; }

    public Prova(decimal nota)
    {
        Nota = nota;
    }

    public decimal CalcularNotaFinal()
    {
        return Nota;
    }
}
```

```csharp
public class Projeto : IAvaliavel
{
    public decimal NotaEntrega { get; private set; }
    public decimal NotaApresentacao { get; private set; }

    public Projeto(decimal notaEntrega, decimal notaApresentacao)
    {
        NotaEntrega = notaEntrega;
        NotaApresentacao = notaApresentacao;
    }

    public decimal CalcularNotaFinal()
    {
        return (NotaEntrega + NotaApresentacao) / 2;
    }
}
```

A interface permite tratar `Prova` e `Projeto` como avaliáveis, mesmo que sejam elementos diferentes.

## 12. Quando usar classe abstrata

Use classe abstrata quando o domínio indicar uma família conceitual real.

Uma classe abstrata tende a ser adequada quando há relação “é um”.

Exemplo:

> Conta corrente é uma conta bancária.

Também é adequada quando existem propriedades comuns entre as classes.

Exemplo:

> Todas as contas possuem número e saldo.

Outro sinal importante é a existência de validações e construtores comuns.

Exemplo:

> Toda conta precisa ter um número válido ao ser criada.

A classe abstrata também é útil quando há métodos concretos reutilizáveis.

Exemplo:

> Todas as contas podem depositar usando a mesma regra.

Por fim, ela é adequada quando há comportamentos que todas as subclasses devem possuir, mas cada uma executa de forma diferente.

Exemplo:

> Todas as contas podem sacar, mas cada tipo de conta pode ter uma regra específica de saque.

A pergunta principal para decidir é:

> As classes derivadas são tipos específicos dessa classe base?

Quando a resposta for sim, uma classe abstrata pode ser uma boa escolha.

---

## 13. Quando usar interface

Use interface quando o foco estiver em um comportamento esperado.

Uma interface tende a ser adequada quando classes diferentes precisam oferecer a mesma capacidade.

Exemplo:

> Prova, projeto e seminário podem calcular nota final.

Também é adequada quando a relação “é capaz de” faz mais sentido do que “é um”.

Exemplo:

> Um relatório é capaz de exportar. Um histórico escolar também é capaz de exportar.

A interface também ajuda quando o código precisa depender de uma abstração, e não de uma implementação específica.

Exemplo:

```csharp
public class ExportadorDeDados
{
    public void Exportar(IExportavel item)
    {
        item.Exportar();
    }
}
```

A classe `ExportadorDeDados` não precisa saber se está exportando um histórico, um relatório ou outro objeto. Ela só precisa receber algo que cumpra o contrato `IExportavel`.

Outra situação comum é quando uma classe precisa cumprir vários contratos ao mesmo tempo.

Exemplo:

```csharp
public class Coordenador : IAutenticavel, INotificavel, IExportavel
{
    public bool Autenticar(string senha)
    {
        return senha == "123";
    }

    public void EnviarNotificacao(string mensagem)
    {
        Console.WriteLine(mensagem);
    }

    public void Exportar()
    {
        Console.WriteLine("Exportando dados do coordenador.");
    }
}
```

A pergunta principal para decidir é:

> Essas classes precisam ser tratadas pelo mesmo comportamento, mesmo sendo diferentes entre si?

Quando a resposta for sim, uma interface pode ser uma boa escolha.

## 14. Quando não usar classe abstrata nem interface

Nem toda classe precisa de uma abstração.

Às vezes, uma classe concreta simples é a melhor solução.

### Exemplo: endereço

```csharp
public class Endereco
{
    public string Rua { get; private set; }
    public string Numero { get; private set; }
    public string Cidade { get; private set; }

    public Endereco(string rua, string numero, string cidade)
    {
        Rua = rua;
        Numero = numero;
        Cidade = cidade;
    }
}
```

Se `Endereco` não possui variações importantes, não precisa de comportamento polimórfico e não será tratado por contrato, talvez não haja motivo para criar:

```csharp
public abstract class Endereco
{
}
```

Ou:

```csharp
public interface IEndereco
{
}
```

Criar abstrações sem necessidade aumenta a complexidade sem trazer benefício real.

Uma boa modelagem não é aquela que usa todos os recursos da linguagem. Uma boa modelagem é aquela que usa os recursos adequados para o problema.

## 15. Comparação entre classe abstrata e interface

| Critério              | Classe abstrata                                                 | Interface                                                    |
| --------------------- | --------------------------------------------------------------- | ------------------------------------------------------------ |
| Ideia principal       | Base conceitual comum                                           | Contrato de comportamento                                    |
| Relação típica        | “É um”                                                          | “É capaz de”                                                 |
| Estado comum          | Pode ter estado comum                                           | Não deve ser usada como entidade de estado                   |
| Construtor            | Pode ter construtor                                             | Não funciona como construtor de entidade                     |
| Métodos concretos     | Pode ter métodos implementados                                  | O foco deve ser o contrato                                   |
| Quantidade por classe | Uma classe base direta                                          | Várias interfaces                                            |
| Uso típico            | Reaproveitar estrutura, estado, validação e comportamento comum | Permitir implementações diferentes de um mesmo comportamento |
| Exemplos              | `Funcionario`, `Produto`, `ContaBancaria`, `DocumentoAcademico` | `INotificavel`, `IExportavel`, `IAutenticavel`, `IAvaliavel` |

A diferença principal pode ser resumida assim:

> Classe abstrata representa uma família. Interface representa um contrato.

## 16. Aplicação prática resolvida: modelando formas de pagamento

### Cenário

Um sistema precisa processar pagamentos por Pix, cartão de crédito e boleto.

Todas as formas de pagamento precisam processar um valor, mas cada uma executa o processamento de forma diferente.

Além disso, suponha que todas tenham uma descrição comum e uma validação básica do valor.

### Objetivo

Decidir se a modelagem deve usar classe abstrata, interface ou as duas.

### Análise do domínio

Existe uma família conceitual?

Sim. Pix, cartão de crédito e boleto podem ser entendidos como tipos específicos de forma de pagamento.

Existe estado comum?

Sim. Todas podem ter uma descrição.

Existe comportamento comum?

Sim. Todas precisam validar se o valor é maior que zero.

Existe comportamento específico?

Sim. Cada tipo processa o pagamento de forma diferente.

Nesse caso, uma classe abstrata pode ser adequada.

### Solução com classe abstrata

```csharp
public abstract class FormaPagamento
{
    public string Descricao { get; private set; }

    protected FormaPagamento(string descricao)
    {
        if (string.IsNullOrWhiteSpace(descricao))
            throw new ArgumentException("Descrição obrigatória.");

        Descricao = descricao;
    }

    protected void ValidarValor(decimal valor)
    {
        if (valor <= 0)
            throw new ArgumentException("O valor deve ser maior que zero.");
    }

    public abstract void Processar(decimal valor);
}
```

A classe abstrata contém:

* estado comum: `Descricao`;
* validação comum: `ValidarValor`;
* comportamento obrigatório: `Processar`.

Agora as subclasses implementam suas próprias regras.

```csharp
public class PagamentoPix : FormaPagamento
{
    public PagamentoPix() : base("Pagamento via Pix")
    {
    }

    public override void Processar(decimal valor)
    {
        ValidarValor(valor);
        Console.WriteLine($"Processando Pix no valor de R$ {valor:F2}");
    }
}
```

```csharp
public class PagamentoCartaoCredito : FormaPagamento
{
    public PagamentoCartaoCredito() : base("Pagamento via cartão de crédito")
    {
    }

    public override void Processar(decimal valor)
    {
        ValidarValor(valor);
        Console.WriteLine($"Processando cartão de crédito no valor de R$ {valor:F2}");
    }
}
```

```csharp
public class PagamentoBoleto : FormaPagamento
{
    public PagamentoBoleto() : base("Pagamento via boleto")
    {
    }

    public override void Processar(decimal valor)
    {
        ValidarValor(valor);
        Console.WriteLine($"Gerando boleto no valor de R$ {valor:F2}");
    }
}
```

### Comentário da solução

A classe abstrata é adequada porque há uma família de objetos. Cada forma de pagamento é um tipo específico da base `FormaPagamento`.

O método `ValidarValor` evita repetição de regra nas subclasses. O método `Processar` permanece abstrato porque cada forma de pagamento executa essa operação de maneira diferente.

### Resultado esperado

Ao executar:

```csharp
FormaPagamento pagamento = new PagamentoPix();
pagamento.Processar(150);
```

O resultado esperado é:

```text
Processando Pix no valor de R$ 150,00
```

### Como validar

A modelagem está adequada se:

* as subclasses realmente forem tipos de `FormaPagamento`;
* houver estado ou comportamento comum reaproveitado;
* cada subclasse implementar apenas a parte que varia;
* a classe abstrata não for genérica demais;
* a abstração tornar o código mais claro.

### Possíveis erros

Um erro seria criar uma classe abstrata sem estado, sem validação e sem comportamento comum apenas porque as classes possuem um método com o mesmo nome. Nesse caso, talvez uma interface fosse suficiente.

Outro erro seria criar uma interface `IFormaPagamento` apenas repetindo tudo que a classe abstrata já resolve, sem necessidade real de múltiplos contratos ou substituição por comportamento.

## 17. Aplicação prática resolvida: exportação de arquivos

### Cenário

Um sistema precisa exportar diferentes tipos de dados: histórico escolar, relatório financeiro e lista de usuários.

Essas classes não pertencem à mesma família conceitual. Porém, todas precisam exportar conteúdo.

### Objetivo

Escolher a melhor abstração para representar a capacidade de exportar.

### Análise do domínio

Existe uma família conceitual comum?

Não necessariamente. Histórico escolar, relatório financeiro e lista de usuários são conceitos diferentes.

Existe uma capacidade comum?

Sim. Todos são capazes de exportar.

Nesse caso, uma interface é adequada.

### Solução com interface

```csharp
public interface IExportavel
{
    void Exportar();
}
```

```csharp
public class HistoricoEscolar : IExportavel
{
    public void Exportar()
    {
        Console.WriteLine("Exportando histórico escolar em PDF.");
    }
}
```

```csharp
public class RelatorioFinanceiro : IExportavel
{
    public void Exportar()
    {
        Console.WriteLine("Exportando relatório financeiro em planilha.");
    }
}
```

```csharp
public class ListaUsuarios : IExportavel
{
    public void Exportar()
    {
        Console.WriteLine("Exportando lista de usuários em CSV.");
    }
}
```

Agora é possível criar um serviço que trabalha com qualquer item exportável:

```csharp
public class ServicoExportacao
{
    public void ExportarItem(IExportavel item)
    {
        item.Exportar();
    }
}
```

### Comentário da solução

A interface é adequada porque não força uma família de herança artificial. Ela apenas declara o comportamento esperado.

O serviço `ServicoExportacao` depende da interface `IExportavel`, e não de classes concretas. Isso torna o código mais flexível.

### Resultado esperado

Ao executar:

```csharp
var servico = new ServicoExportacao();
servico.ExportarItem(new RelatorioFinanceiro());
```

O resultado esperado é:

```text
Exportando relatório financeiro em planilha.
```

### Como validar

A interface está bem aplicada se:

* as classes não precisam compartilhar estado;
* o foco é uma capacidade comum;
* o contrato permite tratar objetos diferentes de forma uniforme;
* a interface não está apenas copiando propriedades de uma classe concreta.

### Possíveis erros

Um erro seria criar uma classe abstrata `DocumentoExportavel` e obrigar `RelatorioFinanceiro`, `HistoricoEscolar` e `ListaUsuarios` a herdarem dela, mesmo que não exista uma família conceitual clara entre elas.

Outro erro seria criar uma interface muito genérica, como:

```csharp
public interface IExecutavel
{
    void Executar();
}
```

Interfaces genéricas demais podem perder significado e tornar a modelagem confusa.

## 18. Erros comuns

### Erro 1: criar interface que apenas copia uma classe

```csharp
public class Cliente
{
    public string Nome { get; private set; }
    public string Email { get; private set; }
}
```

```csharp
public interface ICliente
{
    string Nome { get; }
    string Email { get; }
}
```

Esse tipo de interface pode ser pouco útil quando não há múltiplas implementações, polimorfismo ou desacoplamento real.

Uma interface mais significativa representaria uma capacidade:

```csharp
public interface INotificavel
{
    void EnviarNotificacao(string mensagem);
}
```

### Erro 2: criar classe abstrata sem família conceitual

```csharp
public abstract class OperacaoDoSistema
{
    public abstract void Executar();
}
```

Essa classe pode ser genérica demais. Se qualquer ação do sistema virar uma `OperacaoDoSistema`, a modelagem perde clareza.

Antes de criar uma classe abstrata, pergunte:

> Existe uma família conceitual real?

> As classes derivadas realmente são tipos dessa classe base?

> Existe estado, validação ou comportamento comum?

Se a resposta for não, talvez a classe abstrata não seja necessária.

### Erro 3: escolher pela sintaxe

O erro mais comum é escolher classe abstrata ou interface apenas porque o código compila.

A sintaxe mostra o que é possível. A modelagem mostra o que faz sentido.

Duas estruturas podem compilar, mas apenas uma pode representar bem o domínio.

### Erro 4: criar abstração antes da necessidade

Nem sempre o sistema precisa começar com várias interfaces e classes abstratas.

Quando não há variações, contratos, reaproveitamento ou polimorfismo, uma classe concreta simples pode ser suficiente.

Abstrações prematuras podem dificultar a leitura e a manutenção.

### Erro 5: usar herança para compartilhar qualquer código

Herança não deve ser usada apenas para evitar repetição. Ela deve representar uma relação conceitual correta.

Se duas classes compartilham um trecho de código, mas não pertencem à mesma família, talvez seja melhor extrair um serviço, uma composição ou uma interface.

## 19. Dúvidas frequentes

### Toda interface precisa começar com a letra “I”?

Em C#, é comum nomear interfaces com a letra `I`, como `INotificavel`, `IExportavel` e `IAutenticavel`.

Essa é uma convenção amplamente usada, mas o ponto principal não é o nome. O mais importante é que a interface represente um contrato claro.

### Toda classe abstrata precisa ter método abstrato?

Não necessariamente. Uma classe abstrata pode existir para impedir instanciação direta e concentrar estado ou comportamento comum.

Porém, se ela não possui nenhum comportamento comum, nenhuma regra e nenhuma especialização real, é importante questionar se ela é necessária.

### Interface pode ter propriedades?

Pode declarar propriedades, mas isso não significa que ela deva representar uma entidade de estado.

Interfaces são mais úteis quando representam capacidades e contratos de comportamento.

### Posso usar classe abstrata e interface ao mesmo tempo?

Sim. Isso é comum.

Uma classe pode herdar de uma classe abstrata e implementar uma ou mais interfaces.

Exemplo:

```csharp
public class Professor : Funcionario, INotificavel, IAutenticavel
{
    // Implementações
}
```

Nesse caso, `Professor` é um `Funcionario`, mas também é capaz de receber notificação e autenticar.

### Qual é a regra mais importante?

A regra mais importante é entender o domínio.

Classe abstrata representa uma família conceitual. Interface representa uma capacidade ou contrato.

## 20. Checklist explicado para decidir corretamente

### 1. Verifique se existe uma relação “é um”

Pergunte se as classes derivadas são tipos específicos da classe base.

Por exemplo, `ContaCorrente` é uma `ContaBancaria`. Essa relação indica que uma classe abstrata pode fazer sentido.

Se essa relação não for verdadeira, usar herança pode criar uma modelagem artificial.

### 2. Verifique se existe estado comum

Observe se as classes compartilham propriedades importantes, como nome, código, saldo, matrícula ou preço.

Quando existe estado comum com regras de validação, uma classe abstrata pode centralizar essas informações.

Se não há estado comum, talvez uma interface seja suficiente.

### 3. Verifique se existe comportamento comum reutilizável

Analise se há métodos que podem ser implementados uma vez e reutilizados pelas subclasses.

Por exemplo, em `ContaBancaria`, o método `Depositar` pode ser comum a todas as contas.

Se cada classe implementa tudo de forma independente, uma interface pode representar melhor o contrato.

### 4. Verifique se o foco é uma capacidade

Pergunte se as classes precisam apenas oferecer um comportamento comum.

Por exemplo, diferentes objetos podem ser exportáveis, notificáveis ou autenticáveis.

Quando o foco é a capacidade, uma interface costuma ser mais adequada.

### 5. Verifique se as classes pertencem a famílias diferentes

Se classes de contextos diferentes precisam cumprir o mesmo comportamento, não force uma classe abstrata comum.

Use interface para representar o contrato sem criar uma herança artificial.

### 6. Verifique se a classe precisa implementar múltiplos contratos

Em C#, uma classe pode herdar de apenas uma classe base direta, mas pode implementar várias interfaces.

Se uma classe precisa ser autenticável, notificável e exportável ao mesmo tempo, interfaces são adequadas.

### 7. Verifique se a abstração resolve um problema real

Antes de criar uma interface ou classe abstrata, pergunte o que ela melhora.

Ela reduz repetição relevante? Representa uma família real? Permite trocar implementações? Facilita testes? Torna o domínio mais claro?

Se a resposta for não, talvez a abstração apenas aumente o número de arquivos.

### 8. Verifique se uma classe concreta simples seria suficiente

Nem todo conceito precisa de herança ou contrato.

Se a classe não possui variações, não precisa de polimorfismo e não será substituída por outras implementações, uma classe concreta pode ser a melhor escolha.

## 21. Síntese final

Classe abstrata e interface são recursos diferentes da orientação a objetos em C#.

A classe abstrata representa uma base conceitual. Ela é útil quando existe uma família de objetos, relação “é um”, estado comum, validações compartilhadas e comportamento reutilizável.

A interface representa um contrato de comportamento. Ela é útil quando classes diferentes precisam oferecer a mesma capacidade, mesmo sem pertencer à mesma hierarquia.

A principal diferença é:

> Classe abstrata representa uma família. Interface representa uma capacidade.

Uma classe abstrata responde melhor à pergunta:

> “Que tipo de objeto isto é?”

Uma interface responde melhor à pergunta:

> “O que este objeto é capaz de fazer?”

Em uma boa modelagem, a escolha não é feita pela sintaxe, mas pelo significado do domínio.

---

## Conclusão

Classe abstrata e interface são ferramentas importantes, mas não devem ser usadas automaticamente.

Use classe abstrata quando houver uma base conceitual real, com estado, validações ou comportamento comum. Use interface quando o objetivo for definir um contrato que classes diferentes podem cumprir.

Também é válido usar as duas juntas: uma classe pode herdar uma base conceitual e implementar capacidades adicionais.

O mais importante é evitar abstrações artificiais. Uma boa modelagem orientada a objetos não é a que usa mais recursos, mas a que representa melhor o problema real com clareza, simplicidade e possibilidade de evolução.
