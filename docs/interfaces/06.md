# Interfaces e Baixo Acoplamento em C#

## Objetivo do material

Neste material, você aprenderá como usar interfaces em C# para reduzir o acoplamento entre classes. O foco é compreender por que depender diretamente de classes concretas pode tornar um sistema rígido, difícil de modificar e mais trabalhoso de testar, e como a dependência por contratos permite criar projetos mais flexíveis, organizados e preparados para evolução. O conteúdo foi desenvolvido a partir do material-base sobre interfaces, baixo acoplamento, injeção pelo construtor e injeção manual de dependência. 

---

## 1. Contextualização: por que o acoplamento importa?

Em sistemas orientados a objetos, as classes normalmente precisam colaborar entre si. Uma classe pode precisar enviar uma notificação, calcular um desconto, validar uma senha, gerar um relatório, registrar uma operação ou processar um pagamento.

Essa colaboração não é um problema. O problema aparece quando uma classe fica presa a uma implementação específica.

Imagine uma classe responsável por finalizar pedidos. Ao finalizar um pedido, ela precisa enviar uma notificação ao cliente. Uma primeira solução poderia ser fazer essa classe criar diretamente um objeto responsável por enviar e-mails.

```csharp
public class EmailNotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"Enviando e-mail para {destinatario}: {mensagem}");
    }
}

public class PedidoService
{
    private readonly EmailNotificador _notificador;

    public PedidoService()
    {
        _notificador = new EmailNotificador();
    }

    public void FinalizarPedido(string cliente, string email)
    {
        Console.WriteLine($"Pedido finalizado para {cliente}.");
        _notificador.Enviar(email, "Pedido finalizado.");
    }
}
```

Esse código funciona, mas cria uma dependência direta entre `PedidoService` e `EmailNotificador`. A classe `PedidoService` sabe qual classe concreta deve usar, sabe como criá-la com `new`, sabe que a notificação será por e-mail e chama diretamente o método dessa implementação.

Isso é acoplamento forte.

O problema não aparece apenas quando o código é pequeno. Ele aparece principalmente quando o sistema começa a mudar. Se amanhã for necessário enviar SMS, mensagem por aplicativo ou notificação interna, a classe `PedidoService` provavelmente precisará ser alterada. Quanto mais regras surgem, mais a classe principal cresce, acumula decisões e passa a ter muitos motivos para mudar.

---

## 2. O que é acoplamento?

Acoplamento é o grau de dependência entre partes de um sistema.

Em programação orientada a objetos, dizemos que uma classe está acoplada a outra quando ela depende dessa outra classe para funcionar. Essa dependência pode ser aceitável ou problemática, dependendo do quanto uma classe conhece sobre a outra.

Uma classe tem acoplamento forte quando conhece detalhes demais, por exemplo:

```csharp
private readonly EmailNotificador _notificador;

public PedidoService()
{
    _notificador = new EmailNotificador();
}
```

Nesse caso, `PedidoService` conhece a classe concreta `EmailNotificador` e também decide criá-la. Isso significa que a classe principal não depende apenas do comportamento de notificar; ela depende de uma forma específica de notificação.

Uma classe tem acoplamento mais baixo quando depende apenas de um contrato, isto é, de uma abstração que descreve o comportamento necessário:

```csharp
private readonly INotificador _notificador;

public PedidoService(INotificador notificador)
{
    _notificador = notificador;
}
```

Agora, `PedidoService` não sabe se a notificação será enviada por e-mail, SMS ou outro meio. Ela sabe apenas que recebeu um objeto capaz de enviar uma notificação.

Essa mudança parece pequena, mas altera profundamente a organização do projeto. A classe principal deixa de depender de detalhes concretos e passa a depender de uma capacidade esperada.

## 3. Acoplamento forte: quando a classe conhece detalhes demais

O acoplamento forte costuma aparecer quando uma classe cria internamente suas dependências usando `new`.

Observe este exemplo:

```csharp
public class PedidoService
{
    private readonly EmailNotificador _emailNotificador;
    private readonly SmsNotificador _smsNotificador;

    public PedidoService()
    {
        _emailNotificador = new EmailNotificador();
        _smsNotificador = new SmsNotificador();
    }

    public void FinalizarPedido(string cliente, string contato, string tipoNotificacao)
    {
        Console.WriteLine($"Pedido finalizado para {cliente}.");

        if (tipoNotificacao == "email")
            _emailNotificador.Enviar(contato, "Pedido finalizado.");
        else if (tipoNotificacao == "sms")
            _smsNotificador.Enviar(contato, "Pedido finalizado.");
    }
}
```

Esse código tenta resolver o problema de múltiplas formas de notificação, mas cria outros problemas.

A classe `PedidoService` agora conhece duas implementações concretas: `EmailNotificador` e `SmsNotificador`. Além disso, ela decide qual implementação usar com base em uma condição. Se surgir uma terceira forma de notificação, como mensagem por aplicativo, a classe precisará ser modificada novamente.

Esse é um sinal de alerta. A classe que deveria cuidar da finalização do pedido agora também está decidindo detalhes de envio de notificação.

A responsabilidade principal de `PedidoService` deveria ser finalizar pedidos. Quando ela começa a responder perguntas como “a mensagem será enviada por e-mail?”, “a mensagem será enviada por SMS?” ou “qual classe concreta deve ser instanciada?”, ela passa a acumular conhecimento desnecessário.

Esse tipo de código tende a crescer mal. A cada nova variação, surgem mais condições, mais dependências e mais motivos para alterar uma classe central do sistema.

---

## 4. A solução: depender de uma abstração

A alternativa é fazer a classe principal depender de um contrato, e não de uma implementação concreta.

Em C#, um contrato pode ser representado por uma interface. Uma interface define quais comportamentos uma classe deve oferecer, sem determinar como esses comportamentos serão executados.

Para o exemplo de notificação, podemos criar a interface `INotificador`:

```csharp
public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}
```

Essa interface diz que qualquer notificador deve ter um método chamado `Enviar`, recebendo um destinatário e uma mensagem.

Agora, as implementações concretas podem seguir esse contrato:

```csharp
public class EmailNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"E-mail para {destinatario}: {mensagem}");
    }
}
```

```csharp
public class SmsNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"SMS para {destinatario}: {mensagem}");
    }
}
```

As duas classes são diferentes, mas cumprem o mesmo contrato. Ambas são notificadores porque ambas implementam `INotificador`.

Agora, `PedidoService` pode depender da interface:

```csharp
public class PedidoService
{
    private readonly INotificador _notificador;

    public PedidoService(INotificador notificador)
    {
        _notificador = notificador;
    }

    public void FinalizarPedido(string cliente, string contato)
    {
        Console.WriteLine($"Pedido finalizado para {cliente}.");
        _notificador.Enviar(contato, "Seu pedido foi finalizado com sucesso.");
    }
}
```

A classe `PedidoService` ficou mais flexível. Ela não conhece `EmailNotificador` nem `SmsNotificador`. Também não decide qual notificador usar. Ela apenas recebe algo que cumpre o contrato `INotificador`.

Esse é o ponto central do baixo acoplamento com interfaces: a classe principal depende do comportamento necessário, não dos detalhes concretos de implementação.

## 5. Diferença entre classe concreta e interface

Uma classe concreta contém implementação. Ela define dados, métodos e comportamentos reais.

Exemplo:

```csharp
public class EmailNotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"Enviando e-mail para {destinatario}: {mensagem}");
    }
}
```

Essa classe sabe como enviar uma notificação por e-mail, mesmo que o exemplo use apenas `Console.WriteLine` para simular o envio.

Uma interface define um contrato. Ela descreve o que uma implementação deve oferecer, mas não define a lógica concreta.

Exemplo:

```csharp
public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}
```

A interface não envia e-mail, não envia SMS e não escreve no console. Ela apenas define que existe uma operação chamada `Enviar`.

A relação entre interface e classe concreta pode ser entendida assim:

A interface responde à pergunta: “qual comportamento é esperado?”

A classe concreta responde à pergunta: “como esse comportamento será realizado?”

Essa separação é importante porque permite trocar a forma de execução sem alterar a classe que usa o comportamento.

## 6. Injeção pelo construtor

Injeção de dependência é a prática de entregar a uma classe os objetos de que ela precisa, em vez de fazer a própria classe criar esses objetos internamente.

A forma mais simples apresentada neste material é a injeção pelo construtor.

Na forma mais acoplada, a classe decide sua dependência:

```csharp
public PedidoService()
{
    _notificador = new EmailNotificador();
}
```

Aqui, `PedidoService` cria diretamente um `EmailNotificador`. Isso prende a classe a uma implementação específica.

Na forma menos acoplada, a classe recebe a dependência:

```csharp
public PedidoService(INotificador notificador)
{
    _notificador = notificador;
}
```

Agora, `PedidoService` apenas declara que precisa de um `INotificador`. Ela não sabe qual implementação será usada. Essa decisão fica fora da classe.

Esse padrão melhora a clareza do projeto porque separa duas responsabilidades:

A classe de serviço usa a dependência para executar sua regra.

O ponto de montagem do sistema escolhe qual implementação concreta será usada.

---

## 7. Injeção manual de dependência no `Program.cs`

Em projetos pequenos de console, o arquivo `Program.cs` pode funcionar como o ponto de montagem dos objetos. Ele cria as implementações concretas e as entrega para as classes que dependem dos contratos.

Exemplo usando e-mail:

```csharp
INotificador notificador = new EmailNotificador();

PedidoService pedidoService = new PedidoService(notificador);

pedidoService.FinalizarPedido("Clotilde", "clotilde@email.com");
```

Exemplo usando SMS:

```csharp
INotificador notificador = new SmsNotificador();

PedidoService pedidoService = new PedidoService(notificador);

pedidoService.FinalizarPedido("Bruno", "45999999999");
```

Observe que `PedidoService` não muda. O que muda é a implementação entregue no momento da criação do objeto.

O `new EmailNotificador()` ou `new SmsNotificador()` ainda existe. Objetos concretos precisam ser criados em algum lugar. A diferença é que eles não são criados dentro da classe principal. Eles são criados no ponto de montagem da aplicação.

Esse detalhe é fundamental: baixo acoplamento não elimina classes concretas. Ele apenas impede que classes centrais fiquem presas a detalhes que podem variar.

## 8. Exemplo comentado: cálculo de desconto flexível

O mesmo padrão pode ser aplicado em outros cenários. Imagine um sistema de vendas em que o desconto pode variar conforme o tipo de cliente ou a campanha promocional.

Primeiro, criamos um contrato:

```csharp
public interface ICalculadoraDeDesconto
{
    decimal Calcular(decimal valor);
}
```

Essa interface diz que toda calculadora de desconto deve ter um método `Calcular`, recebendo o valor da venda e retornando o valor do desconto.

Agora, podemos criar diferentes implementações.

```csharp
public class DescontoClienteComum : ICalculadoraDeDesconto
{
    public decimal Calcular(decimal valor)
    {
        return valor * 0.05m;
    }
}
```

Essa classe calcula 5% de desconto.

```csharp
public class DescontoClienteVip : ICalculadoraDeDesconto
{
    public decimal Calcular(decimal valor)
    {
        return valor * 0.15m;
    }
}
```

Essa classe calcula 15% de desconto.

```csharp
public class DescontoPromocional : ICalculadoraDeDesconto
{
    public decimal Calcular(decimal valor)
    {
        return valor * 0.25m;
    }
}
```

Essa classe calcula 25% de desconto.

Agora, a classe `VendaService` pode depender apenas da interface:

```csharp
public class VendaService
{
    private readonly ICalculadoraDeDesconto _calculadoraDeDesconto;

    public VendaService(ICalculadoraDeDesconto calculadoraDeDesconto)
    {
        _calculadoraDeDesconto = calculadoraDeDesconto;
    }

    public decimal CalcularValorFinal(decimal valor)
    {
        decimal desconto = _calculadoraDeDesconto.Calcular(valor);
        return valor - desconto;
    }
}
```

`VendaService` não sabe se a regra é de cliente comum, cliente VIP ou promoção. Ela apenas chama:

```csharp
_calculadoraDeDesconto.Calcular(valor);
```

O comportamento muda conforme a implementação entregue.

Exemplo de montagem:

```csharp
ICalculadoraDeDesconto calculadora = new DescontoClienteVip();

VendaService vendaService = new VendaService(calculadora);

decimal valorFinal = vendaService.CalcularValorFinal(200m);

Console.WriteLine($"Valor final: R$ {valorFinal}");
```

Nesse caso, o desconto é de 15% sobre R$ 200,00. O desconto será R$ 30,00, e o valor final será R$ 170,00.

Se quisermos usar desconto promocional, não precisamos alterar `VendaService`:

```csharp
ICalculadoraDeDesconto calculadora = new DescontoPromocional();

VendaService vendaService = new VendaService(calculadora);

decimal valorFinal = vendaService.CalcularValorFinal(200m);

Console.WriteLine($"Valor final: R$ {valorFinal}");
```

Agora, o desconto é de 25%. O valor final será R$ 150,00.

Esse exemplo mostra baixo acoplamento na prática: a classe de serviço permanece igual, e o comportamento muda pela implementação entregue.

## 9. Exemplo comentado: validação de senha

Outro cenário comum é a validação de senha. Um sistema pode começar com uma regra simples e depois exigir regras mais fortes.

Primeiro, definimos o contrato:

```csharp
public interface IValidadorDeSenha
{
    bool Validar(string senha);
}
```

Esse contrato define que todo validador de senha deve ter um método `Validar`, que recebe uma senha e retorna `true` ou `false`.

Uma validação simples poderia ser:

```csharp
public class ValidadorSenhaSimples : IValidadorDeSenha
{
    public bool Validar(string senha)
    {
        return !string.IsNullOrEmpty(senha) && senha.Length >= 6;
    }
}
```

Essa regra exige que a senha não seja vazia e tenha pelo menos 6 caracteres.

Uma validação mais forte poderia ser:

```csharp
public class ValidadorSenhaForte : IValidadorDeSenha
{
    public bool Validar(string senha)
    {
        return !string.IsNullOrEmpty(senha)
            && senha.Length >= 8
            && senha.Any(char.IsDigit)
            && senha.Any(char.IsUpper);
    }
}
```

Essa regra exige que a senha não seja vazia, tenha pelo menos 8 caracteres, contenha pelo menos um dígito e contenha pelo menos uma letra maiúscula.

Agora, a classe responsável pelo cadastro pode depender apenas da interface:

```csharp
public class CadastroUsuarioService
{
    private readonly IValidadorDeSenha _validadorDeSenha;

    public CadastroUsuarioService(IValidadorDeSenha validadorDeSenha)
    {
        _validadorDeSenha = validadorDeSenha;
    }

    public void Cadastrar(string nome, string senha)
    {
        if (!_validadorDeSenha.Validar(senha))
            throw new ArgumentException("A senha não atende aos critérios exigidos.");

        Console.WriteLine($"Usuário {nome} cadastrado com sucesso.");
    }
}
```

A classe `CadastroUsuarioService` não sabe qual regra concreta está sendo usada. Ela sabe apenas que existe um validador capaz de validar senhas.

Isso permite mudar a política de senha sem alterar o serviço de cadastro. Se o sistema começar usando `ValidadorSenhaSimples` e depois passar a usar `ValidadorSenhaForte`, a classe de cadastro continua igual.

## 10. O que uma classe deve conhecer?

Uma classe deve conhecer o necessário para cumprir sua responsabilidade, e nada mais.

Essa ideia é essencial para manter o projeto organizado. Quando uma classe conhece detalhes demais, ela acumula responsabilidades. Quando uma classe conhece apenas o contrato necessário, ela fica mais focada.

No exemplo do pedido, `PedidoService` precisa saber que deve notificar o cliente ao finalizar o pedido. Ela não precisa saber se a notificação será por e-mail, SMS ou outro canal.

No exemplo da venda, `VendaService` precisa saber que deve calcular um desconto. Ela não precisa saber se a regra é de cliente comum, cliente VIP ou promoção.

No exemplo do cadastro, `CadastroUsuarioService` precisa saber que deve validar uma senha. Ela não precisa conhecer todos os detalhes da regra de validação.

Essa separação ajuda a criar classes mais simples, mais testáveis e mais fáceis de manter.

## 11. Vantagens do baixo acoplamento com interfaces

O baixo acoplamento facilita a manutenção porque mudanças em uma implementação concreta não obrigam alterações na classe que usa o contrato. Se a regra de desconto de cliente VIP mudar de 15% para 20%, basta alterar a classe `DescontoClienteVip`. A classe `VendaService` continua chamando `Calcular(valor)` da mesma forma.

Também facilita a expansão. Se surgir uma nova regra, como `DescontoBlackFriday`, basta criar uma nova classe que implemente `ICalculadoraDeDesconto`. A classe de serviço principal não precisa ser modificada para conhecer essa nova regra.

Outra vantagem importante está nos testes. Para testar uma classe como `PedidoService`, não é necessário enviar e-mails ou SMS reais. Podemos criar uma implementação falsa do contrato:

```csharp
public class NotificadorFake : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"Simulação de envio para {destinatario}: {mensagem}");
    }
}
```

Com isso, é possível testar o comportamento do pedido sem depender de uma tecnologia real de envio.

O baixo acoplamento também melhora a separação de responsabilidades. Cada classe fica mais focada no seu papel. A classe principal executa sua regra de negócio, enquanto as implementações concretas cuidam dos detalhes variáveis.

## 12. Cuidados ao criar interfaces

Interfaces ajudam a reduzir acoplamento, mas isso não significa que todo código precise de interface.

Uma interface deve resolver um problema real de dependência, variação ou contrato. Criar interfaces sem necessidade pode aumentar a complexidade do projeto sem trazer benefício.

Um erro comum é criar interface para uma classe simples que não tem variações. Por exemplo, se existe uma classe `Endereco` usada apenas como estrutura de dados e não há múltiplas formas de endereço, criar uma interface `IEndereco` pode ser desnecessário.

Outro erro é criar interfaces com nomes vagos, como:

```csharp
public interface IProcessador
{
}
```

Esse nome não deixa claro qual contrato está sendo definido. Interfaces devem expressar bem o comportamento esperado. Nomes como `INotificador`, `ICalculadoraDeDesconto`, `IValidadorDeSenha` e `IGeradorRelatorio` são mais claros porque indicam a responsabilidade principal.

Também é importante evitar interfaces grandes demais. Uma interface deve representar um contrato coeso. Se ela obriga uma classe a implementar métodos que não fazem parte de sua responsabilidade, provavelmente está mal modelada.

Interfaces não corrigem automaticamente uma modelagem ruim. Elas reduzem acoplamento quando representam abstrações reais do sistema. Quando usadas sem critério, apenas escondem problemas e aumentam o número de arquivos.

## 13. Aplicação prática resolvida: refatorando `RelatorioService`

### Cenário

Um sistema possui uma classe `RelatorioService` responsável por emitir relatórios. Inicialmente, ela depende diretamente de `GeradorRelatorioPdf`.

```csharp
public class GeradorRelatorioPdf
{
    public void Gerar(string conteudo)
    {
        Console.WriteLine($"Gerando relatório em PDF: {conteudo}");
    }
}

public class RelatorioService
{
    private readonly GeradorRelatorioPdf _gerador;

    public RelatorioService()
    {
        _gerador = new GeradorRelatorioPdf();
    }

    public void Emitir(string conteudo)
    {
        Console.WriteLine("Preparando relatório.");
        _gerador.Gerar(conteudo);
    }
}
```

### Problema

`RelatorioService` está acoplada a `GeradorRelatorioPdf`. Se o sistema precisar gerar relatório em HTML, texto ou planilha, a classe provavelmente precisará ser modificada.

### Objetivo

Refatorar o código para que `RelatorioService` dependa de um contrato, permitindo trocar o formato do relatório sem alterar a classe principal.

### Passo 1: criar a interface

```csharp
public interface IGeradorRelatorio
{
    void Gerar(string conteudo);
}
```

A interface representa o comportamento necessário: gerar um relatório a partir de um conteúdo.

### Passo 2: implementar o gerador em PDF

```csharp
public class GeradorRelatorioPdf : IGeradorRelatorio
{
    public void Gerar(string conteudo)
    {
        Console.WriteLine($"Gerando relatório em PDF: {conteudo}");
    }
}
```

Agora, `GeradorRelatorioPdf` cumpre o contrato `IGeradorRelatorio`.

### Passo 3: criar outra implementação

```csharp
public class GeradorRelatorioHtml : IGeradorRelatorio
{
    public void Gerar(string conteudo)
    {
        Console.WriteLine($"Gerando relatório em HTML: <html><body>{conteudo}</body></html>");
    }
}
```

Essa nova classe gera o relatório em outro formato, mas mantém o mesmo contrato.

### Passo 4: refatorar `RelatorioService`

```csharp
public class RelatorioService
{
    private readonly IGeradorRelatorio _gerador;

    public RelatorioService(IGeradorRelatorio gerador)
    {
        _gerador = gerador;
    }

    public void Emitir(string conteudo)
    {
        Console.WriteLine("Preparando relatório.");
        _gerador.Gerar(conteudo);
    }
}
```

Agora, `RelatorioService` depende apenas de `IGeradorRelatorio`.

### Passo 5: montar os objetos no `Program.cs`

Usando PDF:

```csharp
IGeradorRelatorio gerador = new GeradorRelatorioPdf();

RelatorioService relatorioService = new RelatorioService(gerador);

relatorioService.Emitir("Relatório mensal de vendas");
```

Usando HTML:

```csharp
IGeradorRelatorio gerador = new GeradorRelatorioHtml();

RelatorioService relatorioService = new RelatorioService(gerador);

relatorioService.Emitir("Relatório mensal de vendas");
```

### Comentário da solução

A classe `RelatorioService` não foi alterada para trocar o formato do relatório. Ela continua chamando `Gerar(conteudo)`. O comportamento muda porque outra implementação de `IGeradorRelatorio` foi entregue no construtor.

### Resultado esperado

Ao usar `GeradorRelatorioPdf`, a saída esperada é semelhante a:

```text
Preparando relatório.
Gerando relatório em PDF: Relatório mensal de vendas
```

Ao usar `GeradorRelatorioHtml`, a saída esperada é semelhante a:

```text
Preparando relatório.
Gerando relatório em HTML: <html><body>Relatório mensal de vendas</body></html>
```

### Como validar

A validação principal é observar que `RelatorioService` não contém `new GeradorRelatorioPdf()` nem `new GeradorRelatorioHtml()`. Ela deve receber `IGeradorRelatorio` pelo construtor.

Também é possível validar trocando a implementação no `Program.cs`. Se a troca funcionar sem alterar `RelatorioService`, a refatoração atingiu o objetivo.

### Possíveis erros

Um erro comum é criar a interface, mas continuar instanciando a classe concreta dentro do serviço:

```csharp
public RelatorioService()
{
    _gerador = new GeradorRelatorioPdf();
}
```

Mesmo que exista uma interface no projeto, esse código continua acoplado porque a classe principal ainda decide qual implementação usar.

Outro erro é criar métodos diferentes em cada implementação. Por exemplo, `GerarPdf()` em uma classe e `GerarHtml()` em outra. Isso quebra a ideia de contrato comum. O serviço precisa depender de um método compartilhado, como `Gerar`.

## 14. Erros comuns e dúvidas frequentes

Um erro comum é achar que interface elimina a necessidade de classes concretas. Isso não é verdade. As classes concretas continuam existindo e executando o comportamento real. A diferença é que a classe principal não precisa conhecê-las diretamente.

Outro erro é acreditar que usar interface automaticamente torna o código bom. Interfaces ajudam quando existe uma variação real ou uma dependência que precisa ser isolada. Se forem criadas sem propósito, podem deixar o projeto mais difícil de entender.

Também é comum confundir baixo acoplamento com ausência de dependência. Classes ainda dependem de outras partes do sistema. A diferença é que dependem de contratos mais estáveis, não de detalhes concretos que mudam com mais frequência.

Outra dúvida comum é sobre onde criar os objetos concretos. Em projetos simples, isso pode ser feito no `Program.cs`. Em projetos maiores, frameworks costumam oferecer contêineres de injeção de dependência, mas a ideia conceitual é a mesma: separar quem usa a dependência de quem decide qual implementação será usada.

Também pode surgir a dúvida sobre quando criar uma interface. Uma boa indicação é perguntar: existe mais de uma implementação possível? Essa dependência dificulta testes? Essa regra pode variar? A classe principal está conhecendo detalhes demais? Se a resposta for sim, uma interface pode ser adequada.

## 15. Checklist explicado

Verifique se a classe principal depende de uma interface quando o comportamento pode variar. Isso importa porque variações, como e-mail ou SMS, desconto comum ou promocional, PDF ou HTML, não devem obrigar mudanças em classes centrais. Para validar, procure no serviço principal se o tipo do atributo é uma interface, como `INotificador`, `ICalculadoraDeDesconto` ou `IGeradorRelatorio`. Se a classe depender diretamente de uma implementação concreta, ela ficará mais difícil de modificar.

Verifique se a classe principal não instancia dependências variáveis com `new`. Isso importa porque, ao usar `new` dentro da classe, ela passa a decidir qual implementação concreta será usada. Para validar, procure chamadas como `new EmailNotificador()` dentro de serviços principais. Se isso existir, a classe continua acoplada à implementação.

Verifique se a dependência é recebida pelo construtor. Isso importa porque o construtor deixa explícito o que a classe precisa para funcionar. Para validar, observe se existe um construtor como `PedidoService(INotificador notificador)`. Se a dependência estiver escondida dentro da classe, será mais difícil trocar implementação e testar.

Verifique se a interface representa um comportamento claro. Isso importa porque interfaces devem expressar contratos compreensíveis. Para validar, leia o nome da interface e seus métodos. Uma interface como `INotificador` com o método `Enviar` comunica bem sua intenção. Uma interface vaga ou genérica dificulta a manutenção.

Verifique se as implementações concretas cumprem o mesmo contrato. Isso importa porque a classe principal deve conseguir usar qualquer implementação sem mudar seu código. Para validar, confira se classes como `EmailNotificador` e `SmsNotificador` implementam a mesma interface e possuem o método exigido. Se cada implementação tiver métodos incompatíveis, o contrato não está bem definido.

Verifique se a escolha da implementação foi movida para fora da classe principal. Isso importa porque a classe principal deve executar sua responsabilidade, não decidir detalhes variáveis. Para validar, veja se a escolha está no `Program.cs` ou em outro ponto de montagem. Se a escolha estiver dentro do serviço principal, o acoplamento ainda está alto.

Verifique se a interface não foi criada sem necessidade. Isso importa porque interfaces desnecessárias aumentam a complexidade sem melhorar o projeto. Para validar, pergunte se existe variação real, necessidade de teste com fake ou possibilidade concreta de troca de implementação. Se não houver nenhum desses motivos, talvez a interface não seja necessária.

## 16. Síntese final

Interfaces em C# permitem representar contratos. Um contrato define o comportamento que uma classe deve oferecer, sem prender o restante do sistema a uma implementação específica.

Baixo acoplamento significa reduzir o conhecimento desnecessário entre classes. Uma classe bem projetada deve conhecer o necessário para cumprir sua responsabilidade, mas não deve conhecer detalhes concretos que podem variar.

A injeção pelo construtor permite entregar dependências para uma classe sem que ela precise criá-las internamente. Quando a classe recebe uma interface pelo construtor, ela passa a depender de um contrato, e não de uma classe concreta.

A injeção manual de dependência pode ser feita no `Program.cs` em projetos pequenos. Nesse ponto de montagem, o sistema escolhe qual implementação concreta será usada e a entrega para a classe principal.

Esse padrão facilita manutenção, expansão e testes. Novas implementações podem ser adicionadas sem alterar serviços centrais, regras podem mudar com menor impacto e testes podem usar implementações falsas ou simuladas.

---

## Conclusão

Depender de contratos, e não de detalhes concretos, é uma prática essencial para criar sistemas mais flexíveis em C#.

Quando uma classe depende diretamente de uma implementação, ela fica presa a detalhes que podem mudar. Quando depende de uma interface, ela passa a trabalhar com uma capacidade esperada, permitindo que diferentes implementações sejam usadas sem alterar sua lógica principal.

O objetivo não é criar interfaces para tudo. O objetivo é usar interfaces quando elas realmente representam variações, contratos importantes ou dependências que precisam ser isoladas. Aplicadas com critério, interfaces tornam o código mais claro, mais testável, mais organizado e mais preparado para evolução.
