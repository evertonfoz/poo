# Interfaces em C#: contratos de comportamento para sistemas flexíveis

## Objetivo do material

Neste material, você aprenderá o que é uma interface em C#, por que ela é entendida como um contrato de comportamento e como esse recurso ajuda a criar sistemas mais flexíveis, organizados e menos dependentes de classes concretas.

Ao final, você deverá ser capaz de:

1. explicar o conceito de interface em C#;
2. diferenciar uma interface de uma classe concreta;
3. entender a interface como um contrato de comportamento;
4. identificar situações em que interfaces são úteis;
5. implementar uma interface em classes diferentes;
6. usar uma interface como tipo de referência;
7. reconhecer erros comuns ao trabalhar com interfaces;
8. aplicar interfaces em um pequeno cenário prático.

Este conteúdo foi construído a partir do material-base sobre interfaces, contratos de comportamento e sistemas flexíveis em C# .

## 1. Contextualização: qual problema uma interface ajuda a resolver?

Em muitos sistemas, existem classes diferentes que realizam ações parecidas, mas de formas diferentes.

Imagine um sistema que precisa enviar notificações. A notificação pode ser enviada por:

* e-mail;
* SMS;
* aplicativo;
* registro em log;
* simulação em ambiente de teste.

Cada uma dessas formas possui uma implementação própria. Enviar um e-mail não é igual a enviar um SMS. Registrar uma mensagem em log também não é igual a exibir uma notificação em aplicativo.

Apesar disso, todas essas classes compartilham uma capacidade comum: elas conseguem enviar uma notificação.

O problema aparece quando outras partes do sistema precisam usar essa capacidade. Se uma classe depender diretamente de `EmailNotificador`, ela fica presa ao envio por e-mail. Se amanhã o sistema precisar enviar por SMS, talvez seja necessário alterar o código que já estava funcionando.

A interface resolve esse problema ao permitir que o sistema dependa de um contrato, e não de uma classe concreta específica.

Em vez de o código dizer:

```csharp
Preciso especificamente de um EmailNotificador.
```

ele passa a dizer:

```csharp
Preciso de algo capaz de enviar uma notificação.
```

Essa diferença é importante porque aumenta a flexibilidade do sistema. A classe que usa a notificação não precisa conhecer todos os detalhes da implementação. Ela só precisa saber que existe um método esperado e que ele será cumprido.

## 2. Conceito fundamental: o que é uma interface?

Uma interface em C# é um tipo que define um contrato de comportamento.

Esse contrato informa quais membros uma classe deve possuir para ser considerada compatível com aquela interface. Esses membros podem ser métodos, propriedades, eventos ou indexadores, mas neste material o foco principal estará nos métodos, porque eles são mais fáceis de visualizar inicialmente.

Uma interface responde à pergunta:

```text
Que comportamento esta classe precisa garantir?
```

Por exemplo, uma interface chamada `INotificador` pode definir que toda classe notificadora deve ter um método chamado `Enviar`.

```csharp
public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}
```

Esse código diz que qualquer classe que implementar `INotificador` precisa oferecer um método chamado `Enviar`, que recebe dois textos: um destinatário e uma mensagem.

A interface não diz como a mensagem será enviada. Ela apenas define o que precisa existir.

Isso significa que a interface define o contrato, enquanto a classe concreta define a execução.

## 3. Interface como contrato de comportamento

Pensar em interface como contrato ajuda a entender sua função no código.

Um contrato define uma obrigação. Quando uma classe implementa uma interface, ela assume o compromisso de cumprir tudo o que aquela interface exige.

Observe a interface:

```csharp
public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}
```

Ela estabelece a seguinte regra:

```text
Toda classe que implementar INotificador deve possuir um método Enviar,
recebendo um destinatario e uma mensagem.
```

Agora veja uma classe que cumpre esse contrato:

```csharp
public class EmailNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine(
            $"Enviando e-mail para {destinatario}: {mensagem}");
    }
}
```

O símbolo `:` indica que `EmailNotificador` implementa a interface `INotificador`.

A partir desse momento, a classe é obrigada a implementar o método `Enviar`. Se ela não fizer isso, o código não compila.

A interface funciona como uma promessa formal entre partes do sistema. Quem usa `INotificador` sabe que poderá chamar `Enviar`. Quem implementa `INotificador` precisa garantir que esse método exista.

## 4. Analogia: a tomada elétrica

Uma analogia útil é a tomada elétrica.

Diferentes aparelhos podem ser conectados a uma tomada:

* carregador de celular;
* notebook;
* televisão;
* luminária.

Cada aparelho funciona internamente de uma forma diferente. A tomada não precisa saber como o carregador converte energia, como o notebook gerencia bateria ou como a televisão liga sua tela.

A tomada apenas exige uma coisa: o aparelho precisa ter um plugue compatível.

Em programação, a interface funciona de forma semelhante. Ela define uma forma esperada de interação. A classe que implementa a interface precisa ser compatível com esse contrato.

Assim como a tomada não depende de um aparelho específico, uma classe pode depender de uma interface em vez de depender de uma classe concreta específica.

## 5. Classe concreta e interface: diferenças essenciais

Uma classe concreta normalmente representa algo que pode ser instanciado e executado. Ela possui dados, regras e implementação.

Uma interface representa uma capacidade ou contrato. Ela define o que uma classe deve oferecer, mas não representa, por si só, um objeto concreto pronto para uso.

### Exemplo de classes concretas

```csharp
public class Aluno
{
    public string Nome { get; private set; }

    public Aluno(string nome)
    {
        Nome = nome;
    }
}

public class Pedido
{
    public int Numero { get; private set; }

    public Pedido(int numero)
    {
        Numero = numero;
    }
}
```

As classes `Aluno` e `Pedido` representam entidades do domínio. Elas possuem dados e podem ser instanciadas.

Exemplo:

```csharp
Aluno aluno = new Aluno("Carlos");
Pedido pedido = new Pedido(1024);
```

### Exemplo de interfaces

```csharp
public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}

public interface IExportador
{
    void Exportar(string conteudo);
}

public interface IAutenticavel
{
    bool Autenticar(string senha);
}
```

Essas interfaces não representam objetos concretos. Elas representam capacidades:

`INotificador` representa algo capaz de enviar uma notificação.

`IExportador` representa algo capaz de exportar conteúdo.

`IAutenticavel` representa algo capaz de autenticar.

A diferença central é esta:

```text
Classe concreta representa uma implementação.
Interface representa um contrato.
```

## 6. Convenção de nomes: por que interfaces começam com “I”?

Em C#, é convenção que interfaces comecem com a letra `I`.

Exemplos:

```csharp
public interface INotificador
{
}

public interface ICalculadoraDeFrete
{
}

public interface IRepositorioDeAlunos
{
}

public interface IValidadorDeSenha
{
}

public interface IProcessadorDePagamento
{
}
```

Essa convenção facilita a leitura do código. Ao ver um tipo chamado `INotificador`, o programador entende rapidamente que aquele tipo representa uma interface, não uma classe concreta.

Essa escolha não é apenas estética. Ela ajuda na manutenção, porque torna mais claro quando o código está dependendo de um contrato e quando está dependendo de uma implementação.

## 7. Primeira sintaxe de uma interface

Uma interface é declarada com a palavra-chave `interface`.

```csharp
public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}
```

Vamos analisar o código por partes.

### `public`

Indica que a interface pode ser acessada por outras partes do projeto, respeitando as regras de visibilidade do C#.

### `interface`

Indica que estamos declarando uma interface, e não uma classe.

### `INotificador`

É o nome da interface. Pela convenção do C#, começa com `I`.

### `void Enviar(...)`

É a assinatura do método exigido pelo contrato.

### `string destinatario`

Representa para quem a mensagem será enviada.

### `string mensagem`

Representa o conteúdo da mensagem.

### `void`

Indica que o método não retorna nenhum valor.

A interface está dizendo:

```text
Quem implementar INotificador precisa ter um método Enviar,
que recebe destinatario e mensagem, e não retorna valor.
```

Ela não está dizendo se o envio será feito por e-mail, SMS, aplicativo ou log. Esse detalhe pertence às classes concretas.

## 8. Interface define “o que”, não “como”

Uma das ideias mais importantes sobre interfaces é que elas definem o que deve existir, mas não precisam definir como aquilo será executado.

Observe:

```csharp
public interface IExportador
{
    void Exportar(string conteudo);
}
```

Essa interface define que uma classe exportadora deve possuir um método `Exportar`.

Mas ela não diz se o conteúdo será exportado para:

* PDF;
* CSV;
* JSON;
* HTML;
* XML.

Cada classe concreta pode implementar o mesmo contrato de forma diferente.

```csharp
public class ExportadorPdf : IExportador
{
    public void Exportar(string conteudo)
    {
        Console.WriteLine($"Exportando em PDF: {conteudo}");
    }
}
```

```csharp
public class ExportadorCsv : IExportador
{
    public void Exportar(string conteudo)
    {
        Console.WriteLine($"Exportando em CSV: {conteudo}");
    }
}
```

As duas classes implementam `IExportador`. Ambas possuem o método `Exportar`. O que muda é a forma concreta de exportação.

Essa separação entre contrato e implementação é uma das bases para criar sistemas flexíveis.

## 9. Interface não pode ser instanciada diretamente

Uma classe concreta pode ser instanciada:

```csharp
ExportadorPdf exportador = new ExportadorPdf();
```

Isso é válido porque `ExportadorPdf` possui implementação.

Uma interface, por outro lado, não pode ser instanciada diretamente:

```csharp
IExportador exportador = new IExportador();
```

Esse código é inválido.

A razão é simples: `IExportador` apenas define o contrato. Ela não contém, por si só, uma implementação concreta de exportação.

O correto é instanciar uma classe concreta e armazená-la em uma variável do tipo da interface:

```csharp
IExportador exportador = new ExportadorPdf();
```

Nesse caso, o objeto real é um `ExportadorPdf`, mas a variável é do tipo `IExportador`.

Isso significa que o código passa a enxergar o objeto pelo contrato que ele cumpre.

## 10. Uma classe assumindo um contrato

Quando uma classe implementa uma interface, ela assume o compromisso de implementar todos os membros exigidos.

Exemplo:

```csharp
public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}
```

Classe que implementa a interface:

```csharp
public class EmailNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine(
            $"Enviando e-mail para {destinatario}: {mensagem}");
    }
}
```

A classe `EmailNotificador` cumpre o contrato porque possui o método `Enviar` com a mesma assinatura exigida pela interface.

Agora veja outra implementação:

```csharp
public class SmsNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine(
            $"Enviando SMS para {destinatario}: {mensagem}");
    }
}
```

`EmailNotificador` e `SmsNotificador` fazem coisas diferentes, mas cumprem o mesmo contrato.

O contrato é:

```csharp
void Enviar(string destinatario, string mensagem);
```

A implementação concreta pode variar.

## 11. Múltiplas classes, mesmo contrato

Interfaces são muito úteis quando diferentes classes podem cumprir o mesmo contrato.

Considere três notificadores:

```csharp
public class EmailNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine(
            $"Enviando e-mail para {destinatario}: {mensagem}");
    }
}
```

```csharp
public class SmsNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine(
            $"Enviando SMS para {destinatario}: {mensagem}");
    }
}
```

```csharp
public class LogNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine(
            $"Registrando notificação para {destinatario}: {mensagem}");
    }
}
```

Todas essas classes são diferentes. Porém, todas podem ser tratadas como `INotificador`.

Isso permite que uma parte do sistema trabalhe com a ideia de “notificador” sem precisar saber se a implementação real é e-mail, SMS ou log.

## 12. Interface como tipo de referência

Uma das funções mais importantes de interfaces em C# é permitir que uma variável, parâmetro ou atributo use o tipo da interface.

Exemplo usando e-mail:

```csharp
INotificador notificador = new EmailNotificador();

notificador.Enviar(
    "cliente@email.com",
    "Seu pedido foi confirmado."
);
```

Agora trocando a implementação para SMS:

```csharp
INotificador notificador = new SmsNotificador();

notificador.Enviar(
    "45999999999",
    "Seu pedido foi confirmado."
);
```

Observe que a variável continua sendo do tipo `INotificador`.

O que muda é o objeto concreto:

```text
Antes: new EmailNotificador()
Depois: new SmsNotificador()
```

Isso é importante porque o restante do código pode continuar chamando:

```csharp
notificador.Enviar(...);
```

Sem precisar saber qual classe concreta está por trás.

## 13. O que o código ganha ao depender de uma interface?

Quando uma classe depende de outra classe concreta, ela fica mais acoplada.

Por exemplo, uma classe `PedidoService` poderia depender diretamente de `EmailNotificador`:

```csharp
public class PedidoService
{
    private readonly EmailNotificador _notificador;

    public PedidoService()
    {
        _notificador = new EmailNotificador();
    }

    public void FinalizarPedido(string cliente, string contato)
    {
        Console.WriteLine($"Pedido do cliente {cliente} finalizado.");

        _notificador.Enviar(
            contato,
            "Seu pedido foi finalizado com sucesso.");
    }
}
```

Esse código funciona, mas tem uma limitação: `PedidoService` está presa a `EmailNotificador`.

Se o sistema precisar usar SMS, log ou aplicativo, será necessário alterar a classe `PedidoService`.

Uma versão mais flexível depende da interface:

```csharp
public class PedidoService
{
    private readonly INotificador _notificador;

    public PedidoService(INotificador notificador)
    {
        _notificador = notificador;
    }

    public void FinalizarPedido(string cliente, string contato)
    {
        Console.WriteLine($"Pedido do cliente {cliente} finalizado.");

        _notificador.Enviar(
            contato,
            "Seu pedido foi finalizado com sucesso.");
    }
}
```

Agora `PedidoService` não sabe se a notificação será enviada por e-mail ou SMS. Ela só sabe que recebeu algo capaz de enviar uma notificação.

O uso poderia ser:

```csharp
INotificador notificador = new EmailNotificador();

PedidoService pedidoService = new PedidoService(notificador);

pedidoService.FinalizarPedido(
    "Marina",
    "marina@email.com");
```

Ou:

```csharp
INotificador notificador = new SmsNotificador();

PedidoService pedidoService = new PedidoService(notificador);

pedidoService.FinalizarPedido(
    "Bruno",
    "45999999999");
```

A classe `PedidoService` continua igual. O que muda é apenas a implementação concreta passada para ela.

Esse é um ganho importante: o código fica mais fácil de trocar, testar e evoluir.

## 14. Quando criar uma interface?

Nem toda classe precisa ter uma interface.

Criar interfaces sem necessidade pode deixar o projeto mais complexo, com mais arquivos e mais abstrações do que o necessário.

Uma interface costuma fazer sentido quando existe pelo menos um destes motivos:

### 14.1 Há várias implementações possíveis

Interfaces são úteis quando diferentes classes podem cumprir o mesmo contrato.

Exemplo:

```csharp
public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}
```

Possíveis implementações:

```text
EmailNotificador
SmsNotificador
PushNotificador
LogNotificador
```

Nesse caso, a interface representa uma capacidade comum: enviar notificações.

### 14.2 É necessário reduzir dependência de classe concreta

Se uma classe depende diretamente de outra, a troca de implementação pode exigir alterações internas.

Ao depender de uma interface, a classe depende de uma capacidade, não de uma implementação específica.

### 14.3 O sistema precisa permitir troca de implementação

Exemplo: em produção, o sistema envia e-mail de verdade. Em ambiente de teste, ele apenas simula o envio.

```csharp
public class NotificadorFake : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine(
            $"Simulação de envio para {destinatario}: {mensagem}");
    }
}
```

A interface permite trocar a implementação sem alterar a classe que usa o notificador.

### 14.4 É necessário facilitar testes automatizados

Em testes, pode ser ruim depender de envio real de e-mail, SMS ou pagamento.

Interfaces permitem usar implementações falsas, simuladas ou controladas.

### 14.5 É preciso separar responsabilidades

Interfaces bem nomeadas ajudam a separar papéis.

Exemplos:

```csharp
public interface IValidadorDeSenha
{
    bool Validar(string senha);
}
```

```csharp
public interface IProcessadorDePagamento
{
    void Processar(decimal valor);
}
```

Cada interface representa uma responsabilidade clara.

## 15. Quando uma interface pode ser desnecessária?

Uma interface pode ser desnecessária quando existe apenas uma classe, sem variação real de comportamento e sem necessidade de troca, teste ou desacoplamento.

Exemplo possivelmente desnecessário:

```csharp
public interface IAluno
{
    string Nome { get; }
}
```

Se existe apenas uma classe `Aluno` e nenhuma regra importante de substituição, essa interface pode não trazer benefício real.

Nesse caso, o código pode ficar mais complexo sem necessidade.

Agora compare com uma interface que comunica uma capacidade:

```csharp
public interface IAvaliavel
{
    decimal CalcularNotaFinal();
}
```

Essa interface faz mais sentido se diferentes elementos puderem ser avaliáveis:

```text
Prova
Trabalho
Seminario
ProjetoFinal
```

A pergunta importante é:

```text
Existe um comportamento comum que pode ser cumprido por implementações diferentes?
```

Se a resposta for sim, a interface pode ser útil.

## 16. Nomeando interfaces por comportamento

Uma boa interface comunica uma responsabilidade.

Nomes ruins costumam ser genéricos demais ou representam entidades em vez de capacidades.

### Bons exemplos

```csharp
public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}
```

O nome indica algo capaz de notificar.

```csharp
public interface IExportador
{
    void Exportar(string conteudo);
}
```

O nome indica algo capaz de exportar.

```csharp
public interface ICalculadoraDeFrete
{
    decimal Calcular(decimal valorPedido);
}
```

O nome indica algo capaz de calcular frete.

```csharp
public interface IValidadorDeSenha
{
    bool Validar(string senha);
}
```

O nome indica algo capaz de validar senha.

Uma interface bem nomeada ajuda o leitor do código a entender rapidamente o contrato exigido.

## 17. Interfaces pequenas e responsabilidade única

Uma interface deve representar uma responsabilidade clara.

Evite interfaces grandes, que misturam vários comportamentos diferentes.

Exemplo ruim:

```csharp
public interface ISistema
{
    void CadastrarAluno(string nome);
    void EnviarEmail(string email);
    void GerarRelatorio();
    void ProcessarPagamento(decimal valor);
}
```

Essa interface mistura cadastro, notificação, relatório e pagamento.

O problema é que qualquer classe que implementar `ISistema` será obrigada a implementar todos esses métodos, mesmo que precise de apenas um deles.

Uma solução melhor é separar contratos específicos:

```csharp
public interface ICadastroDeAluno
{
    void Cadastrar(string nome);
}
```

```csharp
public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}
```

```csharp
public interface IRelatorio
{
    void Gerar(string conteudo);
}
```

```csharp
public interface IProcessadorDePagamento
{
    void Processar(decimal valor);
}
```

Interfaces menores tendem a ser mais fáceis de entender, implementar, testar e reutilizar.

Esse cuidado está relacionado a uma ideia importante de projeto: uma classe não deve ser obrigada a depender de métodos que não usa.

## 18. Erros comuns ao implementar interfaces

### Erro 1: esquecer de implementar os membros exigidos

Se uma classe declara que implementa uma interface, precisa implementar todos os membros exigidos por ela.

Código incorreto:

```csharp
public interface IRelatorio
{
    void Gerar(string conteudo);
}

public class RelatorioPdf : IRelatorio
{
    // Erro: não implementa o método Gerar
}
```

A classe `RelatorioPdf` prometeu cumprir o contrato `IRelatorio`, mas não implementou o método `Gerar`.

Código correto:

```csharp
public interface IRelatorio
{
    void Gerar(string conteudo);
}

public class RelatorioPdf : IRelatorio
{
    public void Gerar(string conteudo)
    {
        Console.WriteLine(conteudo);
    }
}
```

Agora a classe cumpre o contrato.

### Erro 2: tentar instanciar a interface diretamente

Código incorreto:

```csharp
IRelatorio relatorio = new IRelatorio();
```

Isso não é válido porque `IRelatorio` não é uma implementação concreta.

Código correto:

```csharp
IRelatorio relatorio = new RelatorioPdf();

relatorio.Gerar("Relatório gerado com sucesso.");
```

A variável é do tipo da interface, mas o objeto criado é uma classe concreta.

### Erro 3: criar interfaces grandes demais

Código problemático:

```csharp
public interface IGerenciadorCompleto
{
    void Cadastrar(string nome);
    void EnviarMensagem(string contato);
    void ExportarRelatorio(string conteudo);
    void ProcessarPagamento(decimal valor);
}
```

Essa interface concentra muitas responsabilidades. O resultado é um contrato difícil de implementar e reaproveitar.

Uma solução melhor é separar capacidades:

```csharp
public interface ICadastrador
{
    void Cadastrar(string nome);
}

public interface IEnviadorDeMensagem
{
    void Enviar(string contato, string mensagem);
}

public interface IExportadorDeRelatorio
{
    void Exportar(string conteudo);
}

public interface IProcessadorDePagamento
{
    void Processar(decimal valor);
}
```

Cada interface representa uma obrigação menor e mais clara.

### Erro 4: criar interface para tudo

Nem toda classe precisa de interface.

Criar uma interface para cada classe, sem motivo real, pode deixar o projeto mais difícil de navegar.

Antes de criar uma interface, pergunte:

```text
Há mais de uma implementação possível?
Essa dependência precisa ser trocada?
Essa abstração facilita testes?
O nome da interface representa uma capacidade clara?
```

Se a resposta for não para todas essas perguntas, talvez a interface seja desnecessária.

### Erro 5: colocar lógica na interface sem necessidade

Em versões modernas do C#, existem recursos como métodos com implementação padrão em interfaces. Porém, para quem está aprendendo e para muitos cenários de projeto, é mais seguro pensar na interface como contrato.

Em geral, se existe lógica compartilhada relevante, avalie usar uma classe base, um serviço auxiliar ou outra estrutura mais adequada.

Colocar lógica demais na interface pode dificultar a leitura e misturar responsabilidades.

## 19. Aplicação prática resolvida: emissão de documentos acadêmicos

### Cenário

Um sistema acadêmico precisa emitir diferentes tipos de documentos:

* declaração de matrícula;
* histórico escolar;
* certificado de conclusão.

Cada documento possui uma forma diferente de emissão, mas todos compartilham uma ação comum: emitir um documento para um estudante.

### Objetivo

Criar uma interface que represente o contrato de emissão de documentos e implementar classes concretas para diferentes tipos de documento.

### Passo 1: identificar o comportamento comum

O comportamento comum é emitir documento.

Esse comportamento representa uma capacidade. Um nome adequado para a interface é:

```csharp
IEmissorDeDocumento
```

### Passo 2: criar a interface

```csharp
public interface IEmissorDeDocumento
{
    void Emitir(string nomeAluno);
}
```

Esse contrato define que qualquer emissor de documento deve possuir um método `Emitir`, recebendo o nome do estudante.

A interface não define se o documento será uma declaração, um histórico ou um certificado. Ela apenas exige a capacidade de emitir.

### Passo 3: criar uma implementação para declaração de matrícula

```csharp
public class EmissorDeclaracaoMatricula : IEmissorDeDocumento
{
    public void Emitir(string nomeAluno)
    {
        Console.WriteLine(
            $"Emitindo declaração de matrícula para {nomeAluno}.");
    }
}
```

Essa classe cumpre o contrato porque implementa o método `Emitir`.

### Passo 4: criar uma implementação para histórico escolar

```csharp
public class EmissorHistoricoEscolar : IEmissorDeDocumento
{
    public void Emitir(string nomeAluno)
    {
        Console.WriteLine(
            $"Emitindo histórico escolar para {nomeAluno}.");
    }
}
```

Essa classe também cumpre o mesmo contrato, mas executa o comportamento de outra forma.

### Passo 5: criar uma implementação para certificado de conclusão

```csharp
public class EmissorCertificadoConclusao : IEmissorDeDocumento
{
    public void Emitir(string nomeAluno)
    {
        Console.WriteLine(
            $"Emitindo certificado de conclusão para {nomeAluno}.");
    }
}
```

Agora existem três classes diferentes que podem ser usadas como `IEmissorDeDocumento`.

### Passo 6: usar a interface como tipo de referência

```csharp
IEmissorDeDocumento emissor = new EmissorDeclaracaoMatricula();

emissor.Emitir("Lucas");
```

Saída esperada:

```text
Emitindo declaração de matrícula para Lucas.
```

Agora trocando a implementação:

```csharp
emissor = new EmissorHistoricoEscolar();

emissor.Emitir("Lucas");
```

Saída esperada:

```text
Emitindo histórico escolar para Lucas.
```

E outra troca:

```csharp
emissor = new EmissorCertificadoConclusao();

emissor.Emitir("Lucas");
```

Saída esperada:

```text
Emitindo certificado de conclusão para Lucas.
```

### Comentário da solução

A variável `emissor` continua sendo do tipo `IEmissorDeDocumento`. O que muda é a classe concreta atribuída a ela.

Isso mostra a principal vantagem da interface: o código pode trabalhar com uma capacidade comum, mesmo quando existem implementações diferentes.

### Como validar

A solução está correta se:

1. a interface `IEmissorDeDocumento` possui o método `Emitir`;
2. cada classe concreta implementa `IEmissorDeDocumento`;
3. cada classe concreta possui o método `Emitir` com a mesma assinatura;
4. o código consegue atribuir diferentes emissores à variável do tipo `IEmissorDeDocumento`;
5. a chamada `emissor.Emitir(...)` funciona independentemente da classe concreta usada.

### Possíveis erros

Um erro comum seria esquecer de implementar `Emitir` em uma das classes:

```csharp
public class EmissorDeclaracaoMatricula : IEmissorDeDocumento
{
}
```

Esse código não compila, porque a classe prometeu cumprir o contrato, mas não implementou o método exigido.

Outro erro seria tentar criar diretamente uma interface:

```csharp
IEmissorDeDocumento emissor = new IEmissorDeDocumento();
```

Esse código é inválido, porque interface não é classe concreta.

## 20. Estudo de caso resolvido: serviço de pedidos com notificação flexível

### Cenário

Um sistema de pedidos precisa avisar o cliente quando um pedido for finalizado.

No início, o aviso será enviado por e-mail. Depois, o sistema poderá enviar por SMS ou registrar em log para testes.

### Objetivo

Criar um serviço de pedidos que não fique preso a uma implementação específica de notificação.

### Solução

Primeiro, definimos o contrato:

```csharp
public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}
```

Depois, criamos uma implementação por e-mail:

```csharp
public class EmailNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine(
            $"Enviando e-mail para {destinatario}: {mensagem}");
    }
}
```

Criamos também uma implementação por SMS:

```csharp
public class SmsNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine(
            $"Enviando SMS para {destinatario}: {mensagem}");
    }
}
```

Agora criamos o serviço de pedidos dependendo da interface:

```csharp
public class PedidoService
{
    private readonly INotificador _notificador;

    public PedidoService(INotificador notificador)
    {
        _notificador = notificador;
    }

    public void FinalizarPedido(string cliente, string contato)
    {
        Console.WriteLine($"Pedido do cliente {cliente} finalizado.");

        _notificador.Enviar(
            contato,
            "Seu pedido foi finalizado com sucesso.");
    }
}
```

Uso com e-mail:

```csharp
INotificador notificador = new EmailNotificador();

PedidoService service = new PedidoService(notificador);

service.FinalizarPedido(
    "Carla",
    "carla@email.com");
```

Saída esperada:

```text
Pedido do cliente Carla finalizado.
Enviando e-mail para carla@email.com: Seu pedido foi finalizado com sucesso.
```

Uso com SMS:

```csharp
INotificador notificador = new SmsNotificador();

PedidoService service = new PedidoService(notificador);

service.FinalizarPedido(
    "Rafael",
    "45999999999");
```

Saída esperada:

```text
Pedido do cliente Rafael finalizado.
Enviando SMS para 45999999999: Seu pedido foi finalizado com sucesso.
```

### Comentário da solução

`PedidoService` não sabe se a notificação será enviada por e-mail ou SMS. Ele apenas conhece o contrato `INotificador`.

Isso torna a classe mais flexível. Para mudar o tipo de notificação, não é necessário alterar o código interno de `PedidoService`. Basta passar outra implementação.

### Validação

A solução está correta se o mesmo `PedidoService` funcionar com `EmailNotificador` e `SmsNotificador` sem alterações internas.

Isso demonstra baixo acoplamento entre o serviço de pedidos e os mecanismos concretos de notificação.

## 21. Dúvidas frequentes

### Interface é igual a classe abstrata?

Não. Interface e classe abstrata são recursos diferentes.

A interface representa principalmente um contrato de comportamento. Ela diz quais membros uma classe deve implementar.

Uma classe abstrata pode conter estado, construtores, campos, métodos concretos e métodos abstratos. Ela costuma ser usada quando existe uma relação mais forte de herança e compartilhamento de estrutura.

Para o foco deste material, pense assim:

```text
Interface: define uma capacidade.
Classe concreta: executa a capacidade.
```

### Uma classe pode implementar mais de uma interface?

Sim. Uma classe pode cumprir mais de um contrato.

Exemplo:

```csharp
public interface IExportador
{
    void Exportar(string conteudo);
}

public interface IRelatorio
{
    void Gerar(string conteudo);
}

public class RelatorioPdf : IRelatorio, IExportador
{
    public void Gerar(string conteudo)
    {
        Console.WriteLine($"Gerando relatório: {conteudo}");
    }

    public void Exportar(string conteudo)
    {
        Console.WriteLine($"Exportando relatório em PDF: {conteudo}");
    }
}
```

A classe `RelatorioPdf` cumpre dois contratos: `IRelatorio` e `IExportador`.

### Posso criar interface com propriedade?

Sim. Interfaces também podem exigir propriedades.

Exemplo:

```csharp
public interface IIdentificavel
{
    int Id { get; }
}
```

Qualquer classe que implementar `IIdentificavel` precisará fornecer a propriedade `Id`.

### Interface sempre melhora o código?

Não. Interface melhora o código quando existe um motivo claro para abstrair um comportamento.

Quando criada sem necessidade, ela pode aumentar a complexidade.

A boa pergunta não é “posso criar uma interface?”, mas sim:

```text
Essa interface representa uma capacidade real e útil no sistema?
```

## 22. Checklist explicado de compreensão e aplicação

### 1. Verifique se a interface representa um comportamento

Uma interface deve comunicar uma capacidade, como notificar, exportar, autenticar, validar, calcular ou emitir.

Isso importa porque interfaces baseadas apenas em entidades podem não trazer flexibilidade real.

Como validar: leia o nome da interface e pergunte se ele responde à ideia “algo capaz de...”. Por exemplo, `INotificador` pode ser entendido como “algo capaz de notificar”.

Se faltar esse cuidado, a interface pode virar apenas uma cópia artificial de uma classe concreta.

### 2. Verifique se o nome da interface segue a convenção do C#

Em C#, interfaces normalmente começam com a letra `I`.

Isso importa porque melhora a leitura do código e ajuda outros programadores a identificarem rapidamente que aquele tipo é um contrato.

Como validar: confira nomes como `INotificador`, `IExportador`, `IValidadorDeSenha` e `IProcessadorDePagamento`.

Se faltar essa convenção, o código ainda pode funcionar, mas ficará menos alinhado ao padrão comum da linguagem.

### 3. Verifique se a interface define “o que” e não “como”

A interface deve declarar o comportamento esperado, sem depender dos detalhes internos da execução.

Isso importa porque a principal função da interface é separar contrato de implementação.

Como validar: leia a interface e veja se ela apenas declara métodos ou propriedades necessárias. A lógica concreta deve estar nas classes que implementam o contrato.

Se faltar essa separação, a interface pode deixar de ser uma abstração simples e passar a concentrar responsabilidades indevidas.

### 4. Verifique se a classe concreta implementa todos os membros exigidos

Quando uma classe implementa uma interface, ela precisa cumprir todo o contrato.

Isso importa porque o compilador exige que a promessa feita pela classe seja cumprida.

Como validar: confira se cada método da interface aparece na classe concreta com a mesma assinatura.

Se faltar algum membro, o código não compila.

### 5. Verifique se a interface está sendo usada como tipo de referência quando fizer sentido

Uma das vantagens de interfaces é permitir que o código dependa do contrato.

Isso importa porque reduz o acoplamento com classes concretas.

Como validar: observe se atributos, parâmetros ou variáveis podem usar o tipo da interface, como:

```csharp
private readonly INotificador _notificador;
```

Se o código depender sempre de classes concretas, a troca de implementação será mais difícil.

### 6. Verifique se a interface não está grande demais

Interfaces devem ter responsabilidades claras e específicas.

Isso importa porque interfaces grandes obrigam classes a implementar métodos que talvez não façam sentido para elas.

Como validar: leia os métodos da interface e veja se todos pertencem à mesma responsabilidade.

Se a interface misturar cadastro, pagamento, relatório e notificação, provavelmente precisa ser dividida.

### 7. Verifique se existe motivo real para criar a interface

Nem toda classe precisa de uma interface.

Isso importa porque abstrações desnecessárias aumentam a complexidade do projeto.

Como validar: pergunte se há múltiplas implementações, necessidade de troca, testes facilitados ou redução de dependência concreta.

Se não houver motivo claro, talvez uma classe simples seja suficiente.

## 23. Síntese final

Interface em C# é um contrato de comportamento.

Ela define quais membros uma classe deve oferecer, mas não precisa definir os detalhes da execução.

Uma classe concreta implementa a interface e fornece o comportamento real.

A interface permite que diferentes classes sejam tratadas pelo mesmo contrato. Por exemplo, `EmailNotificador`, `SmsNotificador` e `LogNotificador` podem ser usados como `INotificador`.

Essa ideia torna o código mais flexível porque uma classe pode depender de uma capacidade, e não de uma implementação específica.

Interfaces são úteis para:

* representar comportamentos comuns;
* permitir múltiplas implementações;
* reduzir acoplamento;
* facilitar substituição de componentes;
* apoiar testes automatizados;
* separar responsabilidades;
* organizar melhor contratos entre partes do sistema.

Ao mesmo tempo, interfaces devem ser usadas com critério. Criar interfaces sem necessidade pode tornar o projeto mais complexo sem benefício real.

---

## Conclusão

Interfaces são uma ferramenta essencial para criar sistemas flexíveis em C#.

Elas ajudam o programador a pensar menos em classes específicas e mais em capacidades esperadas. Em vez de escrever código preso a `EmailNotificador`, por exemplo, é possível escrever código que dependa de `INotificador`.

Essa mudança parece pequena, mas tem grande impacto no projeto. Quando o sistema depende de contratos bem definidos, fica mais fácil trocar implementações, adicionar novas formas de comportamento, testar partes isoladas e manter o código organizado.

A regra principal é lembrar:

```text
Interface define o contrato.
Classe concreta executa o contrato.
```

Com esse entendimento, interfaces deixam de ser apenas uma sintaxe da linguagem e passam a ser uma forma de projetar sistemas mais claros, substituíveis e preparados para mudança.
