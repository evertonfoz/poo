# Polimorfismo com Interfaces em C#: flexibilidade e reusabilidade

## Objetivo do material

Neste material, você aprenderá como **interfaces permitem aplicar polimorfismo em C#**, tratando objetos de classes diferentes por meio de um mesmo contrato. A ideia central é que o código possa chamar o mesmo comportamento, mesmo quando a execução real muda de acordo com a classe concreta utilizada.

Ao final, você deverá ser capaz de:

Compreender o que é polimorfismo com interfaces em C#.

Declarar variáveis, parâmetros e listas usando o tipo de uma interface.

Criar classes diferentes que implementam o mesmo contrato.

Usar interfaces para reduzir dependência em relação a classes concretas.

Aplicar polimorfismo em métodos, serviços e coleções.

Reconhecer erros comuns ao criar interfaces e ao usar polimorfismo.

O conteúdo parte do exemplo de notificadores, serviços acadêmicos, avaliadores e geradores de documentos apresentado no material-base. 

---

# 1. Contextualização: por que usar polimorfismo com interfaces?

Imagine um sistema que precisa enviar notificações para usuários. Essas notificações podem ser enviadas de várias formas:

E-mail.

SMS.

Notificação dentro de um aplicativo.

Registro em log.

Mensagem no console.

Cada forma de envio tem uma implementação diferente. Enviar um e-mail não é igual a enviar um SMS, e registrar uma mensagem em log não é igual a mostrar uma notificação em aplicativo.

Mesmo assim, todas essas opções têm uma responsabilidade em comum: **enviar uma notificação**.

Esse é o ponto em que as interfaces se tornam úteis. Em vez de escrever um código diferente para cada tipo de notificador, podemos criar um contrato comum chamado, por exemplo, `INotificador`.

Esse contrato diz:

“Qualquer classe que for um notificador precisa saber enviar uma mensagem.”

O contrato não explica **como** a mensagem será enviada. Ele apenas define que esse comportamento deve existir.

---

# 2. Conceitos fundamentais

## 2.1 O que é uma interface em C#?

Uma **interface** em C# é um contrato que define comportamentos que uma classe deve implementar.

Ela indica quais métodos, propriedades ou membros uma classe precisa fornecer, mas não define necessariamente a lógica interna desses membros.

Exemplo:

```csharp
public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}
```

Essa interface define que qualquer classe que implemente `INotificador` deve possuir um método chamado `Enviar`, recebendo:

Um `destinatario`, do tipo `string`.

Uma `mensagem`, do tipo `string`.

Nenhum valor de retorno, pois o método é `void`.

A interface define **o que deve existir**, mas não define **como será feito**.

---

## 2.2 O que é uma classe concreta?

Uma **classe concreta** é uma classe que possui implementação real. Ela contém o código que será executado.

Por exemplo:

```csharp
public class EmailNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"Enviando e-mail para {destinatario}: {mensagem}");
    }
}
```

A classe `EmailNotificador` implementa a interface `INotificador`.

Isso significa que ela promete cumprir o contrato definido pela interface. Como a interface exige o método `Enviar`, a classe precisa implementar esse método.

---

## 2.3 O que é polimorfismo?

Polimorfismo é a capacidade de tratar objetos diferentes de forma uniforme, desde que eles compartilhem um mesmo contrato ou uma mesma base.

No caso das interfaces, o polimorfismo acontece quando diferentes classes implementam a mesma interface e podem ser usadas por meio do tipo dessa interface.

Exemplo:

```csharp
INotificador notificador = new EmailNotificador();
notificador.Enviar("clotilde@email.com", "Seu pedido foi confirmado.");
```

A variável `notificador` é do tipo `INotificador`, mas o objeto real criado é `EmailNotificador`.

Também poderíamos trocar a implementação concreta:

```csharp
INotificador notificador = new SmsNotificador();
notificador.Enviar("45999999999", "Seu pedido foi confirmado.");
```

O código continua chamando `Enviar`, mas a execução concreta muda conforme o objeto real.

Essa é a essência do polimorfismo com interfaces:

O código trabalha com o contrato.

A classe concreta executa o comportamento.

# 3. Criando o contrato de notificação

Vamos começar criando uma interface para representar qualquer tipo de notificador.

```csharp
public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}
```

Essa interface representa um contrato simples e claro. Toda classe que implementar `INotificador` deverá ser capaz de enviar uma mensagem para um destinatário.

O nome `INotificador` segue uma convenção comum em C#: interfaces costumam começar com a letra `I`. Isso ajuda a identificar rapidamente que aquele tipo é uma interface.

---

# 4. Criando diferentes implementações

Agora podemos criar diferentes classes concretas que implementam `INotificador`.

## 4.1 Notificador por e-mail

```csharp
public class EmailNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"Enviando e-mail para {destinatario}: {mensagem}");
    }
}
```

Essa classe representa o envio de uma mensagem por e-mail.

Quando o método `Enviar` for chamado, ele exibirá no console uma mensagem indicando que um e-mail está sendo enviado.

Em um sistema real, esse método poderia se conectar a um serviço externo de e-mail. Neste exemplo didático, usamos `Console.WriteLine` para visualizar o comportamento.

---

## 4.2 Notificador por SMS

```csharp
public class SmsNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"Enviando SMS para {destinatario}: {mensagem}");
    }
}
```

Essa classe também implementa `INotificador`, mas sua forma de envio é diferente.

Ela representa um envio por SMS. O contrato continua o mesmo, mas a implementação muda.

---

## 4.3 Notificador por aplicativo

```csharp
public class AppNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"Notificação no app para {destinatario}: {mensagem}");
    }
}
```

Essa implementação representa uma notificação enviada dentro de um aplicativo.

A classe continua obedecendo ao contrato `INotificador`, pois possui o método `Enviar`.

---

## 4.4 Notificador de log

```csharp
public class LogNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"Registrando log para {destinatario}: {mensagem}");
    }
}
```

Essa classe não envia uma mensagem para o usuário final. Ela registra a mensagem em um log.

Mesmo assim, ela pode participar do mesmo contrato porque também possui o comportamento `Enviar`.

Isso mostra que o contrato deve representar uma responsabilidade comum. No exemplo, a responsabilidade comum é lidar com uma notificação.

# 5. Usando a interface como tipo da variável

Uma das formas mais diretas de aplicar polimorfismo com interfaces é declarar uma variável usando o tipo da interface.

```csharp
INotificador notificador = new EmailNotificador();

notificador.Enviar("clotilde@email.com", "Seu pedido foi confirmado.");
```

Nesse trecho:

A variável `notificador` é do tipo `INotificador`.

O objeto real é uma instância de `EmailNotificador`.

O método chamado é `Enviar`.

A execução acontece dentro da classe `EmailNotificador`.

Agora observe a troca da implementação:

```csharp
INotificador notificador = new SmsNotificador();

notificador.Enviar("45999999999", "Seu pedido foi confirmado.");
```

O tipo da variável continua sendo `INotificador`, mas o objeto concreto agora é `SmsNotificador`.

Essa troca é possível porque tanto `EmailNotificador` quanto `SmsNotificador` implementam o mesmo contrato.

---

# 6. Método recebendo interface como parâmetro

Uma aplicação muito importante do polimorfismo com interfaces é declarar parâmetros usando o tipo da interface.

```csharp
public static void EnviarAviso(
    INotificador notificador,
    string destinatario,
    string mensagem)
{
    notificador.Enviar(destinatario, mensagem);
}
```

Esse método não depende de `EmailNotificador`, `SmsNotificador`, `AppNotificador` ou qualquer outra classe concreta.

Ele depende apenas de `INotificador`.

Isso significa que qualquer objeto que implemente `INotificador` pode ser passado para esse método.

Exemplos de uso:

```csharp
EnviarAviso(
    new EmailNotificador(),
    "clotilde@email.com",
    "Sua matrícula foi confirmada."
);
```

```csharp
EnviarAviso(
    new SmsNotificador(),
    "45999999999",
    "Sua matrícula foi confirmada."
);
```

```csharp
EnviarAviso(
    new AppNotificador(),
    "usuario-clotilde",
    "Sua matrícula foi confirmada."
);
```

O método `EnviarAviso` permanece o mesmo. O comportamento muda conforme o objeto concreto recebido.

Isso deixa o código mais flexível, porque o método não precisa ser alterado quando surge uma nova forma de notificação.

---

# 7. Por que isso reduz dependências?

Sem interface, um método poderia depender diretamente de uma classe específica:

```csharp
public static void EnviarAvisoPorEmail(
    EmailNotificador notificador,
    string destinatario,
    string mensagem)
{
    notificador.Enviar(destinatario, mensagem);
}
```

Esse método só funciona com `EmailNotificador`.

Se quisermos enviar SMS, precisaríamos criar outro método ou alterar o método existente.

Com interface, o método depende do contrato:

```csharp
public static void EnviarAviso(
    INotificador notificador,
    string destinatario,
    string mensagem)
{
    notificador.Enviar(destinatario, mensagem);
}
```

Agora o método funciona com qualquer classe que implemente `INotificador`.

Essa redução de dependência é chamada de **baixo acoplamento**.

Baixo acoplamento significa que uma parte do sistema conhece menos detalhes internos da outra. O código fica mais fácil de manter, testar e evoluir.

# 8. Usando interface em uma classe de serviço

Agora vamos criar uma classe responsável por confirmar uma matrícula.

Quando a matrícula é confirmada, o sistema precisa enviar uma mensagem ao aluno. A classe não deve decidir se a mensagem será enviada por e-mail, SMS ou aplicativo. Ela deve depender apenas do contrato `INotificador`.

```csharp
public class MatriculaService
{
    private readonly INotificador _notificador;

    public MatriculaService(INotificador notificador)
    {
        _notificador = notificador;
    }

    public void ConfirmarMatricula(string aluno, string contato)
    {
        Console.WriteLine($"Matrícula confirmada para {aluno}.");

        _notificador.Enviar(
            contato,
            "Sua matrícula foi confirmada."
        );
    }
}
```

Nessa classe:

O campo `_notificador` é do tipo `INotificador`.

O construtor recebe um objeto que implementa `INotificador`.

O método `ConfirmarMatricula` usa o notificador recebido para enviar a mensagem.

A classe `MatriculaService` não cria internamente um `EmailNotificador` ou um `SmsNotificador`. Ela apenas recebe um notificador pronto.

Isso é importante porque a escolha da implementação fica fora da classe.

---

## 8.1 Criando o serviço com diferentes notificadores

Com e-mail:

```csharp
INotificador notificador = new EmailNotificador();

MatriculaService servico = new MatriculaService(notificador);

servico.ConfirmarMatricula("Clotilde", "clotilde@email.com");
```

Com SMS:

```csharp
INotificador notificadorSms = new SmsNotificador();

MatriculaService servicoSms = new MatriculaService(notificadorSms);

servicoSms.ConfirmarMatricula("Bruno", "45999999999");
```

A classe `MatriculaService` não muda.

O que muda é o objeto concreto passado para o construtor.

Esse padrão torna o código mais preparado para evolução. Se surgir uma nova implementação, como `WhatsAppNotificador`, o serviço poderá usá-la sem alteração interna, desde que ela implemente `INotificador`.

---

# 9. A importância do construtor

Observe novamente o construtor:

```csharp
public MatriculaService(INotificador notificador)
{
    _notificador = notificador;
}
```

Esse construtor recebe a dependência de fora.

Isso evita que a classe faça algo como:

```csharp
public MatriculaService()
{
    _notificador = new EmailNotificador();
}
```

Esse segundo exemplo cria um acoplamento direto entre `MatriculaService` e `EmailNotificador`.

O problema é que a classe passa a decidir sozinha qual notificador usar. Se quisermos trocar para SMS, aplicativo ou log, precisaremos modificar o código da própria classe.

Quando recebemos `INotificador` pelo construtor, a classe passa a depender do contrato, não da implementação específica.

Essa prática também facilita testes, porque podemos passar um notificador falso ou simulado durante a verificação do comportamento da classe.

# 10. Polimorfismo com lista de interfaces

Interfaces também podem ser usadas em coleções.

Imagine que o sistema precise enviar a mesma mensagem por vários canais ao mesmo tempo.

Podemos criar uma lista do tipo `List<INotificador>`:

```csharp
List<INotificador> notificadores = new();

notificadores.Add(new EmailNotificador());
notificadores.Add(new SmsNotificador());
notificadores.Add(new AppNotificador());
notificadores.Add(new LogNotificador());
```

Essa lista aceita objetos de classes diferentes porque todos implementam `INotificador`.

Agora podemos percorrer a lista:

```csharp
foreach (INotificador notificador in notificadores)
{
    notificador.Enviar("Clotilde", "Sua inscrição foi registrada.");
}
```

O mesmo método `Enviar` é chamado para todos os objetos.

Entretanto, cada classe executa sua própria versão do método.

Esse é um exemplo claro de polimorfismo:

A chamada é a mesma.

O contrato é o mesmo.

A execução concreta varia conforme o objeto real.

# 11. Comparando código com e sem polimorfismo

## 11.1 Código sem polimorfismo

Sem polimorfismo, o código tende a usar condicionais para decidir qual classe instanciar.

```csharp
if (tipo == "email")
{
    EmailNotificador notificador = new();
    notificador.Enviar("clotilde@email.com", mensagem);
}
else if (tipo == "sms")
{
    SmsNotificador notificador = new();
    notificador.Enviar("45999999999", mensagem);
}
else if (tipo == "app")
{
    AppNotificador notificador = new();
    notificador.Enviar("usuario-clotilde", mensagem);
}
```

Esse código funciona, mas apresenta alguns problemas.

Cada novo tipo de notificador exige uma nova condição.

A lógica de escolha fica misturada com a lógica de envio.

O código depende diretamente de classes concretas.

A manutenção fica mais difícil quando o número de tipos aumenta.

---

## 11.2 Código com polimorfismo

Com polimorfismo, podemos trabalhar com a interface:

```csharp
List<INotificador> notificadores = new()
{
    new EmailNotificador(),
    new SmsNotificador(),
    new AppNotificador()
};

foreach (INotificador notificador in notificadores)
{
    notificador.Enviar("Clotilde", mensagem);
}
```

Agora o código fica menos preocupado com os detalhes de cada classe concreta.

Ele sabe apenas que cada item da lista é um `INotificador` e, portanto, possui o método `Enviar`.

Esse tipo de solução é mais simples de expandir. Para adicionar um novo notificador, criamos uma nova classe que implementa `INotificador` e a adicionamos à lista.

# 12. Segundo exemplo: avaliadores acadêmicos

O mesmo princípio pode ser aplicado a outros domínios.

Imagine um sistema acadêmico em que diferentes componentes podem calcular uma nota final. Cada tipo de avaliação possui uma regra própria.

Uma prova pode ter uma nota direta.

Um trabalho pode calcular a média entre entrega e apresentação.

Um seminário pode combinar conteúdo e comunicação com pesos diferentes.

Apesar das regras diferentes, todos têm algo em comum: conseguem calcular uma nota final.

Podemos representar isso com a interface `IAvaliavel`.

```csharp
public interface IAvaliavel
{
    decimal CalcularNotaFinal();
}
```

Essa interface define que qualquer avaliação deve ser capaz de calcular sua nota final.

---

## 12.1 Classe Prova

```csharp
public class Prova : IAvaliavel
{
    private readonly decimal _nota;

    public Prova(decimal nota)
    {
        _nota = nota;
    }

    public decimal CalcularNotaFinal()
    {
        return _nota;
    }
}
```

A classe `Prova` recebe uma nota no construtor e simplesmente retorna essa nota como nota final.

Essa é uma implementação direta do contrato.

---

## 12.2 Classe Trabalho

```csharp
public class Trabalho : IAvaliavel
{
    private readonly decimal _notaEntrega;
    private readonly decimal _notaApresentacao;

    public Trabalho(decimal notaEntrega, decimal notaApresentacao)
    {
        _notaEntrega = notaEntrega;
        _notaApresentacao = notaApresentacao;
    }

    public decimal CalcularNotaFinal()
    {
        return (_notaEntrega + _notaApresentacao) / 2;
    }
}
```

A classe `Trabalho` calcula a média entre a nota da entrega e a nota da apresentação.

Ela implementa o mesmo método `CalcularNotaFinal`, mas com uma regra própria.

---

## 12.3 Classe Seminario

```csharp
public class Seminario : IAvaliavel
{
    private readonly decimal _notaConteudo;
    private readonly decimal _notaComunicacao;

    public Seminario(decimal notaConteudo, decimal notaComunicacao)
    {
        _notaConteudo = notaConteudo;
        _notaComunicacao = notaComunicacao;
    }

    public decimal CalcularNotaFinal()
    {
        return (_notaConteudo * 0.7m) + (_notaComunicacao * 0.3m);
    }
}
```

A classe `Seminario` calcula uma nota ponderada.

A nota de conteúdo vale 70% da nota final.

A nota de comunicação vale 30% da nota final.

O sufixo `m` em `0.7m` e `0.3m` indica que os valores são do tipo `decimal`, adequado para cálculos numéricos que exigem precisão decimal.

---

# 13. Lista polimórfica de avaliações

Agora podemos criar uma lista de avaliações diferentes:

```csharp
List<IAvaliavel> avaliacoes = new()
{
    new Prova(8.5m),
    new Trabalho(9.0m, 8.0m),
    new Seminario(7.5m, 9.0m)
};
```

Essa lista possui objetos de classes diferentes:

`Prova`.

`Trabalho`.

`Seminario`.

Todos podem estar na mesma lista porque todos implementam `IAvaliavel`.

Agora podemos percorrer a lista:

```csharp
foreach (IAvaliavel avaliacao in avaliacoes)
{
    decimal nota = avaliacao.CalcularNotaFinal();

    Console.WriteLine($"Nota final: {nota:F2}");
}
```

O código chama o mesmo método `CalcularNotaFinal`.

Cada classe executa sua própria regra de cálculo.

O formato `{nota:F2}` exibe o valor com duas casas decimais.

# 14. Serviço para calcular média

Podemos criar um serviço que calcula a média de uma lista de avaliações.

```csharp
public class CalculadoraMedia
{
    public decimal CalcularMedia(List<IAvaliavel> avaliacoes)
    {
        if (avaliacoes.Count == 0)
        {
            throw new ArgumentException("Lista não pode ser vazia.");
        }

        decimal soma = 0;

        foreach (IAvaliavel avaliacao in avaliacoes)
        {
            soma += avaliacao.CalcularNotaFinal();
        }

        return soma / avaliacoes.Count;
    }
}
```

Essa classe depende apenas de `IAvaliavel`.

Ela não precisa saber se a avaliação é uma prova, um trabalho ou um seminário.

A única coisa que importa é que cada avaliação saiba calcular sua nota final.

Isso torna o serviço mais flexível. Novos tipos de avaliação podem ser criados depois sem alterar `CalculadoraMedia`, desde que implementem `IAvaliavel`.

# 15. Interface como contrato mínimo visível

Quando uma variável é declarada com o tipo da interface, o código enxerga apenas os membros definidos no contrato.

Observe esta classe:

```csharp
public class Trabalho : IAvaliavel
{
    public decimal CalcularNotaFinal()
    {
        return 8.5m;
    }

    public void EnviarArquivo()
    {
        Console.WriteLine("Arquivo enviado.");
    }
}
```

A classe `Trabalho` possui dois métodos:

`CalcularNotaFinal`.

`EnviarArquivo`.

Mas a interface `IAvaliavel` define apenas `CalcularNotaFinal`.

Agora observe o uso:

```csharp
IAvaliavel avaliacao = new Trabalho();

avaliacao.CalcularNotaFinal(); 
```

Esse código funciona, porque `CalcularNotaFinal` faz parte da interface `IAvaliavel`.

Mas este código não funciona:

```csharp
avaliacao.EnviarArquivo();
```

O erro acontece porque a variável `avaliacao` é do tipo `IAvaliavel`.

Mesmo que o objeto real seja um `Trabalho`, o código só consegue acessar o que está definido no contrato `IAvaliavel`.

Isso reforça uma ideia importante: uma interface mostra apenas o contrato mínimo visível para quem usa aquele tipo.

# 16. Vantagens do polimorfismo com interfaces

## 16.1 Tratar objetos diferentes por um mesmo contrato

Classes diferentes podem ser usadas de forma uniforme quando implementam a mesma interface.

Isso permite escrever códigos genéricos, que funcionam com várias implementações.

Exemplo:

```csharp
public void Processar(INotificador notificador)
{
    notificador.Enviar("destinatario", "mensagem");
}
```

Esse método pode receber `EmailNotificador`, `SmsNotificador`, `AppNotificador` ou qualquer outra classe que implemente `INotificador`.

---

## 16.2 Reduzir dependência de classes concretas

Quando o código depende de uma interface, ele não precisa conhecer os detalhes de cada classe concreta.

Isso reduz o acoplamento.

Um código menos acoplado costuma ser mais fácil de alterar, testar e reutilizar.

---

## 16.3 Facilitar a troca de implementações

Se uma classe depende de `INotificador`, podemos trocar `EmailNotificador` por `SmsNotificador` sem mudar a classe que usa o notificador.

A troca acontece no ponto em que o objeto concreto é criado ou configurado.

---

## 16.4 Criar listas com objetos de tipos diferentes

Uma lista do tipo da interface pode armazenar objetos de qualquer classe que implemente essa interface.

```csharp
List<INotificador> notificadores = new()
{
    new EmailNotificador(),
    new SmsNotificador(),
    new LogNotificador()
};
```

Essa estrutura é útil quando queremos aplicar a mesma operação a vários objetos diferentes.

---

## 16.5 Tornar o código preparado para evolução

Quando o sistema cresce, novas implementações podem ser adicionadas sem modificar o código que depende apenas do contrato.

Por exemplo, se criarmos:

```csharp
public class WhatsAppNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"Enviando WhatsApp para {destinatario}: {mensagem}");
    }
}
```

Podemos usar essa nova classe onde `INotificador` for esperado.

---

# 17. Cuidados ao usar interfaces

Interfaces são úteis, mas não devem ser criadas sem necessidade.

Uma boa interface deve representar um contrato claro.

## 17.1 Não criar interface apenas para repetir uma classe

Uma interface deve representar uma abstração relevante.

Se existe apenas uma classe, sem previsão real de variação de comportamento, talvez a interface ainda não seja necessária.

Criar interfaces sem necessidade pode deixar o código mais complexo sem trazer benefício.

---

## 17.2 Não criar interfaces com responsabilidades demais

Uma interface deve representar um contrato coeso.

Interface ruim:

```csharp
public interface IAvaliacaoAcademica
{
    decimal CalcularNotaFinal();

    void EnviarArquivo();

    void AgendarApresentacao();

    void CorrigirAutomaticamente();
}
```

Essa interface mistura várias responsabilidades.

Nem toda avaliação acadêmica precisa enviar arquivo.

Nem toda avaliação acadêmica precisa agendar apresentação.

Nem toda avaliação acadêmica pode ser corrigida automaticamente.

Quando uma interface obriga uma classe a implementar métodos que não fazem sentido para ela, o contrato está mal definido.

---

## 17.3 Preferir interfaces menores e específicas

Uma solução melhor é separar os contratos:

```csharp
public interface IAvaliavel
{
    decimal CalcularNotaFinal();
}
```

```csharp
public interface IEnviavel
{
    void EnviarArquivo();
}
```

```csharp
public interface IApresentavel
{
    void AgendarApresentacao();
}
```

Agora cada classe implementa apenas os contratos que fazem sentido para ela.

Uma prova pode ser apenas `IAvaliavel`.

Um trabalho pode ser `IAvaliavel` e `IEnviavel`.

Um seminário pode ser `IAvaliavel` e `IApresentavel`.

Essa separação deixa o modelo mais claro e evita obrigações artificiais.

---

## 17.4 Evitar nomes genéricos demais

Nomes como `IObjeto`, `IProcesso`, `IEntidade` ou `IAcao` geralmente são vagos.

Uma interface deve comunicar claramente o comportamento que representa.

Bons nomes indicam capacidade ou responsabilidade:

`INotificador`: algo capaz de notificar.

`IAvaliavel`: algo capaz de ser avaliado ou calcular nota.

`IGeradorDeDocumento`: algo capaz de gerar documento.

`IEnviavel`: algo capaz de ser enviado.

Um bom nome ajuda o leitor a entender o contrato sem precisar abrir todas as implementações.

---

# 18. Aplicação prática resolvida: gerador de documentos

## Cenário

Um sistema acadêmico precisa gerar diferentes documentos para um aluno:

Declaração de matrícula.

Histórico escolar.

Certificado de conclusão.

Carteirinha estudantil.

Cada documento possui uma forma própria de geração, mas todos compartilham uma responsabilidade comum: gerar um documento para um aluno.

## Objetivo

Criar uma solução usando polimorfismo com interfaces, de modo que diferentes geradores possam ser tratados pelo mesmo contrato.

---

## 18.1 Criando a interface

```csharp
public interface IGeradorDeDocumento
{
    void Gerar(string nomeAluno);
}
```

Essa interface define que todo gerador de documento precisa ter um método `Gerar`.

O método recebe o nome do aluno como parâmetro.

A interface não diz como o documento será gerado. Ela apenas define que a operação deve existir.

---

## 18.2 Criando o gerador de declaração de matrícula

```csharp
public class GeradorDeclaracaoMatricula : IGeradorDeDocumento
{
    public void Gerar(string nomeAluno)
    {
        Console.WriteLine($"Gerando declaração para {nomeAluno}.");
    }
}
```

Essa classe representa a geração de uma declaração de matrícula.

Ela implementa `IGeradorDeDocumento`, portanto precisa fornecer o método `Gerar`.

---

## 18.3 Criando o gerador de histórico escolar

```csharp
public class GeradorHistoricoEscolar : IGeradorDeDocumento
{
    public void Gerar(string nomeAluno)
    {
        Console.WriteLine($"Gerando histórico para {nomeAluno}.");
    }
}
```

Essa classe segue o mesmo contrato, mas representa outro tipo de documento.

---

## 18.4 Criando o gerador de certificado de conclusão

```csharp
public class GeradorCertificadoConclusao : IGeradorDeDocumento
{
    public void Gerar(string nomeAluno)
    {
        Console.WriteLine($"Gerando certificado para {nomeAluno}.");
    }
}
```

Mais uma vez, o contrato é o mesmo, mas a implementação representa outro comportamento concreto.

---

## 18.5 Criando o gerador de carteirinha estudantil

```csharp
public class GeradorCarteirinhaEstudantil : IGeradorDeDocumento
{
    public void Gerar(string nomeAluno)
    {
        Console.WriteLine($"Gerando carteirinha para {nomeAluno}.");
    }
}
```

Essa classe mostra como adicionar uma nova implementação sem alterar o código que percorre os geradores.

---

## 18.6 Criando a lista polimórfica

```csharp
List<IGeradorDeDocumento> geradores = new()
{
    new GeradorDeclaracaoMatricula(),
    new GeradorHistoricoEscolar(),
    new GeradorCertificadoConclusao(),
    new GeradorCarteirinhaEstudantil()
};
```

Essa lista usa o tipo da interface `IGeradorDeDocumento`.

Por isso, ela aceita qualquer objeto cuja classe implemente essa interface.

---

## 18.7 Percorrendo a lista e gerando documentos

```csharp
foreach (IGeradorDeDocumento gerador in geradores)
{
    gerador.Gerar("Clotilde");
}
```

O código chama `Gerar` em cada item da lista.

Cada classe executa sua própria implementação.

O `foreach` não precisa saber qual documento está sendo gerado. Ele só precisa saber que cada item cumpre o contrato `IGeradorDeDocumento`.

---

## 18.8 Resultado esperado

A saída esperada no console será semelhante a:

```text
Gerando declaração para Clotilde.
Gerando histórico para Clotilde.
Gerando certificado para Clotilde.
Gerando carteirinha para Clotilde.
```

Esse resultado mostra que a mesma chamada `Gerar("Clotilde")` produziu comportamentos diferentes conforme a classe concreta.

---

## 18.9 Como validar a solução

Para validar se o polimorfismo foi aplicado corretamente, verifique se a lista foi declarada com o tipo da interface:

```csharp
List<IGeradorDeDocumento> geradores = new();
```

Se a lista estiver declarada com o tipo de uma classe concreta, o exemplo perderá flexibilidade.

Também verifique se todas as classes implementam a interface:

```csharp
public class GeradorHistoricoEscolar : IGeradorDeDocumento
```

Se uma classe não implementar `IGeradorDeDocumento`, ela não poderá ser adicionada à lista polimórfica.

Por fim, valide se o `foreach` chama apenas métodos existentes no contrato:

```csharp
gerador.Gerar("Clotilde");
```

Esse método funciona porque `Gerar` está declarado na interface.

# 19. Erros comuns e dúvidas frequentes

## 19.1 “Criei a classe, mas não consigo adicioná-la à lista da interface”

Isso acontece quando a classe não implementa a interface.

Exemplo incorreto:

```csharp
public class GeradorRelatorio
{
    public void Gerar(string nomeAluno)
    {
        Console.WriteLine($"Gerando relatório para {nomeAluno}.");
    }
}
```

Mesmo tendo um método chamado `Gerar`, essa classe não declarou que implementa `IGeradorDeDocumento`.

Correção:

```csharp
public class GeradorRelatorio : IGeradorDeDocumento
{
    public void Gerar(string nomeAluno)
    {
        Console.WriteLine($"Gerando relatório para {nomeAluno}.");
    }
}
```

Agora a classe cumpre formalmente o contrato.

---

## 19.2 “Por que não consigo chamar um método extra da classe concreta?”

Porque a variável foi declarada com o tipo da interface.

Exemplo:

```csharp
IAvaliavel avaliacao = new Trabalho();
```

Mesmo que `Trabalho` tenha outros métodos, a variável `avaliacao` só enxerga os métodos definidos em `IAvaliavel`.

Isso é esperado. A interface limita o acesso ao contrato declarado.

---

## 19.3 “Interface é a mesma coisa que classe abstrata?”

Não. Interfaces e classes abstratas podem ser usadas para abstração, mas não são a mesma coisa.

Uma interface define um contrato de comportamento.

Uma classe abstrata pode conter estado, construtores, métodos implementados e métodos abstratos.

Em C#, uma classe pode implementar várias interfaces, mas só pode herdar diretamente de uma classe base.

Use interface quando quiser representar uma capacidade ou contrato que pode ser implementado por classes diferentes.

---

## 19.4 “Devo criar interface para tudo?”

Não.

Interfaces são úteis quando existe variação real de comportamento, necessidade de baixo acoplamento, possibilidade de troca de implementação ou uso polimórfico.

Criar interface para toda classe sem necessidade pode tornar o código mais difícil de entender.

Uma boa pergunta é:

“Existem ou podem existir diferentes implementações para esse contrato?”

Se a resposta for sim, uma interface pode fazer sentido.

---

## 19.5 “O método da interface pode ter uma lógica diferente em cada classe?”

Sim.

Esse é justamente um dos principais benefícios do polimorfismo.

A interface define o método. Cada classe decide como executar esse método.

Exemplo:

`EmailNotificador.Enviar` envia e-mail.

`SmsNotificador.Enviar` envia SMS.

`LogNotificador.Enviar` registra log.

A chamada é igual, mas a execução concreta é diferente.

---

# 20. Checklist explicado

## 20.1 Verifique se a interface representa um contrato claro

A interface deve indicar uma responsabilidade compreensível. `INotificador` representa algo capaz de enviar notificações. `IAvaliavel` representa algo capaz de calcular nota final.

Isso importa porque uma interface vaga dificulta a leitura do código e pode obrigar classes a implementarem métodos que não fazem sentido.

Para validar, leia o nome da interface e seus métodos. Se não for possível explicar o contrato em uma frase simples, talvez a interface esteja mal definida.

Se esse cuidado faltar, o sistema pode ganhar abstrações confusas e difíceis de manter.

---

## 20.2 Verifique se as classes implementam todos os métodos exigidos

Toda classe que implementa uma interface precisa cumprir o contrato.

Isso importa porque o compilador espera que a classe forneça os membros definidos pela interface.

Para validar, confira se a classe possui a declaração da interface:

```csharp
public class EmailNotificador : INotificador
```

E se ela implementa o método exigido:

```csharp
public void Enviar(string destinatario, string mensagem)
```

Se esse cuidado faltar, o código não compilará.

---

## 20.3 Verifique se variáveis, parâmetros ou listas usam o tipo da interface quando o objetivo for polimorfismo

O polimorfismo aparece quando o código depende do contrato.

Isso importa porque usar diretamente classes concretas reduz a flexibilidade.

Para validar, procure declarações como:

```csharp
INotificador notificador
```

```csharp
List<INotificador> notificadores
```

```csharp
public MatriculaService(INotificador notificador)
```

Se esse cuidado faltar, o código pode ficar preso a uma implementação específica.

---

## 20.4 Verifique se a classe de serviço não cria internamente a implementação concreta

Uma classe de serviço deve receber a dependência quando o objetivo é manter baixo acoplamento.

Isso importa porque, se a classe cria internamente um `EmailNotificador`, ela fica presa ao e-mail.

Para validar, observe se o objeto é recebido pelo construtor:

```csharp
public MatriculaService(INotificador notificador)
```

E não criado diretamente dentro da classe:

```csharp
_notificador = new EmailNotificador();
```

Se esse cuidado faltar, trocar a implementação exigirá alteração no serviço.

---

## 20.5 Verifique se a interface não mistura responsabilidades demais

Uma interface deve ser coesa.

Isso importa porque classes diferentes podem não conseguir cumprir todos os métodos de uma interface muito grande.

Para validar, analise se todos os métodos da interface fazem sentido para todas as classes que a implementam.

Se alguns métodos só fazem sentido para uma parte das classes, prefira separar em interfaces menores.

Se esse cuidado faltar, as classes podem acabar com métodos vazios, exceções desnecessárias ou implementações artificiais.

---

## 20.6 Verifique se o código chama apenas métodos definidos no contrato

Quando uma variável é do tipo da interface, apenas os métodos da interface ficam visíveis.

Isso importa porque o compilador não permite chamar métodos que não pertencem ao contrato declarado.

Para validar, compare a chamada feita no código com os métodos definidos na interface.

Se esse cuidado faltar, erros de compilação podem ocorrer ao tentar acessar métodos extras da classe concreta.

---

# 21. Síntese final

Interfaces permitem aplicar polimorfismo em C# ao criar contratos comuns para classes diferentes.

Uma interface define o que deve existir.

Uma classe concreta define como o comportamento será executado.

Quando uma variável, parâmetro ou lista usa o tipo da interface, objetos de classes diferentes podem ser tratados de forma uniforme.

O código chama o mesmo método, mas a execução real depende da classe concreta.

Esse recurso ajuda a reduzir acoplamento, facilitar substituições, criar listas polimórficas, organizar responsabilidades e preparar o sistema para evolução.

---

# Conclusão

Polimorfismo com interfaces é uma técnica essencial para construir código flexível e reutilizável em C#.

A principal ideia é simples: o código deve depender de contratos quando não precisa conhecer os detalhes da implementação.

Ao usar interfaces como `INotificador`, `IAvaliavel` ou `IGeradorDeDocumento`, diferentes classes podem ser tratadas pelo mesmo tipo, desde que cumpram o mesmo contrato.

Essa separação entre contrato e implementação torna o sistema mais organizado. O código que usa a interface permanece estável, enquanto novas classes concretas podem ser adicionadas conforme novas necessidades surgem.
