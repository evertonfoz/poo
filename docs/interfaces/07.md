# Interfaces em Associações e Serviços

## Objetivo do material

Neste material, você aprenderá como usar **interfaces** para organizar a colaboração entre objetos, separar responsabilidades e criar sistemas mais flexíveis. O foco será compreender como uma classe pode depender de um **contrato** em vez de depender diretamente de uma implementação concreta.

Ao final, você deverá ser capaz de:

* diferenciar **entidade**, **serviço**, **interface** e **implementação concreta**;
* entender o papel das interfaces em associações entre classes;
* criar serviços que dependem de contratos;
* montar objetos no `Program.cs` usando implementações concretas;
* reconhecer erros comuns de acoplamento e excesso de responsabilidade;
* aplicar esse padrão em cenários como pedidos, matrículas, pagamentos e emissão de certificados.

O conteúdo parte do problema apresentado no material-base: sistemas em que uma operação, como finalizar um pedido, exige cálculo de frete, desconto, notificação e alteração de estado, mas não deve concentrar todas essas responsabilidades em uma única classe. 

---

# 1. Contextualização: o problema de concentrar responsabilidades

Imagine um sistema de pedidos. Quando um pedido é finalizado, o sistema precisa realizar várias ações:

* guardar ou alterar informações do pedido;
* calcular o frete;
* aplicar desconto;
* calcular o total;
* notificar o cliente;
* marcar o pedido como finalizado.

Uma solução inicial seria colocar tudo dentro da classe `Pedido`:

```csharp
public class Pedido
{
    public string Cliente { get; set; }
    public string ContatoCliente { get; set; }
    public decimal ValorProdutos { get; set; }

    public void Finalizar()
    {
        decimal frete = ValorProdutos * 0.10m;
        decimal desconto = ValorProdutos * 0.05m;
        decimal total = ValorProdutos + frete - desconto;

        Console.WriteLine($"Pedido finalizado para {Cliente}.");
        Console.WriteLine($"Total: R$ {total:F2}");
        Console.WriteLine($"Enviando notificação para {ContatoCliente}.");
    }
}
```

Esse código funciona em um exemplo simples, mas apresenta um problema importante: a classe `Pedido` está fazendo coisas demais.

Ela representa o pedido, calcula frete, calcula desconto e envia notificação. Isso mistura responsabilidades diferentes em uma única classe. Com o tempo, qualquer mudança em regras de frete, desconto ou notificação obrigará alterações dentro da entidade `Pedido`.

Esse tipo de modelagem gera **alto acoplamento**. Alto acoplamento acontece quando uma classe conhece detalhes demais sobre outras partes do sistema ou concentra decisões que deveriam estar separadas.

# 2. Conceitos fundamentais

## 2.1 Entidade

Uma **entidade** representa algo importante do domínio do sistema. Ela possui dados, estado e regras essenciais relacionadas a esse conceito.

No exemplo de pedidos, `Pedido` é uma entidade porque representa um pedido real do sistema. Ela deve guardar informações como cliente, contato, valor dos produtos e situação do pedido.

Uma entidade deve proteger suas próprias regras principais. Por exemplo, um pedido não deve ser finalizado duas vezes.

```csharp
public class Pedido
{
    public string Cliente { get; private set; }
    public string ContatoCliente { get; private set; }
    public decimal ValorProdutos { get; private set; }
    public bool Finalizado { get; private set; }

    public Pedido(string cliente, string contatoCliente, decimal valorProdutos)
    {
        if (string.IsNullOrWhiteSpace(cliente))
            throw new ArgumentException("O cliente é obrigatório.");

        if (string.IsNullOrWhiteSpace(contatoCliente))
            throw new ArgumentException("O contato do cliente é obrigatório.");

        if (valorProdutos <= 0)
            throw new ArgumentException("O valor dos produtos deve ser maior que zero.");

        Cliente = cliente;
        ContatoCliente = contatoCliente;
        ValorProdutos = valorProdutos;
        Finalizado = false;
    }

    public void MarcarComoFinalizado()
    {
        if (Finalizado)
            throw new InvalidOperationException("O pedido já está finalizado.");

        Finalizado = true;
    }
}
```

Neste código, a entidade `Pedido` não calcula frete, não calcula desconto e não envia notificação. Ela protege os dados básicos do pedido e controla a regra de finalização.

Isso é importante porque a entidade deve representar o conceito principal do domínio, não detalhes externos de cálculo, comunicação ou infraestrutura.

---

## 2.2 Interface

Uma **interface** define um contrato. Ela diz quais comportamentos uma classe deve oferecer, mas não define como esses comportamentos serão executados.

Por exemplo, o sistema precisa calcular frete. A regra de frete pode mudar: frete padrão, frete grátis, frete por região, frete por peso ou frete promocional. Em vez de prender o serviço a uma regra específica, criamos uma interface:

```csharp
public interface ICalculadoraDeFrete
{
    decimal Calcular(Pedido pedido);
}
```

Essa interface declara que qualquer calculadora de frete deve ter um método `Calcular`, recebendo um `Pedido` e retornando um valor decimal.

A interface não diz se o frete será 10%, zero ou calculado por outra regra. Ela define apenas o contrato.

---

## 2.3 Implementação concreta

Uma **implementação concreta** é uma classe que cumpre uma interface.

Exemplo de frete padrão:

```csharp
public class CalculadoraFretePadrao : ICalculadoraDeFrete
{
    public decimal Calcular(Pedido pedido)
    {
        return pedido.ValorProdutos * 0.10m;
    }
}
```

Exemplo de frete grátis:

```csharp
public class CalculadoraFreteGratis : ICalculadoraDeFrete
{
    public decimal Calcular(Pedido pedido)
    {
        return 0;
    }
}
```

As duas classes cumprem o mesmo contrato, mas aplicam regras diferentes. Isso permite trocar o comportamento sem alterar quem usa a interface.

---

## 2.4 Serviço

Um **serviço** coordena uma operação do sistema. Ele normalmente usa entidades e contratos para executar um caso de uso.

No exemplo, finalizar um pedido envolve:

* calcular frete;
* calcular desconto;
* calcular total;
* marcar o pedido como finalizado;
* enviar uma notificação.

Essa operação não pertence totalmente à entidade `Pedido`, porque envolve comportamentos auxiliares. Por isso, criamos um serviço:

```csharp
public class PedidoService
{
    private readonly ICalculadoraDeFrete _calculadoraDeFrete;
    private readonly ICalculadoraDeDesconto _calculadoraDeDesconto;
    private readonly INotificador _notificador;

    public PedidoService(
        ICalculadoraDeFrete calculadoraDeFrete,
        ICalculadoraDeDesconto calculadoraDeDesconto,
        INotificador notificador)
    {
        _calculadoraDeFrete = calculadoraDeFrete;
        _calculadoraDeDesconto = calculadoraDeDesconto;
        _notificador = notificador;
    }

    public decimal Finalizar(Pedido pedido)
    {
        if (pedido is null)
            throw new ArgumentNullException(nameof(pedido));

        decimal frete = _calculadoraDeFrete.Calcular(pedido);
        decimal desconto = _calculadoraDeDesconto.Calcular(pedido);
        decimal total = pedido.ValorProdutos + frete - desconto;

        pedido.MarcarComoFinalizado();

        _notificador.Enviar(
            pedido.ContatoCliente,
            $"Pedido finalizado. Total: R$ {total:F2}"
        );

        return total;
    }
}
```

O `PedidoService` não sabe qual classe concreta calcula frete, desconto ou envia notificação. Ele conhece apenas os contratos.

Essa é a ideia central: **o serviço depende de interfaces, não de implementações concretas**.

# 3. Diferenças conceituais importantes

## Entidade não é serviço

A entidade representa algo do domínio e protege suas regras internas. O serviço coordena uma operação que envolve diferentes objetos.

A entidade `Pedido` deve saber se já foi finalizada. Mas ela não precisa saber se a notificação será por e-mail, SMS ou console.

## Interface não é implementação

A interface define o que deve existir. A implementação concreta define como o comportamento acontece.

Exemplo:

```csharp
public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}
```

Essa interface diz que deve existir um método para enviar mensagens. Mas ela não diz se a mensagem será enviada por e-mail, SMS ou apenas exibida no console.

Implementações possíveis:

```csharp
public class EmailNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"E-mail enviado para {destinatario}: {mensagem}");
    }
}

public class SmsNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"SMS enviado para {destinatario}: {mensagem}");
    }
}

public class ConsoleNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"Notificação simulada para {destinatario}: {mensagem}");
    }
}
```

Todas as classes cumprem o mesmo contrato, mas cada uma executa o envio de uma forma diferente.

# 4. Associação concreta e associação por interface

Uma associação acontece quando uma classe mantém referência a outra classe ou contrato.

## Associação concreta

Na associação concreta, uma classe depende diretamente de uma implementação específica.

```csharp
public class PedidoService
{
    private readonly CalculadoraFretePadrao _calculadoraDeFrete;
}
```

Nesse caso, `PedidoService` conhece `CalculadoraFretePadrao`. Se a regra mudar para frete grátis, será necessário alterar o código do serviço.

Esse tipo de associação dificulta mudanças e testes.

## Associação por interface

Na associação por interface, a classe depende de um contrato.

```csharp
public class PedidoService
{
    private readonly ICalculadoraDeFrete _calculadoraDeFrete;
}
```

Agora, o serviço não sabe qual calculadora está sendo usada. Ele sabe apenas que existe um objeto capaz de calcular frete.

Isso permite usar:

```csharp
new CalculadoraFretePadrao();
```

ou:

```csharp
new CalculadoraFreteGratis();
```

sem alterar o `PedidoService`.

Essa forma de associação deixa o sistema mais flexível, pois o comportamento concreto pode ser escolhido no momento da montagem dos objetos.

# 5. Contratos auxiliares no sistema de pedidos

Além da calculadora de frete, o sistema pode ter uma calculadora de desconto e um notificador.

```csharp
public interface ICalculadoraDeDesconto
{
    decimal Calcular(Pedido pedido);
}
```

Implementações:

```csharp
public class CalculadoraDescontoPadrao : ICalculadoraDeDesconto
{
    public decimal Calcular(Pedido pedido)
    {
        return pedido.ValorProdutos * 0.05m;
    }
}

public class CalculadoraDescontoPromocional : ICalculadoraDeDesconto
{
    public decimal Calcular(Pedido pedido)
    {
        return pedido.ValorProdutos * 0.15m;
    }
}
```

Contrato de notificação:

```csharp
public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}
```

Essas interfaces representam comportamentos que podem variar. Sempre que uma regra pode mudar ou possuir diferentes formas de execução, uma interface pode ajudar a reduzir o acoplamento.

# 6. Montagem dos objetos no Program.cs

Em um projeto simples de console, o `Program.cs` pode ser usado para montar os objetos. Ele escolhe quais implementações concretas serão utilizadas.

## Configuração padrão

```csharp
ICalculadoraDeFrete calculadoraDeFrete = new CalculadoraFretePadrao();

ICalculadoraDeDesconto calculadoraDeDesconto =
    new CalculadoraDescontoPadrao();

INotificador notificador = new EmailNotificador();

PedidoService pedidoService = new PedidoService(
    calculadoraDeFrete,
    calculadoraDeDesconto,
    notificador
);

Pedido pedido = new Pedido(
    "Clotilde",
    "clotilde@email.com",
    500m
);

decimal total = pedidoService.Finalizar(pedido);

Console.WriteLine($"Total: R$ {total:F2}");
```

Nesse cenário:

* o frete será 10% de R$ 500,00, ou seja, R$ 50,00;
* o desconto será 5% de R$ 500,00, ou seja, R$ 25,00;
* o total será R$ 500,00 + R$ 50,00 - R$ 25,00;
* o total final será R$ 525,00.

## Configuração promocional

```csharp
ICalculadoraDeFrete calculadoraDeFrete = new CalculadoraFreteGratis();

ICalculadoraDeDesconto calculadoraDeDesconto =
    new CalculadoraDescontoPromocional();

INotificador notificador = new SmsNotificador();

PedidoService pedidoService = new PedidoService(
    calculadoraDeFrete,
    calculadoraDeDesconto,
    notificador
);

Pedido pedido = new Pedido(
    "Bruno",
    "45999999999",
    500m
);

decimal total = pedidoService.Finalizar(pedido);

Console.WriteLine($"Total: R$ {total:F2}");
```

Nesse cenário:

* o frete será R$ 0,00;
* o desconto será 15% de R$ 500,00, ou seja, R$ 75,00;
* o total será R$ 500,00 + R$ 0,00 - R$ 75,00;
* o total final será R$ 425,00.

Observe o ponto mais importante: **o `PedidoService` não foi alterado**. Apenas mudaram as implementações escolhidas no `Program.cs`.

# 7. Quando criar um serviço?

Uma classe de serviço costuma fazer sentido quando a operação:

1. envolve mais de uma classe;
2. coordena diferentes objetos;
3. representa um caso de uso do sistema;
4. depende de comportamentos auxiliares;
5. não pertence naturalmente a uma única entidade.

Exemplos de serviços bem definidos:

```csharp
public class PedidoService { }

public class MatriculaService { }

public class PagamentoService { }

public class RelatorioService { }
```

Cada serviço deve ter um motivo claro para existir. Um serviço não deve virar uma classe genérica que faz tudo.

Exemplo problemático:

```csharp
public class SistemaService
{
    public void CadastrarAluno() { }
    public void FinalizarPedido() { }
    public void ProcessarPagamento() { }
    public void GerarRelatorio() { }
    public void EnviarEmail() { }
}
```

Esse serviço mistura operações de áreas diferentes. O nome `SistemaService` não comunica uma responsabilidade específica. Isso dificulta manutenção, testes e evolução do código.

# 8. Exemplo comentado: matrícula de aluno

Agora vamos aplicar a mesma ideia em outro contexto: matrícula acadêmica.

Uma matrícula precisa:

* verificar se a turma possui vaga;
* adicionar o aluno à turma;
* notificar o aluno sobre a matrícula.

## Entidade Aluno

```csharp
public class Aluno
{
    public string Nome { get; private set; }
    public string Email { get; private set; }

    public Aluno(string nome, string email)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("O nome é obrigatório.");

        if (string.IsNullOrWhiteSpace(email))
            throw new ArgumentException("O e-mail é obrigatório.");

        Nome = nome;
        Email = email;
    }
}
```

A entidade `Aluno` guarda dados básicos e valida sua criação.

## Entidade Turma

```csharp
public class Turma
{
    private readonly List<Aluno> _alunos = new();

    public string Nome { get; private set; }
    public int Capacidade { get; private set; }

    public IReadOnlyCollection<Aluno> Alunos => _alunos.AsReadOnly();

    public Turma(string nome, int capacidade)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("O nome da turma é obrigatório.");

        if (capacidade <= 0)
            throw new ArgumentException("A capacidade deve ser maior que zero.");

        Nome = nome;
        Capacidade = capacidade;
    }

    public bool PossuiVaga()
    {
        return _alunos.Count < Capacidade;
    }

    public void AdicionarAluno(Aluno aluno)
    {
        if (aluno is null)
            throw new ArgumentNullException(nameof(aluno));

        if (!PossuiVaga())
            throw new InvalidOperationException("A turma não possui vagas.");

        _alunos.Add(aluno);
    }
}
```

A entidade `Turma` protege sua lista de alunos. A lista interna é privada, e o acesso externo acontece por uma coleção somente leitura.

Essa decisão evita que outras partes do sistema adicionem alunos sem passar pela regra de capacidade.

## Contrato de notificação acadêmica

```csharp
public interface INotificadorAcademico
{
    void Enviar(string email, string mensagem);
}
```

## Implementações concretas

```csharp
public class EmailNotificadorAcademico : INotificadorAcademico
{
    public void Enviar(string email, string mensagem)
    {
        Console.WriteLine($"E-mail acadêmico enviado para {email}: {mensagem}");
    }
}

public class ConsoleNotificadorAcademico : INotificadorAcademico
{
    public void Enviar(string email, string mensagem)
    {
        Console.WriteLine($"Simulação de notificação para {email}: {mensagem}");
    }
}
```

## Serviço de matrícula

```csharp
public class MatriculaService
{
    private readonly INotificadorAcademico _notificador;

    public MatriculaService(INotificadorAcademico notificador)
    {
        _notificador = notificador;
    }

    public void Matricular(Aluno aluno, Turma turma)
    {
        if (aluno is null)
            throw new ArgumentNullException(nameof(aluno));

        if (turma is null)
            throw new ArgumentNullException(nameof(turma));

        turma.AdicionarAluno(aluno);

        _notificador.Enviar(
            aluno.Email,
            $"Sua matrícula na turma {turma.Nome} foi confirmada."
        );
    }
}
```

O serviço coordena o caso de uso. Ele não manipula diretamente a lista interna da turma. Ele chama o método `AdicionarAluno`, respeitando a regra protegida pela entidade.

## Uso no Program.cs

```csharp
INotificadorAcademico notificador = new EmailNotificadorAcademico();

MatriculaService matriculaService = new MatriculaService(notificador);

Aluno aluno = new Aluno("Carla", "carla@email.com");
Turma turma = new Turma("POO", 30);

matriculaService.Matricular(aluno, turma);
```

Resultado esperado:

```text
E-mail acadêmico enviado para carla@email.com: Sua matrícula na turma POO foi confirmada.
```

# 9. Associação entre entidades e associação com contratos

Existem associações que fazem parte do domínio e associações que representam dependências de comportamento.

## Associação entre entidades

```csharp
public class Turma
{
    private readonly List<Aluno> _alunos = new();

    public IReadOnlyCollection<Aluno> Alunos => _alunos.AsReadOnly();
}
```

Uma turma possui alunos. Essa associação é natural no domínio acadêmico. A relação entre `Turma` e `Aluno` faz parte do modelo de negócio.

## Associação com contrato

```csharp
public class MatriculaService
{
    private readonly INotificadorAcademico _notificador;
}
```

Nesse caso, o serviço não possui um notificador como parte do domínio. Ele precisa de um comportamento auxiliar para completar o caso de uso.

Por isso, a associação é feita com uma interface.

Essa diferença é essencial: entidades representam conceitos do domínio; contratos representam comportamentos que podem variar.

# 10. Exemplo comentado: pagamento de venda

Considere uma venda que precisa processar pagamento. O pagamento pode ser feito por Pix, cartão ou outro meio.

## Contrato de pagamento

```csharp
public interface IProcessadorDePagamento
{
    void Processar(decimal valor);
}
```

## Implementações concretas

```csharp
public class ProcessadorPix : IProcessadorDePagamento
{
    public void Processar(decimal valor)
    {
        Console.WriteLine($"Pagamento via Pix: R$ {valor:F2}");
    }
}

public class ProcessadorCartaoCredito : IProcessadorDePagamento
{
    public void Processar(decimal valor)
    {
        Console.WriteLine($"Pagamento no cartão: R$ {valor:F2}");
    }
}
```

## Entidade Venda

```csharp
public class Venda
{
    public string Cliente { get; private set; }
    public decimal Valor { get; private set; }
    public bool Paga { get; private set; }

    public Venda(string cliente, decimal valor)
    {
        if (string.IsNullOrWhiteSpace(cliente))
            throw new ArgumentException("O cliente é obrigatório.");

        if (valor <= 0)
            throw new ArgumentException("O valor da venda deve ser maior que zero.");

        Cliente = cliente;
        Valor = valor;
        Paga = false;
    }

    public void MarcarComoPaga()
    {
        if (Paga)
            throw new InvalidOperationException("A venda já está paga.");

        Paga = true;
    }
}
```

## Serviço de venda

```csharp
public class VendaService
{
    private readonly IProcessadorDePagamento _processador;

    public VendaService(IProcessadorDePagamento processador)
    {
        _processador = processador;
    }

    public void Pagar(Venda venda)
    {
        if (venda is null)
            throw new ArgumentNullException(nameof(venda));

        _processador.Processar(venda.Valor);
        venda.MarcarComoPaga();

        Console.WriteLine($"Venda do cliente {venda.Cliente} marcada como paga.");
    }
}
```

A entidade `Venda` não sabe se o pagamento foi por Pix ou cartão. Ela sabe apenas controlar seu estado interno: se está paga ou não.

O `VendaService` coordena o pagamento usando o contrato `IProcessadorDePagamento`.

# 11. O papel de cada tipo de classe

## Entidade

Representa algo importante do domínio. Possui estado e regras próprias.

Exemplos:

```csharp
Pedido
Aluno
Turma
Venda
```

A entidade deve proteger seus dados e impedir estados inválidos.

## Interface

Representa um contrato de comportamento.

Exemplos:

```csharp
ICalculadoraDeFrete
ICalculadoraDeDesconto
INotificador
IProcessadorDePagamento
```

A interface deve ter nome claro e comunicar exatamente o tipo de comportamento esperado.

## Implementação concreta

Executa o comportamento definido por uma interface.

Exemplos:

```csharp
CalculadoraFretePadrao
CalculadoraFreteGratis
EmailNotificador
SmsNotificador
ProcessadorPix
```

A implementação concreta contém os detalhes de execução.

## Serviço

Coordena uma operação do sistema.

Exemplos:

```csharp
PedidoService
MatriculaService
VendaService
CertificadoService
```

O serviço deve ser focado em um caso de uso ou operação clara.

## Program.cs

Monta os objetos e escolhe as implementações concretas.

O `Program.cs` decide, por exemplo, se o sistema usará `EmailNotificador` ou `SmsNotificador`.

# 12. Cuidados com interfaces genéricas demais

Uma interface deve comunicar claramente seu papel.

Exemplo ruim:

```csharp
public interface IExecutor
{
    void Executar();
}
```

Esse contrato é vago. Executar o quê? Em qual contexto? Com qual objetivo?

Exemplos melhores:

```csharp
public interface IProcessadorDePagamento
{
    void Processar(decimal valor);
}

public interface ICalculadoraDeFrete
{
    decimal Calcular(Pedido pedido);
}

public interface INotificadorAcademico
{
    void Enviar(string email, string mensagem);
}
```

Essas interfaces comunicam melhor sua responsabilidade.

O nome da interface deve ajudar o leitor a entender o contrato sem precisar abrir todas as implementações.

# 13. Organização sugerida de pastas

Em um projeto simples, uma organização possível é separar entidades, interfaces, serviços e implementações.

```text
Projeto/
├── Entidades/
│   ├── Pedido.cs
│   ├── Aluno.cs
│   ├── Turma.cs
│   └── Venda.cs
│
├── Interfaces/
│   ├── ICalculadoraDeFrete.cs
│   ├── ICalculadoraDeDesconto.cs
│   ├── INotificador.cs
│   └── IProcessadorDePagamento.cs
│
├── Servicos/
│   ├── PedidoService.cs
│   ├── MatriculaService.cs
│   └── VendaService.cs
│
├── Implementacoes/
│   ├── CalculadoraFretePadrao.cs
│   ├── CalculadoraFreteGratis.cs
│   ├── CalculadoraDescontoPadrao.cs
│   ├── CalculadoraDescontoPromocional.cs
│   ├── EmailNotificador.cs
│   ├── SmsNotificador.cs
│   └── ProcessadorPix.cs
│
└── Program.cs
```

Essa organização ajuda a localizar responsabilidades:

* `Entidades`: classes com estado e regras do domínio;
* `Interfaces`: contratos de comportamento;
* `Servicos`: casos de uso e coordenação de operações;
* `Implementacoes`: classes concretas que executam contratos;
* `Program.cs`: ponto de montagem dos objetos.

A separação de pastas não resolve sozinha problemas de arquitetura, mas ajuda a tornar explícito o papel de cada classe.

# 14. Aplicação prática resolvida: emissão de certificado

## Cenário

Um sistema precisa emitir certificados para alunos que concluíram um curso. O fluxo deve:

1. verificar se o aluno concluiu o curso;
2. emitir o certificado;
3. notificar o aluno.

A emissão pode ser em PDF ou HTML. A notificação pode ser por e-mail ou SMS. O serviço não deve depender diretamente dessas implementações.

## Objetivo

Criar uma solução com:

* entidade `Aluno`;
* interface `IEmissorDeCertificado`;
* interface `INotificador`;
* implementações concretas;
* serviço `CertificadoService`;
* montagem no `Program.cs`.

---

## Entidade Aluno

```csharp
public class Aluno
{
    public string Nome { get; private set; }
    public string Email { get; private set; }
    public bool CursoConcluido { get; private set; }

    public Aluno(string nome, string email, bool cursoConcluido)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("O nome é obrigatório.");

        if (string.IsNullOrWhiteSpace(email))
            throw new ArgumentException("O e-mail é obrigatório.");

        Nome = nome;
        Email = email;
        CursoConcluido = cursoConcluido;
    }
}
```

Comentário: a entidade `Aluno` guarda dados importantes e informa se o curso foi concluído. Ela não emite certificado nem envia notificação.

---

## Contrato de emissão de certificado

```csharp
public interface IEmissorDeCertificado
{
    void Emitir(Aluno aluno);
}
```

Comentário: o contrato define que qualquer emissor de certificado deve saber emitir um certificado para um aluno.

---

## Implementações de emissão

```csharp
public class EmissorCertificadoPdf : IEmissorDeCertificado
{
    public void Emitir(Aluno aluno)
    {
        Console.WriteLine($"Certificado em PDF emitido para {aluno.Nome}.");
    }
}

public class EmissorCertificadoHtml : IEmissorDeCertificado
{
    public void Emitir(Aluno aluno)
    {
        Console.WriteLine($"Certificado em HTML emitido para {aluno.Nome}.");
    }
}
```

Comentário: as duas classes cumprem o mesmo contrato. O serviço poderá usar qualquer uma delas.

---

## Contrato de notificação

```csharp
public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}
```

## Implementações de notificação

```csharp
public class EmailNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"E-mail enviado para {destinatario}: {mensagem}");
    }
}

public class SmsNotificador : INotificador
{
    public void Enviar(string destinatario, string mensagem)
    {
        Console.WriteLine($"SMS enviado para {destinatario}: {mensagem}");
    }
}
```

Comentário: a notificação pode mudar sem alterar o serviço. Essa flexibilidade acontece porque o serviço depende da interface `INotificador`.

---

## Serviço de certificado

```csharp
public class CertificadoService
{
    private readonly IEmissorDeCertificado _emissor;
    private readonly INotificador _notificador;

    public CertificadoService(
        IEmissorDeCertificado emissor,
        INotificador notificador)
    {
        _emissor = emissor;
        _notificador = notificador;
    }

    public void EmitirCertificado(Aluno aluno)
    {
        if (aluno is null)
            throw new ArgumentNullException(nameof(aluno));

        if (!aluno.CursoConcluido)
            throw new InvalidOperationException("O aluno ainda não concluiu o curso.");

        _emissor.Emitir(aluno);

        _notificador.Enviar(
            aluno.Email,
            "Seu certificado foi emitido com sucesso."
        );
    }
}
```

Comentário: o `CertificadoService` coordena o caso de uso. Ele verifica se o aluno concluiu o curso, chama o emissor e depois chama o notificador.

Ele não sabe se o certificado será PDF ou HTML. Também não sabe se a notificação será por e-mail ou SMS.

---

## Program.cs com emissão em PDF e notificação por e-mail

```csharp
IEmissorDeCertificado emissor = new EmissorCertificadoPdf();
INotificador notificador = new EmailNotificador();

CertificadoService certificadoService =
    new CertificadoService(emissor, notificador);

Aluno aluno = new Aluno(
    "Marcos",
    "marcos@email.com",
    true
);

certificadoService.EmitirCertificado(aluno);
```

Resultado esperado:

```text
Certificado em PDF emitido para Marcos.
E-mail enviado para marcos@email.com: Seu certificado foi emitido com sucesso.
```

## Troca para HTML e SMS

```csharp
IEmissorDeCertificado emissor = new EmissorCertificadoHtml();
INotificador notificador = new SmsNotificador();

CertificadoService certificadoService =
    new CertificadoService(emissor, notificador);

Aluno aluno = new Aluno(
    "Marcos",
    "45999999999",
    true
);

certificadoService.EmitirCertificado(aluno);
```

Resultado esperado:

```text
Certificado em HTML emitido para Marcos.
SMS enviado para 45999999999: Seu certificado foi emitido com sucesso.
```

O `CertificadoService` não foi alterado. Apenas as implementações escolhidas mudaram.

# 15. Erros comuns e dúvidas frequentes

## Erro 1: colocar tudo dentro da entidade

Um erro comum é fazer a entidade executar todas as ações do sistema.

Exemplo problemático:

```csharp
public class Pedido
{
    public void Finalizar()
    {
        CalcularFrete();
        CalcularDesconto();
        EnviarEmail();
        SalvarNoBanco();
    }
}
```

O problema é que a entidade passa a conhecer detalhes de cálculo, comunicação e persistência. Isso cria uma classe grande, difícil de testar e difícil de modificar.

A solução é deixar a entidade cuidar de seu estado e mover a coordenação para um serviço.

---

## Erro 2: serviço genérico demais

Um serviço como `SistemaService` ou `GeralService` costuma indicar falta de responsabilidade clara.

O ideal é que o nome do serviço indique o caso de uso ou área de atuação:

```csharp
PedidoService
MatriculaService
PagamentoService
CertificadoService
```

Quando o nome é claro, fica mais fácil entender onde uma regra deve estar.

---

## Erro 3: interface vaga demais

Interfaces como `IExecutor`, `IGerenciador` ou `IProcessador` podem ser vagas quando não explicam o comportamento real.

Compare:

```csharp
public interface IExecutor
{
    void Executar();
}
```

com:

```csharp
public interface IEmissorDeCertificado
{
    void Emitir(Aluno aluno);
}
```

A segunda interface comunica melhor o contrato.

---

## Erro 4: alterar o serviço para cada nova implementação

Se a cada nova regra de frete for necessário alterar o `PedidoService`, provavelmente o serviço está acoplado demais às implementações concretas.

O ideal é criar uma nova classe que implemente o contrato:

```csharp
public class CalculadoraFretePorRegiao : ICalculadoraDeFrete
{
    public decimal Calcular(Pedido pedido)
    {
        return pedido.ValorProdutos * 0.12m;
    }
}
```

Depois, basta escolher essa implementação na montagem dos objetos.

---

## Erro 5: colocar infraestrutura dentro da entidade

A entidade não deve saber detalhes como envio de e-mail, SMS, banco de dados ou geração de arquivo.

Por exemplo, a entidade `Turma` deve controlar sua capacidade e seus alunos, mas não deve enviar e-mail de confirmação. Essa responsabilidade pertence ao serviço de matrícula, que pode usar um contrato de notificação.

---

# 16. Checklist explicado

## 1. Verifique se a entidade representa um conceito do domínio

A entidade deve representar algo importante para o sistema, como `Pedido`, `Aluno`, `Turma` ou `Venda`.

Isso importa porque entidades são o centro das regras do domínio. Se a entidade for apenas uma coleção de métodos genéricos, o modelo perde clareza.

Para validar, pergunte: “essa classe representa algo real dentro do problema?”. Se a resposta for não, talvez ela não seja uma entidade.

Se esse cuidado faltar, o sistema pode ficar cheio de classes artificiais e difíceis de entender.

---

## 2. Verifique se a entidade protege seu estado

A entidade deve impedir estados inválidos. Por exemplo, uma venda não deve ser marcada como paga duas vezes, e uma turma não deve ultrapassar sua capacidade.

Isso importa porque regras essenciais não devem depender apenas de quem chama a classe corretamente.

Para validar, observe se os atributos importantes têm `private set` e se as mudanças passam por métodos que aplicam regras.

Se esse cuidado faltar, outras partes do sistema podem alterar dados livremente e quebrar regras importantes.

---

## 3. Verifique se comportamentos variáveis foram representados por interfaces

Cálculo de frete, cálculo de desconto, notificação, pagamento e emissão de certificado são exemplos de comportamentos que podem variar.

Isso importa porque regras variáveis mudam com frequência. Interfaces permitem trocar implementações sem alterar serviços centrais.

Para validar, procure comportamentos com mais de uma forma possível. Se houver várias formas de calcular, enviar, processar ou emitir, uma interface pode ser adequada.

Se esse cuidado faltar, o sistema ficará preso a uma implementação específica.

---

## 4. Verifique se o serviço depende de contratos, não de classes concretas

O serviço deve declarar dependências por interfaces:

```csharp
private readonly INotificador _notificador;
```

e não por implementações concretas:

```csharp
private readonly EmailNotificador _notificador;
```

Isso importa porque o serviço deve coordenar o caso de uso, não escolher detalhes de infraestrutura.

Para validar, observe os atributos e o construtor do serviço. Eles devem receber interfaces quando o comportamento puder variar.

Se esse cuidado faltar, cada mudança de implementação pode exigir alteração no serviço.

---

## 5. Verifique se o serviço tem responsabilidade clara

Um serviço deve coordenar uma operação específica. `PedidoService` finaliza pedidos; `MatriculaService` matricula alunos; `CertificadoService` emite certificados.

Isso importa porque serviços genéricos tendem a concentrar muitas regras sem relação entre si.

Para validar, leia o nome do serviço e seus métodos. Eles devem pertencer ao mesmo contexto.

Se esse cuidado faltar, o serviço pode virar uma classe grande e confusa.

---

## 6. Verifique se o Program.cs monta os objetos concretos

Em projetos simples, o `Program.cs` pode ser o local onde as implementações concretas são escolhidas.

Isso importa porque separa a escolha das implementações da lógica do serviço.

Para validar, troque uma implementação concreta no `Program.cs` e veja se o serviço continua igual.

Se esse cuidado faltar, a lógica de escolha pode ficar espalhada em várias classes.

---

## 7. Verifique se os nomes das interfaces comunicam intenção

Interfaces devem ter nomes claros, como `ICalculadoraDeFrete`, `INotificador` e `IProcessadorDePagamento`.

Isso importa porque bons nomes reduzem a necessidade de explicações extras.

Para validar, leia o nome da interface e pergunte: “fica claro qual comportamento ela representa?”.

Se esse cuidado faltar, o código pode ficar tecnicamente correto, mas difícil de entender.

---

# 17. Síntese final

Interfaces ajudam a separar o contrato da implementação. Uma classe que depende de uma interface conhece apenas o comportamento esperado, não os detalhes concretos de execução.

Entidades representam conceitos do domínio e protegem regras essenciais. Serviços coordenam casos de uso que envolvem entidades e comportamentos auxiliares. Implementações concretas executam contratos definidos por interfaces. O `Program.cs` pode montar os objetos e escolher quais implementações serão usadas.

Essa separação reduz acoplamento, melhora a organização do código e facilita mudanças futuras.

---

# Conclusão

Usar interfaces em associações e serviços é uma forma de criar sistemas mais flexíveis e organizados. A entidade fica responsável por proteger seu estado e suas regras principais. O serviço coordena a operação. A interface define o contrato. A implementação concreta executa o comportamento.

Quando o serviço depende de interfaces, novas regras podem ser adicionadas com menos impacto. Para trocar frete padrão por frete grátis, e-mail por SMS ou certificado em PDF por HTML, basta alterar a composição dos objetos, sem modificar a classe central do caso de uso.

Essa estrutura torna o código mais fácil de manter, testar e evoluir.
