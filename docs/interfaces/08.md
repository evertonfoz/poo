# Mini Projeto com Interfaces e Serviços em C#: Domínio, Entidades e Contratos

## Objetivo do material

Neste material, você aprenderá a construir a base de um sistema simples de emissão de certificados acadêmicos usando Programação Orientada a Objetos em C#. O foco desta primeira parte é organizar o domínio do problema, criar entidades com responsabilidades claras, aplicar encapsulamento, definir validações e preparar interfaces que representarão comportamentos variáveis do sistema. 

Ao final, você deverá compreender por que não é adequado colocar toda a lógica em uma única classe, como separar dados e comportamentos, quando criar interfaces e como preparar um projeto para evoluir sem alterar constantemente suas classes principais.

---

## 1. Contextualização do problema

Imagine uma instituição que oferece cursos e precisa emitir certificados para alunos que concluíram suas formações. Para que um certificado seja emitido de forma organizada, o sistema precisa executar algumas etapas:

1. verificar se o aluno concluiu o curso;
2. criar um certificado com os dados do aluno e do curso;
3. emitir o certificado em algum formato, como PDF, HTML ou texto;
4. registrar a emissão, por exemplo em console, arquivo, banco de dados ou API;
5. notificar o aluno, por e-mail, SMS, aplicativo ou outro meio.

Mesmo sendo um sistema simples, ele já apresenta várias responsabilidades diferentes. O erro comum seria colocar tudo em uma única classe, como se a entidade `Aluno` fosse responsável por guardar dados, verificar conclusão, emitir certificado, registrar emissão e enviar notificação.

Esse tipo de solução até pode funcionar no começo, mas se torna difícil de manter. Sempre que uma regra muda, a mesma classe precisa ser alterada. Se amanhã o certificado puder ser emitido em PDF e HTML, a classe cresce. Se depois a notificação puder ser feita por e-mail e SMS, a classe cresce novamente. O resultado é um código acoplado, difícil de testar e difícil de evoluir.

A solução estudada neste material é separar responsabilidades desde o início.

---

## 2. O problema de colocar tudo em uma única classe

Uma implementação inicial ruim poderia ser parecida com esta:

```csharp
public class Aluno
{
    public string Nome { get; set; }
    public string Email { get; set; }
    public bool CursoConcluido { get; set; }

    public void EmitirCertificado()
    {
        if (!CursoConcluido)
        {
            Console.WriteLine("Aluno não concluiu o curso.");
            return;
        }

        Console.WriteLine("Emitindo certificado...");
        Console.WriteLine("Registrando emissão...");
        Console.WriteLine("Enviando notificação...");
    }
}
```

À primeira vista, o código parece simples. A classe `Aluno` possui nome, e-mail, informação de conclusão e um método para emitir o certificado. Porém, ela está fazendo mais do que deveria.

A classe `Aluno` deveria representar o aluno no domínio. Ela pode guardar dados importantes sobre o aluno e regras diretamente relacionadas a ele, como marcar o curso como concluído. Porém, emitir certificado, registrar emissão e enviar notificação são responsabilidades diferentes.

Esse problema é chamado de excesso de responsabilidade. Quando uma classe concentra muitas tarefas, ela se torna difícil de modificar. Uma mudança na forma de notificação poderia obrigar uma alteração na classe `Aluno`, mesmo que o conceito de aluno não tenha mudado. Isso indica que a classe está acoplada a detalhes que não deveriam pertencer a ela.

---

## 3. Separação de responsabilidades

Para organizar melhor o sistema, vamos dividir o projeto em quatro tipos principais de elementos:

### Entidades

As entidades representam os elementos importantes do domínio. Neste projeto, as entidades são:

* `Aluno`;
* `Curso`;
* `Certificado`.

Elas guardam dados e regras essenciais do domínio. Uma entidade não deve assumir responsabilidades externas ao seu conceito principal. Por exemplo, `Certificado` representa o certificado gerado, mas não precisa saber se será emitido em PDF, HTML ou texto.

### Interfaces

As interfaces definem contratos de comportamento. Elas dizem o que uma classe deve fazer, mas não dizem como isso será feito.

Neste projeto, serão criadas três interfaces:

* `IEmissorDeCertificado`;
* `IRegistroDeCertificado`;
* `INotificador`.

Essas interfaces representam comportamentos que podem variar. O emissor pode emitir em PDF, HTML ou texto. O registrador pode gravar em console, arquivo ou banco de dados. O notificador pode enviar e-mail, SMS ou mensagem em aplicativo.

### Implementações concretas

As implementações concretas são classes que cumprem os contratos definidos pelas interfaces. Elas não serão desenvolvidas nesta primeira parte, mas serão preparadas pela criação dos contratos.

Por exemplo, futuramente poderá existir uma classe `EmissorPdf` que implementa `IEmissorDeCertificado`, ou uma classe `NotificadorEmail` que implementa `INotificador`.

### Serviço

O serviço será responsável por orquestrar o fluxo completo de emissão. Ele deverá coordenar a verificação do aluno, a criação do certificado, a emissão, o registro e a notificação.

Nesta primeira parte, o serviço ainda não será implementado. O objetivo agora é preparar a base do projeto.

```text

|   |-- Certificado.cs
|
```

A pasta `Entidades` conterá as classes que representam os principais objetos do domínio. A pasta `Interfaces` conterá os contratos de comportamentos variáveis. As pastas `Implementacoes` e `Servicos` serão usadas em uma etapa posterior, quando o fluxo completo for implementado.

Essa organização facilita a manutenção porque deixa explícito onde cada tipo de código deve ficar. Quando alguém precisar alterar uma entidade, saberá procurar em `Entidades`. Quando precisar criar uma nova forma de emissão, procurará os contratos em `Interfaces` e criará uma implementação concreta na pasta apropriada.

## 5. Entidade Curso

A classe `Curso` representa um curso oferecido pela instituição. Ela deve guardar o nome do curso e sua carga horária. Também deve impedir a criação de cursos inválidos, como cursos sem nome ou com carga horária igual a zero.

```csharp
namespace MiniProjetoCertificados.Entidades;

public class Curso
{
    public string Nome { get; private set; }
    public int CargaHoraria { get; private set; }

    public Curso(string nome, int cargaHoraria)
    {
        if (string.IsNullOrEmpty(nome))
        {
            throw new ArgumentException("O nome do curso é obrigatório.");
        }

        if (cargaHoraria <= 0)
        {
            throw new ArgumentException(
                "A carga horária deve ser maior que zero.");
        }

        Nome = nome;
        CargaHoraria = cargaHoraria;
    }

    public string ObterDescricao()
    {
        return $"{Nome} - {CargaHoraria} horas";
    }
}
```

A classe `Curso` possui duas propriedades: `Nome` e `CargaHoraria`. As duas usam `private set`, o que significa que podem ser lidas por outras partes do sistema, mas só podem ser alteradas dentro da própria classe.

Isso protege o objeto contra alterações indevidas. Sem `private set`, qualquer parte do sistema poderia fazer algo como:

```csharp
curso.Nome = "";
curso.CargaHoraria = -10;
```

Essas alterações quebrariam a validade do objeto. Com `private set`, o curso só pode ser configurado no construtor, passando pelas validações definidas.

A validação do nome impede que um curso seja criado sem identificação:

```csharp
if (string.IsNullOrEmpty(nome))
{
    throw new ArgumentException("O nome do curso é obrigatório.");
}
```

A validação da carga horária impede valores inválidos:

```csharp
if (cargaHoraria <= 0)
{
    throw new ArgumentException(
        "A carga horária deve ser maior que zero.");
}
```

O método `ObterDescricao` retorna uma descrição simples do curso:

```csharp
public string ObterDescricao()
{
    return $"{Nome} - {CargaHoraria} horas";
}
```

Esse método pertence à entidade porque descreve o próprio curso. Ele não emite certificado, não envia notificação e não registra nada. A responsabilidade da classe permanece clara.

## 6. Entidade Aluno

A classe `Aluno` representa a pessoa que poderá receber um certificado. Ela guarda o nome, o e-mail e a informação sobre a conclusão do curso.

```csharp
namespace MiniProjetoCertificados.Entidades;

public class Aluno
{
    public string Nome { get; private set; }
    public string Email { get; private set; }
    public bool CursoConcluido { get; private set; }

    public Aluno(string nome, string email, bool cursoConcluido)
    {
        if (string.IsNullOrWhiteSpace(nome))
        {
            throw new ArgumentException("O nome do aluno é obrigatório.");
        }

        if (string.IsNullOrWhiteSpace(email))
        {
            throw new ArgumentException("O e-mail do aluno é obrigatório.");
        }

        Nome = nome;
        Email = email;
        CursoConcluido = cursoConcluido;
    }

    public void MarcarCursoComoConcluido()
    {
        CursoConcluido = true;
    }
}
```

A entidade `Aluno` também usa `private set` para proteger seus dados. Isso impede alterações diretas como:

```csharp
aluno.Nome = "";
aluno.Email = "";
```

Essa proteção é importante porque um aluno sem nome ou sem e-mail não deveria existir no sistema. A validação acontece no construtor:

```csharp
if (string.IsNullOrWhiteSpace(nome))
{
    throw new ArgumentException("O nome do aluno é obrigatório.");
}
```

O uso de `string.IsNullOrWhiteSpace` é adequado porque considera inválidos valores nulos, vazios ou compostos apenas por espaços.

O método `MarcarCursoComoConcluido` altera o estado de conclusão do aluno:

```csharp
public void MarcarCursoComoConcluido()
{
    CursoConcluido = true;
}
```

Esse método é mais expressivo do que simplesmente permitir a alteração direta da propriedade `CursoConcluido`. Em vez de escrever `aluno.CursoConcluido = true`, o código comunica uma ação do domínio: o curso foi concluído.

Essa diferença melhora a legibilidade do sistema. Quem lê o código entende que existe um evento ou mudança de estado significativa, e não apenas uma alteração técnica em um valor booleano.

## 7. Entidade Certificado

A classe `Certificado` representa o certificado emitido para um aluno em um curso. Ela guarda quatro informações principais:

* aluno;
* curso;
* data de emissão;
* código de verificação.

```csharp
namespace MiniProjetoCertificados.Entidades;

public class Certificado
{
    public Aluno Aluno { get; private set; }
    public Curso Curso { get; private set; }
    public DateTime DataEmissao { get; private set; }
    public string CodigoVerificacao { get; private set; }

    public Certificado(Aluno aluno, Curso curso)
    {
        Aluno = aluno ?? throw new ArgumentNullException(nameof(aluno));
        Curso = curso ?? throw new ArgumentNullException(nameof(curso));
        DataEmissao = DateTime.Now;
        CodigoVerificacao = Guid.NewGuid().ToString()[..8].ToUpper();
    }

    public string ObterResumo()
    {
        return $"Certificado {CodigoVerificacao} - {Aluno.Nome} - " +
               $"{Curso.Nome} - {DataEmissao:dd/MM/yyyy}";
    }
}
```

A entidade `Certificado` depende de um `Aluno` e de um `Curso`. Isso faz sentido porque não existe certificado acadêmico sem alguém que o receba e sem um curso ao qual ele esteja relacionado.

A proteção contra valores nulos é feita com o operador `??`:

```csharp
Aluno = aluno ?? throw new ArgumentNullException(nameof(aluno));
Curso = curso ?? throw new ArgumentNullException(nameof(curso));
```

Esse trecho impede a criação de certificados incompletos. Se o aluno ou o curso não forem informados, uma exceção será lançada.

A data de emissão é definida automaticamente:

```csharp
DataEmissao = DateTime.Now;
```

Isso garante que o certificado registre o momento em que foi criado.

O código de verificação é gerado com `Guid.NewGuid()`:

```csharp
CodigoVerificacao = Guid.NewGuid().ToString()[..8].ToUpper();
```

O `Guid.NewGuid()` cria um identificador único. Em seguida, o código é convertido para texto, reduzido para os oito primeiros caracteres e transformado em letras maiúsculas. Esse código curto facilita a exibição e pode ser usado como referência de validação do certificado.

O método `ObterResumo` retorna uma representação textual do certificado:

```csharp
public string ObterResumo()
{
    return $"Certificado {CodigoVerificacao} - {Aluno.Nome} - " +
           $"{Curso.Nome} - {DataEmissao:dd/MM/yyyy}";
}
```

Esse método é útil para exibir uma informação resumida no console ou em logs simples.

## 8. Por que o Certificado não emite a si mesmo?

Uma dúvida comum é: se a classe `Certificado` representa o certificado, por que ela não possui um método `Emitir()`?

A resposta está na separação de responsabilidades. O certificado é o documento gerado. A emissão é uma ação que pode variar conforme o formato ou o destino.

Emitir um certificado pode significar:

* gerar um arquivo PDF;
* gerar uma página HTML;
* imprimir texto no console;
* enviar dados para uma API externa;
* salvar um documento digital em um serviço de arquivos.

Se a classe `Certificado` tivesse um método `Emitir()`, ela precisaria conhecer todos esses formatos. Isso faria com que a entidade ficasse acoplada a detalhes de saída, tecnologia e infraestrutura.

A entidade deve representar o certificado. O comportamento de emitir será definido por uma interface e implementado por outra classe.

Essa separação permite que o sistema evolua. Se uma nova forma de emissão surgir no futuro, será possível criar uma nova implementação sem alterar a entidade `Certificado`.

## 9. Interfaces como contratos de comportamento

Uma interface define um contrato. Ela informa quais métodos uma classe deve implementar, mas não define como esses métodos serão executados.

Interfaces são úteis quando um comportamento pode variar. Neste projeto, existem três comportamentos variáveis:

1. emitir certificado;
2. registrar certificado;
3. notificar aluno.

Cada um desses comportamentos terá sua própria interface.

---

## 10. Interface IEmissorDeCertificado

A interface `IEmissorDeCertificado` define que qualquer emissor deve saber emitir um certificado.

```csharp
using MiniProjetoCertificados.Entidades;

namespace MiniProjetoCertificados.Interfaces;

public interface IEmissorDeCertificado
{
    void Emitir(Certificado certificado);
}
```

Essa interface não define se a emissão será em PDF, HTML, texto ou outro formato. Ela apenas determina que uma classe emissora deve possuir o método `Emitir`.

Futuramente, uma classe poderia implementar esse contrato assim:

```csharp
public class EmissorTexto : IEmissorDeCertificado
{
    public void Emitir(Certificado certificado)
    {
        Console.WriteLine(certificado.ObterResumo());
    }
}
```

O ponto principal é que o fluxo principal do sistema não precisa saber os detalhes da emissão. Ele precisa apenas de algum objeto que cumpra o contrato `IEmissorDeCertificado`.

---

## 11. Interface IRegistroDeCertificado

A interface `IRegistroDeCertificado` define que qualquer registrador deve saber registrar um certificado.

```csharp
using MiniProjetoCertificados.Entidades;

namespace MiniProjetoCertificados.Interfaces;

public interface IRegistroDeCertificado
{
    void Registrar(Certificado certificado);
}
```

Essa interface não informa onde o certificado será registrado. O registro pode ser feito no console, em um arquivo, em memória, em banco de dados ou em uma API.

Essa decisão fica para as implementações concretas. O contrato apenas garante que qualquer registrador terá o método `Registrar`.

Isso evita que o restante do sistema fique preso a uma forma específica de armazenamento.

---

## 12. Interface INotificador

A interface `INotificador` define que qualquer notificador deve saber enviar uma mensagem para um destinatário.

```csharp
namespace MiniProjetoCertificados.Interfaces;

public interface INotificador
{
    void Enviar(string destinatario, string mensagem);
}
```

Essa interface não define se a mensagem será enviada por e-mail, SMS, aplicativo ou outro meio. Ela apenas estabelece o contrato.

O método recebe dois parâmetros:

```csharp
void Enviar(string destinatario, string mensagem);
```

O parâmetro `destinatario` representa quem receberá a mensagem. Neste projeto, pode ser o e-mail do aluno. O parâmetro `mensagem` representa o conteúdo enviado.

Essa separação permite trocar a forma de notificação sem mudar o restante do fluxo.

## 13. Diferenças conceituais importantes

### Entidade não é serviço

Uma entidade representa algo importante do domínio. Ela guarda dados e regras diretamente ligadas ao seu conceito. `Aluno`, `Curso` e `Certificado` são entidades.

Um serviço coordena ações. Ele costuma reunir várias operações para executar um processo. No caso deste projeto, o serviço de emissão será responsável por coordenar criação, emissão, registro e notificação.

O erro seria transformar uma entidade em serviço. Por exemplo, fazer a classe `Aluno` emitir certificado e enviar notificação mistura conceitos diferentes.

### Interface não é implementação

Uma interface define o que deve ser feito. Uma implementação define como será feito.

A interface `INotificador` diz que uma mensagem deve ser enviada. Uma classe concreta, como `NotificadorEmail`, diria como essa mensagem será enviada por e-mail.

Essa diferença é essencial para manter o sistema flexível.

### Encapsulamento não é apenas esconder propriedades

Encapsular não significa apenas colocar `private set`. Encapsular significa proteger o estado do objeto e permitir alterações por meio de comportamentos controlados.

Na classe `Aluno`, por exemplo, o estado `CursoConcluido` não é alterado diretamente. Ele muda por meio do método `MarcarCursoComoConcluido`, que comunica uma intenção clara do domínio.

### Validação no construtor evita objetos inválidos

Quando uma classe exige dados obrigatórios, o construtor deve garantir que o objeto já nasça válido. Um `Curso` sem nome ou com carga horária negativa não deveria existir no sistema. Por isso a validação é feita no momento da criação.

* as entidades foram criadas nas pastas corretas;
* o console exibe o nome do aluno;
* o método `ObterDescricao` retorna nome e carga horária do curso;
* o método `ObterResumo` exibe código, aluno, curso e data;
* valores inválidos geram exceções.

### Possíveis erros

Um erro comum é esquecer o `using MiniProjetoCertificados.Entidades;` no `Program.cs`. Sem esse `using`, o arquivo pode não reconhecer as classes `Aluno`, `Curso` e `Certificado`.

Outro erro comum é criar arquivos em namespaces diferentes da estrutura esperada. Se a classe estiver em um namespace e o `Program.cs` importar outro, o compilador não encontrará a classe.

Também pode ocorrer erro ao tentar alterar propriedades com `private set` fora da classe. Por exemplo:

```csharp
aluno.Nome = "Outro nome";
```

Esse código não deve compilar, porque `Nome` só pode ser alterado dentro da classe `Aluno`.

## 15. Testando validações

As validações garantem que objetos inválidos não sejam criados.

### Curso sem nome

```csharp
Curso curso = new Curso("", 80);
```

Esse código deve gerar a exceção:

```text
O nome do curso é obrigatório.
```

O erro acontece porque o nome é uma informação obrigatória para identificar o curso.

### Curso com carga horária zero

```csharp
Curso curso = new Curso("POO em C#", 0);
```

Esse código deve gerar a exceção:

```text
A carga horária deve ser maior que zero.
```

A carga horária não pode ser zero porque um curso precisa ter duração válida.

### Aluno sem nome

```csharp
Aluno aluno = new Aluno("", "aluno@email.com", true);
```

Esse código deve gerar a exceção:

```text
O nome do aluno é obrigatório.
```

Um aluno sem nome não é um objeto válido para o domínio.

### Aluno sem e-mail

```csharp
Aluno aluno = new Aluno("Beatriz", "", true);
```

Esse código deve gerar a exceção:

```text
O e-mail do aluno é obrigatório.
```

O e-mail será necessário para notificação, por isso deve ser obrigatório desde a criação do aluno.

## 16. Erros comuns e dúvidas frequentes

### Colocar emissão dentro da entidade Certificado

Esse erro acontece quando se pensa que, por representar um certificado, a classe também deveria emitir o documento. O problema é que a emissão pode variar muito. Se o certificado souber emitir PDF, HTML, texto e integração externa, ele ficará acoplado a detalhes que não pertencem ao domínio principal.

A solução é manter `Certificado` como entidade e usar `IEmissorDeCertificado` para representar o comportamento de emissão.

### Deixar todas as propriedades com set público

Usar `set` público em todas as propriedades permite que qualquer parte do sistema altere dados importantes sem validação. Isso pode criar objetos inconsistentes.

O uso de `private set` reduz esse risco, pois obriga a alteração de estado a passar pela própria classe.

### Criar interfaces antes de entender o comportamento

Interfaces devem representar comportamentos relevantes e variáveis. Não é necessário criar interface para tudo. Neste projeto, emissão, registro e notificação merecem interfaces porque podem ter diferentes implementações.

Criar interfaces sem necessidade pode deixar o projeto mais complexo do que precisa.

### Confundir contrato com implementação

A interface `INotificador` não envia e-mail por si só. Ela apenas define que uma classe notificadora deve ter um método `Enviar`.

Quem realmente envia a mensagem será uma classe concreta criada depois, como um notificador por e-mail, SMS ou console.

### Esperar que a Parte 1 execute o fluxo completo

Nesta etapa, o objetivo não é executar todo o processo de emissão. O objetivo é preparar a estrutura do domínio e os contratos. O fluxo completo dependerá das implementações concretas e de um serviço de emissão.

## 17. Checklist explicado

### Verifique se as entidades representam conceitos do domínio

As classes `Aluno`, `Curso` e `Certificado` devem representar elementos reais do problema. Isso importa porque entidades devem expressar a linguagem do domínio, não detalhes técnicos de infraestrutura. Para validar, leia cada classe e pergunte: “essa classe representa algo importante no sistema de certificados?”. Se uma entidade estiver enviando e-mail, gravando arquivo ou gerando PDF, ela provavelmente está assumindo responsabilidade indevida.

### Verifique se cada entidade possui uma responsabilidade clara

A classe `Curso` deve representar um curso válido. A classe `Aluno` deve representar o aluno e seu estado de conclusão. A classe `Certificado` deve representar o certificado emitido. Isso importa porque responsabilidades misturadas dificultam manutenção. Para validar, observe se cada método da classe está diretamente ligado ao conceito que ela representa. Se faltar essa separação, pequenas mudanças podem exigir alterações em várias partes do código.

### Verifique se as propriedades importantes usam encapsulamento

Propriedades como `Nome`, `Email`, `CargaHoraria`, `DataEmissao` e `CodigoVerificacao` não devem ser alteradas livremente por qualquer parte do sistema. Isso importa para proteger a consistência dos objetos. Para validar, confira se as propriedades usam `private set` quando a alteração direta não deve ser permitida. Se isso faltar, o sistema poderá criar ou modificar objetos para estados inválidos.

### Verifique se os construtores validam dados obrigatórios

Um curso sem nome, um curso com carga horária inválida, um aluno sem nome ou um aluno sem e-mail não devem ser aceitos. Isso importa porque objetos inválidos contaminam o restante do fluxo. Para validar, tente criar objetos com valores vazios, nulos ou inválidos e observe se exceções são lançadas. Se as validações faltarem, erros podem aparecer apenas mais tarde, em partes mais difíceis de rastrear.

### Verifique se o Certificado exige Aluno e Curso

Um certificado precisa estar associado a um aluno e a um curso. Isso importa porque o certificado é o resultado da relação entre quem concluiu e o que foi concluído. Para validar, confira se o construtor de `Certificado` recebe `Aluno` e `Curso` e impede valores nulos. Se isso faltar, o sistema poderá gerar certificados incompletos.

### Verifique se comportamentos variáveis foram definidos por interfaces

Emitir, registrar e notificar são comportamentos que podem mudar. Isso importa porque o sistema pode evoluir para diferentes formatos de emissão, armazenamento e comunicação. Para validar, confira se existem interfaces específicas para esses comportamentos: `IEmissorDeCertificado`, `IRegistroDeCertificado` e `INotificador`. Se essas interfaces faltarem, o fluxo principal pode ficar preso a uma implementação específica.

### Verifique se as interfaces não impõem detalhes concretos

Uma interface deve definir o contrato, não a tecnologia usada. `IEmissorDeCertificado` não deve mencionar PDF diretamente se a emissão puder variar. `INotificador` não deve depender exclusivamente de e-mail se outros canais forem possíveis. Isso importa para manter flexibilidade. Para validar, veja se os nomes e métodos das interfaces são genéricos o suficiente para permitir várias implementações. Se a interface for específica demais, ela perderá parte de sua utilidade.

### Verifique se o Program.cs é usado apenas para teste básico nesta etapa

Nesta primeira parte, o `Program.cs` deve testar a criação das entidades e suas validações. Isso importa porque o serviço completo ainda não existe. Para validar, confira se o teste instancia `Aluno`, `Curso` e `Certificado`, chama métodos simples e imprime resultados. Se o `Program.cs` já estiver concentrando todo o fluxo de emissão, registro e notificação, o projeto estará repetindo o problema de acoplamento inicial.

## 18. Síntese final

Nesta primeira parte do mini projeto, a base do sistema de emissão de certificados foi organizada a partir de três ideias principais.

A primeira ideia é que entidades devem representar conceitos do domínio. `Aluno`, `Curso` e `Certificado` são classes que guardam dados e regras essenciais. Elas não devem assumir tarefas externas, como emitir arquivos, registrar dados em banco ou enviar notificações.

A segunda ideia é que encapsulamento protege o estado dos objetos. O uso de `private set`, validações no construtor e métodos com intenção clara evita que o sistema trabalhe com objetos inválidos ou alterados de forma indevida.

A terceira ideia é que interfaces representam contratos para comportamentos que podem variar. `IEmissorDeCertificado`, `IRegistroDeCertificado` e `INotificador` permitem que o sistema receba diferentes formas de emissão, registro e notificação sem modificar as entidades.

Essa base prepara o projeto para a próxima etapa, em que serão criadas implementações concretas e um serviço responsável por coordenar o fluxo completo de emissão.

---

## Conclusão

Um sistema bem organizado começa pela separação correta de responsabilidades. Mesmo em um mini projeto, é importante evitar que uma única classe concentre dados, regras, emissão, registro e notificação.

Ao criar entidades bem definidas e interfaces para comportamentos variáveis, o projeto se torna mais claro, mais fácil de testar e mais preparado para mudanças. A classe `Aluno` representa o aluno. A classe `Curso` representa o curso. A classe `Certificado` representa o documento emitido. As interfaces representam ações que ainda receberão implementações concretas.

Com essa estrutura, o sistema fica pronto para evoluir para a Parte 2, onde o fluxo completo poderá ser implementado sem comprometer a organização construída nesta base.
