# Strategy aplicado a regras de negócio em C#

## Objetivo do material

Neste material, você aprenderá a aplicar o padrão de projeto **Strategy** em C# para organizar regras de negócio variáveis, como cálculo de desconto, frete, validação, classificação e exportação de dados.

Ao final, você deverá ser capaz de:

1. identificar quando uma regra de negócio varia;
2. reconhecer problemas causados por excesso de `if`, `else` e `switch`;
3. criar uma interface para representar uma estratégia;
4. implementar estratégias concretas em classes separadas;
5. usar composição para conectar uma classe principal à estratégia;
6. justificar tecnicamente quando o Strategy faz sentido e quando ele seria exagero.

O conteúdo parte do exemplo de cálculo de desconto apresentado no material-base, que mostra regras como desconto por cupom, fidelidade, campanha e volume, além da substituição de condicionais por polimorfismo em C#. 

---

# 1. Contextualização: o problema das regras de negócio variáveis

Em muitos sistemas, uma mesma operação pode ser executada de maneiras diferentes. Isso acontece quando existe uma intenção geral, mas várias formas concretas de realizar essa intenção.

No exemplo de descontos, a intenção geral é:

> calcular o desconto de uma compra.

Mas essa intenção pode assumir várias regras específicas:

* desconto por cupom;
* desconto por fidelidade;
* desconto por campanha;
* desconto por volume;
* desconto por primeira compra;
* ausência de desconto.

Todas essas regras pertencem à mesma família: elas calculam desconto. Porém, cada uma possui uma lógica própria.

Um primeiro impulso comum é colocar todas as regras dentro de uma única classe, usando vários `if`, `else` ou `switch`. Isso pode funcionar no começo, mas tende a gerar código rígido, difícil de manter e mais propenso a erros.

Observe um exemplo inicial:

```csharp
public class CalculadoraDesconto
{
    public decimal Calcular(decimal valor, string tipoDesconto)
    {
        if (tipoDesconto == "CUPOM")
        {
            return valor * 0.10m;
        }

        if (tipoDesconto == "FIDELIDADE")
        {
            return valor * 0.15m;
        }

        if (tipoDesconto == "CAMPANHA")
        {
            return valor * 0.20m;
        }

        return 0;
    }
}
```

Uso:

```csharp
CalculadoraDesconto calculadora = new CalculadoraDesconto();

decimal desconto = calculadora.Calcular(500, "CUPOM");

Console.WriteLine(desconto);
```

Esse código calcula corretamente o desconto por cupom. Para uma compra de `500`, o desconto será `50`. O problema não está no resultado imediato. O problema está na forma como o código foi organizado.

A classe `CalculadoraDesconto` conhece todas as regras de desconto. Sempre que uma nova regra surgir, a classe precisará ser modificada. Isso aumenta o risco de quebrar regras antigas que já estavam funcionando.

---

# 2. Problemas da abordagem baseada em condicionais

## 2.1 A classe concentra responsabilidades demais

A classe `CalculadoraDesconto` deveria ter uma responsabilidade clara. Porém, no exemplo inicial, ela acumula várias decisões:

* sabe que existe desconto por cupom;
* sabe que existe desconto por fidelidade;
* sabe que existe desconto por campanha;
* sabe o percentual de cada desconto;
* sabe como escolher qual regra aplicar.

Com o tempo, essa classe pode se tornar um ponto central de alterações. Toda nova regra passa por ela.

Esse problema se relaciona ao princípio da responsabilidade única: uma classe deve ter um motivo principal para mudar. Quando a classe muda por causa de várias regras diferentes, ela fica mais frágil.

## 2.2 O código tende a crescer sem controle

Imagine que o sistema precise adicionar novas regras:

```csharp
if (tipoDesconto == "PRIMEIRA_COMPRA")
{
    return valor * 0.05m;
}

if (tipoDesconto == "ANIVERSARIO")
{
    return valor * 0.12m;
}

if (tipoDesconto == "VOLUME")
{
    return valor * 0.18m;
}
```

A cada nova regra, a classe aumenta. O método `Calcular` passa a misturar várias lógicas. Ler, testar e manter esse código fica mais difícil.

Quando uma regra falha, também se torna mais trabalhoso descobrir qual trecho está causando o problema.

## 2.3 Strings podem gerar erros silenciosos

No exemplo inicial, a escolha da regra depende de strings:

```csharp
decimal desconto = calculadora.Calcular(500, "CUPOM");
```

Se alguém escrever:

```csharp
decimal desconto = calculadora.Calcular(500, "CUPON");
```

O código compila normalmente, mas nenhuma regra será aplicada. Esse tipo de erro é perigoso porque pode não aparecer imediatamente durante a compilação. Ele só aparece em execução, e talvez apenas em um cenário específico.

## 2.4 A classe fica pouco aberta para extensão

Uma boa organização de código permite adicionar novas funcionalidades sem modificar constantemente classes já existentes. Esse é o sentido prático do princípio aberto/fechado: o código deve estar aberto para extensão e fechado para modificação.

Com a abordagem baseada em vários `if`, adicionar uma regra significa alterar a classe principal. Com Strategy, adicionar uma regra significa criar uma nova classe.

Essa diferença é importante porque alterar código existente aumenta o risco de regressão, ou seja, de um comportamento antigo parar de funcionar.

# 3. Ideia central do padrão Strategy

O padrão **Strategy** propõe separar cada variação de comportamento em uma classe própria. Em vez de a classe principal conhecer todas as regras concretas, ela passa a depender de uma abstração.

No caso do desconto:

* existe uma interface que representa a regra geral de cálculo de desconto;
* cada tipo de desconto implementa essa interface;
* a classe `Pedido` usa uma estratégia de desconto sem saber qual implementação concreta está recebendo.

A estrutura geral é:

1. criar uma interface para representar o contrato da estratégia;
2. criar classes concretas para cada regra;
3. fazer a classe principal depender da interface;
4. passar a estratégia para a classe principal por composição;
5. deixar o polimorfismo decidir qual implementação será executada.

O Strategy é especialmente útil quando existem várias formas de executar uma mesma operação e essas formas podem mudar ou aumentar com o tempo.

---

# 4. Criando a interface da estratégia

A interface define o contrato comum. Ela não implementa a regra. Ela apenas declara o que toda estratégia deve fazer.

```csharp
public interface ICalculadoraDesconto
{
    decimal Calcular(decimal valor);
}
```

Essa interface diz:

> qualquer estratégia de desconto deve ser capaz de calcular um desconto a partir de um valor.

A interface não sabe se o desconto será de 10%, 15%, 20% ou zero. Essa decisão fica nas classes concretas.

Essa separação é importante porque permite que o restante do sistema trabalhe com a ideia geral de “calculadora de desconto”, sem depender diretamente de `DescontoPorCupom`, `DescontoPorFidelidade` ou qualquer outra implementação específica.

---

# 5. Criando estratégias concretas

Agora cada regra de desconto pode virar uma classe separada.

```csharp
public class DescontoPorCupom : ICalculadoraDesconto
{
    public decimal Calcular(decimal valor)
    {
        return valor * 0.10m;
    }
}
```

A classe `DescontoPorCupom` representa uma regra específica: aplicar 10% de desconto.

```csharp
public class DescontoPorFidelidade : ICalculadoraDesconto
{
    public decimal Calcular(decimal valor)
    {
        return valor * 0.15m;
    }
}
```

A classe `DescontoPorFidelidade` aplica 15% de desconto.

```csharp
public class DescontoPorCampanha : ICalculadoraDesconto
{
    public decimal Calcular(decimal valor)
    {
        return valor * 0.20m;
    }
}
```

A classe `DescontoPorCampanha` aplica 20% de desconto.

Cada classe é pequena, focada e fácil de testar. Se houver erro no desconto por campanha, a investigação fica concentrada na classe `DescontoPorCampanha`.

---

# 6. Criando a classe que usa a estratégia

A classe `Pedido` representa a compra. Ela possui um valor total e usa uma estratégia de desconto.

```csharp
public class Pedido
{
    public decimal ValorTotal { get; private set; }

    private readonly ICalculadoraDesconto _calculadoraDesconto;

    public Pedido(decimal valorTotal, ICalculadoraDesconto calculadoraDesconto)
    {
        if (valorTotal <= 0)
        {
            throw new ArgumentException("Valor total inválido.");
        }

        _calculadoraDesconto = calculadoraDesconto
            ?? throw new ArgumentNullException(nameof(calculadoraDesconto));

        ValorTotal = valorTotal;
    }

    public decimal CalcularDesconto()
    {
        return _calculadoraDesconto.Calcular(ValorTotal);
    }

    public decimal CalcularValorFinal()
    {
        return ValorTotal - CalcularDesconto();
    }
}
```

Esse código possui decisões importantes.

A classe `Pedido` não herda de `DescontoPorCupom`, porque um pedido não é um desconto. A relação correta não é de herança.

A classe `Pedido` também não possui `if` para decidir qual desconto aplicar. Ela apenas usa a estratégia recebida.

A relação correta é:

> um pedido usa uma estratégia de desconto.

Isso é composição.

# 7. Usando o Strategy no `Program.cs`

## 7.1 Desconto por cupom

```csharp
ICalculadoraDesconto descontoCupom = new DescontoPorCupom();

Pedido pedido = new Pedido(500, descontoCupom);

Console.WriteLine($"Valor total: {pedido.ValorTotal}");
Console.WriteLine($"Desconto: {pedido.CalcularDesconto()}");
Console.WriteLine($"Valor final: {pedido.CalcularValorFinal()}");
```

Resultado esperado:

```text
Valor total: 500
Desconto: 50,00
Valor final: 450,00
```

A compra tem valor total de `500`. Como o desconto por cupom é de 10%, o desconto calculado é `50`. O valor final é `500 - 50`, ou seja, `450`.

## 7.2 Trocando a estratégia

Para aplicar desconto por fidelidade, não é necessário alterar a classe `Pedido`.

```csharp
ICalculadoraDesconto descontoFidelidade = new DescontoPorFidelidade();

Pedido pedido = new Pedido(500, descontoFidelidade);

Console.WriteLine($"Valor final: {pedido.CalcularValorFinal()}");
```

Agora o valor final será calculado com 15% de desconto.

O ponto mais importante é: a classe `Pedido` permanece intacta. Apenas a estratégia passada ao construtor muda.

# 8. Polimorfismo e composição no Strategy

## 8.1 Onde está o polimorfismo?

O polimorfismo aparece porque várias classes diferentes implementam a mesma interface:

```csharp
public class DescontoPorCupom : ICalculadoraDesconto
```

```csharp
public class DescontoPorFidelidade : ICalculadoraDesconto
```

```csharp
public class DescontoPorCampanha : ICalculadoraDesconto
```

A classe `Pedido` trabalha com o tipo abstrato:

```csharp
private readonly ICalculadoraDesconto _calculadoraDesconto;
```

Quando o código executa:

```csharp
_calculadoraDesconto.Calcular(ValorTotal);
```

o método chamado depende do objeto real recebido em tempo de execução.

Se o objeto for `DescontoPorCupom`, será executada a regra de cupom. Se for `DescontoPorFidelidade`, será executada a regra de fidelidade. Se for `DescontoPorCampanha`, será executada a regra de campanha.

Isso é polimorfismo por interface.

## 8.2 Onde está a composição?

A composição aparece porque `Pedido` possui uma dependência para `ICalculadoraDesconto`.

```csharp
private readonly ICalculadoraDesconto _calculadoraDesconto;
```

A classe `Pedido` é composta por uma estratégia de desconto. Ela usa a estratégia para completar seu comportamento.

A relação não é:

> Pedido é um desconto.

A relação correta é:

> Pedido usa uma estratégia de desconto.

Por isso, composição é mais adequada do que herança nesse caso.

---

# 9. Adicionando uma nova estratégia

Imagine que o sistema precise de um desconto por primeira compra. Com a solução baseada em `if`, seria necessário alterar a classe `CalculadoraDesconto`.

Com Strategy, basta criar uma nova classe:

```csharp
public class DescontoPorPrimeiraCompra : ICalculadoraDesconto
{
    public decimal Calcular(decimal valor)
    {
        return valor * 0.05m;
    }
}
```

Uso:

```csharp
Pedido pedido = new Pedido(500, new DescontoPorPrimeiraCompra());

Console.WriteLine($"Valor final: {pedido.CalcularValorFinal()}");
```

Neste exemplo, o desconto será de 5%. Para uma compra de `500`, o desconto será `25`, e o valor final será `475`.

A classe `Pedido` não precisou ser modificada. As estratégias antigas também não foram alteradas. Isso reduz o risco de quebrar comportamentos já existentes.

---

# 10. Estratégia para ausência de desconto

Uma abordagem ruim seria permitir que o pedido recebesse `null` quando não houvesse desconto. Isso obrigaria a classe `Pedido` a verificar se a estratégia existe antes de calcular.

Exemplo indesejado:

```csharp
if (_calculadoraDesconto == null)
{
    return 0;
}
```

Esse tipo de verificação espalha exceções pela regra principal.

Uma alternativa melhor é criar uma estratégia específica para ausência de desconto:

```csharp
public class SemDesconto : ICalculadoraDesconto
{
    public decimal Calcular(decimal valor)
    {
        return 0;
    }
}
```

Uso:

```csharp
Pedido pedido = new Pedido(500, new SemDesconto());

Console.WriteLine($"Valor final: {pedido.CalcularValorFinal()}");
```

Resultado esperado:

```text
Valor final: 500
```

Agora o pedido sempre possui uma estratégia válida. Isso torna o código mais previsível.

---

# 11. Estratégia percentual configurável

Nem toda estratégia precisa ter um percentual fixo escrito diretamente no método. Algumas podem receber configurações no construtor.

```csharp
public class DescontoPercentual : ICalculadoraDesconto
{
    public decimal Percentual { get; private set; }

    public DescontoPercentual(decimal percentual)
    {
        if (percentual < 0 || percentual > 1)
        {
            throw new ArgumentException("Percentual inválido.");
        }

        Percentual = percentual;
    }

    public decimal Calcular(decimal valor)
    {
        return valor * Percentual;
    }
}
```

Uso:

```csharp
Pedido pedido = new Pedido(500, new DescontoPercentual(0.12m));

Console.WriteLine($"Desconto: {pedido.CalcularDesconto()}");
Console.WriteLine($"Valor final: {pedido.CalcularValorFinal()}");
```

Resultado esperado:

```text
Desconto: 60,00
Valor final: 440,00
```

O valor `0.12m` representa 12%. A validação no construtor impede percentuais inválidos, como `-0.10m` ou `1.50m`.

Essa estratégia é útil quando o percentual pode vir de uma configuração, campanha, regra administrativa ou cadastro.

---

# 12. Protegendo o valor final do pedido

Uma estratégia pode calcular um desconto maior que o valor total, especialmente se houver erro de configuração ou regra especial. Nesse caso, o pedido deve proteger o valor final para que ele nunca fique negativo.

```csharp
public decimal CalcularValorFinal()
{
    decimal desconto = CalcularDesconto();

    if (desconto > ValorTotal)
    {
        return 0;
    }

    return ValorTotal - desconto;
}
```

Essa regra fica no `Pedido` porque é ele que conhece o valor total e o valor final. A estratégia calcula o desconto; o pedido decide como o desconto afeta o total da compra.

Esse ponto é importante: usar Strategy não significa jogar todas as regras para as estratégias. Cada regra deve ficar na classe que tem a responsabilidade mais adequada.

# 13. Exemplo completo com `Produto`, `ItemPedido` e `Pedido`

Agora vamos organizar melhor o domínio, separando produto, item do pedido e pedido.

## 13.1 Classe `Produto`

```csharp
public class Produto
{
    public string Nome { get; private set; }
    public decimal Preco { get; private set; }

    public Produto(string nome, decimal preco)
    {
        if (string.IsNullOrEmpty(nome))
        {
            throw new ArgumentException("Nome inválido.");
        }

        if (preco <= 0)
        {
            throw new ArgumentException("Preço inválido.");
        }

        Nome = nome;
        Preco = preco;
    }
}
```

A classe `Produto` representa um produto vendido. Ela valida se o nome foi informado e se o preço é maior que zero.

Essas validações pertencem ao produto, porque um produto sem nome ou com preço inválido não deveria existir no sistema.

## 13.2 Classe `ItemPedido`

```csharp
public class ItemPedido
{
    public Produto Produto { get; private set; }
    public int Quantidade { get; private set; }

    public ItemPedido(Produto produto, int quantidade)
    {
        Produto = produto
            ?? throw new ArgumentNullException(nameof(produto));

        if (quantidade <= 0)
        {
            throw new ArgumentException("Quantidade inválida.");
        }

        Quantidade = quantidade;
    }

    public decimal CalcularSubtotal()
    {
        return Produto.Preco * Quantidade;
    }
}
```

A classe `ItemPedido` representa um produto dentro de um pedido, com sua quantidade.

O subtotal do item é calculado multiplicando o preço do produto pela quantidade:

```csharp
return Produto.Preco * Quantidade;
```

Se um teclado custa `250` e a quantidade é `1`, o subtotal é `250`. Se um mouse custa `150` e a quantidade é `2`, o subtotal é `300`.

## 13.3 Classe `Pedido` com coleção de itens

```csharp
public class Pedido
{
    private readonly List<ItemPedido> _itens = new List<ItemPedido>();
    private readonly ICalculadoraDesconto _calculadoraDesconto;

    public IReadOnlyCollection<ItemPedido> Itens => _itens.AsReadOnly();

    public Pedido(ICalculadoraDesconto calculadoraDesconto)
    {
        _calculadoraDesconto = calculadoraDesconto
            ?? throw new ArgumentNullException(nameof(calculadoraDesconto));
    }

    public void AdicionarItem(ItemPedido item)
    {
        if (item == null)
        {
            throw new ArgumentNullException(nameof(item));
        }

        _itens.Add(item);
    }

    public decimal CalcularValorTotal()
    {
        return _itens.Sum(i => i.CalcularSubtotal());
    }

    public decimal CalcularDesconto()
    {
        return _calculadoraDesconto.Calcular(CalcularValorTotal());
    }

    public decimal CalcularValorFinal()
    {
        decimal total = CalcularValorTotal();
        decimal desconto = CalcularDesconto();

        return desconto > total ? 0 : total - desconto;
    }
}
```

A classe `Pedido` possui uma lista privada de itens:

```csharp
private readonly List<ItemPedido> _itens = new List<ItemPedido>();
```

Ela expõe essa lista como leitura:

```csharp
public IReadOnlyCollection<ItemPedido> Itens => _itens.AsReadOnly();
```

Isso evita que outras partes do sistema modifiquem a lista diretamente. Para adicionar um item, é necessário usar o método `AdicionarItem`.

O pedido também recebe uma estratégia de desconto:

```csharp
private readonly ICalculadoraDesconto _calculadoraDesconto;
```

Assim, o pedido não precisa conhecer qual desconto está sendo aplicado.

## 13.4 Uso completo no `Program.cs`

```csharp
Produto teclado = new Produto("Teclado Mecânico", 250);
Produto mouse = new Produto("Mouse Gamer", 150);

Pedido pedido = new Pedido(new DescontoPorCupom());

pedido.AdicionarItem(new ItemPedido(teclado, 1));
pedido.AdicionarItem(new ItemPedido(mouse, 2));

Console.WriteLine($"Valor total: {pedido.CalcularValorTotal()}");
Console.WriteLine($"Desconto: {pedido.CalcularDesconto()}");
Console.WriteLine($"Valor final: {pedido.CalcularValorFinal()}");
```

Cálculo esperado:

* teclado: `250 * 1 = 250`;
* mouse: `150 * 2 = 300`;
* valor total: `250 + 300 = 550`;
* desconto por cupom: `10% de 550 = 55`;
* valor final: `550 - 55 = 495`.

Saída esperada:

```text
Valor total: 550
Desconto: 55,00
Valor final: 495,00
```

Esse exemplo mostra uma separação mais realista de responsabilidades:

* `Produto` conhece nome e preço;
* `ItemPedido` conhece produto e quantidade;
* `Pedido` conhece seus itens e calcula total;
* `ICalculadoraDesconto` representa a regra variável de desconto;
* cada estratégia concreta implementa uma regra específica.

# 14. Strategy versus herança

Uma dúvida comum é: por que não criar subclasses de `Pedido`?

Por exemplo:

```text
PedidoComCupom
PedidoComFidelidade
PedidoComCampanha
```

Essa abordagem pode parecer simples no começo. Porém, ela piora quando surgem outras variações além do desconto.

Imagine que o pedido também varie por:

* tipo de entrega;
* forma de pagamento;
* tipo de cliente;
* regra de imposto;
* regra de desconto.

Com herança, poderíamos acabar criando nomes como:

```text
PedidoClienteVipComCupomEntregaExpressa
PedidoClienteComumSemDescontoEntregaNormal
PedidoClienteParceiroComCampanhaEntregaRetirada
```

Isso é um sinal de hierarquia artificial. O número de subclasses cresce por combinação, não por necessidade real.

Com Strategy, cada dimensão de variação pode ser separada:

```csharp
public interface ICalculadoraDesconto
{
    decimal Calcular(decimal valor);
}
```

```csharp
public interface ICalculadoraFrete
{
    decimal CalcularFrete(Pedido pedido);
}
```

```csharp
public interface ICalculadoraImposto
{
    decimal CalcularImposto(Pedido pedido);
}
```

Assim, desconto, frete e imposto podem variar de forma independente. O sistema fica mais flexível sem criar uma explosão de subclasses.

---

# 15. Quando usar Strategy

O Strategy faz sentido quando existe uma família de algoritmos ou regras que compartilham uma intenção, mas têm implementações diferentes.

Use Strategy quando:

* há várias formas de executar uma mesma operação;
* a classe principal tem muitos condicionais escolhendo comportamentos;
* novas variações podem surgir;
* as regras precisam ser testadas separadamente;
* a classe principal não deveria conhecer todas as implementações;
* existe polimorfismo real;
* a regra variável é importante o suficiente para merecer uma abstração.

Exemplos adequados:

* cálculo de desconto;
* cálculo de frete;
* cálculo de imposto;
* validação de documentos;
* exportação de relatórios;
* classificação de desempenho;
* cálculo de juros por tipo de contrato.

---

# 16. Quando não usar Strategy

Nem todo `if` precisa virar Strategy.

Não use Strategy quando:

* existe apenas uma regra simples;
* a variação dificilmente existirá;
* a interface não resolve um problema claro;
* o código ficará mais complexo sem necessidade;
* o `if` é apenas uma validação básica.

Exemplo de validação que não precisa virar Strategy:

```csharp
if (valorTotal <= 0)
{
    throw new ArgumentException("Valor total inválido.");
}
```

Esse `if` não representa uma família de algoritmos. Ele apenas protege uma regra básica de validade. Criar uma estratégia para isso tornaria o código artificialmente complexo.

O bom uso do Strategy exige equilíbrio. O padrão deve resolver um problema real, não ser aplicado apenas para “usar padrão de projeto”.

# 17. Strategy em outros contextos

O Strategy não serve apenas para desconto. Ele pode ser usado em qualquer comportamento variável.

## 17.1 Validação de documentos

A intenção geral é validar um documento. As variações podem ser CPF, CNPJ ou matrícula institucional.

```csharp
public interface IValidadorDocumento
{
    bool Validar(string documento);
}
```

```csharp
public class ValidadorCpf : IValidadorDocumento
{
    public bool Validar(string documento)
    {
        return !string.IsNullOrEmpty(documento) && documento.Length == 11;
    }
}
```

```csharp
public class ValidadorCnpj : IValidadorDocumento
```

Esse exemplo é simplificado. Ele verifica apenas o tamanho do documento. Em um sistema real, a validação poderia incluir dígitos verificadores e outras regras.

# 20. Aplicação prática resolvida: escolhendo Strategy para cálculo de frete

## Cenário

Um sistema de vendas precisa calcular frete de três formas:

* frete normal: 5% do valor do pedido;
* frete expresso: 12% do valor do pedido;
* retirada no local: sem cobrança de frete.

A classe `Pedido` não deve conter vários `if` para decidir qual frete aplicar.

## Objetivo

Aplicar o padrão Strategy para separar as regras de frete em classes independentes.

## Solução

Primeiro, criamos a interface:

```csharp
public interface ICalculadoraFrete
{
    decimal Calcular(decimal valorPedido);
}
```

Agora criamos as estratégias concretas:

```csharp
public class FreteNormal : ICalculadoraFrete
{
    public decimal Calcular(decimal valorPedido)
    {
        return valorPedido * 0.05m;
    }
}
```

```csharp
public class FreteExpresso : ICalculadoraFrete
{
    public decimal Calcular(decimal valorPedido)
    {
        return valorPedido * 0.12m;
    }
}
```

```csharp
public class RetiradaNoLocal : ICalculadoraFrete
{
    public decimal Calcular(decimal valorPedido)
    {
        return 0;
    }
}
```

Agora uma classe pode usar a estratégia:

```csharp
public class SimuladorEntrega
{
    private readonly ICalculadoraFrete _calculadoraFrete;

    public SimuladorEntrega(ICalculadoraFrete calculadoraFrete)
    {
        _calculadoraFrete = calculadoraFrete
            ?? throw new ArgumentNullException(nameof(calculadoraFrete));
    }

    public decimal CalcularFrete(decimal valorPedido)
    {
        if (valorPedido <= 0)
        {
            throw new ArgumentException("Valor do pedido inválido.");
        }

        return _calculadoraFrete.Calcular(valorPedido);
    }
}
```

Uso:

```csharp
SimuladorEntrega simulador = new SimuladorEntrega(new FreteExpresso());

decimal frete = simulador.CalcularFrete(500);

Console.WriteLine($"Frete: {frete}");
```

Resultado esperado:

```text
Frete: 60,00
```

## Comentário da solução

O valor do pedido é `500`. O frete expresso cobra 12%. Portanto:

```text
500 * 0,12 = 60
```

A classe `SimuladorEntrega` não sabe se o frete é normal, expresso ou retirada. Ela apenas usa a interface `ICalculadoraFrete`.

## Como validar

A validação pode ser feita testando cada estratégia:

```csharp
Console.WriteLine(new FreteNormal().Calcular(500));      // 25
Console.WriteLine(new FreteExpresso().Calcular(500));    // 60
Console.WriteLine(new RetiradaNoLocal().Calcular(500));  // 0
```

Se os valores forem `25`, `60` e `0`, as regras básicas estão funcionando.

## Possíveis erros

Um erro comum seria colocar a escolha do frete dentro de `SimuladorEntrega` usando strings:

```csharp
if (tipoFrete == "EXPRESSO")
```

Isso volta ao problema original. O objetivo do Strategy é evitar que a classe principal conheça todas as variações concretas.

# 21. Erros comuns e dúvidas frequentes

## Erro 1: usar Strategy para qualquer `if`

Nem todo condicional é um problema. Validações simples, como verificar se um valor é maior que zero, não precisam virar estratégia.

Strategy deve ser usado para comportamentos variáveis, não para qualquer decisão pequena.

## Erro 2: deixar a classe principal escolher a estratégia por string

Se a classe principal faz isso:

```csharp
if (tipoDesconto == "CUPOM")
{
    _calculadoraDesconto = new DescontoPorCupom();
}
```

ela continua conhecendo as implementações concretas. Nesse caso, parte do problema permanece.

A escolha da estratégia pode ficar em outro ponto do sistema, como uma camada de aplicação, uma factory ou uma configuração. O importante é que a classe principal não fique cheia de regras concretas.

## Erro 3: usar herança quando a relação correta é composição

Um pedido não é um desconto. Um pedido usa uma regra de desconto.

Quando a frase correta for “usa um”, composição costuma fazer mais sentido. Quando a frase correta for “é um”, herança pode fazer sentido. No caso do Strategy, a composição é a base do padrão.

## Erro 4: criar interfaces sem variação real

Criar uma interface com apenas uma implementação e sem previsão realista de variação pode tornar o código mais complexo sem benefício.

Antes de aplicar Strategy, pergunte:

> existe uma família real de regras ou algoritmos?

Se a resposta for não, talvez o Strategy não seja necessário.

## Erro 5: não validar dados de entrada

Mesmo usando Strategy, as classes ainda precisam proteger suas invariantes.

Exemplo:

```csharp
if (percentual < 0 || percentual > 1)
{
    throw new ArgumentException("Percentual inválido.");
}
```

Essa validação impede que uma estratégia percentual seja criada com valores inválidos.

## Erro 6: colocar a regra no lugar errado

A estratégia deve calcular o desconto. O pedido deve proteger o valor final. Produto deve validar preço e nome. ItemPedido deve validar quantidade.

Quando cada regra fica no lugar adequado, o sistema fica mais fácil de entender e manter.

# 22. Checklist explicado de compreensão

## Verifique se existe uma família de regras variáveis

Antes de aplicar Strategy, identifique se existe uma operação geral com várias formas de execução. No exemplo de descontos, a operação geral é calcular desconto, e as variações são cupom, fidelidade, campanha e outras. Isso importa porque Strategy só faz sentido quando há variação real. Para validar, tente descrever as regras em uma frase comum: “todas calculam desconto, mas cada uma calcula de um jeito”. Se não houver essa família de regras, o padrão pode ser desnecessário.

## Verifique se a regra variável foi representada por uma interface

A interface é o contrato que permite o polimorfismo. No exemplo, `ICalculadoraDesconto` define o método `Calcular`. Isso importa porque a classe principal deve depender da abstração, não das implementações concretas. Para validar, veja se `Pedido` usa `ICalculadoraDesconto` em vez de usar diretamente `DescontoPorCupom` ou `DescontoPorFidelidade`. Se a classe principal depender de classes concretas, a flexibilidade diminui.

## Verifique se cada estratégia concreta tem uma responsabilidade clara

Cada classe concreta deve implementar uma regra específica. `DescontoPorCupom` calcula desconto por cupom. `SemDesconto` retorna zero. `DescontoPercentual` usa um percentual configurável. Isso importa porque classes pequenas são mais fáceis de testar e corrigir. Para validar, leia cada classe e veja se ela faz apenas uma coisa. Se uma estratégia tiver vários `if` para decidir outras regras, talvez ela esteja acumulando responsabilidades.

## Verifique se a classe principal usa composição

A classe principal deve receber ou possuir uma estratégia. No exemplo, `Pedido` possui uma dependência de `ICalculadoraDesconto`. Isso importa porque o pedido usa uma regra de desconto, mas não é um tipo de desconto. Para validar, procure a dependência privada da interface e veja se ela é usada no cálculo. Se a solução usa herança artificial, pode haver risco de crescimento excessivo de subclasses.

## Verifique se o polimorfismo realmente acontece

O polimorfismo ocorre quando o mesmo método é chamado em objetos diferentes e cada objeto responde de acordo com sua própria implementação. No exemplo, o método `Calcular` existe em várias estratégias. Isso importa porque o Strategy depende desse comportamento para substituir condicionais. Para validar, crie uma lista de `ICalculadoraDesconto` com várias estratégias e chame `Calcular` em cada uma. Se cada objeto retorna um resultado diferente usando o mesmo contrato, o polimorfismo está funcionando.

## Verifique se novas regras podem ser adicionadas sem alterar a classe principal

Uma das principais vantagens do Strategy é permitir extensão. Para validar, tente adicionar `DescontoPorPrimeiraCompra`. Se você conseguir criar uma nova classe sem modificar `Pedido`, a estrutura está bem aplicada. Se toda nova regra obriga alteração em `Pedido`, o padrão não foi usado corretamente.

## Verifique se validações simples não foram transformadas em Strategy sem necessidade

Validações como `valor <= 0` não representam uma família de algoritmos. Isso importa porque aplicar padrão demais pode deixar o código difícil de entender. Para validar, revise os pontos em que há `if`. Pergunte se o `if` representa uma variação de comportamento ou apenas uma proteção básica. Se for apenas validação, não há necessidade de Strategy.

## Verifique se a ausência de comportamento foi modelada de forma explícita

No caso de desconto, a ausência de desconto pode ser representada por `SemDesconto`. Isso importa porque evita o uso de `null` e reduz verificações extras. Para validar, crie um pedido com `new SemDesconto()` e confirme que o valor final permanece igual ao valor total. Se o código precisa testar `null` a todo momento, a modelagem pode ser melhorada.

# 23. Síntese final

O padrão Strategy organiza comportamentos variáveis em classes separadas. Em C#, ele costuma ser implementado com:

* uma interface que representa o contrato da regra;
* várias classes concretas que implementam esse contrato;
* uma classe principal que usa a interface por composição;
* polimorfismo em tempo de execução para executar a regra correta.

No exemplo de descontos, `ICalculadoraDesconto` representa a regra geral. Classes como `DescontoPorCupom`, `DescontoPorFidelidade`, `DescontoPorCampanha`, `SemDesconto` e `DescontoPercentual` representam variações específicas. A classe `Pedido` usa a interface sem conhecer os detalhes de cada regra.

Essa organização reduz condicionais excessivos, melhora a separação de responsabilidades, facilita testes e permite adicionar novas regras com menor risco de afetar comportamentos antigos.

---

# Conclusão

O Strategy é uma solução adequada quando uma regra de negócio possui várias formas de execução e essas formas podem crescer ou mudar. Ele ajuda a transformar condicionais repetitivos em polimorfismo, tornando o código mais organizado e flexível.

Ao aplicar Strategy, o mais importante não é apenas criar uma interface e várias classes. O mais importante é posicionar corretamente as responsabilidades: a estratégia calcula a regra variável, a classe principal usa a estratégia por composição e cada objeto protege as regras que pertencem ao seu próprio contexto.

Usado com critério, o Strategy melhora a manutenção do sistema. Usado sem necessidade, ele pode aumentar a complexidade. Por isso, a decisão técnica deve sempre partir do problema real: existe uma família de comportamentos variáveis que precisa ser organizada? Se sim, Strategy é uma excelente opção.
