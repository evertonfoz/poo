# Repository e Service como preparação para acesso a dados em C#

## Objetivo do material

Neste material, você aprenderá a organizar uma aplicação orientada a objetos em C# usando **Repository** e **Service** antes de introduzir banco de dados. A ideia central é separar responsabilidades para que a aplicação deixe de concentrar leitura de dados, regras de negócio, criação de objetos e armazenamento diretamente no `Program.cs`. Essa preparação facilita a evolução futura para uma camada de acesso a dados, como DAL com SQLite, sem reescrever toda a lógica da aplicação. O conteúdo foi estruturado a partir do material-base sobre Repository e Service em C# .

Ao final, você deverá compreender:

* o papel de uma entidade no domínio;
* o papel de um Repository;
* o papel de um Service;
* a diferença entre entidade, Repository, Service, DAL e `Program.cs`;
* por que usar interfaces para repositórios;
* como criar um repositório em memória;
* como preparar a aplicação para trocar armazenamento em memória por SQLite no futuro.

---

# 1. O problema: quando o `Program.cs` faz coisas demais

Em aplicações pequenas, é comum começar com tudo dentro do `Program.cs`. Por exemplo, o programa lê dados do console, valida se os campos estão preenchidos, cria um objeto `Aluno`, adiciona esse objeto a uma lista e exibe os resultados.

Esse tipo de código pode funcionar em exercícios iniciais, mas cria um problema importante: **mistura de responsabilidades**.

Um `Program.cs` sobrecarregado pode acabar fazendo ao mesmo tempo:

* leitura de dados do usuário;
* validação de regras de negócio;
* criação de entidades;
* armazenamento em listas;
* consulta de objetos;
* alteração e remoção de dados;
* exibição de mensagens;
* futuramente, abertura de conexão com banco e execução de SQL.

O problema fica maior quando a aplicação precisa usar banco de dados. Se comandos SQL forem colocados diretamente no `Program.cs`, a interface com o usuário, a regra de negócio e o acesso a dados ficam misturados no mesmo lugar.

Exemplo de código problemático em um fluxo principal:

```csharp
using var connection = new SqlConnection("Data Source=escola.db");
connection.Open();

var command = connection.CreateCommand();
command.CommandText = @"
INSERT INTO alunos (nome, matricula)
VALUES ($nome, $matricula)
";

command.Parameters.AddWithValue("$nome", nome);
command.Parameters.AddWithValue("$matricula", matricula);
command.ExecuteNonQuery();
```

Esse trecho salva dados no banco, mas não deveria estar no fluxo principal da aplicação. O `Program.cs` deveria iniciar a aplicação, chamar serviços e apresentar resultados, não conhecer detalhes de persistência.

Quando esse acoplamento acontece, qualquer mudança no banco, nas regras ou na forma de armazenamento obriga alterações em várias partes do sistema.

# 2. Separação de responsabilidades

Separar responsabilidades significa definir claramente o papel de cada parte do sistema. Em uma aplicação orientada a objetos organizada, cada camada deve ter uma função específica.

Uma divisão possível é:

| Parte        | Responsabilidade principal                                           |
| ------------ | -------------------------------------------------------------------- |
| Entidade     | Representa um conceito do domínio e protege seu próprio estado       |
| Repository   | Organiza operações de armazenamento e recuperação de objetos         |
| Service      | Coordena casos de uso e regras que envolvem fluxos da aplicação      |
| DAL          | Executa detalhes técnicos de acesso ao banco de dados                |
| `Program.cs` | Inicia a aplicação, coleta dados, chama serviços e mostra resultados |

Neste material, o foco está em **Repository** e **Service**. A DAL será importante quando o projeto começar a usar SQLite ou outro banco de dados.

---

# 3. Entidade: o coração do domínio

Uma **entidade** representa um conceito importante do sistema. Em um sistema escolar, por exemplo, `Aluno` pode ser uma entidade. Em um sistema de biblioteca, `Livro` pode ser uma entidade. Em um sistema de vendas, `Produto` ou `Pedido` podem ser entidades.

A entidade deve proteger os dados que fazem parte do seu estado. Isso significa que ela não deve aceitar valores inválidos quando for criada ou alterada.

Exemplo de entidade `Aluno`:

```csharp
public class Aluno
{
    public int Id { get; private set; }
    public string Nome { get; private set; }
    public string Matricula { get; private set; }

    public Aluno(int id, string nome, string matricula)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("Nome inválido.");

        if (string.IsNullOrWhiteSpace(matricula))
            throw new ArgumentException("Matrícula inválida.");

        Id = id;
        Nome = nome;
        Matricula = matricula;
    }

    public static Aluno CriarNovo(string nome, string matricula)
    {
        return new Aluno(0, nome, matricula);
    }

    public void AlterarNome(string novoNome)
    {
        if (string.IsNullOrWhiteSpace(novoNome))
            throw new ArgumentException("Nome inválido.");

        Nome = novoNome;
    }
}
```

Esse código possui alguns pontos importantes.

A propriedade `Id` tem `private set`, porque o identificador do aluno não deve ser alterado livremente por qualquer parte do sistema. O mesmo vale para `Nome` e `Matricula`: eles só podem ser definidos pelo construtor ou por métodos específicos.

O construtor valida se `nome` e `matricula` são válidos. Isso impede que um aluno seja criado em estado inválido.

O método `AlterarNome` permite mudar o nome, mas mantém a validação. Assim, a entidade continua protegendo seu próprio estado.

A entidade **não deve** abrir conexão com banco, executar SQL, ler teclado, exibir menu ou salvar a si mesma. Ela representa o domínio, não a infraestrutura.

# 4. O que é Repository

**Repository** é um padrão usado para organizar o acesso a objetos armazenados ou persistidos. Ele funciona como uma abstração de uma coleção de objetos do domínio.

Em vez de espalhar listas, comandos SQL ou detalhes de armazenamento pelo sistema, o Repository concentra operações como:

* adicionar um objeto;
* buscar por identificador;
* buscar por algum atributo importante;
* listar objetos;
* atualizar um objeto;
* remover um objeto.

No caso de alunos, o repositório pode oferecer operações como:

```csharp
void Adicionar(Aluno aluno);
Aluno? ObterPorId(int id);
Aluno? ObterPorMatricula(string matricula);
IReadOnlyCollection<Aluno> Listar();
void Atualizar(Aluno aluno);
void Remover(int id);
```

O Repository não é a entidade. A entidade `Aluno` representa um aluno. O Repository representa o mecanismo de armazenamento e recuperação de alunos.

A entidade responde à pergunta: “O que é um aluno e quais regras protegem seus dados?”

O Repository responde à pergunta: “Como armazenar, localizar, listar, atualizar e remover alunos?”

---

# 5. Por que criar uma interface para o Repository

Uma interface define um contrato. Ela diz **o que** uma classe deve fazer, mas não diz **como** ela fará.

Exemplo:

```csharp
public interface IAlunoRepository
{
    void Adicionar(Aluno aluno);
    Aluno? ObterPorId(int id);
    Aluno? ObterPorMatricula(string matricula);
    IReadOnlyCollection<Aluno> Listar();
    void Atualizar(Aluno aluno);
    void Remover(int id);
}
```

Essa interface define as operações necessárias para lidar com alunos. Porém, ela não informa se os dados serão armazenados em lista, arquivo, SQLite, SQL Server, PostgreSQL ou qualquer outro mecanismo.

Isso é importante porque o restante da aplicação pode depender da interface `IAlunoRepository`, e não de uma implementação concreta.

Hoje, a aplicação pode usar:

```csharp
IAlunoRepository alunoRepository = new AlunoRepositoryEmMemoria();
```

No futuro, poderá usar:

```csharp
IAlunoRepository alunoRepository = new SqliteAlunoRepository();
```

Se as duas classes respeitarem a mesma interface, o `AlunoService` poderá continuar igual. Esse é o poder da abstração: trocar a tecnologia de armazenamento sem reescrever a lógica do caso de uso.

# 6. Repository em memória

Antes de usar SQLite, é útil criar um repositório em memória. Ele armazena os objetos em uma lista interna. Isso ajuda a aprender o padrão Repository sem misturar banco de dados no início.

Exemplo:

```csharp
public class AlunoRepositoryEmMemoria : IAlunoRepository
{
    private readonly List<Aluno> _alunos = new List<Aluno>();
    private int _proximoId = 1;

    public void Adicionar(Aluno aluno)
    {
        if (aluno == null)
            throw new ArgumentNullException(nameof(aluno));

        Aluno alunoComId = new Aluno(
            _proximoId,
            aluno.Nome,
            aluno.Matricula
        );

        _alunos.Add(alunoComId);
        _proximoId++;
    }

    public Aluno? ObterPorId(int id)
    {
        return _alunos.FirstOrDefault(a => a.Id == id);
    }

    public Aluno? ObterPorMatricula(string matricula)
    {
        return _alunos.FirstOrDefault(a => a.Matricula == matricula);
    }

    public IReadOnlyCollection<Aluno> Listar()
    {
        return _alunos.AsReadOnly();
    }

    public void Atualizar(Aluno aluno)
    {
        Aluno? existente = ObterPorId(aluno.Id);

        if (existente == null)
            throw new InvalidOperationException("Aluno não encontrado.");

        existente.AlterarNome(aluno.Nome);
    }

    public void Remover(int id)
    {
        Aluno? aluno = ObterPorId(id);

        if (aluno == null)
            throw new InvalidOperationException("Aluno não encontrado.");

        _alunos.Remove(aluno);
    }
}
```

Nesse código, a lista `_alunos` é privada. Isso é importante porque impede que outras partes do sistema manipulem diretamente a coleção.

Sem Repository, alguém poderia fazer:

```csharp
List<Aluno> alunos = new List<Aluno>();

alunos.Clear();
alunos.Add(null);
alunos.RemoveAt(0);
```

Esse tipo de acesso direto torna a aplicação frágil. Qualquer parte do sistema poderia apagar todos os alunos, inserir valores inválidos ou remover itens sem validação.

Com Repository, as operações ficam controladas. A aplicação só pode manipular alunos pelos métodos definidos no contrato.

# 7. O que é Service

**Service** é uma classe que coordena um caso de uso da aplicação.

Enquanto a entidade protege regras internas de um objeto, o Service organiza fluxos que normalmente envolvem várias etapas.

O caso de uso “Cadastrar aluno”, por exemplo, pode envolver:

1. receber nome e matrícula;
2. verificar se já existe aluno com a matrícula informada;
3. criar o objeto `Aluno`;
4. enviar o objeto para o Repository;
5. tratar erros de duplicidade ou dados inválidos.

Essas etapas não devem ficar todas no `Program.cs`, porque são regras da aplicação. Também não devem ficar dentro da entidade `Aluno`, porque a entidade não deve consultar repositórios.

Por isso, criamos um Service.

---

# 8. Criando o `AlunoService`

O `AlunoService` depende de `IAlunoRepository`. Isso significa que ele não sabe se os alunos estão em memória, em arquivo ou em SQLite.

```csharp
public class AlunoService
{
    private readonly IAlunoRepository _alunoRepository;

    public AlunoService(IAlunoRepository alunoRepository)
    {
        _alunoRepository = alunoRepository
            ?? throw new ArgumentNullException(nameof(alunoRepository));
    }

    public void CadastrarAluno(string nome, string matricula)
    {
        Aluno? alunoExistente =
            _alunoRepository.ObterPorMatricula(matricula);

        if (alunoExistente != null)
            throw new InvalidOperationException("Matrícula já cadastrada.");

        Aluno aluno = Aluno.CriarNovo(nome, matricula);

        _alunoRepository.Adicionar(aluno);
    }

    public IReadOnlyCollection<Aluno> ListarAlunos()
    {
        return _alunoRepository.Listar();
    }

    public void AlterarNome(int id, string novoNome)
    {
        Aluno? aluno = _alunoRepository.ObterPorId(id);

        if (aluno == null)
            throw new InvalidOperationException("Aluno não encontrado.");

        aluno.AlterarNome(novoNome);

        _alunoRepository.Atualizar(aluno);
    }

    public void RemoverAluno(int id)
    {
        Aluno? aluno = _alunoRepository.ObterPorId(id);

        if (aluno == null)
            throw new InvalidOperationException("Aluno não encontrado.");

        _alunoRepository.Remover(id);
    }
}
```

O método `CadastrarAluno` mostra bem o papel do Service. Ele verifica duplicidade de matrícula antes de criar o aluno. Essa regra depende de uma consulta ao repositório, então faz sentido estar no Service.

O método `AlterarNome` busca o aluno, verifica se ele existe, pede para a própria entidade alterar o nome e depois solicita ao repositório que atualize o registro.

O método `RemoverAluno` também coordena o caso de uso: primeiro verifica se o aluno existe, depois chama o Repository para remover.

# 9. `Program.cs` usando Service

Com Repository e Service, o `Program.cs` fica mais simples. Ele não precisa conhecer a lista interna nem as regras de cadastro.

```csharp
IAlunoRepository alunoRepository = new AlunoRepositoryEmMemoria();
AlunoService alunoService = new AlunoService(alunoRepository);

try
{
    alunoService.CadastrarAluno("Carlos", "2026001");
    alunoService.CadastrarAluno("Marina", "2026002");

    IReadOnlyCollection<Aluno> alunos = alunoService.ListarAlunos();

    foreach (Aluno aluno in alunos)
    {
        Console.WriteLine($"{aluno.Id} - {aluno.Nome} - {aluno.Matricula}");
    }
}
catch (Exception ex)
{
    Console.WriteLine(ex.Message);
}
```

Nesse fluxo, o `Program.cs` faz apenas três coisas principais.

Primeiro, instancia as dependências necessárias. Ele cria um Repository concreto e passa esse Repository para o Service.

Depois, chama os métodos do Service para executar casos de uso.

Por fim, exibe resultados ou mensagens de erro.

Essa separação deixa a aplicação mais fácil de manter. Se o repositório em memória for trocado por SQLite, a lógica de cadastro, alteração e remoção não precisa ser reescrita.

# 10. Diferença entre Repository e DAL

Repository e DAL estão relacionados, mas não são exatamente a mesma coisa.

O **Repository** fala a linguagem do domínio. Ele trabalha com entidades e operações significativas para a aplicação.

Exemplo:

```csharp
Aluno? ObterPorMatricula(string matricula);
IReadOnlyCollection<Aluno> Listar();
void Adicionar(Aluno aluno);
```

Essas operações fazem sentido para quem pensa no domínio escolar. O Repository trabalha com objetos como `Aluno`.

A **DAL**, ou Data Access Layer, é uma camada mais técnica. Ela lida diretamente com detalhes de banco de dados, como:

* abrir conexão;
* fechar conexão;
* executar comandos SQL;
* mapear registros do banco para objetos;
* tratar detalhes específicos do mecanismo de persistência.

Em projetos pequenos, a implementação concreta do Repository pode conter o código de acesso a dados. Por exemplo, uma classe `SqliteAlunoRepository` pode implementar `IAlunoRepository` e executar comandos SQL internamente.

Em projetos mais organizados, pode existir uma separação maior:

```text
IAlunoRepository
SqliteAlunoRepository
DatabaseConnection
AlunoDal
```

Nesse caso, o Repository continua oferecendo operações de domínio, enquanto a DAL cuida dos detalhes técnicos do banco.

# 11. Limites de cada camada

Uma boa organização depende de respeitar os limites de cada parte do sistema.

## Entidade

A entidade deve representar um conceito do domínio e proteger seu próprio estado.

Ela pode:

* validar seus próprios dados;
* impedir estado inválido;
* oferecer métodos de alteração controlada;
* representar regras internas do objeto.

Ela não deve:

* ler dados do teclado;
* exibir menu;
* acessar Repository;
* abrir conexão com banco;
* executar SQL;
* salvar a si mesma no banco.

Quando uma entidade acessa diretamente um Repository, ela passa a depender de persistência. Isso cria acoplamento e dificulta testes, manutenção e evolução.

## Repository

O Repository deve organizar operações de armazenamento e recuperação.

Ele pode:

* adicionar;
* buscar;
* listar;
* atualizar;
* remover.

Ele não deve concentrar regras de negócio complexas. Por exemplo, a regra “não cadastrar aluno com matrícula duplicada” não deve ficar como responsabilidade principal do Repository. O Repository pode permitir buscar por matrícula, mas quem decide se o cadastro pode continuar é o Service.

## Service

O Service coordena casos de uso.

Ele pode:

* verificar duplicidade antes de cadastrar;
* buscar entidade antes de alterar;
* coordenar chamadas ao Repository;
* aplicar regras que envolvem mais de uma etapa;
* organizar o fluxo da aplicação.

Ele não deve virar uma classe gigante com tudo dentro. Regras internas da entidade devem permanecer na entidade. Regras técnicas de banco devem permanecer no Repository ou na DAL.

## `Program.cs`

O `Program.cs` deve ser o ponto de entrada da aplicação.

Ele pode:

* iniciar dependências;
* chamar serviços;
* receber dados do usuário;
* exibir resultados.

Ele não deve concentrar regras de negócio, manipular listas diretamente ou executar comandos SQL.

# 12. Organização em pastas ou projetos

Uma aplicação pode ser organizada em projetos separados ou em pastas. O importante é deixar claro onde cada responsabilidade fica.

Exemplo com projetos:

```text
Escola/
├── Escola.Dominio/
│   ├── Entidades/
│   │   └── Aluno.cs
│   └── Repositorios/
│       └── IAlunoRepository.cs
├── Escola.Aplicacao/
│   └── AlunoService.cs
├── Escola.DAL/
│   └── AlunoRepositoryEmMemoria.cs
└── Escola.ConsoleApp/
    └── Program.cs
```

Exemplo com pastas em um único projeto:

```text
Projeto/
├── Dominio/
│   ├── Entidades/
│   │   └── Aluno.cs
│   └── Repositorios/
│       └── IAlunoRepository.cs
├── Aplicacao/
│   └── AlunoService.cs
├── Infraestrutura/
│   └── AlunoRepositoryEmMemoria.cs
└── Program.cs
```

Em projetos menores, usar pastas já ajuda bastante. Em projetos maiores, separar em projetos diferentes pode deixar as dependências mais controladas.

Uma organização comum é:

* domínio não depende de infraestrutura;
* aplicação depende do domínio;
* infraestrutura implementa contratos definidos no domínio;
* console app usa aplicação e infraestrutura para executar o programa.

---

# 13. Fluxo completo da aplicação

Com Repository e Service, o fluxo atual em memória pode ser entendido assim:

```text
Program.cs
    chama AlunoService
        usa IAlunoRepository
            implementado por AlunoRepositoryEmMemoria
                armazena em List<Aluno>
```

No futuro, com SQLite, o fluxo pode ficar assim:

```text
Program.cs
    chama AlunoService
        usa IAlunoRepository
            implementado por SqliteAlunoRepository
                acessa SQLite
```

O ponto principal é que `AlunoService` continua dependendo da interface `IAlunoRepository`.

A implementação concreta muda, mas o contrato permanece.

# 14. Aplicação prática resolvida: cadastro de livros com Repository e Service

## Cenário

Uma aplicação precisa cadastrar livros. Cada livro possui título, autor e ISBN. O ISBN não pode se repetir, porque identifica uma edição específica de um livro.

## Objetivo

Criar uma estrutura com:

* entidade `Livro`;
* interface `ILivroRepository`;
* implementação `LivroRepositoryEmMemoria`;
* classe `LivroService`;
* uso no `Program.cs`.

## Solução

### Entidade `Livro`

```csharp
public class Livro
{
    public int Id { get; private set; }
    public string Titulo { get; private set; }
    public string Autor { get; private set; }
    public string Isbn { get; private set; }

    public Livro(int id, string titulo, string autor, string isbn)
    {
        if (string.IsNullOrWhiteSpace(titulo))
            throw new ArgumentException("Título inválido.");

        if (string.IsNullOrWhiteSpace(autor))
            throw new ArgumentException("Autor inválido.");

        if (string.IsNullOrWhiteSpace(isbn))
            throw new ArgumentException("ISBN inválido.");

        Id = id;
        Titulo = titulo;
        Autor = autor;
        Isbn = isbn;
    }

    public static Livro CriarNovo(string titulo, string autor, string isbn)
    {
        return new Livro(0, titulo, autor, isbn);
    }

    public void AlterarTitulo(string novoTitulo)
    {
        if (string.IsNullOrWhiteSpace(novoTitulo))
            throw new ArgumentException("Título inválido.");

        Titulo = novoTitulo;
    }
}
```

A entidade `Livro` protege seus próprios dados. Ela não permite título, autor ou ISBN vazios.

A regra de ISBN duplicado não está dentro da entidade, porque a entidade sozinha não conhece os outros livros cadastrados. Para saber se um ISBN já existe, é necessário consultar o repositório. Por isso, essa regra ficará no Service.

### Interface `ILivroRepository`

```csharp
public interface ILivroRepository
{
    void Adicionar(Livro livro);
    Livro? ObterPorId(int id);
    Livro? ObterPorIsbn(string isbn);
    IReadOnlyCollection<Livro> Listar();
    void Atualizar(Livro livro);
    void Remover(int id);
}
```

A interface define o contrato de armazenamento de livros. Ela não diz se os dados estão em lista, arquivo ou banco.

### Repository em memória

```csharp
public class LivroRepositoryEmMemoria : ILivroRepository
{
    private readonly List<Livro> _livros = new List<Livro>();
    private int _proximoId = 1;

    public void Adicionar(Livro livro)
    {
        if (livro == null)
            throw new ArgumentNullException(nameof(livro));

        Livro livroComId = new Livro(
            _proximoId,
            livro.Titulo,
            livro.Autor,
            livro.Isbn
        );

        _livros.Add(livroComId);
        _proximoId++;
    }

    public Livro? ObterPorId(int id)
    {
        return _livros.FirstOrDefault(l => l.Id == id);
    }

    public Livro? ObterPorIsbn(string isbn)
    {
        return _livros.FirstOrDefault(l => l.Isbn == isbn);
    }

    public IReadOnlyCollection<Livro> Listar()
    {
        return _livros.AsReadOnly();
    }

    public void Atualizar(Livro livro)
    {
        Livro? existente = ObterPorId(livro.Id);

        if (existente == null)
            throw new InvalidOperationException("Livro não encontrado.");

        existente.AlterarTitulo(livro.Titulo);
    }

    public void Remover(int id)
    {
        Livro? livro = ObterPorId(id);

        if (livro == null)
            throw new InvalidOperationException("Livro não encontrado.");

        _livros.Remove(livro);
    }
}
```

A lista `_livros` é privada. Isso impede manipulação externa direta e protege a coleção contra operações indevidas.

### Service

```csharp
public class LivroService
{
    private readonly ILivroRepository _livroRepository;

    public LivroService(ILivroRepository livroRepository)
    {
        _livroRepository = livroRepository
            ?? throw new ArgumentNullException(nameof(livroRepository));
    }

    public void CadastrarLivro(string titulo, string autor, string isbn)
    {
        Livro? existente = _livroRepository.ObterPorIsbn(isbn);

        if (existente != null)
            throw new InvalidOperationException("ISBN já cadastrado.");

        Livro livro = Livro.CriarNovo(titulo, autor, isbn);

        _livroRepository.Adicionar(livro);
    }

    public IReadOnlyCollection<Livro> ListarLivros()
    {
        return _livroRepository.Listar();
    }

    public void AlterarTitulo(int id, string novoTitulo)
    {
        Livro? livro = _livroRepository.ObterPorId(id);

        if (livro == null)
            throw new InvalidOperationException("Livro não encontrado.");

        livro.AlterarTitulo(novoTitulo);

        _livroRepository.Atualizar(livro);
    }

    public void RemoverLivro(int id)
    {
        Livro? livro = _livroRepository.ObterPorId(id);

        if (livro == null)
            throw new InvalidOperationException("Livro não encontrado.");

        _livroRepository.Remover(id);
    }
}
```

O Service coordena o caso de uso. Ele verifica se o ISBN já existe antes de cadastrar. Essa regra depende de consulta ao repositório, então não pertence somente à entidade.

### Uso no `Program.cs`

```csharp
ILivroRepository livroRepository = new LivroRepositoryEmMemoria();
LivroService livroService = new LivroService(livroRepository);

try
{
    livroService.CadastrarLivro(

    }
}
catch (Exception ex)

    Console.WriteLine(ex.Message);

```

## Resultado esperado

A aplicação deve cadastrar dois livros e listar seus dados no console.

Uma saída possível seria:

```text
1 - Programação Orientada a Objetos - Roberto Lima - 978-85-0000-001-1
2 - Introdução a C# - Fernanda Torres - 978-85-0000-002-8
```

## Como validar

A implementação está correta se:

* livros com título, autor ou ISBN vazios geram erro;
* livros com ISBN repetido não são cadastrados;
* o `Program.cs` não manipula lista diretamente;
* o `LivroService` depende de `ILivroRepository`;
* o Repository em memória implementa todas as operações da interface;
* a troca futura para SQLite exigiria criar uma nova implementação da interface, e não reescrever o Service.

## Possíveis erros

Um erro comum é colocar a verificação de ISBN duplicado no `Program.cs`. Isso funciona no início, mas espalha regra de negócio no ponto de entrada da aplicação.

Outro erro é deixar a lista pública no Repository. Isso permite que qualquer parte do sistema modifique os dados sem passar pelas operações controladas.

Também é comum colocar SQL dentro do Service. O Service deve coordenar o caso de uso, mas não deve lidar diretamente com comandos técnicos de banco.

# 15. Erros comuns e dúvidas frequentes

## “Repository é a mesma coisa que banco de dados?”

Não. Repository é uma abstração. Ele pode usar banco de dados, lista em memória, arquivo ou outro mecanismo. O papel dele é oferecer operações de armazenamento e recuperação em uma linguagem próxima do domínio.

## “Service substitui entidade?”

Não. O Service coordena casos de uso. A entidade continua responsável por proteger seu próprio estado.

Se o nome de um aluno não pode ser vazio, essa validação deve estar na entidade. Se a matrícula não pode se repetir, o Service pode coordenar essa verificação usando o Repository.

## “Posso colocar tudo no Service?”

Não é uma boa prática. Um Service muito grande vira uma classe centralizadora e difícil de manter. Ele deve coordenar fluxos, não absorver todas as responsabilidades do sistema.

## “Por que não usar `List<Aluno>` diretamente?”

Porque a lista exposta permite alterações sem controle. O Repository encapsula o armazenamento e define operações permitidas.

## “Quando entra a DAL?”

A DAL entra quando a aplicação precisa lidar com detalhes técnicos de banco de dados. Ela pode ser usada por uma implementação concreta do Repository, como `SqliteAlunoRepository`.

## “O que muda quando eu trocar memória por SQLite?”

A principal mudança deve estar na implementação concreta do Repository. O Service deve continuar dependendo da interface.

# 16. Checklist explicado de compreensão

## Verifique se a entidade representa um conceito do domínio

A entidade deve representar algo importante para o problema, como `Aluno`, `Livro`, `Produto`, `Turma` ou `Pedido`. Isso importa porque a entidade concentra dados e comportamentos ligados a esse conceito. Para validar, observe se a classe possui propriedades e métodos relacionados ao domínio. Se faltar essa clareza, a aplicação pode virar um conjunto de dados soltos sem regras bem definidas.

## Verifique se a entidade protege seu próprio estado

A entidade deve impedir valores inválidos, como nome vazio, matrícula vazia, preço negativo ou ISBN vazio. Isso importa porque objetos inválidos espalham erros pelo sistema. Para validar, tente criar uma entidade com dados inválidos e verifique se uma exceção é lançada. Se essa proteção faltar, o sistema poderá armazenar informações inconsistentes.

## Verifique se o Repository concentra operações de armazenamento

O Repository deve conter métodos como adicionar, buscar, listar, atualizar e remover. Isso importa porque evita que listas ou comandos de banco fiquem espalhados. Para validar, veja se o `Program.cs` ou o Service manipulam diretamente uma lista interna. Se manipularem, o encapsulamento do armazenamento foi quebrado.

## Verifique se existe uma interface para o Repository

A interface permite que o sistema dependa de um contrato, não de uma classe concreta. Isso importa porque facilita trocar memória por SQLite no futuro. Para validar, observe se o Service recebe `IAlunoRepository`, `ILivroRepository` ou outra interface equivalente no construtor. Se o Service depender diretamente de `AlunoRepositoryEmMemoria`, a troca de implementação será mais difícil.

## Verifique se o Service coordena casos de uso

O Service deve organizar fluxos como cadastrar, alterar, listar e remover. Isso importa porque regras que envolvem várias etapas não devem ficar no `Program.cs`. Para validar, observe se o método de cadastro verifica duplicidade, cria a entidade e chama o Repository. Se essas etapas estiverem espalhadas, a lógica da aplicação está fragmentada.

## Verifique se o `Program.cs` está simples

O `Program.cs` deve iniciar dependências, chamar serviços e exibir resultados. Isso importa porque ele é o ponto de entrada, não o centro das regras do sistema. Para validar, procure regras de negócio, listas expostas ou SQL no `Program.cs`. Se encontrar, há mistura de responsabilidades.

## Verifique se a DAL não foi confundida com Service

A DAL lida com detalhes técnicos de banco. O Service coordena casos de uso. Isso importa porque misturar SQL com regra de negócio dificulta manutenção. Para validar, veja se comandos SQL estão dentro do Service. Se estiverem, a separação entre aplicação e acesso a dados está fraca.

## Verifique se a troca de implementação é possível

A aplicação deve permitir trocar `AlunoRepositoryEmMemoria` por `SqliteAlunoRepository` mantendo o Service igual. Isso importa porque demonstra baixo acoplamento. Para validar, veja se ambas as implementações podem respeitar a mesma interface. Se a troca exigir alterar várias regras do Service, a abstração não foi bem aplicada.

# 17. Síntese final

Repository e Service ajudam a organizar aplicações orientadas a objetos antes da introdução de banco de dados.

A entidade representa o domínio e protege seus próprios dados.

O Repository abstrai o armazenamento e recuperação de objetos.

A interface do Repository permite trocar a implementação concreta sem alterar a lógica principal da aplicação.

O Service coordena casos de uso e aplica regras que envolvem consulta, validação e persistência.

O `Program.cs` deve permanecer simples, chamando serviços e exibindo resultados.

A DAL será responsável pelos detalhes técnicos do banco quando o sistema passar a usar SQLite ou outro mecanismo de persistência.

---

# Conclusão

Separar Repository, Service, entidade, DAL e `Program.cs` prepara a aplicação para crescer com menos acoplamento. Antes de usar SQLite, o repositório em memória permite praticar a organização correta das responsabilidades. Quando o banco de dados for introduzido, a aplicação já estará mais preparada: será necessário trocar a implementação concreta do Repository, enquanto a lógica dos casos de uso poderá continuar concentrada no Service.
