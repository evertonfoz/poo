# Composição versus Herança em C#

## Objetivo do material

Neste material, você aprenderá a decidir quando usar **herança**, **composição** e **interfaces** na modelagem orientada a objetos em C#. Essa decisão é importante porque influencia diretamente a flexibilidade, a clareza, a manutenção e a evolução do código.

Ao final, você deverá ser capaz de:

1. Diferenciar relações do tipo **“é um”** e **“tem um”**.
2. Identificar quando uma classe representa uma especialização real de outra.
3. Reconhecer quando uma classe apenas possui, usa ou é formada por outro objeto.
4. Evitar hierarquias artificiais criadas apenas para reaproveitamento de código.
5. Usar composição com interfaces para permitir variação de comportamento.
6. Justificar tecnicamente decisões de modelagem orientada a objetos.

Este conteúdo foi desenvolvido a partir do material-base sobre composição versus herança em C# .

---

# 1. Contextualização do problema

Na Programação Orientada a Objetos, é comum que programadores iniciantes usem **herança** como primeira solução para quase tudo. Muitas vezes, isso acontece porque duas classes possuem atributos parecidos ou porque se deseja reaproveitar métodos já existentes.

Porém, herança não deve ser usada apenas para reaproveitar código. Herança representa uma relação conceitual forte entre classes. Quando usada sem critério, ela pode criar sistemas rígidos, difíceis de alterar e com muitas subclasses desnecessárias.

Imagine um sistema de notificações. Uma modelagem baseada apenas em herança poderia gerar classes como:

```csharp
NotificacaoEmailPrioritaria
NotificacaoEmailNormal
NotificacaoSmsPrioritaria
NotificacaoSmsNormal
NotificacaoWhatsAppPrioritaria
NotificacaoWhatsAppNormal
```

O problema não é apenas o número de classes. O problema principal é que diferentes variações estão sendo misturadas na herança: canal de envio, prioridade, formato da mensagem e estratégia de tratamento de falhas. Quando novas combinações surgirem, novas subclasses precisarão ser criadas.

Nesse tipo de situação, a composição tende a produzir um modelo mais flexível.

# 2. Conceitos fundamentais

## 2.1 O que é herança?

Herança é um mecanismo da orientação a objetos em que uma classe mais específica deriva de uma classe mais geral.

A relação representada pela herança é do tipo:

> **A é um tipo de B.**

Exemplos:

```text
FuncionarioMensalista é um Funcionario.
FuncionarioHorista é um Funcionario.
ProdutoDigital é um Produto.
ProdutoFisico é um Produto.
ContaCorrente é uma ContaBancaria.
```

A herança costuma fazer sentido quando:

* existe uma generalização clara;
* as subclasses compartilham uma identidade comum;
* há comportamento comum na classe base;
* há comportamento especializado nas subclasses;
* faz sentido tratar objetos diferentes pelo mesmo tipo base;
* existe polimorfismo real.

Observe um exemplo válido:

```csharp
public abstract class Funcionario
{
    public string Nome { get; private set; }

    protected Funcionario(string nome)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("Nome inválido.");

        Nome = nome;
    }

    public abstract decimal CalcularPagamento();
}
```

Nesse caso, `Funcionario` representa um conceito geral. As subclasses poderão representar formas específicas de funcionário, cada uma com sua própria regra de pagamento.

Exemplo de subclasses:

```csharp
public class FuncionarioMensalista : Funcionario
{
    public decimal SalarioMensal { get; private set; }

    public FuncionarioMensalista(string nome, decimal salarioMensal)
        : base(nome)
    {
        if (salarioMensal <= 0)
            throw new ArgumentException("Salário mensal inválido.");

        SalarioMensal = salarioMensal;
    }

    public override decimal CalcularPagamento()
    {
        return SalarioMensal;
    }
}

public class FuncionarioHorista : Funcionario
{
    public decimal ValorHora { get; private set; }
    public int HorasTrabalhadas { get; private set; }

    public FuncionarioHorista(string nome, decimal valorHora, int horasTrabalhadas)
        : base(nome)
    {
        if (valorHora <= 0)
            throw new ArgumentException("Valor da hora inválido.");

        if (horasTrabalhadas < 0)
            throw new ArgumentException("Horas trabalhadas inválidas.");

        ValorHora = valorHora;
        HorasTrabalhadas = horasTrabalhadas;
    }

    public override decimal CalcularPagamento()
    {
        return ValorHora * HorasTrabalhadas;
    }
}
```

Uso polimórfico:

```csharp
List<Funcionario> funcionarios = new List<Funcionario>
{
    new FuncionarioMensalista("Carlos", 3000),
    new FuncionarioHorista("Marina", 80, 40)
};

foreach (Funcionario funcionario in funcionarios)
{
    Console.WriteLine(funcionario.CalcularPagamento());
}
```

O código trata todos os objetos como `Funcionario`, mas cada objeto executa sua própria versão de `CalcularPagamento`. Isso é **polimorfismo**.

## 2.2 O que é composição?

Composição é uma forma de modelagem em que um objeto possui, usa ou é formado por outro objeto.

A relação representada pela composição é do tipo:

> **A tem um B.**
> **A usa um B.**
> **A é composto por B.**

Exemplos:

```text
Pedido possui Itens.
Carro possui Motor.
Computador possui Processador.
NotaFiscal possui Itens.
Cliente possui Endereco.
```

Na composição, uma classe não herda da outra. Ela mantém uma referência para outro objeto.

Exemplo:

```csharp
public class Endereco
{
    public string Rua { get; private set; }
    public string Cidade { get; private set; }

    public Endereco(string rua, string cidade)
    {
        if (string.IsNullOrWhiteSpace(rua))
            throw new ArgumentException("Rua inválida.");

        if (string.IsNullOrWhiteSpace(cidade))
            throw new ArgumentException("Cidade inválida.");

        Rua = rua;
        Cidade = cidade;
    }
}

public class Cliente
{
    public string Nome { get; private set; }
    public Endereco Endereco { get; private set; }

    public Cliente(string nome, Endereco endereco)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("Nome inválido.");

        Endereco = endereco
            ?? throw new ArgumentNullException(nameof(endereco));

        Nome = nome;
    }
}
```

Nesse exemplo, `Cliente` não é um `Endereco`. A relação correta é:

```text
Cliente possui Endereco.
```

Se fosse usada herança, a modelagem ficaria conceitualmente errada.

# 3. A pergunta principal: “é um” ou “tem um”?

Uma forma prática de decidir entre herança e composição é perguntar:

```text
A classe A é um tipo de B?
```

Se a resposta for sim, herança pode fazer sentido.

```text
A classe A tem, usa ou possui B?
```

Se a resposta for sim, composição provavelmente é a melhor escolha.

Exemplos:

| Relação                     | Tipo de relação | Melhor escolha             |
| --------------------------- | --------------: | -------------------------- |
| Aluno é uma Pessoa          |            É um | Herança pode fazer sentido |
| Aluno possui Matrícula      |          Tem um | Composição                 |
| ProdutoDigital é um Produto |            É um | Herança pode fazer sentido |
| Produto usa RegraDeDesconto |          Usa um | Composição com interface   |
| Carro possui Motor          |          Tem um | Composição                 |
| Venda usa FormaDePagamento  |          Usa um | Composição com interface   |

A pergunta “é um?” ajuda, mas não deve ser usada sozinha. Também é necessário avaliar se a herança deixará o sistema rígido. Uma relação pode parecer herança no início, mas se muitas variações combináveis começarem a surgir, composição com interfaces pode ser mais adequada.

# 4. Herança bem utilizada

A herança é adequada quando existe uma especialização real.

Considere um sistema bancário com contas diferentes:

```text
ContaCorrente é uma ContaBancaria.
ContaPoupanca é uma ContaBancaria.
```

As duas contas possuem número e saldo, mas podem ter comportamentos específicos. A conta corrente pode cobrar tarifa. A conta poupança pode ter regra de rendimento.

Exemplo:

```csharp
public abstract class ContaBancaria
{
    public string Numero { get; private set; }
    public decimal Saldo { get; private set; }

    protected ContaBancaria(string numero, decimal saldoInicial)
    {
        if (string.IsNullOrWhiteSpace(numero))
            throw new ArgumentException("Número da conta inválido.");

        if (saldoInicial < 0)
            throw new ArgumentException("Saldo inicial não pode ser negativo.");

        Numero = numero;
        Saldo = saldoInicial;
    }

    public void Depositar(decimal valor)
    {
        if (valor <= 0)
            throw new ArgumentException("Valor de depósito inválido.");

        Saldo += valor;
    }

    public virtual void Sacar(decimal valor)
    {
        if (valor <= 0)
            throw new ArgumentException("Valor de saque inválido.");

        if (valor > Saldo)
            throw new InvalidOperationException("Saldo insuficiente.");

        Saldo -= valor;
    }

    public abstract void AplicarRegraMensal();
}
```

Subclasses:

```csharp
public class ContaCorrente : ContaBancaria
{
    private const decimal TarifaMensal = 15;

    public ContaCorrente(string numero, decimal saldoInicial)
        : base(numero, saldoInicial)
    {
    }

    public override void AplicarRegraMensal()
    {
        Sacar(TarifaMensal);
    }
}

public class ContaPoupanca : ContaBancaria
{
    private const decimal TaxaRendimento = 0.005m;

    public ContaPoupanca(string numero, decimal saldoInicial)
        : base(numero, saldoInicial)
    {
    }

    public override void AplicarRegraMensal()
    {
        decimal rendimento = Saldo * TaxaRendimento;
        Depositar(rendimento);
    }
}
```

Uso:

```csharp
List<ContaBancaria> contas = new List<ContaBancaria>
{
    new ContaCorrente("001", 1000),
    new ContaPoupanca("002", 1000)
};

foreach (ContaBancaria conta in contas)
{
    conta.AplicarRegraMensal();
    Console.WriteLine($"Conta {conta.Numero}: saldo {conta.Saldo}");
}
```

Esse é um uso coerente de herança porque:

* conta corrente e conta poupança são tipos de conta bancária;
* existe estrutura comum;
* existe comportamento especializado;
* o código consegue tratar ambas como `ContaBancaria`;
* há polimorfismo real em `AplicarRegraMensal`.

# 5. Composição bem utilizada

A composição é adequada quando um objeto possui ou usa outro.

Considere um pedido com itens:

```text
Pedido possui Itens.
```

Um pedido não é um item. Um item também não é um pedido. A relação correta é composição.

```csharp
public class ItemPedido
{
    public string Produto { get; private set; }
    public int Quantidade { get; private set; }
    public decimal ValorUnitario { get; private set; }

    public ItemPedido(string produto, int quantidade, decimal valorUnitario)
    {
        if (string.IsNullOrWhiteSpace(produto))
            throw new ArgumentException("Produto inválido.");

        if (quantidade <= 0)
            throw new ArgumentException("Quantidade inválida.");

        if (valorUnitario <= 0)
            throw new ArgumentException("Valor unitário inválido.");

        Produto = produto;
        Quantidade = quantidade;
        ValorUnitario = valorUnitario;
    }

    public decimal CalcularSubtotal()
    {
        return Quantidade * ValorUnitario;
    }
}
```

Classe `Pedido`:

```csharp
public class Pedido
{
    private readonly List<ItemPedido> _itens = new List<ItemPedido>();

    public IReadOnlyCollection<ItemPedido> Itens => _itens.AsReadOnly();

    public void AdicionarItem(ItemPedido item)
    {
        if (item == null)
            throw new ArgumentNullException(nameof(item));

        _itens.Add(item);
    }

    public decimal CalcularTotal()
    {
        decimal total = 0;

        foreach (ItemPedido item in _itens)
        {
            total += item.CalcularSubtotal();
        }

        return total;
    }
}
```

Uso:

```csharp
Pedido pedido = new Pedido();

pedido.AdicionarItem(new ItemPedido("Livro", 2, 50));
pedido.AdicionarItem(new ItemPedido("Caderno", 3, 20));

Console.WriteLine(pedido.CalcularTotal());
```

Resultado esperado:

```text
160
```

Esse exemplo mostra composição porque `Pedido` possui uma lista de `ItemPedido`. A lista interna é protegida por encapsulamento, pois o código externo não consegue alterar diretamente a coleção `_itens`.

# 6. Interface e composição para comportamento variável

Interfaces são úteis quando existem diferentes formas de executar o mesmo comportamento.

Exemplo:

```text
Um pedido precisa calcular frete.
O cálculo pode ser normal, expresso ou promocional.
```

Criar subclasses como `PedidoComFreteNormal`, `PedidoComFreteExpresso` e `PedidoComFretePromocional` pode ser uma má escolha, porque o tipo de frete é uma variação de comportamento, não uma especialização essencial de pedido.

Uma solução mais flexível é criar uma interface:

```csharp
public interface ICalculadoraFrete
{
    decimal Calcular(decimal peso);
}
```

Implementações:

```csharp
public class FreteNormal : ICalculadoraFrete
{
    public decimal Calcular(decimal peso)
    {
        return peso * 5;
    }
}

public class FreteExpresso : ICalculadoraFrete
{
    public decimal Calcular(decimal peso)
    {
        return peso * 10;
    }
}
```

Classe `Pedido` usando composição:

```csharp
public class PedidoComFrete
{
    public decimal PesoTotal { get; private set; }
    private readonly ICalculadoraFrete _calculadoraFrete;

    public PedidoComFrete(decimal pesoTotal, ICalculadoraFrete calculadoraFrete)
    {
        if (pesoTotal <= 0)
            throw new ArgumentException("Peso inválido.");

        _calculadoraFrete = calculadoraFrete
            ?? throw new ArgumentNullException(nameof(calculadoraFrete));

        PesoTotal = pesoTotal;
    }

    public decimal CalcularFrete()
    {
        return _calculadoraFrete.Calcular(PesoTotal);
    }
}
```

Uso:

```csharp
PedidoComFrete pedidoNormal = new PedidoComFrete(4, new FreteNormal());
PedidoComFrete pedidoExpresso = new PedidoComFrete(4, new FreteExpresso());

Console.WriteLine(pedidoNormal.CalcularFrete());
Console.WriteLine(pedidoExpresso.CalcularFrete());
```

Resultado esperado:

```text
20
40
```

O comportamento muda porque o objeto recebeu uma implementação diferente de `ICalculadoraFrete`.

Esse tipo de solução é mais flexível porque:

* `PedidoComFrete` não precisa conhecer os detalhes do cálculo;
* novas formas de frete podem ser adicionadas sem alterar a classe principal;
* o código depende de um contrato, não de uma classe concreta;
* há polimorfismo por interface.

# 7. Herança mal utilizada: hierarquias artificiais

Uma hierarquia artificial acontece quando a herança é criada apenas porque duas classes possuem atributos parecidos.

Exemplo problemático:

```csharp
public class Pessoa
{
    public string Nome { get; set; }
}

public class Empresa : Pessoa
{
    public string Cnpj { get; set; }
}
```

Esse modelo é inadequado porque uma empresa não é uma pessoa no sentido conceitual comum do domínio. Uma empresa pode ter um responsável, um representante ou um contato, mas isso não significa que ela deva herdar de `Pessoa`.

Modelagem melhor:

```csharp
public class Pessoa
{
    public string Nome { get; private set; }

    public Pessoa(string nome)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("Nome inválido.");

        Nome = nome;
    }
}

public class Empresa
{
    public string RazaoSocial { get; private set; }
    public string Cnpj { get; private set; }
    public Pessoa Responsavel { get; private set; }

    public Empresa(string razaoSocial, string cnpj, Pessoa responsavel)
    {
        if (string.IsNullOrWhiteSpace(razaoSocial))
            throw new ArgumentException("Razão social inválida.");

        if (string.IsNullOrWhiteSpace(cnpj))
            throw new ArgumentException("CNPJ inválido.");

        Responsavel = responsavel
            ?? throw new ArgumentNullException(nameof(responsavel));

        RazaoSocial = razaoSocial;
        Cnpj = cnpj;
    }
}
```

Agora a relação está correta:

```text
Empresa possui um responsável.
Responsável é uma Pessoa.
```

Esse modelo é mais fiel ao domínio e evita uma herança conceitualmente falsa.

# 8. Composição não elimina herança

Composição não substitui herança em todos os casos. A ideia não é afirmar que herança é ruim. A ideia é usar cada recurso no lugar certo.

Um mesmo modelo pode usar herança e composição ao mesmo tempo.

Exemplo:

```text
NotaFiscal é um Documento.
NotaFiscal possui Itens.
```

A primeira relação pode ser herança. A segunda relação deve ser composição.

Classe base:

```csharp
public abstract class Documento
{
    public string Numero { get; private set; }

    protected Documento(string numero)
    {
        if (string.IsNullOrWhiteSpace(numero))
            throw new ArgumentException("Número inválido.");

        Numero = numero;
    }

    public abstract decimal CalcularValorFinal();
}
```

Item da nota fiscal:

```csharp
public class ItemNotaFiscal
{
    public string Descricao { get; private set; }
    public decimal Valor { get; private set; }

    public ItemNotaFiscal(string descricao, decimal valor)
    {
        if (string.IsNullOrWhiteSpace(descricao))
            throw new ArgumentException("Descrição inválida.");

        if (valor <= 0)
            throw new ArgumentException("Valor inválido.");

        Descricao = descricao;
        Valor = valor;
    }
}
```

Nota fiscal:

```csharp
public class NotaFiscal : Documento
{
    private readonly List<ItemNotaFiscal> _itens = new List<ItemNotaFiscal>();

    public IReadOnlyCollection<ItemNotaFiscal> Itens => _itens.AsReadOnly();

    public NotaFiscal(string numero)
        : base(numero)
    {
    }

    public void AdicionarItem(ItemNotaFiscal item)
    {
        if (item == null)
            throw new ArgumentNullException(nameof(item));

        _itens.Add(item);
    }

    public override decimal CalcularValorFinal()
    {
        decimal total = 0;

        foreach (ItemNotaFiscal item in _itens)
        {
            total += item.Valor;
        }

        return total;
    }
}
```

Nesse exemplo:

* `NotaFiscal` herda de `Documento`, porque nota fiscal é um tipo de documento;
* `NotaFiscal` possui itens, portanto usa composição;
* os itens são protegidos por encapsulamento;
* a regra de totalização fica dentro da própria nota fiscal.

# 9. Herança gera acoplamento mais forte

Quando uma classe herda de outra, ela passa a depender diretamente da estrutura e do comportamento da classe base. Isso pode ser útil quando a relação conceitual é verdadeira, mas pode ser um problema quando a hierarquia foi criada apenas por conveniência.

Considere relatórios que podem ser exportados em diferentes formatos:

```text
RelatorioFinanceiroPdf
RelatorioFinanceiroCsv
RelatorioEstoquePdf
RelatorioEstoqueCsv
RelatorioVendasPdf
RelatorioVendasCsv
```

Essa solução mistura dois eixos de variação:

1. O tipo do relatório.
2. O formato de exportação.

Quando eixos de variação são combinados por herança, o número de classes tende a crescer rapidamente.

Uma alternativa melhor é usar composição:

```csharp
public interface IExportadorRelatorio
{
    void Exportar(string conteudo);
}
```

Implementações:

```csharp
public class ExportadorPdf : IExportadorRelatorio
{
    public void Exportar(string conteudo)
    {
        Console.WriteLine($"Exportando PDF: {conteudo}");
    }
}

public class ExportadorCsv : IExportadorRelatorio
{
    public void Exportar(string conteudo)
    {
        Console.WriteLine($"Exportando CSV: {conteudo}");
    }
}
```

Classe principal:

```csharp
public class Relatorio
{
    private readonly IExportadorRelatorio _exportador;

    public Relatorio(IExportadorRelatorio exportador)
    {
        _exportador = exportador
            ?? throw new ArgumentNullException(nameof(exportador));
    }

    public void Gerar()
    {
        string conteudo = "Dados do relatório";
        _exportador.Exportar(conteudo);
    }
}
```

Uso:

```csharp
Relatorio relatorioPdf = new Relatorio(new ExportadorPdf());
relatorioPdf.Gerar();

Relatorio relatorioCsv = new Relatorio(new ExportadorCsv());
relatorioCsv.Gerar();
```

A classe `Relatorio` apenas usa um exportador. Ela não precisa saber se a exportação será em PDF, CSV, HTML ou JSON. Isso reduz o acoplamento e facilita a extensão.

# 10. Comparação direta entre herança e composição

| Critério          | Herança                              | Composição                                      |
| ----------------- | ------------------------------------ | ----------------------------------------------- |
| Relação principal | “É um”                               | “Tem um”, “usa um” ou “é composto por”          |
| Exemplo           | `ContaCorrente é uma ContaBancaria`  | `Pedido possui Itens`                           |
| Acoplamento       | Mais forte                           | Geralmente menor                                |
| Reaproveitamento  | Por classe base                      | Por objetos colaboradores                       |
| Flexibilidade     | Menor quando há muitas variações     | Maior para comportamentos intercambiáveis       |
| Polimorfismo      | Por sobrescrita de métodos           | Por interfaces ou objetos substituíveis         |
| Risco comum       | Criar hierarquias artificiais        | Criar objetos demais sem responsabilidade clara |
| Melhor uso        | Especialização conceitual verdadeira | Variação de comportamento e relações “tem um”   |

A escolha não deve ser feita por hábito. Deve ser feita a partir do domínio, das responsabilidades e da estabilidade esperada da modelagem.

# 11. Aplicação prática resolvida: sistema de avaliação de entregas

## Cenário

Um sistema precisa representar entregas acadêmicas. Cada entrega possui uma descrição e uma nota base. A nota final pode ser calculada de formas diferentes: correção manual, correção com bônus ou outras estratégias futuras.

Uma solução ruim seria criar subclasses como:

```text
EntregaComCorrecaoManual
EntregaComCorrecaoComBonus
EntregaComCorrecaoPorRubrica
EntregaComCorrecaoManualComBonus
```

Essa modelagem tende a crescer demais e mistura a entrega com a forma de correção.

## Objetivo

Criar uma solução em C# que separe:

* a entidade `Entrega`;
* a regra de correção;
* a possibilidade de trocar o critério de correção sem alterar a classe `Entrega`.

## Solução

Interface:

```csharp
public interface ICriterioCorrecao
{
    decimal Corrigir(decimal notaBase);
}
```

Critério de correção manual:

```csharp
public class CorrecaoManual : ICriterioCorrecao
{
    public decimal Corrigir(decimal notaBase)
    {
        return notaBase;
    }
}
```

Critério com bônus:

```csharp
public class CorrecaoComBonus : ICriterioCorrecao
{
    private readonly decimal _bonus;

    public CorrecaoComBonus(decimal bonus)
    {
        if (bonus < 0)
            throw new ArgumentException("Bônus inválido.");

        _bonus = bonus;
    }

    public decimal Corrigir(decimal notaBase)
    {
        decimal notaFinal = notaBase + _bonus;

        if (notaFinal > 10)
            return 10;

        return notaFinal;
    }
}
```

Classe `Entrega`:

```csharp
public class Entrega
{
    public string Descricao { get; private set; }
    public decimal NotaBase { get; private set; }

    private readonly ICriterioCorrecao _criterioCorrecao;

    public Entrega(
        string descricao,
        decimal notaBase,
        ICriterioCorrecao criterioCorrecao)
    {
        if (string.IsNullOrWhiteSpace(descricao))
            throw new ArgumentException("Descrição inválida.");

        if (notaBase < 0 || notaBase > 10)
            throw new ArgumentException("Nota base inválida.");

        _criterioCorrecao = criterioCorrecao
            ?? throw new ArgumentNullException(nameof(criterioCorrecao));

        Descricao = descricao;
        NotaBase = notaBase;
    }

    public decimal ObterNotaFinal()
    {
        return _criterioCorrecao.Corrigir(NotaBase);
    }
}
```

Programa de teste:

```csharp
Entrega entrega1 = new Entrega(
    "Projeto de classes",
    8,
    new CorrecaoManual());

Entrega entrega2 = new Entrega(
    "Projeto com defesa",
    8,
    new CorrecaoComBonus(1));

Console.WriteLine(entrega1.ObterNotaFinal());
Console.WriteLine(entrega2.ObterNotaFinal());
```

## Resultado esperado

```text
8
9
```

## Comentário da solução

A classe `Entrega` não precisa saber como a nota será corrigida. Ela apenas depende do contrato `ICriterioCorrecao`.

Isso é composição porque `Entrega` usa um objeto que representa o critério de correção.

Também existe polimorfismo, pois `CorrecaoManual` e `CorrecaoComBonus` implementam a mesma interface e podem ser usadas no mesmo ponto do código.

## Como validar

A solução está correta se:

* `Entrega` não possui subclasses para cada tipo de correção;
* novas correções podem ser criadas implementando `ICriterioCorrecao`;
* a nota base rejeita valores menores que 0 ou maiores que 10;
* a correção com bônus não permite nota final acima de 10;
* o programa imprime `8` e `9` no exemplo apresentado.

## Possíveis erros

Um erro comum seria colocar todas as regras dentro de `Entrega` usando `if` ou `switch`, por exemplo:

```csharp
if (tipoCorrecao == "BONUS")
{
    // aplica bônus
}
```

Esse caminho deixa a classe crescer a cada nova regra. Com interface e composição, novas regras podem ser adicionadas sem modificar a classe principal.

# 12. Estudo de caso resolvido: turma com estudantes

## Cenário

Um sistema acadêmico precisa representar uma turma com vários estudantes matriculados. A turma deve impedir matrícula duplicada.

## Decisão de modelagem

A relação correta é:

```text
Turma possui Estudantes.
```

Portanto, a escolha principal é composição.

Não faz sentido dizer que `Turma` é um `Estudante`. Também não faz sentido dizer que `Estudante` é uma `Turma`.

## Solução

Classe `Estudante`:

```csharp
public class Estudante
{
    public string Matricula { get; private set; }
    public string Nome { get; private set; }

    public Estudante(string matricula, string nome)
    {
        if (string.IsNullOrWhiteSpace(matricula))
            throw new ArgumentException("Matrícula inválida.");

        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("Nome inválido.");

        Matricula = matricula;
        Nome = nome;
    }
}
```

Classe `Turma`:

```csharp
public class Turma
{
    public string Codigo { get; private set; }

    private readonly List<Estudante> _estudantes = new List<Estudante>();

    public IReadOnlyCollection<Estudante> Estudantes => _estudantes.AsReadOnly();

    public Turma(string codigo)
    {
        if (string.IsNullOrWhiteSpace(codigo))
            throw new ArgumentException("Código da turma inválido.");

        Codigo = codigo;
    }

    public void Matricular(Estudante estudante)
    {
        if (estudante == null)
            throw new ArgumentNullException(nameof(estudante));

        bool jaMatriculado = _estudantes.Any(e => e.Matricula == estudante.Matricula);

        if (jaMatriculado)
            throw new InvalidOperationException("Estudante já matriculado nesta turma.");

        _estudantes.Add(estudante);
    }

    public int ObterQuantidadeDeEstudantes()
    {
        return _estudantes.Count;
    }
}
```

Programa de teste:

```csharp
Turma turma = new Turma("POO-01");

Estudante estudante1 = new Estudante("2024001", "Carlos");
Estudante estudante2 = new Estudante("2024002", "Marina");

turma.Matricular(estudante1);
turma.Matricular(estudante2);

Console.WriteLine(turma.ObterQuantidadeDeEstudantes());
```

Resultado esperado:

```text
2
```

Teste de matrícula duplicada:

```csharp
turma.Matricular(new Estudante("2024001", "Carlos"));
```

Resultado esperado:

```text
InvalidOperationException: Estudante já matriculado nesta turma.
```

## Comentário da solução

A lista `_estudantes` está encapsulada. O código externo não consegue adicionar ou remover estudantes diretamente da lista. Para matricular alguém, é obrigatório passar pelo método `Matricular`, que protege a regra de negócio contra duplicidade.

## Como validar

A modelagem está correta se:

* `Turma` possui uma coleção de `Estudante`;
* não existe herança entre `Turma` e `Estudante`;
* matrícula duplicada é impedida;
* o estado interno da lista não é exposto diretamente;
* a regra de matrícula fica dentro da classe `Turma`.

# 13. Relação com padrões de projeto

A decisão entre composição e herança prepara o caminho para vários padrões de projeto.

## Strategy

O padrão Strategy permite trocar algoritmos em tempo de execução por meio de composição.

Exemplos deste material:

```text
ICalculadoraFrete
ICriterioCorrecao
IExportadorRelatorio
```

Nesses casos, a classe principal não implementa todas as variações. Ela recebe um objeto que sabe executar a variação desejada.

## Repository

O padrão Repository costuma usar composição para separar o acesso a dados da lógica de negócio. Uma classe de serviço pode usar um repositório sem depender diretamente de detalhes de banco de dados, arquivo ou API.

## Factory

O padrão Factory ajuda a centralizar a criação de objetos. Ele pode ser útil quando a escolha da implementação correta depende de regras específicas.

## Service

Classes de serviço podem coordenar objetos, repositórios e regras de negócio usando composição. A ideia é organizar responsabilidades sem criar heranças artificiais.

# 14. Erros comuns e dúvidas frequentes

## Erro 1: usar herança apenas para reaproveitar atributos

Ter atributos parecidos não significa que duas classes tenham relação de herança.

Exemplo incorreto:

```text
Empresa herda de Pessoa porque ambas têm nome.
```

O correto é analisar o significado do domínio. Se empresa não é pessoa, a herança não deve existir.

## Erro 2: criar subclasses para cada combinação de variação

Quando aparecem classes como:

```text
RelatorioFinanceiroPdf
RelatorioFinanceiroCsv
RelatorioEstoquePdf
RelatorioEstoqueCsv
```

é provável que a herança esteja sendo usada para combinar variações independentes. Nesse caso, composição com interface costuma ser melhor.

## Erro 3: confundir “usa um” com “é um”

Se uma classe apenas usa outra para realizar uma parte do trabalho, isso é composição.

Exemplo:

```text
Pedido usa CalculadoraFrete.
```

Não faria sentido dizer:

```text
Pedido é uma CalculadoraFrete.
```

## Erro 4: expor coleções internas diretamente

Este código pode ser perigoso:

```csharp
public List<ItemPedido> Itens { get; set; }
```

Ele permite que qualquer parte do sistema altere os itens do pedido sem passar por regras de validação.

Uma alternativa melhor é:

```csharp
private readonly List<ItemPedido> _itens = new List<ItemPedido>();

public IReadOnlyCollection<ItemPedido> Itens => _itens.AsReadOnly();
```

Assim, o objeto protege seu próprio estado.

## Erro 5: criar interfaces sem necessidade

Interfaces são úteis quando existe variação real de comportamento ou necessidade de desacoplamento. Criar interface para tudo pode deixar o sistema mais complexo sem benefício claro.

Uma boa pergunta é:

```text
Existem múltiplas formas de executar este comportamento?
```

Se sim, interface pode fazer sentido. Se não, talvez uma classe concreta simples seja suficiente.

# 15. Checklist explicado de decisão

## 15.1 Verifique se a herança representa uma relação “é um”

Antes de criar uma subclasse, confirme se a frase “A é um tipo de B” faz sentido no domínio.

Exemplo válido:

```text
ContaCorrente é uma ContaBancaria.
```

Exemplo problemático:

```text
Empresa é uma Pessoa.
```

Isso importa porque herança cria uma dependência forte entre as classes. Se a relação conceitual estiver errada, o sistema herdará comportamentos e significados inadequados.

Para validar, tente substituir a classe base pela classe filha em uma frase real do domínio. Se a frase ficar estranha, a herança provavelmente está errada.

## 15.2 Verifique se a composição representa uma relação “tem um” ou “usa um”

Quando uma classe depende de outra para realizar parte do trabalho, use composição.

Exemplo:

```text
Pedido usa ICalculadoraFrete.
NotaFiscal possui ItemNotaFiscal.
Turma possui Estudante.
```

Isso importa porque composição permite organizar responsabilidades sem forçar uma hierarquia. O sistema fica mais flexível e mais próximo do domínio real.

Para validar, pergunte se o objeto interno poderia ser trocado, adicionado, removido ou substituído. Se sim, composição tende a ser adequada.

## 15.3 Verifique se existem variações combináveis

Se o sistema possui várias variações independentes, evite criar subclasses para cada combinação.

Exemplo de variações independentes:

```text
Tipo de relatório: financeiro, estoque, vendas.
Formato de exportação: PDF, CSV, HTML.
```

Criar uma subclasse para cada combinação gera explosão de classes.

Para validar, conte quantas classes seriam necessárias se uma nova variação fosse adicionada. Se o número crescer rapidamente, prefira composição com interfaces.

## 15.4 Verifique se há polimorfismo real

Herança e interfaces fazem mais sentido quando o código pode tratar objetos diferentes por um mesmo tipo.

Exemplo:

```csharp
List<Funcionario> funcionarios = new List<Funcionario>();
```

ou:

```csharp
ICalculadoraFrete calculadora = new FreteExpresso();
```

Isso importa porque polimorfismo permite escrever código mais genérico e extensível.

Para validar, identifique onde o código chama o mesmo método em objetos diferentes e obtém comportamentos diferentes.

## 15.5 Verifique se o encapsulamento foi preservado

As propriedades devem proteger o estado interno do objeto. Evite permitir alterações livres em atributos importantes.

Prefira:

```csharp
public string Nome { get; private set; }
```

em vez de:

```csharp
public string Nome { get; set; }
```

Isso importa porque objetos devem proteger suas próprias regras. Se qualquer parte do sistema puder alterar o estado diretamente, as validações podem ser ignoradas.

Para validar, tente criar um objeto inválido ou alterar sua coleção interna diretamente. Se isso for possível, o encapsulamento precisa melhorar.

## 15.6 Verifique se os construtores validam dados obrigatórios

Construtores devem impedir que objetos nasçam inválidos.

Exemplo:

```csharp
if (string.IsNullOrWhiteSpace(nome))
    throw new ArgumentException("Nome inválido.");
```

Isso importa porque objetos inválidos espalham problemas pelo sistema. Quanto mais cedo o erro for detectado, mais fácil será corrigir.

Para validar, tente instanciar a classe com valores nulos, vazios, negativos ou fora do intervalo permitido.

## 15.7 Verifique se a modelagem pode ser explicada tecnicamente

Uma boa modelagem deve ser justificável.

Você deve conseguir responder:

```text
Por que usei herança aqui?
Por que usei composição aqui?
Onde existe polimorfismo?
Que regra de negócio esta classe protege?
O que aconteceria se eu usasse herança no lugar de composição?
```

Isso importa porque decisões de modelagem afetam manutenção futura. Se a escolha não pode ser explicada, talvez tenha sido feita por hábito.

---

# 16. Síntese final

Herança, composição e interfaces são recursos complementares da orientação a objetos.

Use **herança** quando houver uma relação verdadeira de especialização:

```text
FuncionarioMensalista é um Funcionario.
ContaCorrente é uma ContaBancaria.
NotaFiscal é um Documento.
```

Use **composição** quando uma classe possuir, usar ou depender de outra:

```text
Pedido possui Itens.
Cliente possui Endereco.
Turma possui Estudantes.
Relatorio usa Exportador.
```

Use **interfaces** quando houver comportamento variável:

```text
ICalculadoraFrete
ICriterioCorrecao
IExportadorRelatorio
```

A herança tende a criar acoplamento mais forte. A composição tende a favorecer flexibilidade, especialmente quando combinada com interfaces.

---

# Conclusão

Uma boa modelagem orientada a objetos não escolhe herança ou composição por costume. Ela analisa o domínio, identifica responsabilidades e escolhe a relação que melhor representa o problema.

A herança é adequada quando uma classe realmente é uma especialização de outra. A composição é adequada quando uma classe possui, usa ou é formada por outro objeto. Interfaces ajudam quando existem diferentes formas de executar um comportamento.

Em sistemas reais, herança, composição, interfaces, encapsulamento e polimorfismo trabalham juntos. O ponto central é saber qual recurso usar em cada situação e conseguir defender tecnicamente essa escolha.
