# Introdução a Padrões de Projeto em C#

## Objetivo do material

Neste material, você aprenderá o que são padrões de projeto, por que eles existem e como eles ajudam a organizar sistemas orientados a objetos em C#. O foco é reconhecer problemas recorrentes de design de software e compreender como padrões como **Strategy**, **Factory**, **Repository** e **Service** podem tornar o código mais claro, flexível e fácil de manter. 

Ao final, você deverá ser capaz de:

Reconhecer quando um problema de organização de código pode ser resolvido com um padrão de projeto.

Diferenciar um padrão de projeto de uma simples cópia de código.

Relacionar padrões de projeto com conceitos de orientação a objetos, como interfaces, composição, encapsulamento e polimorfismo.

Aplicar os padrões Strategy, Factory, Repository e Service em situações simples, evitando exageros e complexidade desnecessária.

---

# 1. O problema que leva aos padrões de projeto

Em projetos orientados a objetos, certos problemas aparecem repetidamente. Esses problemas não dependem do tipo de sistema: podem surgir em sistemas comerciais, acadêmicos, financeiros, jogos, aplicações web, aplicações desktop ou ferramentas internas.

Alguns exemplos comuns são:

Uma classe com muitos `if` para escolher regras diferentes.

Uma classe que depende diretamente de outra classe concreta, dificultando a troca de comportamento.

Comandos SQL espalhados pelo `Program.cs` ou por várias partes do sistema.

Criação de objetos complexos repetida em vários lugares.

Regras de negócio misturadas com entrada de dados, validação, persistência e apresentação.

Essas situações indicam que o código está começando a perder organização. O sistema até pode funcionar, mas fica mais difícil de alterar, testar e entender.

Um padrão de projeto surge justamente como uma resposta conhecida para um problema recorrente de design. Ele não é uma solução mágica, mas uma forma já consolidada de organizar classes, objetos e responsabilidades.

---

# 2. O que é um padrão de projeto

Um **padrão de projeto** é uma solução recorrente para um problema recorrente de design de software.

Ele descreve uma forma de organizar o código para resolver um tipo de problema que aparece com frequência. Um padrão de projeto normalmente envolve classes, objetos, interfaces, responsabilidades e formas de colaboração entre partes do sistema.

Um padrão de projeto não é:

um pacote que você instala;

uma biblioteca pronta;

um código que deve ser copiado sempre igual;

um enfeite para deixar o projeto parecendo mais avançado;

uma regra obrigatória para toda classe do sistema.

Estudar padrões de projeto não significa decorar nomes. O mais importante é aprender a reconhecer o problema que cada padrão resolve.

Por exemplo, o padrão **Strategy** ajuda quando existem várias formas de executar uma regra, como vários tipos de desconto. O padrão **Repository** ajuda quando o acesso a dados está espalhado pelo sistema. O padrão **Factory** ajuda quando a criação de objetos exige decisões ou validações. O padrão **Service** ajuda quando é necessário coordenar um fluxo de aplicação.

A pergunta mais importante antes de usar qualquer padrão é:

**Qual problema este padrão está resolvendo?**

Se não houver uma resposta clara, talvez o padrão não seja necessário naquele momento.

---

# 3. Padrão de projeto não é enfeite

Um erro comum é criar várias camadas, interfaces e classes apenas para o código parecer mais profissional.

Por exemplo, imagine um projeto que possui:

```csharp
IALuno
Aluno
AlunoBase
AlunoFactory
AlunoFactoryImpl
AlunoService
IALunoService
AlunoManager
AlunoHandler
AlunoProcessor
AlunoRepository
IALunoRepository
AlunoRepositoryBase
```

Se essas classes existem sem uma necessidade real, o projeto não ficou mais organizado. Ele ficou mais difícil de entender.

Padrões devem reduzir problemas, não aumentar confusão. Quando aplicados sem critério, eles criam complexidade acidental: muitos arquivos, muitos nomes parecidos e muitas indireções para uma lógica simples.

Um bom uso de padrões acontece quando o padrão deixa o código mais claro, mais testável, mais flexível ou mais fácil de evoluir.

# 4. Relação entre padrões de projeto e orientação a objetos

Padrões de projeto dependem fortemente dos conceitos fundamentais da programação orientada a objetos. Eles são formas organizadas de aplicar esses conceitos em problemas reais.

## Classes e objetos

Uma classe define a estrutura e o comportamento de um tipo de objeto. Um objeto é uma instância dessa classe.

Em padrões de projeto, as classes costumam representar responsabilidades específicas. Por exemplo, uma classe pode representar uma regra de desconto, outra pode representar um repositório de alunos e outra pode coordenar o cadastro de um aluno.

## Encapsulamento

Encapsular significa proteger detalhes internos e expor apenas o que é necessário.

No padrão Repository, por exemplo, o sistema não precisa saber como o banco de dados funciona internamente. Ele apenas chama métodos como `Adicionar`, `Listar` ou `ObterPorId`.

## Interface

Uma interface define um contrato. Ela diz quais métodos uma classe deve implementar, sem definir exatamente como esses métodos funcionarão.

No padrão Strategy, a interface permite que a classe principal dependa de uma abstração, não de uma implementação concreta.

Exemplo:

```csharp
public interface ICalculadoraDesconto
{
    decimal Calcular(decimal valor);
}
```

Essa interface informa que qualquer calculadora de desconto deve ter um método `Calcular`. A forma exata do cálculo pode variar em cada implementação.

## Polimorfismo

Polimorfismo permite tratar objetos diferentes por meio de uma mesma interface ou classe base.

Se `DescontoPorCupom` e `DescontoPorFidelidade` implementam `ICalculadoraDesconto`, uma classe `Pedido` pode usar qualquer uma delas sem conhecer os detalhes.

## Composição

Composição ocorre quando uma classe usa outra classe como parte de sua estrutura ou funcionamento.

No padrão Strategy, em vez de herdar uma regra de desconto, o pedido recebe uma calculadora de desconto. Isso torna a troca de comportamento mais flexível.

---

# 5. Categorias de padrões de projeto

Os padrões de projeto costumam ser organizados em três grupos principais: criacionais, estruturais e comportamentais.

## Padrões criacionais

Padrões criacionais tratam da criação de objetos.

Eles são úteis quando criar um objeto envolve mais do que simplesmente usar `new`.

Eles ajudam a responder perguntas como:

Como criar objetos complexos sem duplicar lógica?

Como escolher qual classe concreta deve ser instanciada?

Como garantir que um objeto seja criado em estado válido?

Exemplos de padrões criacionais incluem **Factory Method**, **Builder** e **Singleton**. Neste material, o foco será o uso do padrão **Factory** como forma de centralizar criação de objetos.

## Padrões estruturais

Padrões estruturais tratam da organização entre classes e objetos.

Eles ajudam quando é necessário adaptar, compor ou reorganizar relações entre partes do sistema.

Eles ajudam a responder perguntas como:

Como adaptar uma classe para ser usada por outra?

Como compor objetos sem criar heranças rígidas?

Como adicionar comportamento sem alterar a classe original?

Exemplos de padrões estruturais incluem **Adapter**, **Decorator** e **Facade**.

## Padrões comportamentais

Padrões comportamentais tratam de comportamentos, algoritmos, regras e comunicação entre objetos.

Eles ajudam quando existem variações de comportamento ou fluxos que precisam ser separados.

Exemplos:

**Strategy**: permite trocar uma regra de cálculo sem alterar a classe principal.

**Command**: encapsula comandos diferentes como objetos independentes.

**Observer**: permite notificar objetos quando algo muda.

**Template Method**: organiza etapas de um algoritmo com variações em subclasses.

**State**: altera o comportamento de um objeto conforme seu estado interno muda.

Neste material, o padrão comportamental mais importante será o **Strategy**.

# 6. Problema recorrente: muitos condicionais

Imagine uma classe responsável por calcular descontos:

```csharp
public class CalculadoraDesconto
{
    public decimal Calcular(decimal valor, string tipo)
    {
        if (tipo == "CUPOM")
            return valor * 0.10m;

        if (tipo == "FIDELIDADE")
            return valor * 0.15m;

        if (tipo == "PROMOCAO")
            return valor * 0.20m;

        return 0;
    }
}
```

Esse código funciona, mas apresenta um problema de design.

Sempre que surgir um novo tipo de desconto, a classe `CalculadoraDesconto` precisará ser alterada. Por exemplo:

desconto por primeira compra;

desconto por aniversário;

desconto por campanha especial;

desconto por volume;

desconto por forma de pagamento.

O problema não é o uso de `if` em si. Condicionais fazem parte da programação. O problema aparece quando várias regras diferentes ficam concentradas dentro da mesma classe.

Essa concentração dificulta manutenção, testes e evolução. A classe passa a ter muitos motivos para mudar.

Nessa situação, o padrão **Strategy** pode ajudar.

# 7. Padrão Strategy

O padrão **Strategy** permite separar uma regra variável em classes diferentes. Ele é útil quando existem várias formas de executar uma mesma operação.

No exemplo dos descontos, a operação é sempre a mesma: calcular desconto. O que varia é a regra usada para calcular.

## 7.1 Criando a interface da estratégia

```csharp
public interface ICalculadoraDesconto
{
    decimal Calcular(decimal valor);
}
```

Essa interface define o contrato das estratégias de desconto. Qualquer classe que implemente essa interface será capaz de calcular um desconto.

A classe principal não precisa saber se o desconto é por cupom, fidelidade ou promoção. Ela só precisa saber que existe um método `Calcular`.

## 7.2 Criando implementações diferentes

```csharp
public class DescontoPorCupom : ICalculadoraDesconto
{
    public decimal Calcular(decimal valor)
    {
        return valor * 0.10m;
    }
}
```

A classe `DescontoPorCupom` representa uma regra específica: desconto de 10%.

```csharp
public class DescontoPorFidelidade : ICalculadoraDesconto
{
    public decimal Calcular(decimal valor)
    {
        return valor * 0.15m;
    }
}
```

A classe `DescontoPorFidelidade` representa outra regra: desconto de 15%.

Cada regra fica isolada em sua própria classe. Isso facilita testes e manutenção.

## 7.3 Classe principal usando a interface

```csharp
public class Pedido
{
    public decimal ValorTotal { get; private set; }

    private readonly ICalculadoraDesconto _calculadoraDesconto;

    public Pedido(decimal valorTotal, ICalculadoraDesconto calculadoraDesconto)
    {
        ValorTotal = valorTotal;
        _calculadoraDesconto = calculadoraDesconto;
    }

    public decimal CalcularValorComDesconto()
    {
        decimal desconto = _calculadoraDesconto.Calcular(ValorTotal);
        return ValorTotal - desconto;
    }
}
```

A classe `Pedido` depende de `ICalculadoraDesconto`, e não de uma classe concreta.

Isso significa que o pedido pode receber qualquer estratégia de desconto, desde que ela implemente a interface.

## 7.4 Uso do Strategy

```csharp
ICalculadoraDesconto desconto = new DescontoPorCupom();

Pedido pedido = new Pedido(500, desconto);

Console.WriteLine(pedido.CalcularValorComDesconto());
```

Resultado esperado:

```csharp
450
```

O valor inicial é 500. O desconto por cupom é de 10%, ou seja, 50. O valor final é 450.

## 7.5 Por que o Strategy melhora o código

O Strategy melhora o código porque separa regras diferentes em classes diferentes.

Com isso:

a classe `Pedido` não precisa conhecer todos os tipos de desconto;

novas regras podem ser adicionadas sem modificar a classe principal;

cada regra pode ser testada separadamente;

o código fica mais alinhado ao princípio de depender de abstrações.

O padrão Strategy é especialmente útil quando muitos condicionais escolhem comportamentos diferentes.

# 8. Padrão Factory

O padrão **Factory** ajuda a centralizar a criação de objetos. Ele é útil quando a criação envolve decisão, validação ou montagem.

Criar um objeto nem sempre é apenas chamar `new`. Às vezes, o objeto precisa receber dependências, passar por validações ou ser montado de uma forma específica.

## 8.1 Problema: criação espalhada

Imagine que vários pontos do sistema criam pedidos com desconto:

```csharp
Pedido pedido1 = new Pedido(500, new DescontoPorCupom());
Pedido pedido2 = new Pedido(800, new DescontoPorFidelidade());
```

Esse código parece simples, mas a lógica de criação começa a se espalhar.

Se a forma de criar um pedido mudar, será necessário procurar todos os lugares onde `Pedido` é instanciado. Isso aumenta o risco de inconsistência.

## 8.2 Criando uma Factory

```csharp
public static class PedidoFactory
{
    public static Pedido CriarComCupom(decimal valor)
    {
        ICalculadoraDesconto desconto = new DescontoPorCupom();
        return new Pedido(valor, desconto);
    }

    public static Pedido CriarComFidelidade(decimal valor)
    {
        ICalculadoraDesconto desconto = new DescontoPorFidelidade();
        return new Pedido(valor, desconto);
    }
}
```

A Factory centraliza a montagem do objeto `Pedido`.

Agora, quem usa o sistema não precisa saber quais classes concretas devem ser instanciadas para cada tipo de pedido.

## 8.3 Uso da Factory

```csharp
Pedido pedido = PedidoFactory.CriarComCupom(500);

Console.WriteLine(pedido.CalcularValorComDesconto());
```

Resultado esperado:

```csharp
450
```

A Factory criou um pedido com a estratégia de desconto por cupom.

## 8.4 Quando usar Factory

Use Factory quando:

a criação do objeto envolve mais de uma etapa;

a criação exige validação;

a criação depende de uma escolha;

a montagem de objetos está sendo repetida em vários lugares;

o código cliente está conhecendo detalhes demais sobre como montar o objeto.

Não crie Factory para toda classe. Se a criação é simples, direta e não está duplicada, usar `new` pode ser suficiente.

# 9. Padrão Repository

O padrão **Repository** separa o domínio da persistência de dados. Ele cria uma camada responsável pelas operações de armazenamento, consulta, atualização e remoção.

O problema que o Repository resolve aparece quando comandos SQL ou detalhes de banco de dados ficam espalhados pelo sistema.

## 9.1 Problema: SQL espalhado

Exemplo ruim:

```csharp
var comando = conexao.CreateCommand();
comando.CommandText = "INSERT INTO alunos...";
```

Se esse tipo de código aparece diretamente no `Program.cs`, no serviço, na entidade ou em várias classes diferentes, o sistema fica acoplado ao banco de dados.

Isso gera problemas:

fica difícil trocar o banco;

fica difícil testar regras sem acessar banco real;

fica difícil localizar consultas;

fica difícil manter alterações na estrutura dos dados;

o restante do sistema passa a conhecer detalhes de persistência.

## 9.2 Criando o contrato do Repository

```csharp
public interface IAlunoRepository
{
    void Adicionar(Aluno aluno);
    Aluno? ObterPorId(int id);
    Aluno? ObterPorMatricula(string matricula);
    IReadOnlyCollection<Aluno> Listar();
    void Atualizar(Aluno aluno);
    void Remover(int id);
}
```

Essa interface define as operações necessárias para manipular alunos.

Observe que ela não diz se os dados estão em SQLite, SQL Server, arquivo, memória ou outro banco. Ela apenas define o que o sistema precisa fazer.

## 9.3 Implementação concreta

```csharp
public class SqliteAlunoRepository : IAlunoRepository
{
    public void Adicionar(Aluno aluno)
    {
        // INSERT no SQLite
    }

    public Aluno? ObterPorId(int id)
    {
        // SELECT no SQLite
        return null;
    }

    public Aluno? ObterPorMatricula(string matricula)
    {
        // SELECT no SQLite filtrando pela matrícula
        return null;
    }

    public IReadOnlyCollection<Aluno> Listar()
    {
        // SELECT no SQLite retornando vários alunos
        return new List<Aluno>();
    }

    public void Atualizar(Aluno aluno)
    {
        // UPDATE no SQLite
    }

    public void Remover(int id)
    {
        // DELETE no SQLite
    }
}
```

A classe `SqliteAlunoRepository` conhece os detalhes do SQLite. O restante do sistema não precisa conhecer.

## 9.4 Por que o Repository melhora o código

O Repository melhora o código porque isola a persistência.

A aplicação passa a depender de um contrato, como `IAlunoRepository`, e não diretamente de comandos SQL.

Isso torna o sistema mais organizado e testável. Em testes, por exemplo, é possível criar uma implementação em memória do repositório, sem acessar um banco real.

# 10. Padrão Service

Um **Service** organiza casos de uso e fluxos de aplicação. Ele coordena objetos, valida regras de aplicação e chama repositórios quando necessário.

O Service não deve ser usado como depósito de qualquer método. Um bom serviço tem uma responsabilidade clara.

## 10.1 Exemplo de entidade Aluno

```csharp
public class Aluno
{
    public string Nome { get; private set; }
    public string Matricula { get; private set; }

    public Aluno(string nome, string matricula)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("Nome é obrigatório.");

        if (string.IsNullOrWhiteSpace(matricula))
            throw new ArgumentException("Matrícula é obrigatória.");

        Nome = nome;
        Matricula = matricula;
    }
}
```

A entidade `Aluno` protege seus próprios dados. Ela não permite que um aluno seja criado sem nome ou sem matrícula.

Isso é responsabilidade da entidade, porque faz parte da validade do próprio objeto.

## 10.2 Criando o Service

```csharp
public class AlunoService
{
    private readonly IAlunoRepository _repositorio;

    public AlunoService(IAlunoRepository repositorio)
    {
        _repositorio = repositorio;
    }

    public void CadastrarAluno(string nome, string matricula)
    {
        Aluno? existente = _repositorio.ObterPorMatricula(matricula);

        if (existente != null)
            throw new InvalidOperationException("Matrícula já cadastrada.");

        Aluno aluno = new Aluno(nome, matricula);

        _repositorio.Adicionar(aluno);
    }
}
```

O `AlunoService` coordena o caso de uso de cadastro.

Ele faz quatro coisas principais:

consulta o repositório para verificar se a matrícula já existe;

aplica uma regra de aplicação, impedindo matrícula duplicada;

cria o objeto `Aluno`;

delega ao repositório a persistência.

## 10.3 O que o Service não deve fazer

Um Service não deve concentrar todas as responsabilidades do sistema.

Ele não deve substituir a entidade. Se uma regra pertence ao próprio objeto, ela deve estar na entidade.

Ele não deve conter SQL diretamente. Isso é responsabilidade do Repository.

Ele não deve ser apenas uma classe com métodos genéricos sem coesão.

Um Service bem definido representa um fluxo de aplicação, como cadastrar aluno, finalizar pedido, gerar matrícula ou registrar pagamento.

# 11. Diferença entre Entidade, Service e Repository

É fundamental não misturar responsabilidades.

## Entidade

A entidade representa um conceito importante do domínio do sistema.

Exemplos:

`Aluno`;

`Produto`;

`Pedido`;

`Turma`;

`Pagamento`.

A entidade deve proteger seus próprios dados e conter comportamentos diretamente relacionados ao objeto.

Exemplo: um aluno não deve existir sem nome e matrícula. Essa validação pode estar na entidade `Aluno`.

## Service

O Service coordena um caso de uso.

Ele chama repositórios, cria entidades, aplica regras de aplicação e organiza o fluxo.

Exemplos:

`CadastrarAluno`;

`FinalizarPedido`;

`MatricularEstudante`;

`RegistrarPagamento`.

O Service não deve saber como o banco grava os dados. Ele apenas solicita essa ação ao Repository.

## Repository

O Repository cuida da persistência.

Ele salva, busca, atualiza e remove dados. Também esconde detalhes técnicos do banco.

Exemplos:

`AlunoRepository`;

`PedidoRepository`;

`ProdutoRepository`.

O Repository não deve decidir regras de negócio, como “matrícula já cadastrada”. Ele apenas fornece os dados necessários para que o Service tome essa decisão.

# 12. Como os padrões se conectam em uma aplicação

Em uma aplicação simples, os padrões podem trabalhar juntos.

Uma possível estrutura de projeto seria:

```text
MinhaSolucao
│
├── MinhaSolucao.Dominio
│   ├── Aluno.cs
│   └── IAlunoRepository.cs
│
├── MinhaSolucao.Aplicacao
│   └── AlunoService.cs
│
├── MinhaSolucao.DAL
│   └── SqliteAlunoRepository.cs
│
└── MinhaSolucao.ConsoleApp
    └── Program.cs
```

Essa estrutura separa responsabilidades.

A camada de domínio contém a entidade e o contrato do repositório.

A camada de aplicação contém o serviço que coordena o caso de uso.

A camada de acesso a dados contém a implementação concreta do repositório.

O `ConsoleApp` apenas interage com o usuário e chama os serviços necessários.

O objetivo não é criar complexidade desnecessária. O objetivo é impedir que tudo fique misturado em um único arquivo.

# 13. Código desorganizado versus código organizado

## 13.1 Código sem organização

```csharp
// Program.cs — tudo misturado

Console.WriteLine("Nome:");
string nome = Console.ReadLine();

Console.WriteLine("Matrícula:");
string matricula = Console.ReadLine();

if (string.IsNullOrEmpty(nome))
{
    Console.WriteLine("Inválido.");
    return;
}

// SQL aqui...
// Validação de matrícula aqui...
// Criação do objeto aqui...
// Regra de negócio aqui...

Console.WriteLine("Cadastrado.");
```

Esse código mistura muitas responsabilidades:

entrada de dados;

validação;

regra de negócio;

criação de objeto;

acesso ao banco;

apresentação de resultado.

No começo, isso pode parecer mais simples. Porém, conforme o sistema cresce, o `Program.cs` vira um arquivo difícil de manter.

## 13.2 Código melhor organizado

```csharp
// Program.cs — apenas orquestra entrada e saída

Console.WriteLine("Nome:");
string nome = Console.ReadLine();

Console.WriteLine("Matrícula:");
string matricula = Console.ReadLine();

try
{
    alunoService.CadastrarAluno(nome, matricula);
    Console.WriteLine("Sucesso.");
}
catch (Exception ex)
{
    Console.WriteLine(ex.Message);
}
```

Nesse segundo exemplo, o `Program.cs` não contém a regra completa de cadastro. Ele apenas lê os dados, chama o serviço e mostra o resultado.

A regra de aplicação fica no `AlunoService`.

A persistência fica no `IAlunoRepository` e em sua implementação concreta.

A validade do objeto fica na entidade `Aluno`.

Cada parte possui uma responsabilidade clara.

# 14. Aplicação prática resolvida: cadastro de aluno com Service e Repository

## Cenário

Um sistema de console precisa cadastrar alunos. Cada aluno deve ter nome e matrícula. Não pode haver dois alunos com a mesma matrícula.

O sistema deve ser organizado para evitar que validações, criação de objeto e acesso a dados fiquem todos dentro do `Program.cs`.

## Objetivo

Criar uma estrutura simples usando:

entidade `Aluno`;

interface `IAlunoRepository`;

implementação em memória `AlunoRepositoryEmMemoria`;

service `AlunoService`;

uso no `Program.cs`.

## Solução

### Entidade Aluno

```csharp
public class Aluno
{
    public string Nome { get; private set; }
    public string Matricula { get; private set; }

    public Aluno(string nome, string matricula)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("Nome é obrigatório.");

        if (string.IsNullOrWhiteSpace(matricula))
            throw new ArgumentException("Matrícula é obrigatória.");

        Nome = nome;
        Matricula = matricula;
    }
}
```

A entidade garante que um aluno não seja criado em estado inválido.

Se o nome ou a matrícula estiverem vazios, uma exceção será lançada. Isso impede que objetos inválidos circulem pelo sistema.

### Interface do Repository

```csharp
public interface IAlunoRepository
{
    void Adicionar(Aluno aluno);
    Aluno? ObterPorMatricula(string matricula);
    IReadOnlyCollection<Aluno> Listar();
}
```

A interface define o contrato de persistência. O Service poderá usar esse contrato sem saber onde os dados estão armazenados.

### Repository em memória

```csharp
public class AlunoRepositoryEmMemoria : IAlunoRepository
{
    private readonly List<Aluno> _alunos = new List<Aluno>();

    public void Adicionar(Aluno aluno)
    {
        _alunos.Add(aluno);
    }

    public Aluno? ObterPorMatricula(string matricula)
    {
        return _alunos.FirstOrDefault(a => a.Matricula == matricula);
    }

    public IReadOnlyCollection<Aluno> Listar()
    {
        return _alunos.AsReadOnly();
    }
}
```

Essa implementação usa uma lista em memória. Ela é útil para estudo, testes e demonstrações.

Em um sistema real, poderia existir outra implementação usando SQLite, SQL Server ou outro mecanismo de persistência.

### Service de aluno

```csharp
public class AlunoService
{
    private readonly IAlunoRepository _repositorio;

    public AlunoService(IAlunoRepository repositorio)
    {
        _repositorio = repositorio;
    }

    public void CadastrarAluno(string nome, string matricula)
    {
        Aluno? alunoExistente = _repositorio.ObterPorMatricula(matricula);

        if (alunoExistente != null)
            throw new InvalidOperationException("Já existe aluno com essa matrícula.");

        Aluno novoAluno = new Aluno(nome, matricula);

        _repositorio.Adicionar(novoAluno);
    }
}
```

O Service coordena a regra de cadastro.

Ele verifica se já existe aluno com a matrícula informada. Se existir, impede o cadastro. Se não existir, cria o aluno e solicita ao repositório que salve o objeto.

### Uso no Program.cs

```csharp
IAlunoRepository repositorio = new AlunoRepositoryEmMemoria();
AlunoService alunoService = new AlunoService(repositorio);

Console.WriteLine("Nome:");
string nome = Console.ReadLine();

Console.WriteLine("Matrícula:");
string matricula = Console.ReadLine();

try
{
    alunoService.CadastrarAluno(nome, matricula);
    Console.WriteLine("Aluno cadastrado com sucesso.");
}
catch (Exception ex)
{
    Console.WriteLine(ex.Message);
}
```

O `Program.cs` ficou responsável apenas pela interação com o usuário. Ele não contém a regra de matrícula duplicada, não cria diretamente a lista de alunos e não decide como persistir os dados.

## Resultado esperado

Se o usuário informar um nome e uma matrícula ainda não cadastrada, o sistema exibirá:

```text
Aluno cadastrado com sucesso.
```

Se o nome estiver vazio, será exibida uma mensagem indicando que o nome é obrigatório.

Se a matrícula estiver vazia, será exibida uma mensagem indicando que a matrícula é obrigatória.

Se a matrícula já existir, será exibida a mensagem:

```text
Já existe aluno com essa matrícula.
```

## Como validar

Para validar se a solução está correta, verifique se o `Program.cs` não contém regra de negócio. Ele deve apenas receber dados, chamar o Service e exibir mensagens.

Verifique se o `AlunoService` coordena o cadastro e impede matrícula duplicada.

Verifique se o `AlunoRepositoryEmMemoria` apenas armazena e consulta alunos, sem decidir regras de negócio.

Verifique se a entidade `Aluno` protege seus próprios dados obrigatórios.

## Possíveis erros

Um erro comum seria colocar a verificação de matrícula duplicada dentro do `Program.cs`. Isso faria a regra de negócio ficar misturada com a interface de usuário.

Outro erro seria colocar mensagens de console dentro do `AlunoService`. Isso acoplaria o serviço a uma aplicação de console, dificultando reutilização em outros tipos de interface.

Também seria inadequado colocar SQL diretamente no `AlunoService`. O acesso a dados deve ficar no Repository.

# 15. Como reconhecer que um padrão é útil

Um padrão de projeto pode ser útil quando há sinais claros de dificuldade no design.

## A mesma lógica está duplicada em vários lugares

Quando a mesma lógica aparece em vários arquivos, qualquer mudança precisa ser repetida. Isso aumenta o risco de inconsistência.

Nesse caso, pode ser necessário centralizar a lógica em uma classe, método, Factory, Service ou outro componente adequado.

## Uma classe está ficando grande demais

Uma classe muito grande normalmente possui responsabilidades demais.

Quando uma classe valida, calcula, cria objetos, acessa banco e exibe mensagens, ela está acumulando papéis que deveriam estar separados.

## Muitos `if` escolhem comportamentos diferentes

Quando vários condicionais escolhem regras alternativas, como tipos de desconto ou formatos de exportação, o Strategy pode ser uma solução.

O objetivo é separar cada comportamento variável em uma implementação própria.

## O `Program.cs` concentra regra de negócio

O `Program.cs` deve ser uma camada de entrada e orquestração simples. Quando ele começa a conter regras importantes do sistema, o código fica difícil de reaproveitar e testar.

Nesse caso, um Service pode ajudar.

## SQL está espalhado pelo sistema

Quando comandos SQL aparecem em várias classes, o sistema fica acoplado ao banco.

Nesse caso, o Repository pode ajudar a centralizar a persistência.

## Criar objetos exige repetir várias etapas

Quando a criação de objetos exige montar dependências, validar dados ou escolher implementações, uma Factory pode ajudar.

# 16. Erros comuns e dúvidas frequentes

## “Todo `if` deve virar Strategy?”

Não. Condicionais simples são normais.

O Strategy faz sentido quando os condicionais representam comportamentos diferentes, tendem a crescer e dificultam a manutenção.

Se existe apenas uma decisão simples e pouco provável de mudar, usar Strategy pode ser exagero.

## “Toda classe precisa de interface?”

Não. Interfaces são úteis quando existe uma necessidade real de abstração.

Uma interface costuma fazer sentido quando há mais de uma implementação possível, quando você quer facilitar testes ou quando uma camada deve depender de contrato, não de classe concreta.

Criar interface para tudo pode gerar excesso de arquivos sem benefício real.

## “Repository é o mesmo que banco de dados?”

Não. Repository não é o banco. Ele é uma camada de acesso aos dados.

O banco armazena os dados. O Repository organiza como a aplicação conversa com esse armazenamento.

## “Service é onde coloco todos os métodos?”

Não. Um Service deve ter responsabilidade clara.

Ele deve representar casos de uso ou fluxos de aplicação. Se ele vira um depósito de métodos sem relação entre si, o design fica ruim.

## “Factory substitui o uso de `new`?”

Não. Factory não elimina o `new`. Ela centraliza a criação quando essa criação tem alguma complexidade.

Se criar o objeto é simples e direto, usar `new` pode ser perfeitamente adequado.

## “Padrões sempre deixam o código melhor?”

Não. Padrões usados sem necessidade podem piorar o código.

Um padrão é bom quando resolve um problema real. Se ele aumenta arquivos, nomes e indireções sem melhorar clareza, provavelmente está sendo usado de forma exagerada.

# 17. Checklist explicado de compreensão

## Verifique se você sabe explicar o que é um padrão de projeto

Você deve conseguir explicar que um padrão de projeto é uma solução recorrente para um problema recorrente de design. Isso importa porque o foco não está no nome do padrão, mas no problema que ele resolve. Para validar, tente explicar um padrão sem mostrar código. Se a explicação depender apenas de decorar uma estrutura, o conceito ainda precisa ser reforçado.

## Verifique se você entende que padrão não é código pronto para copiar

Um padrão orienta uma solução, mas cada projeto pode implementá-lo de forma diferente. Isso importa porque copiar código sem entender o problema pode criar soluções inadequadas. Para validar, observe se você consegue adaptar o mesmo padrão a outro exemplo, como desconto, exportação de relatório ou cadastro de aluno.

## Verifique se você reconhece problemas recorrentes de design

Você deve conseguir identificar sinais como lógica duplicada, muitos condicionais, SQL espalhado, criação repetida de objetos e classes grandes demais. Isso importa porque padrões só fazem sentido quando existe um problema real. Para validar, analise uma classe e pergunte: “Essa classe tem responsabilidades demais?” e “Esse comportamento tende a variar?”.

## Verifique se você sabe relacionar Strategy com variação de comportamento

O Strategy é adequado quando existem várias formas de executar uma operação. Isso importa porque ele separa cada comportamento em uma classe específica. Para validar, veja se você consegue transformar uma sequência de `if` de desconto em uma interface e implementações diferentes.

## Verifique se você sabe quando uma Factory é útil

Factory é útil quando a criação de objetos envolve decisão, validação ou montagem repetida. Isso importa porque a criação espalhada pode gerar inconsistência. Para validar, procure no código se o mesmo objeto está sendo criado da mesma maneira em vários lugares.

## Verifique se você entende o papel do Repository

Repository centraliza o acesso a dados e esconde detalhes de persistência. Isso importa porque o restante do sistema não deve depender diretamente de SQL ou detalhes do banco. Para validar, confirme se comandos como `INSERT`, `SELECT`, `UPDATE` e `DELETE` estão concentrados em classes apropriadas de repositório.

## Verifique se você entende o papel do Service

Service coordena casos de uso e fluxos de aplicação. Isso importa porque regras de aplicação não devem ficar espalhadas pelo `Program.cs`, pela entidade ou pelo Repository. Para validar, observe se o Service chama repositórios, cria entidades e aplica regras de fluxo sem assumir responsabilidades de apresentação ou persistência direta.

## Verifique se você evita exagero nos padrões

Usar padrões demais pode tornar o sistema mais confuso. Isso importa porque a finalidade de um padrão é simplificar uma dificuldade real, não aumentar a quantidade de arquivos. Para validar, pergunte: “Que problema esta interface, Factory ou Service resolve?”. Se a resposta não for clara, talvez a estrutura seja desnecessária.

# 18. Síntese final

Padrões de projeto ajudam a resolver problemas recorrentes de design de software.

Eles não devem ser usados como enfeite, nem como forma de deixar o código artificialmente complexo.

O padrão **Strategy** é útil quando existem várias formas de executar uma regra ou comportamento.

O padrão **Factory** é útil quando a criação de objetos envolve decisão, validação ou montagem repetida.

O padrão **Repository** é útil quando o acesso a dados precisa ser separado do restante do sistema.

O padrão **Service** é útil quando um caso de uso precisa coordenar entidades, regras e repositórios.

A base de todos esses padrões está na orientação a objetos: encapsulamento, interfaces, composição, polimorfismo e separação de responsabilidades.

O bom uso de padrões começa pela pergunta: **qual problema de design estou tentando resolver?**

---

# Conclusão

Padrões de projeto são ferramentas para organizar melhor o código conforme um sistema cresce. Eles ajudam a evitar classes enormes, regras duplicadas, dependências rígidas e responsabilidades misturadas.

Em C#, padrões como Strategy, Factory, Repository e Service aparecem naturalmente quando o desenvolvedor passa a estruturar melhor aplicações orientadas a objetos.

O objetivo não é usar todos os padrões em todos os projetos. O objetivo é reconhecer problemas reais e escolher soluções adequadas. Um código bem organizado não é aquele que possui mais classes, interfaces ou camadas. É aquele em que cada parte tem uma responsabilidade clara, pode ser compreendida com facilidade e pode evoluir sem causar confusão no restante do sistema.
