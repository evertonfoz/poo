# Quando Usar Classe Abstrata, Interface, Herança ou Composição em C#

Material autossuficiente elaborado a partir do conteúdo-base enviado sobre modelagem orientada a objetos em C#. 

## 1. Objetivo do material

Neste material, você aprenderá a decidir quando usar **classe concreta**, **classe abstrata**, **interface**, **herança** ou **composição** em C#.

A ideia principal é entender que programar orientado a objetos não é apenas escrever classes, propriedades e métodos. Uma boa modelagem exige compreender o papel de cada classe no domínio do problema, o tipo de relação entre os objetos e o nível de flexibilidade necessário para o sistema evoluir.

Ao final, você deverá ser capaz de:

* diferenciar os principais recursos de modelagem orientada a objetos;
* justificar tecnicamente uma escolha entre herança, composição, classe abstrata e interface;
* evitar heranças artificiais, interfaces sem propósito e acoplamento excessivo;
* reconhecer polimorfismo por herança e polimorfismo por interface;
* construir modelos mais claros, flexíveis e coerentes com o domínio do problema.

---

# 2. O problema da escolha incorreta em POO

Em Programação Orientada a Objetos, um código pode **compilar**, **executar** e ainda assim estar mal modelado.

Isso acontece quando o desenvolvedor escolhe um recurso apenas porque conhece sua sintaxe, e não porque ele representa corretamente o problema. Por exemplo, criar uma herança apenas para reaproveitar atributos pode parecer prático no início, mas pode gerar uma hierarquia rígida e difícil de manter.

Uma escolha incorreta costuma gerar problemas como:

## Classes sobrecarregadas

Uma classe fica responsável por muitas coisas ao mesmo tempo. Ela guarda dados, valida regras, calcula valores, acessa recursos externos, decide fluxos e ainda executa ações que deveriam estar em outros objetos.

Isso dificulta testes, manutenção e reaproveitamento.

## Heranças sem sentido

A herança deve representar uma relação do tipo **“é um”**. Quando ela é usada apenas para reaproveitar propriedades ou métodos, a modelagem fica artificial.

Por exemplo, se uma classe `Carro` herdasse de `Motor` só porque todo carro possui motor, a relação estaria errada. Um carro **tem um** motor, mas não **é um** motor.

## Interfaces desnecessárias

Interfaces são úteis quando existe comportamento variável, troca de implementação ou dependência por contrato. Porém, criar interface para tudo pode deixar o projeto mais complexo sem ganho real.

A pergunta correta não é “é boa prática criar interface?”, mas sim: **qual problema esta interface resolve?**

## Acoplamento excessivo

Acoplamento excessivo ocorre quando uma classe depende demais de outra classe concreta. Isso torna o sistema mais difícil de alterar.

Se uma regra muda e várias classes precisam ser modificadas, é provável que a modelagem esteja rígida demais.

# 3. Antes de escolher: perguntas de modelagem

Antes de implementar uma classe, é importante responder algumas perguntas:

## O conceito existe diretamente no sistema?

Se sim, provavelmente é uma **classe concreta**.

Exemplo: `Produto`, `Pedido`, `Cliente`, `Venda`, `Aluno`.

## O conceito é uma ideia geral que precisa ser especializada?

Se sim, pode ser uma **classe abstrata**.

Exemplo: `ContaBancaria`, `Ingresso`, `Funcionario`, `Documento`.

## Existe uma relação “é um”?

Se sim, pode haver **herança**.

Exemplo: `ContaCorrente` é uma `ContaBancaria`.

## Existe uma relação “tem um”, “usa um” ou “é formado por”?

Se sim, provavelmente é **composição**.

Exemplo: `Pedido` tem `Itens`; `Carro` tem `Motor`; `Venda` usa uma `FormaPagamento`.

## Existe comportamento variável?

Se sim, pode ser adequado usar **interface**.

Exemplo: várias formas de pagamento, várias formas de exportação, várias estratégias de frete.

# 4. Classe concreta

Uma **classe concreta** é uma classe que pode ser instanciada diretamente. Ela representa um conceito específico do domínio e normalmente possui estado, propriedades, construtores, validações, métodos e regras próprias.

Uma classe concreta deve existir quando o objeto faz sentido por si só dentro do sistema.

## Exemplo: Produto

```csharp
public class Produto
{
    public string Nome { get; private set; }
    public decimal Preco { get; private set; }

    public Produto(string nome, decimal preco)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("Nome inválido.");

        if (preco <= 0)
            throw new ArgumentException("Preço inválido.");

        Nome = nome;
        Preco = preco;
    }

    public void AlterarPreco(decimal novoPreco)
    {
        if (novoPreco <= 0)
            throw new ArgumentException("Preço inválido.");

        Preco = novoPreco;
    }
}
```

Nesse exemplo, `Produto` é uma classe concreta porque um produto pode existir diretamente no sistema. Ele possui dados próprios, como `Nome` e `Preco`, e também regras próprias, como impedir preço menor ou igual a zero.

O construtor garante que o objeto já nasça em um estado válido. O método `AlterarPreco` protege a regra de negócio mesmo depois da criação do objeto.

## Quando usar classe concreta

Use classe concreta quando o conceito pode existir diretamente no domínio, possui dados e regras próprias, pode ser instanciado e não representa apenas um contrato ou uma generalização incompleta.

Exemplos comuns:

```text
Produto
Cliente
Pedido
ItemPedido
Turma
Disciplina
Matricula
Endereco
Venda
Pagamento
```

Uma classe concreta deve ser clara, específica e responsável por proteger as regras relacionadas ao conceito que representa.

# 5. Classe abstrata

Uma **classe abstrata** é uma classe que não deve ser instanciada diretamente. Ela representa uma ideia geral, incompleta ou genérica, que precisa ser especializada por classes concretas.

A classe abstrata é útil quando existe uma generalização real, com estado ou comportamento comum, mas também existem partes que dependem da especialização.

## Exemplo: ContaBancaria

```csharp
public abstract class ContaBancaria
{
    public string Numero { get; private set; }
    public decimal Saldo { get; private set; }

    protected ContaBancaria(string numero)
    {
        if (string.IsNullOrWhiteSpace(numero))
            throw new ArgumentException("Número inválido.");

        Numero = numero;
        Saldo = 0;
    }

    public void Depositar(decimal valor)
    {
        if (valor <= 0)
            throw new ArgumentException("Valor inválido.");

        Saldo += valor;
    }

    public void Sacar(decimal valor)
    {
        if (valor <= 0)
            throw new ArgumentException("Valor inválido.");

        if (valor > Saldo)
            throw new InvalidOperationException("Saldo insuficiente.");

        Saldo -= valor;
    }

    public abstract decimal CalcularTarifaMensal();
}
```

A classe `ContaBancaria` possui propriedades e métodos comuns a todas as contas, como `Numero`, `Saldo`, `Depositar` e `Sacar`.

Porém, ela também possui um comportamento que depende do tipo específico de conta: `CalcularTarifaMensal`. Por isso, esse método é abstrato. Cada classe filha deverá implementar sua própria regra.

## Especializações concretas

```csharp
public class ContaCorrente : ContaBancaria
{
    public ContaCorrente(string numero) : base(numero)
    {
    }

    public override decimal CalcularTarifaMensal()
    {
        return 25;
    }
}

public class ContaPoupanca : ContaBancaria
{
    public ContaPoupanca(string numero) : base(numero)
    {
    }

    public override decimal CalcularTarifaMensal()
    {
        return 0;
    }
}
```

`ContaCorrente` e `ContaPoupanca` são tipos específicos de `ContaBancaria`. Elas herdam o que é comum e implementam o que varia.

## Quando usar classe abstrata

Use classe abstrata quando existe uma generalização real, a classe base não faz sentido sozinha, há estado e comportamento comum entre as subclasses e existe comportamento obrigatório que cada subclasse precisa implementar.

A pergunta principal é:

**A classe filha é realmente um tipo da classe base?**

Se a resposta for não, provavelmente não é caso de classe abstrata com herança.

# 6. Interface

Uma **interface** define um contrato de comportamento. Ela diz o que uma classe deve fazer, mas não representa necessariamente o que essa classe é.

Interfaces são especialmente úteis quando classes diferentes precisam oferecer a mesma operação sem pertencer à mesma hierarquia.

## Exemplo: exportação

```csharp
public interface IExportador
{
    void Exportar(string conteudo);
}
```

A interface `IExportador` define que qualquer classe exportadora deve possuir o método `Exportar`.

Agora podemos ter implementações diferentes:

```csharp
public class ExportadorPdf : IExportador
{
    public void Exportar(string conteudo)
    {
        Console.WriteLine($"Exportando PDF: {conteudo}");
    }
}

public class ExportadorCsv : IExportador
{
    public void Exportar(string conteudo)
    {
        Console.WriteLine($"Exportando CSV: {conteudo}");
    }
}
```

`ExportadorPdf` e `ExportadorCsv` não precisam herdar de uma classe base comum. O ponto importante é que ambos sabem exportar.

A interface representa uma **capacidade**, não uma identidade.

## Outros exemplos de interfaces

```csharp
public interface ICalculadoraDesconto
{
    decimal Calcular(decimal valor);
}

public interface IValidadorDocumento
{
    bool Validar(string documento);
}

public interface INotificador
{
    void Enviar(string mensagem);
}
```

Essas interfaces fazem sentido quando existem diferentes formas de calcular desconto, validar documento ou enviar notificação.

## Quando usar interface

Use interface quando existe comportamento que pode ter várias implementações, quando você quer depender de um contrato em vez de uma classe concreta, quando deseja permitir troca de implementação ou quando quer aplicar polimorfismo por comportamento.

Exemplo: um sistema pode ter `PagamentoPix`, `PagamentoCartao` e `PagamentoBoleto`. Todos pagam, mas cada um paga de uma forma diferente.

## Quando evitar interface

Evite interface quando existe apenas uma implementação, nenhuma variação real, nenhuma necessidade de troca e ninguém depende de um contrato abstrato.

Exemplo artificial:

```csharp
public interface IProduto
{
    string Nome { get; }
    decimal Preco { get; }
}

public class Produto : IProduto
{
    public string Nome { get; private set; }
    public decimal Preco { get; private set; }
}
```

Esse código não está necessariamente errado, mas a interface pode ser desnecessária se não houver comportamento variável nem necessidade de substituição.

A pergunta correta é:

**Qual problema esta interface resolve?**

Se a resposta for apenas “porque é boa prática”, a interface provavelmente não foi bem justificada.

# 7. Herança

A **herança** permite criar uma classe a partir de outra. Ela deve representar uma relação do tipo **“é um”**.

A herança permite reutilizar estrutura e comportamento, mas também cria uma dependência forte entre a classe filha e a classe base. Por isso, deve ser usada com cuidado.

## Exemplo com polimorfismo

```csharp
List<ContaBancaria> contas = new();

contas.Add(new ContaCorrente("001"));
contas.Add(new ContaPoupanca("002"));

foreach (ContaBancaria conta in contas)
{
    Console.WriteLine(conta.CalcularTarifaMensal());
}
```

Nesse exemplo, a lista usa o tipo `ContaBancaria`, mas cada objeto executa sua própria versão de `CalcularTarifaMensal`.

Isso é polimorfismo por herança.

## Quando usar herança

Use herança quando a classe filha é realmente uma especialização da classe base, existe uma relação conceitual forte, há comportamento comum, existe possibilidade de polimorfismo e as subclasses podem substituir a classe base sem quebrar o sentido do programa.

Exemplo adequado:

```text
ContaCorrente é uma ContaBancaria.
ContaPoupanca é uma ContaBancaria.
IngressoVip é um Ingresso.
Professor é um Funcionario.
```

## Quando evitar herança

Evite herança quando a relação entre as classes é apenas “tem um”, quando você quer apenas reaproveitar atributos, quando a hierarquia cresce demais, quando há muitas combinações de variações ou quando a classe base começa a receber regras que só servem para algumas filhas.

Um sinal de problema é a explosão de subclasses, como:

```text
RelatorioPdf
RelatorioCsv
RelatorioHtml
RelatorioFinanceiroPdf
RelatorioFinanceiroCsv
RelatorioFinanceiroHtml
```

Nesse caso, provavelmente o tipo de relatório e a forma de exportação são variações diferentes. Em vez de criar uma classe para cada combinação, faz mais sentido separar responsabilidades usando composição e interface.

# 8. Composição

A **composição** ocorre quando uma classe possui, usa ou é formada por outro objeto. A relação é **“tem um”**, **“usa um”** ou **“é composto por”**.

Composição costuma ser mais flexível que herança, principalmente quando partes do comportamento precisam variar.

## Exemplo: Carro e Motor

```csharp
public class Motor
{
    public string Modelo { get; private set; }

    public Motor(string modelo)
    {
        if (string.IsNullOrWhiteSpace(modelo))
            throw new ArgumentException("Modelo inválido.");

        Modelo = modelo;
    }
}

public class Carro
{
    public string Placa { get; private set; }
    public Motor Motor { get; private set; }

    public Carro(string placa, Motor motor)
    {
        if (string.IsNullOrWhiteSpace(placa))
            throw new ArgumentException("Placa inválida.");

        Motor = motor ?? throw new ArgumentNullException(nameof(motor));
        Placa = placa;
    }
}
```

`Carro` possui um `Motor`. Ele não é um motor. Por isso, composição é a escolha correta.

## Quando usar composição

Use composição quando uma classe possui outra, usa outra, é formada por partes, precisa delegar uma operação, precisa trocar parte do comportamento, deve evitar hierarquias longas ou precisa reduzir acoplamento.

A composição ajuda a separar responsabilidades. Em vez de uma classe tentar resolver tudo sozinha, ela colabora com outros objetos.

---

# 9. Composição com interface

A composição se torna ainda mais poderosa quando combinada com interfaces. Isso permite trocar comportamentos sem alterar a classe principal.

## Exemplo: cálculo de frete

```csharp
public interface ICalculadoraFrete
{
    decimal Calcular(decimal peso);
}

public class FreteNormal : ICalculadoraFrete
{
    public decimal Calcular(decimal peso)
    {
        return peso * 5;
    }
}

public class FreteExpresso : ICalculadoraFrete
{
    public decimal Calcular(decimal peso)
    {
        return peso * 10;
    }
}
```

Agora a classe `Pedido` pode depender da interface, não de uma classe concreta:

```csharp
public class Pedido
{
    public decimal PesoTotal { get; private set; }
    private readonly ICalculadoraFrete _calculadoraFrete;

    public Pedido(decimal pesoTotal, ICalculadoraFrete calculadoraFrete)
    {
        if (pesoTotal <= 0)
            throw new ArgumentException("Peso inválido.");

        _calculadoraFrete = calculadoraFrete 
            ?? throw new ArgumentNullException(nameof(calculadoraFrete));

        PesoTotal = pesoTotal;
    }

    public decimal CalcularFrete()
    {
        return _calculadoraFrete.Calcular(PesoTotal);
    }
}
```

Uso:

```csharp
Pedido pedidoNormal = new Pedido(10, new FreteNormal());
Pedido pedidoExpresso = new Pedido(10, new FreteExpresso());

Console.WriteLine(pedidoNormal.CalcularFrete());   // 50
Console.WriteLine(pedidoExpresso.CalcularFrete()); // 100
```

A classe `Pedido` não precisa saber como o frete é calculado. Ela apenas delega essa responsabilidade para uma implementação de `ICalculadoraFrete`.

Isso reduz acoplamento e facilita mudanças futuras. Se surgir uma nova regra, como `FreteInternacional`, basta criar outra classe que implemente a interface.

# 10. Comparação entre os recursos

| Recurso         | Representa                       |       Pode ser instanciado? | Use quando                                                          |
| --------------- | -------------------------------- | --------------------------: | ------------------------------------------------------------------- |
| Classe concreta | Conceito específico do domínio   |                         Sim | O objeto existe diretamente e possui estado e comportamento próprio |
| Classe abstrata | Generalização incompleta         |                         Não | Há estado ou comportamento comum e especializações obrigatórias     |
| Interface       | Contrato de comportamento        |                         Não | Há comportamento variável ou troca de implementação                 |
| Herança         | Relação “é um”                   |      Depende da classe base | Uma classe é tipo especializado de outra                            |
| Composição      | Relação “tem”, “usa” ou “possui” | Sim, nos objetos envolvidos | Um objeto é formado por outro ou delega comportamento               |

A escolha correta depende do significado conceitual. Sintaxe parecida não significa intenção parecida.

# 11. Exemplo integrado: sistema de venda de ingressos

Imagine um sistema com diferentes tipos de ingresso e diferentes formas de pagamento.

Requisitos:

* Todo ingresso possui código e valor base.
* Um ingresso comum custa o valor base.
* Um ingresso VIP custa 50% a mais.
* A venda deve aceitar diferentes formas de pagamento.
* As formas de pagamento podem variar, como Pix e cartão.
* A classe `Venda` deve combinar ingresso e forma de pagamento sem criar uma classe para cada combinação.

## Classe abstrata: Ingresso

```csharp
public abstract class Ingresso
{
    public string Codigo { get; private set; }
    public decimal ValorBase { get; private set; }

    protected Ingresso(string codigo, decimal valorBase)
    {
        if (string.IsNullOrWhiteSpace(codigo))
            throw new ArgumentException("Código inválido.");

        if (valorBase <= 0)
            throw new ArgumentException("Valor base inválido.");

        Codigo = codigo;
        ValorBase = valorBase;
    }

    public abstract decimal CalcularValorFinal();
}
```

`Ingresso` é abstrata porque representa uma ideia geral. Ela possui estado comum, mas não define sozinha como o valor final será calculado.

## Herança: tipos de ingresso

```csharp
public class IngressoComum : Ingresso
{
    public IngressoComum(string codigo, decimal valorBase)
        : base(codigo, valorBase)
    {
    }

    public override decimal CalcularValorFinal()
    {
        return ValorBase;
    }
}

public class IngressoVip : Ingresso
{
    public IngressoVip(string codigo, decimal valorBase)
        : base(codigo, valorBase)
    {
    }

    public override decimal CalcularValorFinal()
    {
        return ValorBase * 1.5m;
    }
}
```

`IngressoComum` e `IngressoVip` herdam de `Ingresso` porque são tipos de ingresso. A relação “é um” está presente.

## Interface: forma de pagamento

```csharp
public interface IFormaPagamento
{
    void Pagar(decimal valor);
}
```

A interface define um contrato: toda forma de pagamento deve saber pagar um valor.

## Implementações da interface

```csharp
public class PagamentoCartao : IFormaPagamento
{
    public void Pagar(decimal valor)
    {
        Console.WriteLine($"Pagamento de R$ {valor} no cartão.");
    }
}

public class PagamentoPix : IFormaPagamento
{
    public void Pagar(decimal valor)
    {
        Console.WriteLine($"Pagamento de R$ {valor} via Pix.");
    }
}
```

`PagamentoCartao` e `PagamentoPix` não precisam herdar de uma mesma classe base. O que importa é que ambos cumprem o contrato `IFormaPagamento`.

## Composição: Venda

```csharp
public class Venda
{
    public Ingresso Ingresso { get; private set; }
    private readonly IFormaPagamento _formaPagamento;

    public Venda(Ingresso ingresso, IFormaPagamento formaPagamento)
    {
        Ingresso = ingresso 
            ?? throw new ArgumentNullException(nameof(ingresso));

        _formaPagamento = formaPagamento 
            ?? throw new ArgumentNullException(nameof(formaPagamento));
    }

    public void Finalizar()
    {
        decimal valorFinal = Ingresso.CalcularValorFinal();
        _formaPagamento.Pagar(valorFinal);
    }
}
```

A classe `Venda` possui um `Ingresso` e usa uma `IFormaPagamento`. Ela não herda de `Ingresso`, nem de `PagamentoPix`, nem de `PagamentoCartao`.

Isso é composição.

## Uso no Program.cs

```csharp
Ingresso ingresso = new IngressoVip("VIP-001", 100);
IFormaPagamento pagamento = new PagamentoPix();

Venda venda = new Venda(ingresso, pagamento);
venda.Finalizar();
```

Resultado esperado:

```text
Pagamento de R$ 150 via Pix.
```

## Análise do exemplo

A classe abstrata `Ingresso` centraliza o que é comum a todos os ingressos. As classes `IngressoComum` e `IngressoVip` usam herança porque são especializações reais de ingresso. A interface `IFormaPagamento` define um comportamento variável. A classe `Venda` usa composição para combinar um ingresso com uma forma de pagamento.

Uma decisão ruim seria criar classes como:

```text
VendaPix
VendaCartao
VendaIngressoVipPix
VendaIngressoVipCartao
VendaIngressoComumPix
VendaIngressoComumCartao
```

Esse crescimento de combinações indica rigidez. A composição evita essa explosão de classes.

# 12. Polimorfismo por herança e por interface

## Polimorfismo por herança

Ocorre quando diferentes subclasses são tratadas pelo tipo da classe base, mas cada uma executa seu próprio comportamento.

```csharp
List<Ingresso> ingressos = new();

ingressos.Add(new IngressoComum("COM-001", 100));
ingressos.Add(new IngressoVip("VIP-001", 100));

foreach (Ingresso ingresso in ingressos)
{
    Console.WriteLine(ingresso.CalcularValorFinal());
}
```

Saída esperada:

```text
100
150
```

A variável é do tipo `Ingresso`, mas o comportamento executado depende do objeto real: `IngressoComum` ou `IngressoVip`.

## Polimorfismo por interface

Ocorre quando diferentes classes são tratadas pelo tipo da interface, mas cada uma executa sua própria implementação.

```csharp
List<IFormaPagamento> formas = new();

formas.Add(new PagamentoCartao());
formas.Add(new PagamentoPix());

foreach (IFormaPagamento forma in formas)
{
    forma.Pagar(150);
}
```

Saída esperada:

```text
Pagamento de R$ 150 no cartão.
Pagamento de R$ 150 via Pix.
```

Cada forma de pagamento executa o método `Pagar` de maneira diferente.

## Diferença principal

Na herança, o foco é a identidade:

```text
IngressoVip é um Ingresso.
ContaCorrente é uma ContaBancaria.
```

Na interface, o foco é a capacidade:

```text
PagamentoPix sabe pagar.
ExportadorPdf sabe exportar.
ValidadorCpf sabe validar.
```

# 13. Roteiro para decidir a modelagem

## Passo 1: identifique os conceitos do domínio

Observe quais objetos realmente existem no problema.

Em um sistema de vendas, podem existir:

```text
Pedido
ItemPedido
Produto
Cliente
Pagamento
Entrega
Desconto
```

Cada conceito deve ser analisado. Alguns serão classes concretas, outros poderão ser interfaces, classes abstratas ou objetos compostos.

## Passo 2: identifique relações

Procure relações como:

```text
é um
tem um
usa um
é formado por
```

Exemplos:

```text
IngressoVip é um Ingresso.
Pedido tem Itens.
Carro tem Motor.
Venda usa FormaPagamento.
Turma possui Alunos.
```

Essas relações ajudam a decidir entre herança e composição.

## Passo 3: identifique comportamentos variáveis

Pergunte se existe mais de uma forma de executar determinada operação.

Exemplos:

```text
Calcular frete
Calcular desconto
Validar documento
Exportar relatório
Processar pagamento
Enviar notificação
```

Quando há várias formas possíveis, uma interface costuma ser adequada.

## Passo 4: identifique generalizações reais

Pergunte se existem classes que compartilham estado e comportamento e são especializações de uma ideia comum.

Exemplo:

```text
ContaCorrente e ContaPoupanca são tipos de ContaBancaria.
IngressoComum e IngressoVip são tipos de Ingresso.
```

Se a classe base não deve ser instanciada diretamente e existe comportamento comum, uma classe abstrata pode ser adequada.

## Passo 5: avalie a rigidez da solução

Pergunte:

**Se surgir uma nova variação, quantas classes precisarão mudar?**

Se a resposta for “muitas”, a modelagem provavelmente está rígida.

Por exemplo, se adicionar uma nova forma de pagamento exige alterar várias classes de venda, talvez a forma de pagamento devesse estar separada por interface e composição.

# 14. Aplicação prática resolvida: sistema de pedidos com pagamento e frete

## Cenário

Um sistema precisa registrar pedidos. Cada pedido possui cliente, itens, uma forma de pagamento e uma estratégia de frete.

Regras:

* Um pedido deve ter cliente.
* Um item deve ter descrição, quantidade e preço unitário.
* A quantidade deve ser maior que zero.
* O preço unitário deve ser maior que zero.
* O pedido deve proteger sua lista interna de itens.
* O cálculo de frete pode variar.
* A forma de pagamento pode variar.

## Objetivo

Criar uma modelagem usando:

* classes concretas;
* composição;
* interface;
* encapsulamento;
* validação em construtores;
* polimorfismo por interface.

## Classe Cliente

```csharp
public class Cliente
{
    public string Nome { get; private set; }

    public Cliente(string nome)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("Nome do cliente inválido.");

        Nome = nome;
    }
}
```

`Cliente` é uma classe concreta porque representa um conceito que existe diretamente no sistema.

## Classe ItemPedido

```csharp
public class ItemPedido
{
    public string Descricao { get; private set; }
    public int Quantidade { get; private set; }
    public decimal PrecoUnitario { get; private set; }

    public ItemPedido(string descricao, int quantidade, decimal precoUnitario)
    {
        if (string.IsNullOrWhiteSpace(descricao))
            throw new ArgumentException("Descrição inválida.");

        if (quantidade <= 0)
            throw new ArgumentException("Quantidade inválida.");

        if (precoUnitario <= 0)
            throw new ArgumentException("Preço unitário inválido.");

        Descricao = descricao;
        Quantidade = quantidade;
        PrecoUnitario = precoUnitario;
    }

    public decimal CalcularSubtotal()
    {
        return Quantidade * PrecoUnitario;
    }
}
```

`ItemPedido` protege suas próprias regras. Ele não permite quantidade nem preço inválidos.

## Interface de frete

```csharp
public interface ICalculadoraFrete
{
    decimal Calcular(decimal valorPedido);
}
```

A interface existe porque o frete pode variar. O pedido não deve conhecer diretamente todas as regras possíveis.

## Implementações de frete

```csharp
public class FreteNormal : ICalculadoraFrete
{
    public decimal Calcular(decimal valorPedido)
    {
        return 15;
    }
}

public class FreteGratisParaPedidosAltos : ICalculadoraFrete
{
    public decimal Calcular(decimal valorPedido)
    {
        if (valorPedido >= 200)
            return 0;

        return 20;
    }
}
```

As duas classes implementam o mesmo contrato, mas possuem regras diferentes.

## Interface de pagamento

```csharp
public interface IFormaPagamento
{
    void Pagar(decimal valor);
}
```

A interface existe porque o pagamento também pode variar.

## Implementações de pagamento

```csharp
public class PagamentoPix : IFormaPagamento
{
    public void Pagar(decimal valor)
    {
        Console.WriteLine($"Pagamento de R$ {valor} realizado via Pix.");
    }
}

public class PagamentoCartao : IFormaPagamento
{
    public void Pagar(decimal valor)
    {
        Console.WriteLine($"Pagamento de R$ {valor} realizado no cartão.");
    }
}
```

## Classe Pedido

```csharp
public class Pedido
{
    private readonly List<ItemPedido> _itens = new();

    public Cliente Cliente { get; private set; }
    public IReadOnlyCollection<ItemPedido> Itens => _itens.AsReadOnly();

    private readonly ICalculadoraFrete _calculadoraFrete;
    private readonly IFormaPagamento _formaPagamento;

    public Pedido(
        Cliente cliente,
        ICalculadoraFrete calculadoraFrete,
        IFormaPagamento formaPagamento)
    {
        Cliente = cliente 
            ?? throw new ArgumentNullException(nameof(cliente));

        _calculadoraFrete = calculadoraFrete 
            ?? throw new ArgumentNullException(nameof(calculadoraFrete));

        _formaPagamento = formaPagamento 
            ?? throw new ArgumentNullException(nameof(formaPagamento));
    }

    public void AdicionarItem(ItemPedido item)
    {
        if (item == null)
            throw new ArgumentNullException(nameof(item));

        _itens.Add(item);
    }

    public decimal CalcularTotalItens()
    {
        return _itens.Sum(item => item.CalcularSubtotal());
    }

    public decimal CalcularTotal()
    {
        decimal totalItens = CalcularTotalItens();
        decimal frete = _calculadoraFrete.Calcular(totalItens);

        return totalItens + frete;
    }

    public void Finalizar()
    {
        if (!_itens.Any())
            throw new InvalidOperationException("O pedido deve ter pelo menos um item.");

        decimal total = CalcularTotal();
        _formaPagamento.Pagar(total);
    }
}
```

A classe `Pedido` usa composição porque possui `Cliente`, possui itens, usa uma calculadora de frete e usa uma forma de pagamento.

A lista de itens é protegida. O código externo não consegue substituir a lista diretamente. Para adicionar item, precisa passar pelo método `AdicionarItem`, que valida a entrada.

## Program.cs

```csharp
Cliente cliente = new Cliente("Carlos");

ICalculadoraFrete frete = new FreteGratisParaPedidosAltos();
IFormaPagamento pagamento = new PagamentoPix();

Pedido pedido = new Pedido(cliente, frete, pagamento);

pedido.AdicionarItem(new ItemPedido("Teclado", 1, 120));
pedido.AdicionarItem(new ItemPedido("Mouse", 2, 50));

pedido.Finalizar();
```

## Resultado esperado

O total dos itens será:

```text
Teclado: 1 x 120 = 120
Mouse: 2 x 50 = 100
Total dos itens = 220
```

Como o total é maior ou igual a 200, o frete será gratuito.

Saída esperada:

```text
Pagamento de R$ 220 realizado via Pix.
```

## Como validar a modelagem

A modelagem está correta porque `Pedido` não herda de `Cliente`, `FreteNormal` ou `PagamentoPix`. Ele apenas possui ou usa esses objetos. Isso representa composição.

As interfaces `ICalculadoraFrete` e `IFormaPagamento` são justificadas porque existem comportamentos variáveis.

O encapsulamento está correto porque a coleção interna `_itens` não é exposta como `List<ItemPedido>` pública e mutável.

## Possíveis erros

Um erro seria criar classes como `PedidoPix`, `PedidoCartao`, `PedidoFreteNormalPix` e `PedidoFreteGratisCartao`. Isso criaria muitas combinações desnecessárias.

Outro erro seria deixar a lista pública:

```csharp
public List<ItemPedido> Itens { get; set; }
```

Nesse caso, qualquer parte do sistema poderia substituir ou alterar a lista sem passar pelas regras do pedido.

# 15. Erros comuns de modelagem

## Erro 1: usar herança apenas para reaproveitar atributos

Duas classes terem atributos parecidos não significa que uma deva herdar da outra.

A pergunta correta é:

**A classe filha é realmente um tipo da classe base?**

Se a resposta for não, evite herança.

## Erro 2: criar interface sem variação

Se existe apenas uma implementação, nenhuma troca prevista e nenhum código depende do contrato, a interface pode ser desnecessária.

Isso não significa que interfaces sejam ruins. Significa que elas devem resolver um problema real.

## Erro 3: criar classe abstrata sem comportamento comum

Uma classe abstrata deve ter um propósito. Ela pode concentrar estado comum, comportamento comum ou exigir implementação de métodos abstratos relevantes.

Uma classe abstrata vazia ou sem papel claro pode indicar modelagem artificial.

## Erro 4: expor coleções internas

Código ruim:

```csharp
public class Pedido
{
    public List<ItemPedido> Itens { get; set; }
}
```

Esse código permite que qualquer parte do sistema altere a lista diretamente, substitua a lista inteira ou insira itens inválidos.

Código melhor:

```csharp
public class Pedido
{
    private readonly List<ItemPedido> _itens = new();

    public IReadOnlyCollection<ItemPedido> Itens => _itens.AsReadOnly();

    public void AdicionarItem(ItemPedido item)
    {
        if (item == null)
            throw new ArgumentNullException(nameof(item));

        _itens.Add(item);
    }
}
```

Agora a classe `Pedido` controla como os itens são adicionados.

## Erro 5: colocar toda a lógica no construtor

O construtor deve inicializar o estado essencial do objeto. Ele pode validar dados básicos, mas não deve concentrar toda a lógica complexa do sistema.

Quando o construtor executa regras demais, o código fica difícil de testar, reutilizar e manter.

## Erro 6: confundir identidade com capacidade

Herança representa identidade:

```text
ContaCorrente é uma ContaBancaria.
```

Interface representa capacidade:

```text
PagamentoPix sabe pagar.
ExportadorCsv sabe exportar.
```

Quando essa diferença não é respeitada, surgem hierarquias artificiais.

# 16. Quadro de decisão rápida

| Pergunta                                                       | Recurso mais provável      |
| -------------------------------------------------------------- | -------------------------- |
| O conceito pode ser instanciado diretamente?                   | Classe concreta            |
| O conceito é uma generalização incompleta?                     | Classe abstrata            |
| Existe relação “é um”?                                         | Herança                    |
| Existe relação “tem um”?                                       | Composição                 |
| Existe relação “usa um”?                                       | Composição                 |
| Existe comportamento variável?                                 | Interface                  |
| Existem várias formas de calcular, validar, pagar ou exportar? | Interface com polimorfismo |
| Existe estado e comportamento comum entre especializações?     | Classe abstrata            |
| A classe só quer reaproveitar atributos de outra?              | Evitar herança             |
| A variação gera muitas combinações de subclasses?              | Preferir composição        |

Esse quadro não substitui a análise do domínio, mas ajuda a organizar a decisão.

# 17. Checklist explicado de modelagem

## Verifique se suas classes concretas representam conceitos reais do domínio

Uma classe concreta deve representar algo que existe diretamente no problema. Para validar, pergunte se faz sentido criar um objeto daquela classe no sistema. Se a resposta for não, talvez ela seja abstrata demais ou represente apenas um comportamento.

## Verifique se suas classes abstratas representam generalizações reais

Uma classe abstrata deve representar uma ideia comum que não deveria ser instanciada diretamente. Para validar, pergunte se as classes filhas são realmente tipos da classe base. Se não forem, a herança provavelmente está errada.

## Verifique se suas interfaces resolvem comportamento variável

Uma interface deve representar um contrato útil. Para validar, pergunte se existem ou podem existir múltiplas implementações. Se houver apenas uma implementação sem necessidade de troca, a interface pode estar adicionando complexidade desnecessária.

## Verifique se suas heranças representam relação “é um”

A herança deve expressar especialização. Para validar, leia a frase em voz alta: “classe filha é uma classe base”. Se a frase parecer estranha, a relação provavelmente não é de herança.

## Verifique se suas composições representam relação “tem”, “usa” ou “possui”

A composição deve ser usada quando um objeto depende de outro para existir, colaborar ou executar uma tarefa. Para validar, tente formular a relação como “Pedido tem itens” ou “Venda usa forma de pagamento”. Se fizer sentido, composição é um bom caminho.

## Verifique se você evitou herança apenas para reaproveitar código

Reaproveitamento de código não é motivo suficiente para herança. Se não houver especialização real, prefira composição ou extração de comportamento para outra classe.

## Verifique se você evitou interface sem necessidade

Interfaces devem simplificar a troca de implementação ou reduzir acoplamento. Se ninguém usa o contrato e não há variação real, a interface pode ser removida sem prejuízo.

## Verifique se suas coleções internas estão protegidas

Listas públicas e mutáveis permitem alterações fora do controle da classe. Para validar, verifique se a coleção é exposta como leitura, por exemplo com `IReadOnlyCollection`, e se as alterações passam por métodos que protegem regras.

## Verifique se os construtores validam o estado inicial

Um objeto não deve nascer inválido. Para validar, confira se valores obrigatórios, números positivos e referências nulas são tratados no construtor.

## Verifique se métodos protegem regras de negócio

Não basta validar no construtor. Métodos que alteram o estado também precisam proteger regras. Por exemplo, `AlterarPreco` deve impedir preço inválido mesmo depois que o produto foi criado.

## Verifique se você consegue explicar onde existe polimorfismo

Polimorfismo deve ser reconhecível. Para validar, identifique se diferentes objetos são tratados por uma classe base ou interface comum e executam comportamentos diferentes.

## Verifique se você consegue defender sua modelagem

Uma boa modelagem deve ter justificativa. Para validar, explique por que cada classe existe, por que usou herança ou composição, por que criou interfaces e como a solução reagiria a mudanças futuras.

# 18. Síntese final

Classe concreta representa algo que pode existir diretamente no sistema, com estado e comportamento próprios.

Classe abstrata representa uma generalização incompleta. Ela é útil quando há estado ou comportamento comum, mas a classe base não deve ser instanciada diretamente.

Interface representa um contrato de comportamento. Ela é especialmente útil quando existem variações de implementação ou quando o sistema deve depender de uma abstração.

Herança representa especialização. A classe filha deve ser realmente um tipo da classe base.

Composição representa colaboração, posse ou formação. Uma classe pode ter, usar ou ser formada por outros objetos.

A modelagem orientada a objetos melhora quando cada recurso é usado com intenção. O objetivo não é usar todos os recursos em todo sistema, mas escolher o recurso que melhor representa o domínio e reduz rigidez.

---

# 19. Conclusão

Uma boa modelagem em C# não depende apenas de conhecer a sintaxe de classes, interfaces e herança. Ela depende de entender o problema.

Antes de criar uma classe abstrata, pergunte se existe uma generalização real. Antes de usar herança, pergunte se a relação é realmente “é um”. Antes de criar uma interface, pergunte qual comportamento variável ela representa. Antes de acoplar uma classe diretamente a outra, pergunte se composição com interface tornaria a solução mais flexível.

O código bem modelado é aquele que expressa corretamente o domínio, protege regras importantes, evita dependências desnecessárias e consegue evoluir sem gerar uma explosão de classes ou alterações espalhadas pelo sistema.
