# Factory para Criação de Objetos em C#

Material didático autossuficiente baseado no conteúdo enviado sobre Factory em C#, criação de objetos, Strategy, composição, responsabilidades e preparação para Repository, Service, DAL e SQLite. 

## Objetivo do material

Neste material, você aprenderá a usar o padrão Factory em C# para organizar a criação de objetos de forma clara, reutilizável e segura.

Ao estudar este conteúdo, você deverá ser capaz de:

1. Explicar qual problema uma Factory resolve.
2. Identificar quando a criação de objetos está simples e quando começa a ficar complexa.
3. Implementar uma Factory simples em C#.
4. Usar Factory em conjunto com interfaces e Strategy.
5. Evitar duplicação de código na criação de objetos.
6. Diferenciar Factory, entidade, Strategy, Service, Repository, DAL e `Program.cs`.
7. Preparar o código para cenários futuros com persistência, Repository, DAL e SQLite.

Factory não deve ser vista como uma regra obrigatória para toda classe. Ela é útil quando existe uma lógica de criação relevante, como escolha entre implementações, montagem de objetos compostos, aplicação de valores padrão ou centralização de regras de criação.

# 1. Contextualização do problema

Em C#, criar objetos normalmente é algo simples. Usamos a palavra-chave `new`, chamamos o construtor e passamos os dados necessários.

Exemplo:

```csharp
Produto produto = new Produto("Teclado", 150);
```

Esse código é direto. Ele cria um objeto `Produto` com nome e preço. Quando a criação é simples assim, normalmente não há necessidade de usar Factory.

O problema aparece quando a criação de objetos começa a envolver várias etapas, decisões, dependências e regras.

Observe este exemplo:

```csharp
Produto produto = new Produto("Teclado", 150);
ItemPedido item = new ItemPedido(produto, 2);
ICalculadoraDesconto desconto = new DescontoPorCupom();
Pedido pedido = new Pedido(desconto);
pedido.AdicionarItem(item);
```

Esse código ainda é compreensível, mas já mostra sinais de maior complexidade. Para criar um `Pedido`, foi necessário:

1. Criar um `Produto`.
2. Criar um `ItemPedido`.
3. Escolher uma estratégia de desconto.
4. Criar o `Pedido`.
5. Adicionar o item ao pedido.

Se essa sequência aparecer em vários pontos do sistema, o código ficará duplicado. Se uma regra de criação mudar, será necessário alterar vários lugares. Isso aumenta o risco de inconsistência.

Factory surge exatamente para lidar com esse tipo de situação.

---

# 2. O que é Factory

Factory significa “fábrica”. Em programação orientada a objetos, uma Factory é uma classe ou método responsável por criar objetos.

A ideia principal é centralizar a lógica de criação em um único lugar.

Uma Factory pode ser usada para:

* escolher qual classe concreta deve ser criada;
* montar um objeto com suas dependências;
* aplicar valores padrão;
* evitar repetição de código de criação;
* deixar o `Program.cs` mais limpo;
* tornar explícita a intenção por trás da criação de um objeto.

Exemplo simples de Factory:

```csharp
public static class CalculadoraDescontoFactory
{
    public static ICalculadoraDesconto Criar(TipoDesconto tipoDesconto)
    {
        return tipoDesconto switch
        {
            TipoDesconto.Cupom => new DescontoPorCupom(),
            TipoDesconto.Campanha => new DescontoPorCampanha(),
            _ => new SemDesconto()
        };
    }
}
```

Nesse exemplo, a Factory decide qual implementação de `ICalculadoraDesconto` deve ser criada.

O código que usa a Factory não precisa conhecer todos os detalhes de criação:

```csharp
ICalculadoraDesconto desconto =
    CalculadoraDescontoFactory.Criar(TipoDesconto.Cupom);
```

A decisão fica centralizada.

# 3. Criação simples não precisa de Factory

Nem toda criação de objeto deve ser colocada em uma Factory.

Quando o objeto é criado de forma direta, clara e sem decisões adicionais, o construtor público costuma ser suficiente.

Exemplo:

```csharp
public class Produto
{
    public string Nome { get; private set; }
    public decimal Preco { get; private set; }

    public Produto(string nome, decimal preco)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("Nome inválido.");

        if (preco <= 0)
            throw new ArgumentException("Preço inválido.");

        Nome = nome;
        Preco = preco;
    }
}
```

Uso:

```csharp
Produto produto = new Produto("Teclado", 150);
```

Esse código está adequado. O construtor recebe os dados necessários e valida o estado interno do objeto.

Uma Factory como esta não agrega valor:

```csharp
public static class ProdutoFactory
{
    public static Produto Criar(string nome, decimal preco)
    {
        return new Produto(nome, preco);
    }
}
```

Nesse caso, a Factory apenas repassa os parâmetros para o construtor. Ela não toma decisão, não monta dependências, não aplica valores padrão e não melhora a clareza do código.

A pergunta principal deve ser:

**A Factory está resolvendo algum problema real?**

Se a resposta for não, provavelmente ela não é necessária.

# 4. Quando a criação começa a incomodar

A criação de objetos merece atenção quando apresenta alguns sinais.

## 4.1 Duplicação

Acontece quando o mesmo conjunto de objetos precisa ser montado em vários lugares.

Exemplo:

```csharp
Produto produto = new Produto("Monitor", 900);
ItemPedido item = new ItemPedido(produto, 1);
Pedido pedido = new Pedido(new DescontoPorCampanha());
pedido.AdicionarItem(item);
```

Se esse trecho aparece em várias partes do sistema, qualquer mudança na criação do pedido exigirá alterações repetidas. Uma Factory pode centralizar essa montagem.

## 4.2 Escolha entre classes concretas

Acontece quando o código precisa decidir qual classe usar com base em uma condição.

Exemplo:

```csharp
ICalculadoraDesconto desconto;

if (tipoDesconto == "CUPOM")
{
    desconto = new DescontoPorCupom();
}
else if (tipoDesconto == "CAMPANHA")
{
    desconto = new DescontoPorCampanha();
}
else
{
    desconto = new SemDesconto();
}
```

Esse tipo de decisão, se espalhado pelo sistema, gera duplicação e risco de erro.

## 4.3 Dependências obrigatórias

Um objeto pode depender de outros objetos para funcionar.

Exemplo:

```csharp
Pedido pedido = new Pedido(calculadoraDesconto);
```

Nesse caso, `Pedido` depende de uma implementação de `ICalculadoraDesconto`. Se a escolha da calculadora for repetida em vários pontos, uma Factory pode organizar esse processo.

## 4.4 Regras e validações de criação

Às vezes, o modo de criar um objeto depende de uma regra.

Exemplo:

```csharp
Matricula matricula = Matricula.CriarAtiva("EST001", "TURMA01");
```

Aqui, o método comunica que a matrícula será criada ativa. A criação não é apenas “instanciar”; ela expressa uma intenção.

## 4.5 `Program.cs` poluído

Em projetos didáticos ou aplicações simples de console, é comum o `Program.cs` concentrar muitos exemplos. Porém, se ele começa a ficar cheio de `new`, decisões, montagem de objetos e regras, o código fica difícil de ler.

A Factory ajuda a deixar o ponto de entrada mais limpo.

# 5. Primeiro exemplo útil: Factory com decisão

Imagine um sistema com diferentes formas de calcular desconto.

Temos uma interface:

```csharp
public interface ICalculadoraDesconto
{
    decimal Calcular(decimal valor);
}
```

E algumas implementações:

```csharp
public class SemDesconto : ICalculadoraDesconto
{
    public decimal Calcular(decimal valor) => 0;
}

public class DescontoPorCupom : ICalculadoraDesconto
{
    public decimal Calcular(decimal valor) => valor * 0.10m;
}

public class DescontoPorCampanha : ICalculadoraDesconto
{
    public decimal Calcular(decimal valor) => valor * 0.20m;
}
```

Cada classe representa uma forma diferente de calcular desconto.

Sem Factory, a decisão pode ficar espalhada:

```csharp
ICalculadoraDesconto desconto;

if (tipoDesconto == "CUPOM")
{
    desconto = new DescontoPorCupom();
}
else if (tipoDesconto == "CAMPANHA")
{
    desconto = new DescontoPorCampanha();
}
else
{
    desconto = new SemDesconto();
}
```

O problema não é o `if` em si. O problema é repetir essa decisão em vários pontos do sistema.

Com Factory:

```csharp
public static class CalculadoraDescontoFactory
{
    public static ICalculadoraDesconto Criar(string tipoDesconto)
    {
        if (tipoDesconto == "CUPOM")
            return new DescontoPorCupom();

        if (tipoDesconto == "CAMPANHA")
            return new DescontoPorCampanha();

        return new SemDesconto();
    }
}
```

Uso:

```csharp
ICalculadoraDesconto desconto =
    CalculadoraDescontoFactory.Criar("CUPOM");
```

Agora a decisão sobre qual classe criar está em um único lugar.

Se amanhã for necessário adicionar `DescontoProgressivo`, a alteração será feita na Factory, não em todos os pontos do sistema.

# 6. Melhorando a Factory com enum e switch expression

Usar strings como `"CUPOM"` ou `"CAMPANHA"` funciona, mas tem um problema: erros de digitação podem passar despercebidos.

Exemplo:

```csharp
ICalculadoraDesconto desconto =
    CalculadoraDescontoFactory.Criar("CUPPOM");
```

O código compila, mas a string está errada. Dependendo da implementação, o sistema pode cair no desconto padrão sem avisar.

Uma solução melhor é usar `enum`.

```csharp
public enum TipoDesconto
{
    Nenhum,
    Cupom,
    Campanha
}
```

Agora a Factory pode receber um tipo mais seguro:

```csharp
public static class CalculadoraDescontoFactory
{
    public static ICalculadoraDesconto Criar(TipoDesconto tipoDesconto)
    {
        return tipoDesconto switch
        {
            TipoDesconto.Cupom => new DescontoPorCupom(),
            TipoDesconto.Campanha => new DescontoPorCampanha(),
            _ => new SemDesconto()
        };
    }
}
```

Uso:

```csharp
ICalculadoraDesconto desconto =
    CalculadoraDescontoFactory.Criar(TipoDesconto.Campanha);
```

Esse código é melhor porque:

1. Evita strings soltas.
2. Aproveita o autocomplete da IDE.
3. Reduz erros de digitação.
4. Deixa explícitas as opções válidas.
5. Torna a Factory mais clara e expressiva.

A `switch expression` também deixa o código mais conciso. Ela comunica que o retorno depende diretamente do valor de `tipoDesconto`.

# 7. Factory com parâmetros: cuidado com ambiguidade

Algumas implementações precisam de dados adicionais para serem criadas.

Imagine uma nova estratégia:

```csharp
public class DescontoPercentual : ICalculadoraDesconto
{
    private readonly decimal _percentual;

    public DescontoPercentual(decimal percentual)
    {
        if (percentual < 0 || percentual > 1)
            throw new ArgumentException("Percentual inválido.");

        _percentual = percentual;
    }

    public decimal Calcular(decimal valor)
    {
        return valor * _percentual;
    }
}
```

A Factory poderia ser escrita assim:

```csharp
public static ICalculadoraDesconto Criar(
    TipoDesconto tipoDesconto,
    decimal percentual = 0)
{
    return tipoDesconto switch
    {
        TipoDesconto.Cupom => new DescontoPorCupom(),
        TipoDesconto.Campanha => new DescontoPorCampanha(),
        TipoDesconto.Percentual => new DescontoPercentual(percentual),
        _ => new SemDesconto()
    };
}
```

O problema é que o parâmetro `percentual` só faz sentido para `TipoDesconto.Percentual`.

Este uso pode confundir:

```csharp
ICalculadoraDesconto desconto =
    CalculadoraDescontoFactory.Criar(TipoDesconto.Cupom, 0.50m);
```

O percentual foi passado, mas será ignorado. Isso não fica claro para quem lê o código.

Uma alternativa mais explícita é criar métodos específicos:

```csharp
public static class CalculadoraDescontoFactory
{
    public static ICalculadoraDesconto CriarSemDesconto()
        => new SemDesconto();

    public static ICalculadoraDesconto CriarPorCupom()
        => new DescontoPorCupom();

    public static ICalculadoraDesconto CriarPorCampanha()
        => new DescontoPorCampanha();

    public static ICalculadoraDesconto CriarPercentual(decimal percentual)
        => new DescontoPercentual(percentual);
}
```

Uso:

```csharp
ICalculadoraDesconto desconto =
    CalculadoraDescontoFactory.CriarPercentual(0.15m);
```

Esse código deixa clara a intenção: criar uma calculadora de desconto percentual com 15%.

Quando os parâmetros variam muito entre as opções, métodos específicos podem ser mais legíveis do que um único método genérico.

# 8. Factory para montar objeto composto

Factory também é útil quando um objeto precisa ser criado junto com outros objetos.

Considere as classes `Produto`, `ItemPedido` e `Pedido`.

Um pedido com um item pode exigir a seguinte montagem:

```csharp
Produto produto = new Produto("Monitor", 900);
ItemPedido item = new ItemPedido(produto, 1);
ICalculadoraDesconto desconto = new DescontoPorCampanha();
Pedido pedido = new Pedido(desconto);
pedido.AdicionarItem(item);
```

Essa montagem pode ser centralizada:

```csharp
public static class PedidoFactory
{
    public static Pedido CriarPedidoComUmItem(
        string nomeProduto,
        decimal precoProduto,
        int quantidade,
        ICalculadoraDesconto calculadoraDesconto)
    {
        Produto produto = new Produto(nomeProduto, precoProduto);
        ItemPedido item = new ItemPedido(produto, quantidade);

        Pedido pedido = new Pedido(calculadoraDesconto);
        pedido.AdicionarItem(item);

        return pedido;
    }
}
```

Uso:

```csharp
Pedido pedido = PedidoFactory.CriarPedidoComUmItem(
    "Monitor",
    900,
    1,
    new DescontoPorCampanha()
);
```

Esse método deixa claro que o objetivo é criar um pedido com um item. A montagem dos objetos internos fica centralizada.

A Factory está fazendo algo útil porque evita repetição e organiza a composição entre objetos.

---

# 9. Factory não deve esconder regras demais

Uma Factory deve melhorar a clareza, não piorá-la.

Este exemplo é problemático:

```csharp
Pedido pedido = PedidoFactory.Criar("PROMOCAO_ESPECIAL");
```

O nome `Criar` é vago. O parâmetro `"PROMOCAO_ESPECIAL"` também não explica o que acontece.

Esse método pode estar:

* criando produto;
* aplicando desconto;
* associando cliente;
* validando estoque;
* buscando dados;
* adicionando itens;
* usando alguma regra de campanha.

Quem lê o código não sabe.

Uma versão mais clara seria:

```csharp
Pedido pedido =
    PedidoFactory.CriarPedidoComDescontoDeCampanha();
```

Ou:

```csharp
Pedido pedido =
    PedidoFactory.CriarPedidoInicial(cliente, itens, new DescontoPorCampanha());
```

O nome do método deve comunicar a intenção da criação.

Uma boa Factory deve responder rapidamente à pergunta:

**O que exatamente está sendo criado e com quais regras principais?**

Se a resposta só aparece lendo a implementação interna, talvez a Factory esteja escondendo decisões demais.

# 10. Método de criação dentro da própria classe

Nem toda Factory precisa ser uma classe separada. Em alguns casos, a própria classe pode ter métodos estáticos de criação.

Isso é útil quando a regra de criação pertence fortemente à própria classe.

Exemplo:

```csharp
public class Matricula
{
    public string CodigoEstudante { get; private set; }
    public string CodigoTurma { get; private set; }
    public DateTime DataMatricula { get; private set; }
    public bool Ativa { get; private set; }

    private Matricula(
        string codigoEstudante,
        string codigoTurma,
        DateTime dataMatricula,
        bool ativa)
    {
        CodigoEstudante = codigoEstudante;
        CodigoTurma = codigoTurma;
        DataMatricula = dataMatricula;
        Ativa = ativa;
    }

    public static Matricula CriarAtiva(
        string codigoEstudante,
        string codigoTurma)
    {
        if (string.IsNullOrWhiteSpace(codigoEstudante))
            throw new ArgumentException("Código do estudante inválido.");

        if (string.IsNullOrWhiteSpace(codigoTurma))
            throw new ArgumentException("Código da turma inválido.");

        return new Matricula(
            codigoEstudante,
            codigoTurma,
            DateTime.Now,
            true);
    }
}
```

Uso:

```csharp
Matricula matricula = Matricula.CriarAtiva("EST001", "TURMA01");
```

Esse método comunica uma regra importante: toda matrícula criada por `CriarAtiva` nasce ativa e com a data atual.

O construtor privado impede que outras partes do sistema criem uma matrícula de forma inconsistente.

# 11. Factory externa ou método estático na própria classe

Existem duas formas comuns de centralizar criação: Factory externa e método estático dentro da própria classe.

## 11.1 Factory externa

Exemplo:

```csharp
public static class PedidoFactory
{
    public static Pedido CriarPedidoComUmItem(...)
    {
        // Montagem do pedido.
    }
}
```

A Factory externa é útil quando:

* a criação envolve várias classes;
* a montagem é externa ao objeto principal;
* existem combinações entre objetos;
* o objeto principal não deve conhecer todos os detalhes de montagem;
* a criação depende de estratégias, itens, produtos ou configurações externas.

No exemplo do pedido, faz sentido uma `PedidoFactory` porque criar um pedido pode envolver produto, item e desconto.

## 11.2 Método estático na própria classe

Exemplo:

```csharp
public static Matricula CriarAtiva(
    string codigoEstudante,
    string codigoTurma)
{
    // Criação da matrícula.
}
```

O método estático na própria classe é útil quando:

* a regra de criação pertence diretamente à entidade;
* queremos nomear modos específicos de criação;
* queremos evitar construtores confusos;
* o objeto deve proteger melhor sua própria criação;
* a criação não depende de montar várias classes externas.

No exemplo da matrícula, `CriarAtiva` faz sentido dentro da própria classe porque a regra “matrícula ativa com data atual” pertence ao conceito de matrícula.

# 12. Factory e encapsulamento

Factory não substitui encapsulamento.

Mesmo que um objeto seja criado por uma Factory, a própria classe ainda deve proteger seu estado interno.

Exemplo correto:

```csharp
public class Produto
{
    public string Nome { get; private set; }
    public decimal Preco { get; private set; }

    public Produto(string nome, decimal preco)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("Nome inválido.");

        if (preco <= 0)
            throw new ArgumentException("Preço inválido.");

        Nome = nome;
        Preco = preco;
    }
}
```

Nesse exemplo, `Produto` valida seus próprios dados. Mesmo que uma Factory tente criar um produto inválido, o construtor impedirá.

Exemplo incorreto:

```csharp
public class Produto
{
    public string Nome { get; set; }
    public decimal Preco { get; set; }
}
```

Nesse caso, qualquer parte do sistema pode alterar o produto para um estado inválido:

```csharp
Produto produto = new Produto();
produto.Nome = "";
produto.Preco = -50;
```

Confiar apenas na Factory para validar é perigoso. A Factory pode centralizar a criação, mas a entidade deve continuar responsável por proteger seu próprio estado.

A regra é:

**Factory cria ou monta objetos. A entidade protege suas próprias invariantes.**

# 13. Factory e Strategy trabalhando juntos

Factory e Strategy combinam muito bem.

Strategy separa comportamentos variáveis. Factory escolhe ou monta a estratégia adequada.

Exemplo com frete:

```csharp
public interface ICalculadoraFrete
{
    decimal Calcular(decimal peso);
}
```

Implementações:

```csharp
public class FreteRetirada : ICalculadoraFrete
{
    public decimal Calcular(decimal peso) => 0;
}

public class FreteNormal : ICalculadoraFrete
{
    public decimal Calcular(decimal peso) => peso * 5;
}

public class FreteExpresso : ICalculadoraFrete
{
    public decimal Calcular(decimal peso) => peso * 10;
}
```

Enum:

```csharp
public enum TipoFrete
{
    Retirada,
    Normal,
    Expresso
}
```

Factory:

```csharp
public static class CalculadoraFreteFactory
{
    public static ICalculadoraFrete Criar(TipoFrete tipoFrete)
    {
        return tipoFrete switch
        {
            TipoFrete.Normal => new FreteNormal(),
            TipoFrete.Expresso => new FreteExpresso(),
            _ => new FreteRetirada()
        };
    }
}
```

Uso:

```csharp
ICalculadoraFrete calculadoraFrete =
    CalculadoraFreteFactory.Criar(TipoFrete.Expresso);

decimal frete = calculadoraFrete.Calcular(12);

Console.WriteLine(frete);
```

Resultado esperado:

```csharp
120
```

Comentário:

* `TipoFrete.Expresso` faz a Factory criar `FreteExpresso`.
* `FreteExpresso` calcula o frete multiplicando o peso por 10.
* Como o peso é 12, o resultado é `12 * 10 = 120`.

Nesse caso:

* Strategy está nas classes `FreteRetirada`, `FreteNormal` e `FreteExpresso`.
* Factory está na classe `CalculadoraFreteFactory`.
* Polimorfismo aparece porque o código usa a interface `ICalculadoraFrete`, não a classe concreta diretamente.

# 14. Factory preparando acesso a dados

Ao trabalhar com DAL, SQLite e Repository, a criação de objetos também se torna importante.

Quando um sistema busca dados no banco, ele recebe linhas de tabela. Essas linhas precisam ser transformadas em objetos.

Exemplo de tabela:

```text
alunos

id | nome   | matricula
1  | Carlos | 2026001
```

Podemos ter duas situações diferentes:

## 14.1 Criar um objeto novo

```csharp
Aluno alunoNovo = Aluno.CriarNovo("Carlos", "2026001");
```

Esse método comunica que o aluno ainda está sendo criado no sistema. Ele pode ainda não ter `id`, porque o banco de dados pode gerar esse identificador depois.

## 14.2 Restaurar um objeto existente do banco

```csharp
Aluno alunoExistente =
    Aluno.RestaurarDoBanco(1, "Carlos", "2026001");
```

Esse método comunica outra intenção: o aluno já existia no banco e está sendo reconstruído como objeto em memória.

Essa distinção é importante porque “criar novo” e “restaurar do banco” não representam a mesma situação.

Um exemplo possível:

```csharp
public class Aluno
{
    public int Id { get; private set; }
    public string Nome { get; private set; }
    public string Matricula { get; private set; }

    private Aluno(int id, string nome, string matricula)
    {
        Id = id;
        Nome = nome;
        Matricula = matricula;
    }

    public static Aluno CriarNovo(string nome, string matricula)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("Nome inválido.");

        if (string.IsNullOrWhiteSpace(matricula))
            throw new ArgumentException("Matrícula inválida.");

        return new Aluno(0, nome, matricula);
    }

    public static Aluno RestaurarDoBanco(
        int id,
        string nome,
        string matricula)
    {
        if (id <= 0)
            throw new ArgumentException("Id inválido.");

        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("Nome inválido.");

        if (string.IsNullOrWhiteSpace(matricula))
            throw new ArgumentException("Matrícula inválida.");

        return new Aluno(id, nome, matricula);
    }
}
```

Comentário:

* `CriarNovo` usa `id = 0` para representar um objeto ainda não persistido.
* `RestaurarDoBanco` exige um `id` válido, pois representa um registro já existente.
* Os dois métodos deixam clara a intenção de criação.
* A validação continua dentro da classe `Aluno`.

---

# 15. Separação de responsabilidades

Factory deve criar ou montar objetos. Ela não deve assumir responsabilidades que pertencem a outras partes do sistema.

Uma boa separação ajuda a manter o código compreensível.

| Elemento   | Responsabilidade principal                                    |
| ---------- | ------------------------------------------------------------- |
| Entidade   | Representar um conceito do domínio e proteger regras internas |
| Strategy   | Representar uma variação de comportamento                     |
| Factory    | Criar ou montar objetos                                       |
| Service    | Coordenar casos de uso                                        |
| Repository | Abstrair a persistência                                       |
| DAL        | Executar acesso a dados                                       |
| Program.cs | Demonstrar ou iniciar o fluxo da aplicação                    |

## Exemplo de responsabilidade correta

Uma Factory de desconto pode criar a estratégia de desconto:

```csharp
ICalculadoraDesconto desconto =
    CalculadoraDescontoFactory.Criar(TipoDesconto.Cupom);
```

## Exemplo de responsabilidade incorreta

Uma Factory não deveria executar SQL diretamente:

```csharp
public static Pedido CriarPedidoDoBanco(int id)
{
    // Problema: Factory acessando banco diretamente.
    // Essa responsabilidade deveria estar em Repository ou DAL.
}
```

O problema desse exemplo é misturar criação de objetos com acesso a dados.

A Factory pode até receber dados já carregados e montar objetos, mas buscar esses dados no banco não deve ser responsabilidade dela.

# 16. Exemplo completo: Pedido com Factory e Strategy

A seguir, veja um exemplo completo e comentado.

## 16.1 Interface de desconto

```csharp
public interface ICalculadoraDesconto
{
    decimal Calcular(decimal valor);
}
```

A interface define um contrato. Toda calculadora de desconto deve implementar o método `Calcular`.

## 16.2 Estratégias de desconto

```csharp
public class SemDesconto : ICalculadoraDesconto
{
    public decimal Calcular(decimal valor) => 0;
}
```

`SemDesconto` representa a ausência de desconto.

```csharp
public class DescontoPorCupom : ICalculadoraDesconto
{
    public decimal Calcular(decimal valor) => valor * 0.10m;
}
```

`DescontoPorCupom` aplica 10% de desconto.

```csharp
public class DescontoPorCampanha : ICalculadoraDesconto
{
    public decimal Calcular(decimal valor) => valor * 0.20m;
}
```

`DescontoPorCampanha` aplica 20% de desconto.

## 16.3 Enum de tipo de desconto

```csharp
public enum TipoDesconto
{
    Nenhum,
    Cupom,
    Campanha
}
```

O enum representa as opções válidas de desconto.

## 16.4 Factory de desconto

```csharp
public static class CalculadoraDescontoFactory
{
    public static ICalculadoraDesconto Criar(TipoDesconto tipo)
    {
        return tipo switch
        {
            TipoDesconto.Cupom => new DescontoPorCupom(),
            TipoDesconto.Campanha => new DescontoPorCampanha(),
            _ => new SemDesconto()
        };
    }
}
```

A Factory escolhe a implementação correta de acordo com o tipo informado.

## 16.5 Classe Produto

```csharp
public class Produto
{
    public string Nome { get; private set; }
    public decimal Preco { get; private set; }

    public Produto(string nome, decimal preco)
    {
        if (string.IsNullOrWhiteSpace(nome))
            throw new ArgumentException("Nome inválido.");

        if (preco <= 0)
            throw new ArgumentException("Preço inválido.");

        Nome = nome;
        Preco = preco;
    }
}
```

`Produto` protege seu próprio estado. Nome vazio e preço inválido não são permitidos.

## 16.6 Classe ItemPedido

```csharp
public class ItemPedido
{
    public Produto Produto { get; private set; }
    public int Quantidade { get; private set; }

    public ItemPedido(Produto produto, int quantidade)
    {
        Produto = produto ?? throw new ArgumentNullException(nameof(produto));

        if (quantidade <= 0)
            throw new ArgumentException("Quantidade inválida.");

        Quantidade = quantidade;
    }

    public decimal CalcularSubtotal()
    {
        return Produto.Preco * Quantidade;
    }
}
```

`ItemPedido` associa um produto a uma quantidade.

O método `CalcularSubtotal` multiplica preço por quantidade.

## 16.7 Classe Pedido

```csharp
public class Pedido
{
    private readonly List<ItemPedido> _itens = new();
    private readonly ICalculadoraDesconto _calculadoraDesconto;

    public Pedido(ICalculadoraDesconto calculadoraDesconto)
    {
        _calculadoraDesconto = calculadoraDesconto
            ?? throw new ArgumentNullException(nameof(calculadoraDesconto));
    }

    public void AdicionarItem(ItemPedido item)
    {
        if (item == null)
            throw new ArgumentNullException(nameof(item));

        _itens.Add(item);
    }

    public decimal CalcularValorTotal()
    {
        return _itens.Sum(item => item.CalcularSubtotal());
    }

    public decimal CalcularValorFinal()
    {
        decimal total = CalcularValorTotal();
        decimal desconto = _calculadoraDesconto.Calcular(total);

        return total - desconto;
    }
}
```

`Pedido` não sabe qual desconto está sendo usado. Ele depende da interface `ICalculadoraDesconto`.

Isso permite trocar a estratégia de desconto sem alterar a classe `Pedido`.

## 16.8 PedidoFactory

```csharp
public static class PedidoFactory
{
    public static Pedido CriarPedidoComUmItem(
        string nomeProduto,
        decimal precoProduto,
        int quantidade,
        TipoDesconto tipoDesconto)
    {
        ICalculadoraDesconto desconto =
            CalculadoraDescontoFactory.Criar(tipoDesconto);

        Produto produto = new Produto(nomeProduto, precoProduto);
        ItemPedido item = new ItemPedido(produto, quantidade);

        Pedido pedido = new Pedido(desconto);
        pedido.AdicionarItem(item);

        return pedido;
    }
}
```

A `PedidoFactory` coordena a montagem do pedido:

1. Cria a estratégia de desconto usando outra Factory.
2. Cria o produto.
3. Cria o item do pedido.
4. Cria o pedido.
5. Adiciona o item ao pedido.
6. Retorna o pedido pronto para uso.

## 16.9 Uso no Program.cs

```csharp
Pedido pedido = PedidoFactory.CriarPedidoComUmItem(
    "Monitor",
    900,
    1,
    TipoDesconto.Campanha
);

Console.WriteLine($"Total: {pedido.CalcularValorTotal()}");
Console.WriteLine($"Final: {pedido.CalcularValorFinal()}");
```

Resultado esperado:

```text
Total: 900
Final: 720
```

Explicação:

* O produto custa 900.
* A quantidade é 1.
* O total é 900.
* O desconto de campanha é 20%.
* 20% de 900 é 180.
* O valor final é 900 - 180 = 720.

# 17. Aplicação prática resolvida: Factory de Frete

## Cenário

Um sistema precisa calcular frete de três formas:

1. Retirada na loja: frete igual a zero.
2. Frete normal: peso multiplicado por 5.
3. Frete expresso: peso multiplicado por 10.

O objetivo é evitar que o `Program.cs` precise decidir manualmente qual classe de frete instanciar.

## Objetivo

Criar uma solução com:

* interface `ICalculadoraFrete`;
* três estratégias de frete;
* enum `TipoFrete`;
* Factory `CalculadoraFreteFactory`;
* demonstração de uso.

## Solução

```csharp
public interface ICalculadoraFrete
{
    decimal Calcular(decimal peso);
}
```

A interface define o comportamento comum: calcular frete a partir do peso.

```csharp
public class FreteRetirada : ICalculadoraFrete
{
    public decimal Calcular(decimal peso)
    {
        return 0;
    }
}
```

Retirada não cobra frete.

```csharp
public class FreteNormal : ICalculadoraFrete
{
    public decimal Calcular(decimal peso)
    {
        return peso * 5;
    }
}
```

Frete normal multiplica o peso por 5.

```csharp
public class FreteExpresso : ICalculadoraFrete
{
    public decimal Calcular(decimal peso)
    {
        return peso * 10;
    }
}
```

Frete expresso multiplica o peso por 10.

```csharp
public enum TipoFrete
{
    Retirada,
    Normal,
    Expresso
}
```

O enum define as opções válidas.

```csharp
public static class CalculadoraFreteFactory
{
    public static ICalculadoraFrete Criar(TipoFrete tipoFrete)
    {
        return tipoFrete switch
        {
            TipoFrete.Normal => new FreteNormal(),
            TipoFrete.Expresso => new FreteExpresso(),
            _ => new FreteRetirada()
        };
    }
}
```

A Factory decide qual classe concreta criar.

## Demonstração

```csharp
ICalculadoraFrete calculadora =
    CalculadoraFreteFactory.Criar(TipoFrete.Expresso);

decimal valorFrete = calculadora.Calcular(12);

Console.WriteLine(valorFrete);
```

## Resultado esperado

```text
120
```

## Comentário da solução

O código principal não precisa escrever:

```csharp
new FreteExpresso()
```

Ele pede à Factory uma calculadora com base no `TipoFrete`.

Isso reduz acoplamento entre o código de uso e as classes concretas.

## Como validar

A validação pode ser feita testando cada tipo de frete:

```csharp
Console.WriteLine(
    CalculadoraFreteFactory.Criar(TipoFrete.Retirada).Calcular(12)
); // 0

Console.WriteLine(
    CalculadoraFreteFactory.Criar(TipoFrete.Normal).Calcular(12)
); // 60

Console.WriteLine(
    CalculadoraFreteFactory.Criar(TipoFrete.Expresso).Calcular(12)
); // 120
```

Se os resultados forem `0`, `60` e `120`, a Factory está selecionando corretamente as estratégias.

## Possíveis erros

Um erro comum seria colocar o cálculo diretamente dentro da Factory:

```csharp
public static decimal CalcularFrete(TipoFrete tipoFrete, decimal peso)
{
    // Mistura criação com cálculo.
}
```

Isso enfraquece o uso de Strategy. A Factory deve criar a calculadora. A calculadora deve calcular.

Outro erro seria usar string:

```csharp
CalculadoraFreteFactory.Criar("EXPRESSO");
```

Com string, um erro de digitação pode passar despercebido. O enum torna a opção mais segura.

# 18. Erros comuns e dúvidas frequentes

## 18.1 Criar Factory para tudo

Nem toda classe precisa de Factory. Se o construtor é claro e direto, use o construtor.

Factory demais pode deixar o sistema mais difícil de navegar.

## 18.2 Usar Factory apenas para trocar o nome do construtor

Este código não agrega valor:

```csharp
ProdutoFactory.Criar("Mouse", 80);
```

Se internamente ele apenas faz isto:

```csharp
return new Produto("Mouse", 80);
```

a Factory provavelmente é desnecessária.

## 18.3 Colocar acesso ao banco dentro da Factory

Factory não deve executar SQL nem coordenar persistência.

Acesso a banco pertence ao Repository ou ao DAL, dependendo da arquitetura usada.

## 18.4 Remover validações da entidade

A entidade deve continuar protegendo seu próprio estado.

Mesmo que a Factory valide, o construtor ou método de criação da entidade também deve impedir estados inválidos.

## 18.5 Criar métodos com nomes vagos

Evite:

```csharp
PedidoFactory.Criar("X");
```

Prefira nomes que comuniquem intenção:

```csharp
PedidoFactory.CriarPedidoComDescontoDeCampanha();
```

ou:

```csharp
PedidoFactory.CriarPedidoComUmItem(
    "Monitor",
    900,
    1,
    TipoDesconto.Campanha
);
```

## 18.6 Confundir Factory com Strategy

Strategy representa comportamentos variáveis.

Factory cria ou seleciona objetos.

No exemplo de frete:

* `FreteNormal`, `FreteExpresso` e `FreteRetirada` são Strategies.
* `CalculadoraFreteFactory` é a Factory.

## 18.7 Confundir Factory com Service

Service coordena casos de uso.

Factory cria objetos.

Se uma classe está processando uma compra, validando fluxo, chamando repositório e coordenando várias etapas de negócio, ela provavelmente é um Service, não uma Factory.

## 18.8 Confundir Factory com Repository

Repository abstrai persistência.

Factory cria ou monta objetos.

Se uma classe busca, salva, atualiza ou remove dados, ela não é apenas uma Factory.

# 19. Checklist explicado

## 19.1 Verifique se a criação envolve decisão

O que verificar: veja se o código precisa escolher entre várias classes concretas, como `DescontoPorCupom`, `DescontoPorCampanha` ou `SemDesconto`.

Por que importa: quando essa decisão fica espalhada, o sistema fica repetitivo e mais sujeito a erros.

Como validar: procure trechos repetidos com `if`, `else if`, `switch` ou múltiplos `new` escolhidos por condição.

O que acontece se faltar: a mesma regra pode ser implementada de formas diferentes em pontos distintos do sistema.

## 19.2 Verifique se existe montagem de múltiplos objetos

O que verificar: observe se criar um objeto exige criar outros antes, como produto, item, desconto e pedido.

Por que importa: montagens repetidas tornam o código mais difícil de manter.

Como validar: identifique sequências de criação que aparecem mais de uma vez.

O que acontece se faltar: alterações simples, como adicionar uma nova dependência, exigirão mudanças em vários lugares.

## 19.3 Verifique se a Factory realmente agrega valor

O que verificar: confirme se a Factory decide, monta, nomeia uma intenção ou aplica uma regra de criação.

Por que importa: uma Factory que apenas chama o construtor adiciona complexidade sem benefício.

Como validar: leia o método da Factory e pergunte: “ele faz algo além de `return new Classe(...)`?”

O que acontece se faltar: o projeto pode ficar cheio de classes desnecessárias.

## 19.4 Verifique se as entidades continuam protegidas

O que verificar: confira se as entidades validam seus dados e usam `private set` quando necessário.

Por que importa: Factory não deve ser a única barreira contra objetos inválidos.

Como validar: tente criar um objeto com dados inválidos e veja se a própria classe impede.

O que acontece se faltar: qualquer parte do sistema poderá deixar objetos em estado inconsistente.

## 19.5 Verifique se nomes de métodos são claros

O que verificar: analise se o nome do método indica o que está sendo criado e com qual intenção.

Por que importa: uma Factory deve facilitar a leitura do código.

Como validar: leia uma chamada de método sem abrir sua implementação. Se a intenção não ficar clara, o nome precisa melhorar.

O que acontece se faltar: a Factory pode esconder decisões importantes demais.

## 19.6 Verifique se Strategy e Factory estão separadas

O que verificar: veja se as classes de Strategy executam o comportamento e se a Factory apenas escolhe ou cria essas classes.

Por que importa: misturar criação com comportamento dificulta manutenção.

Como validar: no exemplo de frete, confirme que o cálculo está em `FreteNormal`, `FreteExpresso` e `FreteRetirada`, não dentro da Factory.

O que acontece se faltar: a Factory cresce demais e começa a concentrar lógica que deveria estar em outras classes.

## 19.7 Verifique se enum foi usado quando há opções conhecidas

O que verificar: veja se opções como tipo de desconto ou tipo de frete estão representadas por `enum`, não por strings soltas.

Por que importa: enums reduzem erros de digitação e deixam as opções válidas mais explícitas.

Como validar: procure chamadas como `Criar("CUPOM")`. Elas podem ser substituídas por `Criar(TipoDesconto.Cupom)`.

O que acontece se faltar: erros de texto podem compilar e gerar comportamento inesperado.

## 19.8 Verifique se a Factory não acessa banco de dados diretamente

O que verificar: veja se há SQL, conexão, comandos ou consultas dentro da Factory.

Por que importa: Factory deve criar objetos, não executar persistência.

Como validar: procure termos como conexão, comando SQL, `INSERT`, `SELECT`, `UPDATE` ou chamadas diretas ao banco dentro da Factory.

O que acontece se faltar: responsabilidades ficam misturadas, dificultando manutenção e testes.

# 20. Síntese final

Factory é um padrão útil para organizar a criação de objetos quando a criação envolve decisões, dependências, composição, valores padrão ou regras de criação.

Ela não deve ser usada automaticamente em toda classe. Quando o construtor é simples, claro e suficiente, a Factory pode ser desnecessária.

A Factory é especialmente útil quando trabalha com interfaces e Strategy. Nesse cenário, Strategy representa comportamentos variáveis, enquanto Factory escolhe qual implementação concreta será usada.

Também é importante lembrar que Factory não substitui encapsulamento. As entidades devem continuar validando seus próprios dados e protegendo seu estado interno.

Em sistemas com acesso a dados, Factory ajuda a pensar na diferença entre criar um objeto novo e restaurar um objeto existente, mas não deve assumir o papel de Repository ou DAL.

---

# Conclusão

O padrão Factory melhora a organização do código quando usado para resolver um problema real de criação. Ele centraliza decisões, reduz duplicação, melhora a legibilidade e prepara o sistema para evoluir com mais segurança.

Uma boa Factory deixa o código mais claro. Uma Factory mal usada apenas adiciona camadas desnecessárias.

Ao decidir usar Factory, observe sempre três perguntas:

1. Existe decisão, montagem ou regra relevante na criação?
2. A Factory torna o código mais claro e menos duplicado?
3. As responsabilidades continuam bem separadas?

Quando a resposta for sim, Factory pode ser uma excelente escolha para organizar a criação de objetos em C#.
